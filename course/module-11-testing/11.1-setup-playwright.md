# 11.1 — Setup Playwright

> End-to-end tests against a real database and a real Stripe test mode. No mocks, no lies.

## Why this matters

Billing logic, RLS policies, and tier gating touch three systems (your app, Supabase, Stripe). Unit tests can cover each in isolation, but the bugs that ship to production live in the *seams between* them: a webhook writes with the wrong client, an RLS policy blocks a legitimate query, a CTA goes to the wrong URL because of a deployment typo. End-to-end tests exercise all three at once.

Playwright is the right tool: runs real browsers, can mock network calls when you want, and its test runner is as friendly as `vitest`. We'll lean on it for auth flows (Module 11.2) and CRUD (Module 11.3). Module 12 wires the whole suite into CI.

## The Principal Engineer lens

**Tests are code; spend the same care on them.** A brittle test suite is worse than no tests — it trains developers to ignore red CI. Three things make tests durable: a clean test-mode database per run, stable selectors that aren't CSS classes, and asserting *behaviour* not *implementation*.

Corollary: **run tests against your local Supabase, not a shared staging DB.** Every test run wipes and re-seeds. Shared state across tests is a lose-lose — fixtures collide, runs are non-deterministic, and one flaky test poisons the rest.

## Step 1 — Install

From `app/`:

```bash
pnpm add -D @playwright/test@1.51.2
pnpm exec playwright install chromium
```

Pinned version. `chromium` only — we don't need Firefox / WebKit coverage for a CRUD SaaS, and extra browsers triple the CI time.

## Step 2 — The config

Create `app/playwright.config.ts`:

```ts
// app/playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
	testDir: './e2e',
	timeout: 30_000,
	fullyParallel: false, // serial: fixtures write shared rows
	retries: process.env.CI ? 2 : 0,
	workers: 1,
	reporter: process.env.CI ? 'github' : 'list',
	use: {
		baseURL: 'http://localhost:5173',
		trace: 'retain-on-failure',
		screenshot: 'only-on-failure'
	},
	projects: [
		{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }
	],
	webServer: {
		command: 'pnpm dev',
		url: 'http://localhost:5173',
		reuseExistingServer: !process.env.CI,
		timeout: 60_000
	}
});
```

Worth pausing on three knobs.

## Step 3 — Why `fullyParallel: false` and `workers: 1`

Playwright defaults to parallel tests across multiple workers. That's fine for independent tests; it's a nightmare when tests share a database. Our tests create users, contacts, subscriptions — concurrent runs would collide.

Trade-off: slower suite. Acceptable — CRUD SaaS test suites are typically 30–90 seconds total. Parallelism is for big suites; stay serial until you measure a reason not to.

Module 12 covers scaling this: one Supabase project per worker, or a per-test DB reset, unlocks parallelism. For now: serial + deterministic.

## Step 4 — `trace: 'retain-on-failure'` — the debugging superpower

Playwright's trace viewer records every action, screenshot, network request, and DOM snapshot during a test. `retain-on-failure` keeps traces only for failed tests (full traces are large). Opening one:

```bash
pnpm exec playwright show-trace test-results/.../trace.zip
```

Gives you a scrubbable timeline of the failure — exactly what the page looked like and what the network did. Most failing tests diagnose themselves within 30 seconds of opening the trace.

## Step 5 — Add package scripts

In `app/package.json`:

```json
{
	"scripts": {
		"test": "playwright test",
		"test:ui": "playwright test --ui",
		"test:debug": "playwright test --debug"
	}
}
```

- `pnpm test` — what CI runs.
- `pnpm test:ui` — interactive runner. Opens a UI where you pick tests to run and see traces live. Day-to-day development.
- `pnpm test:debug` — step through with Chrome DevTools attached.

## Step 6 — The e2e directory structure

```
app/e2e/
├── fixtures/
│   ├── auth.ts           # signed-in user fixture
│   └── stripe.ts         # test clock + customer fixture
├── utils/
│   ├── reset.ts          # truncate DB before each spec
│   └── selectors.ts      # shared data-testid helpers
├── auth.spec.ts          # Module 11.2
└── crud.spec.ts          # Module 11.3
```

Three disciplines baked in:

- **Fixtures** for setup shared across tests (signed-in user, Stripe test clock).
- **Utils** for plumbing (reset the DB, common selectors).
- **Spec files** contain only assertions — no setup noise.

## Step 7 — The reset utility

Before each spec we nuke app-owned tables. The `auth.users` table is trickier — Supabase manages it — so we delete via its admin API:

```ts
// app/e2e/utils/reset.ts
import { createClient } from '@supabase/supabase-js';
import 'dotenv/config';

const admin = createClient(
	process.env.PUBLIC_SUPABASE_URL!,
	process.env.SUPABASE_SERVICE_ROLE_KEY!
);

export async function resetDb(): Promise<void> {
	// Order matters: children before parents.
	await admin.from('contacts').delete().neq('id', '00000000-0000-0000-0000-000000000000');
	await admin.from('stripe_subscriptions').delete().neq('id', '___none___');
	await admin.from('stripe_customers').delete().neq('user_id', '00000000-0000-0000-0000-000000000000');
	await admin.from('stripe_events').delete().neq('id', '___none___');

	// Auth users last.
	const { data } = await admin.auth.admin.listUsers();
	for (const u of data?.users ?? []) {
		await admin.auth.admin.deleteUser(u.id);
	}
}
```

`.neq('id', '...')` is the "delete all rows" idiom since Supabase requires a filter. `cascade` on the foreign keys handles the rest.

## Step 8 — The `data-testid` convention

CSS classes change. Text changes. `data-testid` is the stable contract between test and component:

```svelte
<!-- src/routes/(app)/app/contacts/+page.svelte -->
<button data-testid="new-contact-button" onclick={...}>New contact</button>
<ul data-testid="contact-list">
	{#each contacts as c (c.id)}
		<li data-testid="contact-row" data-contact-id={c.id}>{c.full_name}</li>
	{/each}
</ul>
```

Test-side:

```ts
// app/e2e/utils/selectors.ts
import type { Page } from '@playwright/test';

export const sel = {
	newContactButton: (page: Page) => page.getByTestId('new-contact-button'),
	contactList: (page: Page) => page.getByTestId('contact-list'),
	contactRow: (page: Page, id?: string) =>
		id ? page.locator(`[data-testid="contact-row"][data-contact-id="${id}"]`)
			: page.getByTestId('contact-row')
};
```

Centralising selectors means refactoring a component doesn't touch test code.

## Step 9 — Verify the plumbing

Create a smoke test at `app/e2e/smoke.spec.ts`:

```ts
import { test, expect } from '@playwright/test';

test('dev server responds with pricing page', async ({ page }) => {
	await page.goto('/pricing');
	await expect(page.getByRole('heading', { name: /transparent pricing/i })).toBeVisible();
});
```

Run it:

```bash
pnpm test smoke
```

If you see "1 passed" in green, the config, webServer auto-start, and base URL are all correct. Delete this file before Module 11.2 (it's a throwaway).

## Step 10 — CI note (full treatment in Module 12)

Playwright in CI needs:

- `PUBLIC_SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` env vars (local Supabase started earlier in the job).
- `STRIPE_SECRET_KEY` pointing at a test-mode key (never a live key).
- `pnpm exec playwright install --with-deps chromium` to pull system deps on the first run.

Keep this in mind; we'll wire it up in 12.4.

## Verify

- `pnpm test smoke` passes.
- `pnpm test:ui` opens the interactive runner.
- `playwright show-trace` works against a failing trace.
- Deleting all rows via `resetDb()` leaves the DB empty (`select count(*) from contacts` → 0).

## Common traps

- **Running tests against a staging Supabase.** Data collision on every run. Local Supabase per machine; cleaned DB per test. Non-negotiable.
- **Parallel workers with shared state.** Flakes proportional to test count squared. Stay serial until you architect isolation.
- **Testing CSS classes (`page.locator('.btn-primary')`).** Break on the first Tailwind refactor. `data-testid` or `getByRole` with accessible names.
- **Long timeouts.** Default 30s is plenty. If a test needs 90s, either something's actually wrong with the app or the test is waiting on the wrong signal. Fix the signal, not the timeout.
- **Skipping trace retention in CI.** Red CI with no trace is a 30-minute debugging loop. Always keep failure traces.

## Recap

Playwright installed, configured for serial runs with retained traces, backed by a DB reset utility and stable `data-testid` selectors. The plumbing is boring; the tests that come next are where the value compounds.
