# 11.2 — Auth Flow Tests

> Register, log in, log out, gate a route. Four tests that cover 90% of auth bugs forever.

## Why this matters

Auth is the thinnest surface with the biggest consequences. If login breaks, nobody can use your app. If the `(app)` guard breaks, everyone can see everyone else's data. If logout leaves a cookie behind, users share sessions on shared computers. These aren't hypothetical — each is a real bug every SaaS eventually ships without tests.

The good news: auth flows are highly scriptable. A few well-chosen tests give enormous coverage. We'll write four.

## The Principal Engineer lens

**Test the promises the auth system makes, not its internals.** The promise isn't "call `signInWithPassword` with these args." The promise is "if I enter the right email and password, I end up logged in on my dashboard." Test the outside, and the implementation can change freely underneath.

Corollary: **use real Supabase Auth, not mocks.** The whole point of end-to-end tests is catching integration failures. Mocking Supabase throws away the signal.

## Step 1 — The auth fixture

Reusable "signed-in user" setup in `app/e2e/fixtures/auth.ts`:

```ts
// app/e2e/fixtures/auth.ts
import { test as base, type Page } from '@playwright/test';
import { createClient } from '@supabase/supabase-js';
import 'dotenv/config';

const admin = createClient(
	process.env.PUBLIC_SUPABASE_URL!,
	process.env.SUPABASE_SERVICE_ROLE_KEY!
);

type AuthedUser = {
	email: string;
	password: string;
	userId: string;
};

export const test = base.extend<{ authedUser: AuthedUser; authedPage: Page }>({
	authedUser: async ({}, use) => {
		const email = `user-${crypto.randomUUID()}@example.com`;
		const password = 'Password123!';

		const { data, error } = await admin.auth.admin.createUser({
			email,
			password,
			email_confirm: true,
			user_metadata: { full_name: 'Test User' }
		});
		if (error) throw error;

		await use({ email, password, userId: data.user!.id });

		await admin.auth.admin.deleteUser(data.user!.id);
	},

	authedPage: async ({ page, authedUser }, use) => {
		await page.goto('/login');
		await page.getByLabel('Email').fill(authedUser.email);
		await page.getByLabel('Password').fill(authedUser.password);
		await page.getByRole('button', { name: /log in/i }).click();
		await page.waitForURL('/app');
		await use(page);
	}
});

export { expect } from '@playwright/test';
```

Two fixtures:

- `authedUser` — creates the user via Supabase Admin API (skips email confirmation), yields credentials, deletes after.
- `authedPage` — takes a `page` and logs in with `authedUser`, yields the logged-in page.

Tests import `test` from here instead of `@playwright/test`, and get both for free.

## Step 2 — Why `email_confirm: true`

Supabase normally requires a confirmation click. The admin API lets us skip it for test users. This is *the* right shortcut — we're not testing the email link flow (Module 12.6 briefly covers doing that with a maildev-style setup). For auth flow correctness, pre-confirmed is fine.

## Step 3 — Test 1: Register a new user

`app/e2e/auth.spec.ts`:

```ts
import { test, expect } from './fixtures/auth';
import { resetDb } from './utils/reset';

test.beforeEach(async () => {
	await resetDb();
});

test('register → auto-login → land on /app', async ({ page }) => {
	const email = `new-${crypto.randomUUID()}@example.com`;

	await page.goto('/register');
	await page.getByLabel('Full name').fill('New User');
	await page.getByLabel('Email').fill(email);
	await page.getByLabel('Password', { exact: true }).fill('Password123!');
	await page.getByLabel('Confirm password').fill('Password123!');
	await page.getByRole('button', { name: /create account/i }).click();

	// Should land on /app — Supabase auto-signs-in when email confirm is off.
	await page.waitForURL('/app');
	await expect(page.getByText('Test User').or(page.getByText('New User'))).toBeVisible({ timeout: 5000 });
});
```

Pragma: we assume Supabase is configured with "Confirm email = off" in local dev (set in Module 1.2). If it's on, this test would stop at "Check your email" — not wrong, but a different flow to test separately.

The key assertion: `waitForURL('/app')`. If registration succeeds, the app routes you there. If anything failed (validation error, DB error, RLS), you stay on `/register` and the test fails at the URL wait.

## Step 4 — Test 2: Log in

```ts
test('log in with existing credentials', async ({ page, authedUser }) => {
	await page.goto('/login');
	await page.getByLabel('Email').fill(authedUser.email);
	await page.getByLabel('Password').fill(authedUser.password);
	await page.getByRole('button', { name: /log in/i }).click();

	await page.waitForURL('/app');
	await expect(page.getByRole('link', { name: /dashboard|contacts/i })).toBeVisible();
});
```

`authedUser` is injected by the fixture; this test doesn't re-create the user. It logs in with the credentials the fixture produced and asserts a dashboard link is visible — proving the `(app)` layout rendered.

## Step 5 — Test 3: Log out

```ts
test('log out returns to login', async ({ authedPage }) => {
	await authedPage.getByTestId('user-menu-trigger').click();
	await authedPage.getByRole('menuitem', { name: /log out/i }).click();

	// After logout, the redirect lands on /login.
	await authedPage.waitForURL('/login');

	// And protected routes bounce back to login.
	await authedPage.goto('/app');
	await authedPage.waitForURL(/\/login/);
});
```

The second assertion matters more than the first. We're checking that after logout, the *server-side guard* still rejects you — not just that the client-side menu navigated away.

## Step 6 — Test 4: Protected route gating

```ts
test('unauthenticated user cannot access /app', async ({ page }) => {
	await page.goto('/app');
	await page.waitForURL(/\/login(\?.*)?$/);

	// Redirect should include a `next` query param so the login page can
	// bounce back after success.
	expect(page.url()).toContain('next=%2Fapp');
});

test('unauthenticated user cannot access /account', async ({ page }) => {
	await page.goto('/account');
	await page.waitForURL(/\/login/);
});
```

Two micro-tests, one concern: the route guard from Module 3.3 works. If someone accidentally weakens the `requireUser` implementation, this catches it.

## Step 7 — Test 5: Login bounceback

```ts
test('login redirects to ?next after success', async ({ page, authedUser }) => {
	await page.goto('/login?next=%2Fapp%2Fcontacts');
	await page.getByLabel('Email').fill(authedUser.email);
	await page.getByLabel('Password').fill(authedUser.password);
	await page.getByRole('button', { name: /log in/i }).click();

	await page.waitForURL('/app/contacts');
});

test('login ignores malicious ?next pointing off-origin', async ({ page, authedUser }) => {
	await page.goto('/login?next=https%3A%2F%2Fevil.example.com');
	await page.getByLabel('Email').fill(authedUser.email);
	await page.getByLabel('Password').fill(authedUser.password);
	await page.getByRole('button', { name: /log in/i }).click();

	// Should land on /app (the safe default), not evil.example.com.
	await page.waitForURL('/app');
});
```

The second test is the one that justifies writing the first. We built the `next` validation in Module 3.2 (`next.startsWith('/') && !next.startsWith('//')`). This test proves the validation actually runs. Without it, open-redirect attacks are one regression away.

## Step 8 — Test 6: Session persistence across reloads

```ts
test('session persists across page reload', async ({ authedPage }) => {
	await authedPage.reload();
	await expect(authedPage).toHaveURL(/\/app/);

	// Should not flash to /login.
	const url = authedPage.url();
	expect(url).not.toContain('/login');
});
```

This test guards against a subtle bug class: server hooks failing to hydrate the session from cookies. If someone refactors `hooks.server.ts` incorrectly, reloads will bounce to login. This test catches it.

## Step 9 — Stabilising flaky selectors

If any of these tests flakes, the usual suspects:

- **Animation in progress.** Add `await page.waitForLoadState('networkidle')` after navigation, or rely on a `data-testid` attribute that only appears when fully mounted.
- **Two visible "Log in" elements** (e.g., a header link and a submit button). Use `getByRole('button', ...)` to disambiguate from `getByRole('link', ...)`.
- **Invalidation race.** A form submit triggers layout reload; a click too soon after asserts the old DOM. Use `expect(...).toBeVisible()` with a generous `timeout` option to wait for the post-submit UI.

## Step 10 — Running the suite

```bash
pnpm test auth
```

Expected: 6 tests pass, ~15–30 seconds wall-clock (the register flow includes form submit + redirect, which take a few seconds on a cold server).

If any fail, open the trace:

```bash
pnpm exec playwright show-trace test-results/.../trace.zip
```

## Verify

- All 6 tests in `auth.spec.ts` pass.
- Traces are retained for failures only (check `test-results/` — it's empty on all-green).
- Running `pnpm test` without `auth` runs every spec (still just one at this point, smoke already deleted).

## Common traps

- **Leaving users in the DB across runs.** The fixture deletes on teardown; `resetDb` in `beforeEach` mops up anything the fixture missed. Don't skip either.
- **Hardcoding user emails.** Two test runs collide. `crypto.randomUUID()` generates unique emails per run.
- **Asserting on localised text.** If your app ever supports i18n, `getByRole({ name: /log in/i })` will still work — but `getByText('Log in')` breaks for Spanish users. Prefer roles + accessible names.
- **Forgetting the `next` safety test.** Every auth system in production has an open-redirect bug at some point; your test should make regressions impossible.
- **Testing the Supabase client directly.** You're not testing Supabase — you're testing your integration. Go through the browser.
