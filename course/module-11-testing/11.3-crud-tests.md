# 11.3 — CRUD Tests

> Create a contact. Read it. Update it. Delete it. Hit the tier gate. Verify RLS. Done.

## Why this matters

Every bug that makes it to production in a CRUD app falls into one of four categories:

- **Data not saving** — form posts, DB receives nothing or the wrong thing.
- **Data leaking** — user A sees user B's records (the RLS class).
- **Data not updating reactively** — mutation succeeds but the UI still shows stale state.
- **Gating bypass** — tier limit ignored somewhere.

A compact CRUD spec covers all four. Combined with Module 11.2's auth tests, the suite is ready to wire into CI.

## The Principal Engineer lens

**Don't let tests depend on each other.** Each test creates what it needs and asserts on it. A test that "depends on the earlier test having created a contact" is a test that fails mysteriously when someone runs `playwright test --grep 'update'` alone.

Corollary: **test RLS at the test layer, not just via unit tests on policies.** RLS is a cross-cutting contract: "user A can't see user B's rows." The only way to verify that end-to-end is to log in as A, try to read B's data, and fail. Do it.

## Step 1 — The setup

Add imports and a `beforeEach` at the top of `app/e2e/crud.spec.ts`:

```ts
// app/e2e/crud.spec.ts
import { test, expect } from './fixtures/auth';
import { resetDb } from './utils/reset';
import { sel } from './utils/selectors';

test.beforeEach(async () => {
	await resetDb();
});
```

Every test starts from a clean DB. One user per test, created by the `authedUser` fixture, deleted after.

## Step 2 — Create a contact

```ts
test('create contact appears in the list', async ({ authedPage }) => {
	const page = authedPage;

	await page.goto('/app/contacts');
	await sel.newContactButton(page).click();

	await page.getByLabel('Full name').fill('Ada Lovelace');
	await page.getByLabel('Email').fill('ada@example.com');
	await page.getByRole('button', { name: /save|create/i }).click();

	const row = page.getByText('Ada Lovelace');
	await expect(row).toBeVisible();

	// Reload — the row must still be there (not a client-only fake).
	await page.reload();
	await expect(page.getByText('Ada Lovelace')).toBeVisible();
});
```

The reload at the end is the critical assertion. "Mutation succeeded AND the DB really has the row" vs. "the UI just looked right." Without the reload, a silent client-side-only optimistic update would pass the test.

## Step 3 — Update a contact

```ts
test('update contact persists', async ({ authedPage }) => {
	const page = authedPage;

	// Arrange: create via the API, not the UI.
	// Tests that target a specific flow shouldn't re-test prerequisites.
	await createContactViaApi(page, {
		full_name: 'Grace Hopper',
		email: 'grace@example.com'
	});

	await page.goto('/app/contacts');
	await page.getByText('Grace Hopper').click();

	await page.getByLabel('Full name').fill('Rear Admiral Grace Hopper');
	await page.getByRole('button', { name: /save/i }).click();

	await expect(page.getByText('Rear Admiral Grace Hopper')).toBeVisible();
	await page.reload();
	await expect(page.getByText('Rear Admiral Grace Hopper')).toBeVisible();
});
```

`createContactViaApi` is a tiny helper; we'll write it in Step 6.

Pattern to internalise: **tests that *assert* a flow should test it; tests that *depend on* a flow should use the API helper.** This keeps each test focused.

## Step 4 — Delete a contact

```ts
test('delete contact removes it from the list', async ({ authedPage }) => {
	const page = authedPage;

	await createContactViaApi(page, { full_name: 'Alan Turing', email: 'alan@example.com' });
	await page.goto('/app/contacts');
	await page.getByText('Alan Turing').click();

	await page.getByRole('button', { name: /delete|remove/i }).click();
	// Confirm modal.
	await page.getByRole('button', { name: /yes|confirm|delete/i }).last().click();

	await expect(page.getByText('Alan Turing')).toHaveCount(0);
	await page.reload();
	await expect(page.getByText('Alan Turing')).toHaveCount(0);
});
```

`.last()` because there are two "Delete" buttons momentarily visible: the row action and the confirm in the modal. `last()` picks the modal's.

## Step 5 — Tier gate: Free user hits limit

```ts
test('free user is blocked at the 5th contact', async ({ authedPage }) => {
	const page = authedPage;

	for (let i = 0; i < 5; i++) {
		await createContactViaApi(page, {
			full_name: `Contact ${i}`,
			email: `c${i}@example.com`
		});
	}

	await page.goto('/app/contacts');

	// The button should be aria-disabled with a tooltip/reason.
	const btn = sel.newContactButton(page);
	await expect(btn).toHaveAttribute('aria-disabled', 'true');

	// Clicking still works (opens the upgrade modal — Module 10.3).
	await btn.click();
	await expect(page.getByRole('dialog')).toContainText(/upgrade|limit/i);
});
```

Three assertions in one test: the button reflects denied state, clicking opens the modal, the modal text makes sense. Each assertion guards against a separate regression.

## Step 6 — Server-side enforcement bypass attempt

```ts
test('server rejects direct create call when at limit', async ({ authedPage, authedUser }) => {
	const page = authedPage;

	for (let i = 0; i < 5; i++) {
		await createContactViaApi(page, {
			full_name: `Contact ${i}`,
			email: `c${i}@example.com`
		});
	}

	// Try to bypass the UI: call the remote endpoint directly.
	const response = await page.request.post('/?/contacts.remote.createContact', {
		form: { full_name: 'Bypass Attempt' }
	});

	expect(response.status()).toBe(402);
	const body = await response.json();
	expect(body).toMatchObject({ code: 'ENTITLEMENT_DENIED' });
});
```

This is the test that justifies the whole tier-gating effort: **disable the UI button all you want — if the server isn't enforcing, someone can POST their way past it.** Here we prove the server does its job.

## Step 7 — RLS isolation

```ts
test('user cannot read another user contacts', async ({ browser, authedUser }) => {
	// Alice: our fixture user.
	const alice = authedUser;

	// Seed one of Alice's contacts via admin client.
	await createContactAsAdmin(alice.userId, 'Alice Only', 'alice@example.com');

	// Bob: a second user, distinct session.
	const bob = await createTestUser();
	const bobContext = await browser.newContext();
	const bobPage = await bobContext.newPage();
	await login(bobPage, bob);

	await bobPage.goto('/app/contacts');
	await expect(bobPage.getByText('Alice Only')).toHaveCount(0);

	// And confirm via the API:
	const res = await bobPage.request.get('/api/contacts');
	const list = await res.json();
	expect(list.find((c: { full_name: string }) => c.full_name === 'Alice Only')).toBeUndefined();

	await bobContext.close();
	await deleteTestUser(bob.userId);
});
```

This test is longer and more setup-heavy, but it's the most important one in the suite. RLS regressions are invisible to normal user flows — only a multi-user test exercises them. If this test ever fails, stop the release.

Helpers referenced:

- `createTestUser()` — mint a second user via admin API.
- `login(page, user)` — same as the `authedPage` fixture's inner logic.
- `createContactAsAdmin(userId, ...)` — insert a row bypassing RLS for arrange-only seeding.
- `deleteTestUser(userId)` — teardown.

Put these in `app/e2e/utils/data.ts` so they're shared.

## Step 8 — The helpers, one place

```ts
// app/e2e/utils/data.ts
import { createClient } from '@supabase/supabase-js';
import type { Page } from '@playwright/test';
import 'dotenv/config';

const admin = createClient(
	process.env.PUBLIC_SUPABASE_URL!,
	process.env.SUPABASE_SERVICE_ROLE_KEY!
);

export async function createContactViaApi(
	page: Page,
	data: { full_name: string; email?: string }
): Promise<void> {
	const res = await page.request.post('/?/contacts.remote.createContact', { form: data });
	if (res.status() !== 200) {
		throw new Error(`createContactViaApi failed: ${res.status()}`);
	}
}

export async function createContactAsAdmin(
	userId: string,
	full_name: string,
	email: string
): Promise<void> {
	const { error } = await admin
		.from('contacts')
		.insert({ user_id: userId, full_name, email });
	if (error) throw error;
}

export async function createTestUser(): Promise<{
	userId: string;
	email: string;
	password: string;
}> {
	const email = `user-${crypto.randomUUID()}@example.com`;
	const password = 'Password123!';
	const { data, error } = await admin.auth.admin.createUser({
		email,
		password,
		email_confirm: true
	});
	if (error) throw error;
	return { userId: data.user!.id, email, password };
}

export async function deleteTestUser(userId: string): Promise<void> {
	await admin.auth.admin.deleteUser(userId);
}

export async function login(
	page: Page,
	credentials: { email: string; password: string }
): Promise<void> {
	await page.goto('/login');
	await page.getByLabel('Email').fill(credentials.email);
	await page.getByLabel('Password').fill(credentials.password);
	await page.getByRole('button', { name: /log in/i }).click();
	await page.waitForURL('/app');
}
```

Imported into specs as needed. Keep it to one file while the suite stays small.

## Step 9 — Optional: snapshot the contact card

For purely visual regressions, Playwright's screenshot assertions are handy:

```ts
test('contact card renders as expected', async ({ authedPage }) => {
	const page = authedPage;
	await createContactViaApi(page, { full_name: 'Snapshot Person' });
	await page.goto('/app/contacts');

	const row = page.getByText('Snapshot Person').locator('..');
	await expect(row).toHaveScreenshot('contact-row.png', { maxDiffPixelRatio: 0.01 });
});
```

Use sparingly — visual snapshots are high-maintenance (font rendering differs across platforms). Module 12 shows how to pin the CI runner's exact fonts if you go this route. For most CRUD tests, the functional assertions from Steps 2–7 are enough.

## Step 10 — Run the whole suite

```bash
pnpm test
```

Expected: auth + CRUD, roughly 10–15 tests, 30–60 seconds. All green.

Red? Open the trace for the specific failing test. Ninety percent of failures come from timing — either an assertion running before the UI settled, or `resetDb()` not catching up between tests.

## Verify

- `pnpm test crud` passes all tests in `crud.spec.ts`.
- `pnpm test` (all specs) passes.
- The RLS isolation test actually ran two browser contexts (check the trace — you'll see both Alice's and Bob's pages).
- Removing an RLS policy temporarily (e.g. `drop policy "contacts_select_own" on public.contacts`) breaks the isolation test. This is your sanity check that the test genuinely enforces what it claims.

## Common traps

- **Chaining tests** ("this test relies on the previous one creating data"). Non-isolated tests rot over time. Always arrange fresh.
- **Using the UI for arrangement in every test.** Slow and brittle. Use API helpers for prerequisites; reserve UI interactions for the behavior you're actually testing.
- **Skipping the cross-user RLS test.** Every other test uses one user; RLS failures hide until multi-user. This test alone justifies Playwright.
- **Relying on `waitForTimeout`.** Time-based waits are the main source of flakes. Wait for specific conditions (URL, element, text) instead.
- **Not closing extra browser contexts.** Opened a second context for Bob? Close it. Leaked contexts accumulate and OOM the runner over long suites.
