# 8.3 — Pricing Page Config

> The bit of data that tells the UI *how* to present tiers, separate from *what* tiers exist.

## Why this matters

`src/lib/config/pricing.ts` (Module 5.5) tells the app what we *sell*: tier IDs, names, descriptions, contact limits, lookup keys. But it doesn't tell the UI things like:

- Which tier is the "recommended" one with a highlight border?
- What feature bullets appear under each tier on the marketing page?
- What's the CTA label — "Upgrade," "Downgrade," or "Contact us"?
- Which features get a ✓ vs an ✗ for each tier?

These are **presentation** concerns. Mixing them into `pricing.ts` would couple the tier-identity logic (used in tier gating, webhook handlers) with UI-specific knobs. Separation = cleanly swap the pricing page design without touching billing logic.

## The Principal Engineer lens

**Static data belongs in a typed config, not in JSX/templates.** The minute you paste `"20% off"` into a `.svelte` file, it's untestable, unsearchable, and eventually duplicated. A config file gives you grep-ability and one-place-to-edit.

Corollary: **keep marketing copy close to the team that owns it.** For most teams that's a single designer/PM editing `pricing-page.ts`. Tier IDs and lookup keys are engineering concerns; copy is not. Splitting the files means a PM can change a bullet without a reviewer needing to understand Supabase RLS.

## Step 1 — Design the config

Create `src/lib/config/pricing-page.ts`:

```ts
// src/lib/config/pricing-page.ts
import type { TierId } from './pricing';

export interface FeatureBullet {

	tagline: string;            // 1-liner under the name
```

A few decisions made on purpose.

## Step 2 — Why three CTA variants per tier

A pricing page button has three states depending on the viewer's current plan:

| Viewer is on… | Plus card says | Pro card says |
|---|---|---|
| Free | Upgrade to Plus | Upgrade to Pro |
| Plus | Manage subscription | Upgrade to Pro |
| Pro | Downgrade to Plus | Manage subscription |

Three CTAs per tier covers this cleanly. The component picks one based on the current subscription. Alternative: one CTA + a bunch of `{#if}` blocks in the template. Messier; the data model should describe the states, not the template.

## Step 3 — Why `highlighted: boolean` is a single flag, not an enum

We could have `style: 'default' | 'popular' | 'enterprise'` but only one tier is ever highlighted at a time. A boolean is enough. If we ever add a second visual state, we upgrade to an enum *then* — don't design for speculative variance.

## Step 4 — Interval toggle default

Pricing pages typically default to monthly (easier anchor price) or yearly (pushes the better per-month rate). Add a constant:

```ts
// src/lib/config/pricing-page.ts (append)
export const PRICING_DEFAULT_INTERVAL: 'monthly' | 'yearly' = 'monthly';
export const PRICING_YEARLY_DISCOUNT_LABEL = 'Save 20%';
```

Contactly defaults to monthly. Swapping is a one-line change. The "Save 20%" label is displayed next to the yearly option on the toggle — derived copy, not a field on each tier.

## Step 5 — Derive the yearly discount at runtime (sanity check)

Our marketing says "Save 20%." Let's make sure the amounts in Stripe actually do. Add a util:

```ts
// src/lib/server/billing/discount.ts
import type { Tier } from '$lib/server/billing/types';

/**
 * Returns the implied yearly discount as a fraction (0.20 = 20% off),
 * or null if either price is missing.
 */
export function yearlyDiscount(tier: Tier): number | null {
	const m = tier.prices.find((p) => p.interval === 'monthly');
	const y = tier.prices.find((p) => p.interval === 'yearly');
	if (!m || !y) return null;

	const fullYear = m.unitAmount * 12;
	const saved = fullYear - y.unitAmount;
	return saved / fullYear;
}
```

For Plus: `(1000 * 12 - 9600) / 12000 = 0.20`. For Pro: `(2000 * 12 - 19200) / 24000 = 0.20`. The label matches the reality.

Where we use this: a dev-only assertion in the pricing page server loader that warns if any tier's actual discount is more than a percentage point off the label. Catches silent drift between marketing and Stripe.

## Step 6 — Formatting cents → dollars

Every tier needs a human display: `$10.00/mo` or `$8.00/mo billed annually`. Money formatting is a recurring UI need; centralise it:

```ts
// src/lib/utils/money.ts
export function formatUSD(cents: number): string {
	return new Intl.NumberFormat('en-US', {
		style: 'currency',
		currency: 'USD',
		minimumFractionDigits: 0,
		maximumFractionDigits: 2
	}).format(cents / 100);
}

export function formatPerMonth(cents: number, interval: 'monthly' | 'yearly'): string {
	const monthly = interval === 'yearly' ? cents / 12 : cents;
	return `${formatUSD(monthly)}/mo`;
}
```

`$10/mo` when billed monthly, `$8/mo` when billed yearly — both strings a component can render directly.

## Step 7 — Wire the config into the tiers query

From Module 7.2 we have a `tiers` query that returns raw `Tier[]`. For the pricing page specifically we want *tiers joined with presentation data*. Don't mutate the DTO — compose:

```ts
// src/lib/server/billing/pricing-page.ts
import { listTiers } from './products';
import { PRICING_PRESENTATION } from '$lib/config/pricing-page';
import type { Tier } from './types';
import type { PricingTierPresentation } from '$lib/config/pricing-page';

export interface PricingPageTier {
	tier: Tier;
	presentation: PricingTierPresentation;
}

export async function listPricingPageTiers(): Promise<PricingPageTier[]> {
	const tiers = await listTiers();
	const out: PricingPageTier[] = [];
	for (const presentation of PRICING_PRESENTATION) {
		const tier = tiers.find((t) => t.id === presentation.id);
		if (!tier) continue;
		out.push({ tier, presentation });
	}
	return out;
}
```

`PRICING_PRESENTATION` dictates the order (free / plus / pro). Tiers without a presentation entry are silently omitted. The pricing page renders what this returns; no per-tier branching in the template.

## Step 8 — The server query for the page

```ts
// src/lib/server/billing/pricing-page.remote.ts
import { query } from '$app/server';
import { listPricingPageTiers } from './pricing-page';

export const pricingPageTiers = query(async () => {
	return await listPricingPageTiers();
});
```

Public query. No auth required. The pricing page renders for logged-out visitors too.

## Step 9 — What we deliberately kept out of the config

- **Prices as strings.** The UI formats via `formatPerMonth`; the config only holds lookup keys, because Stripe owns amounts.
- **Feature *descriptions*.** Only one-liner bullets. Long form belongs in a marketing site, not in code.
- **Stripe product IDs.** We've been over this (Module 5.6). Lookup keys only.
- **Colour / theme data.** That's component styling. Tailwind classes live next to the component.

Every omission is a future migration dodged.

## Verify

- `src/lib/config/pricing-page.ts` exists and exports `PRICING_PRESENTATION` with 3 entries.
- `listPricingPageTiers()` returns 3 entries in the order free / plus / pro.
- `formatPerMonth(1000, 'monthly') === '$10/mo'`.
- `yearlyDiscount(plusTier)` ≈ 0.20.

## Common traps

- **Merging `pricing.ts` and `pricing-page.ts`.** They evolve on different cadences and are touched by different roles. Keep them separate.
- **Hardcoding prices in the template.** You'll update the seed and the UI won't match. Always derive from the tiers query.
- **Formatting money in component code.** Locale, currency, rounding — one util, reused. Otherwise you'll get `$10.00` in one place and `$10` in another.
- **Treating `highlighted: true` as exclusive.** Nothing enforces only one tier being highlighted. Add a build-time assertion if it matters, or just review it at design time.

## Recap

Presentation config lives in `pricing-page.ts`, merges with the tiers DTO via `listPricingPageTiers`, gets served as a public query. All that's left: render it.
