# 8.1 — Create Products & Prices (Programmatically)

> In Module 5 we clicked the dashboard. Now we write the code that does it for us — forever.

## Why this matters

Every click in the Stripe dashboard is a snapshot of someone's decision at one point in time. Three weeks later nobody remembers why `plus_monthly` was set to $11 instead of $10, why Pro has no description, or whether Plus's yearly discount is 15% or 20%. The dashboard is a UI, not a source of truth.

A seed script fixes this. Run it against a fresh Stripe account and you get identical Products + Prices every time. Run it against an existing account and it converges — missing things get created, correct things are left alone, drifted things raise a flag.

This lesson designs the script. Module 8.2 runs it.

## The Principal Engineer lens

**Configuration lives in git.** Any bit of state that affects how your app behaves — pricing included — must have a text-file origin, reviewable in a PR. "I changed it in the dashboard" is the billing equivalent of "it works on my machine."

Corollary: **the script must be idempotent.** You'll run it on every deploy, every new dev onboarding, every environment reset. If it creates duplicates on the second run, it's useless. Idempotency is a design requirement, not a nice-to-have.

## Step 1 — Decide the script's contract

We want one command, `pnpm seed:stripe`, that:

1. Reads `TIERS` from `src/lib/config/pricing.ts` — the single source of truth for what we offer.
2. Asks Stripe "which lookup keys exist?" via `prices.list({ lookup_keys: [...] })`.
3. For each *missing* lookup key, creates the Product (if needed) and the Price.
4. For each *existing* lookup key, verifies amount/interval match and logs a warning if they drift.
5. Exits 0 on success, non-zero on any drift or error.

That's it. No deletes. No amount mutations (Stripe rejects those anyway). The script *creates and validates* — it never destroys.

## Step 2 — The shape of the script file

Create `app/scripts/seed-stripe.ts`:

```ts
// app/scripts/seed-stripe.ts
import Stripe from 'stripe';
import 'dotenv/config';
import { TIERS } from '../src/lib/config/pricing';

const secret = process.env.STRIPE_SECRET_KEY;
if (!secret) {
	console.error('STRIPE_SECRET_KEY missing. Add it to .env.');
	process.exit(1);
}

const stripe = new Stripe(secret, {
	apiVersion: '2026-03-25.dahlia'
});
```

Using `dotenv/config` lets the script read `.env` without SvelteKit. We intentionally don't use `$env/...` here — the script runs via `tsx`, outside the SvelteKit bundle.

## Step 3 — Expected prices derived from `TIERS`

We encode the *intended* amounts in a local table (not in `pricing.ts`, because `pricing.ts` is the UI/meta config — amounts come from Stripe at runtime). This is the seed's source of truth for "what should Stripe look like":

```ts
interface ExpectedPrice {
	lookupKey: string;
	productName: string;     // e.g. 'Plus'
	productDescription: string;
	unitAmount: number;      // cents
	currency: 'usd';
	interval: 'month' | 'year';
}

const EXPECTED: ExpectedPrice[] = [
	{
		lookupKey: 'plus_monthly',
		productName: 'Plus',
		productDescription: 'More contacts, priority email support.',
		unitAmount: 1000,
		currency: 'usd',
		interval: 'month'
	},
	{
		lookupKey: 'plus_yearly',
		productName: 'Plus',
		productDescription: 'More contacts, priority email support.',
		unitAmount: 9600,
		currency: 'usd',
		interval: 'year'
	},
	{
		lookupKey: 'pro_monthly',
		productName: 'Pro',
		productDescription: 'Unlimited contacts, premium support.',
		unitAmount: 2000,
		currency: 'usd',
		interval: 'month'
	},
	{
		lookupKey: 'pro_yearly',
		productName: 'Pro',
		productDescription: 'Unlimited contacts, premium support.',
		unitAmount: 19200,
		currency: 'usd',
		interval: 'year'
	}
];
```

Four prices, two products. Keep this table small and obvious — it'll be code-reviewed every time it changes.

## Step 4 — Product get-or-create

Products need to be fetched or created by *name* (Stripe doesn't offer lookup keys on products). To avoid creating duplicates when re-running, we list by name:

```ts
async function getOrCreateProduct(
	name: string,
	description: string
): Promise<string> {
	const existing = await stripe.products.search({
		query: `name:"${name}" AND active:"true"`,
		limit: 1
	});
	if (existing.data[0]) {
		const p = existing.data[0];
		if (p.description !== description) {
			console.warn(
				`[seed] Product "${name}" description drifted. ` +
					`Stripe: "${p.description}". Config: "${description}". Skipping update.`
			);
		}
		return p.id;
	}

	const created = await stripe.products.create({ name, description });
	console.log(`[seed] created product ${name} (${created.id})`);
	return created.id;
}
```

`stripe.products.search` uses Stripe's search-syntax DSL. It's eventually consistent (~1 minute lag after a create), so on a completely fresh account the script might create a duplicate if run twice in quick succession. In practice: run once, verify, stop worrying.

If you need stronger guarantees, store the Stripe product ID in `TIERS` after the first run — but that's hardcoding IDs again, which we explicitly rejected in Module 5.6. The search + "don't run the script in a tight loop" convention is the pragmatic answer.

## Step 5 — Price get-or-create

Now the main loop:

```ts
async function ensurePrice(e: ExpectedPrice): Promise<void> {
	const existing = await stripe.prices.list({
		lookup_keys: [e.lookupKey],
		active: true,
		limit: 1
	});
	const p = existing.data[0];

	if (p) {
		// Verify it matches expectations.
		const interval = p.recurring?.interval;
		const drift: string[] = [];
		if (p.unit_amount !== e.unitAmount) {
			drift.push(`amount: expected ${e.unitAmount}, got ${p.unit_amount}`);
		}
		if (interval !== e.interval) {
			drift.push(`interval: expected ${e.interval}, got ${interval}`);
		}
		if (p.currency !== e.currency) {
			drift.push(`currency: expected ${e.currency}, got ${p.currency}`);
		}
		if (drift.length) {
			console.warn(
				`[seed] Price "${e.lookupKey}" has drifted from config:\n  - ` +
					drift.join('\n  - ') +
					`\n  Archive and recreate to fix.`
			);
			process.exitCode = 1;
		} else {
			console.log(`[seed] ok: ${e.lookupKey} matches config`);
		}
		return;
	}

	// Not found — create it.
	const productId = await getOrCreateProduct(e.productName, e.productDescription);
	const created = await stripe.prices.create({
		product: productId,
		unit_amount: e.unitAmount,
		currency: e.currency,
		recurring: { interval: e.interval },
		lookup_key: e.lookupKey,
		nickname: `${e.productName} ${e.interval}ly (seed)`
	});
	console.log(`[seed] created price ${e.lookupKey} (${created.id})`);
}
```

Key details:

- **`process.exitCode = 1` on drift** (not `process.exit(1)`). We don't halt — we still want to check the other prices. Setting `exitCode` means the script eventually exits non-zero *after* finishing all work.
- **`nickname` is human-facing in the dashboard.** Lookup key is the machine handle; nickname is the "what is this?" label. Good hygiene.
- **We never mutate existing prices.** Stripe rejects `unit_amount` changes. If the config says $11 and Stripe says $10, the script warns — a human deliberately archives the old price and creates a new one. We don't automate destruction.

## Step 6 — The top-level driver

```ts
async function main() {
	console.log('[seed] starting Stripe seed');
	for (const expected of EXPECTED) {
		await ensurePrice(expected);
	}
	if (process.exitCode) {
		console.error('\n[seed] completed with drift warnings — see above.');
	} else {
		console.log('\n[seed] all prices match config.');
	}
}

main().catch((err) => {
	console.error('[seed] failed:', err);
	process.exit(1);
});
```

Sequential, not parallel. Four prices — parallelism saves maybe 200ms and confuses log output.

## Step 7 — Register as a package script

In `app/package.json`:

```json
{
	"scripts": {
		"seed:stripe": "tsx scripts/seed-stripe.ts"
	}
}
```

And make sure `tsx@4.22.3` is already in `devDependencies` (we added it in Module 4 for the Supabase seed script).

## Step 8 — Think about what this script is NOT for

The seed script is a **one-way convergence tool**: local config → Stripe. It does not:

- Pull prices *from* Stripe into `pricing.ts`. Stripe isn't the source of truth for what we *offer*.
- Delete archived prices. Archives are history; history stays.
- Archive active prices that aren't in the config. A rogue price in Stripe surfaces as a dashboard line item we can see and handle manually — safer than automatic destruction.

Keep the script boring. The day you're tempted to add "clever" behaviour to it is the day you should split that behaviour into a separate, explicit script.

## Verify

- `cat app/scripts/seed-stripe.ts` renders the file you wrote.
- `pnpm seed:stripe` (against an already-seeded Stripe) prints four `ok:` lines and exits 0.
- Temporarily change `plus_monthly`'s amount in the script to 1100, re-run — see the drift warning + non-zero exit.
- Revert the change.

## Common traps

- **Not pinning `apiVersion`.** You'd run the script today with behaviour X and next month with behaviour Y after Stripe auto-rolls. Pin it.
- **Running against live mode by accident.** The script uses whatever `STRIPE_SECRET_KEY` is in `.env`. Double-check the key starts with `sk_test_` before running in dev.
- **Adding `.del()` calls to "clean up."** Seeds create; humans delete. Keeping them separate makes mistakes recoverable.
- **Parallelising with `Promise.all` and hitting Stripe's rate limit.** Four requests serially is fine; a hundred in parallel triggers backoff. Stay sequential until there's a measured reason not to.
