# 8.2 — Seeding Stripe Data

> Run the script. Watch it converge. Wire it into your dev loop so you never forget.

## Why this matters

The seed script from 8.1 is only as useful as the habit of running it. New contributor clones the repo? They need the same Stripe products. Test mode got wiped? Same. CI spun up a fresh preview environment? Same. If seeding isn't a one-command, always-available action, people skip it and everything downstream breaks in ways that look like bugs.

This lesson runs the script for real, adds a one-shot dev hook so it can't be forgotten, and covers what to do when the first run fails (it always does the first time).

## The Principal Engineer lens

**Make the right thing the easy thing.** Developers don't skip seeds because they're lazy; they skip them because they forgot or it was inconvenient. A `postinstall` script removes the forget path. A clear error message when seeding fails removes the "something's broken and I don't know why" path.

Corollary: **loud failures, quiet successes.** The script should print one line per price on the happy path and a multi-line diagnostic with a fix on the sad path. Not the other way round.

## Step 1 — First run, against the dashboard you manually populated

Assuming you followed Module 5.5, your Stripe test account already has `plus_monthly`, `plus_yearly`, `pro_monthly`, `pro_yearly`. Run:

```bash
cd app
pnpm seed:stripe
```

Expected output:

```
[seed] starting Stripe seed
[seed] ok: plus_monthly matches config
[seed] ok: plus_yearly matches config
[seed] ok: pro_monthly matches config
[seed] ok: pro_yearly matches config

[seed] all prices match config.
```

Four `ok` lines, exit 0. The script found what Module 5.5 created, verified every field, and is satisfied.

## Step 2 — Proof that it creates what's missing

Let's delete one price (in test mode) and re-run:

1. Stripe Dashboard → Products → Plus → click `plus_yearly` → **Archive price**.
2. `pnpm seed:stripe`.

Now you should see:

```
[seed] ok: plus_monthly matches config
[seed] created price plus_yearly (price_1Pz...)
[seed] ok: pro_monthly matches config
[seed] ok: pro_yearly matches config

[seed] all prices match config.
```

The script detected the absence (archived prices don't match `active: true`), re-created the price, linked the same lookup key, and kept the product. This is the convergence behaviour you want.

## Step 3 — Proof that it warns on drift

Temporarily edit `app/scripts/seed-stripe.ts`, change `plus_monthly`'s `unitAmount` from `1000` to `1100`, save, and run:

```
[seed] Price "plus_monthly" has drifted from config:
  - amount: expected 1100, got 1000
  Archive and recreate to fix.
[seed] ok: plus_yearly matches config
...

[seed] completed with drift warnings — see above.
```

Exit code 1. The script can't auto-fix amount drift (Stripe forbids it) so it surfaces the drift and asks a human. Revert your edit before moving on.

## Step 4 — Wire it into `postinstall`

In `app/package.json`:

```json
{
	"scripts": {
		"postinstall": "node -e \"process.env.SKIP_SEED || require('child_process').spawnSync('pnpm',['seed:stripe'],{stdio:'inherit'})\""
	}
}
```

What this does: after `pnpm install`, the seed runs automatically. New contributors type one command (`pnpm install`), pull a fresh test-mode Stripe, and get working products. The `SKIP_SEED` env var is an escape hatch for CI environments that don't need it (or that haven't configured Stripe yet).

**Is this too clever?** Mildly. Some teams prefer an explicit "did you run pnpm seed:stripe?" entry in the README. Both work. The `postinstall` wins on contributor-onboarding latency; the README wins on surprise-factor. Pick the style that fits your team.

## Step 5 — Handle the "no keys in .env yet" case

If someone runs `pnpm install` before setting up `.env`, the seed fails. The script already handles this (Module 8.1 Step 2) with:

```ts
if (!secret) {
	console.error('STRIPE_SECRET_KEY missing. Add it to .env.');
	process.exit(1);
}
```

But `postinstall` failing is jarring. Beef up the message:

```ts
if (!secret) {
	console.error(`
STRIPE_SECRET_KEY missing.

Quick fix:
  1. Copy .env.example to .env: \`cp .env.example .env\`
  2. Add your Stripe test key (starts with sk_test_) from
     https://dashboard.stripe.com/test/apikeys
  3. Re-run: \`pnpm seed:stripe\`

(Or set SKIP_SEED=1 to skip the seed on postinstall.)
`);
	process.exit(1);
}
```

Ten seconds of formatting saves every future contributor from a confusing first-install experience.

## Step 6 — Add a sanity check at app boot

Back in `src/lib/server/billing/products.ts` (Module 7.2) we wrote `assertAllPaidTiersSeeded`. Wire it into `hooks.server.ts`:

```ts
// src/hooks.server.ts (around existing setup)
import { assertAllPaidTiersSeeded } from '$lib/server/billing/products';
import { dev } from '$app/environment';

let seedCheckPromise: Promise<void> | null = null;

export const handle = sequence(async ({ event, resolve }) => {
	// Fire-and-check-later: doesn't block the request, but surfaces early.
	if (dev && !seedCheckPromise) {
		seedCheckPromise = assertAllPaidTiersSeeded().catch((err) => {
			console.error('[startup] Stripe seed check failed:', err.message);
			seedCheckPromise = null; // allow retry
		});
	}
	return resolve(event);
}, /* other handles */);
```

In production, skip this check (startup-time Stripe calls can add cold-start latency; we trust the deploy pipeline to have seeded correctly). In dev, it's a tripwire — the first request after `pnpm dev` prints the error to the terminal if the seed is missing.

## Step 7 — The CI implication

When GitHub Actions or Vercel build the app, the seed should *not* run against production Stripe. Module 12 covers the split: `postinstall` checks for `SKIP_SEED` and respects it, and we set `SKIP_SEED=1` in CI. Production Stripe is seeded once, manually, via `pnpm seed:stripe` run against a `STRIPE_SECRET_KEY` starting with `sk_live_`. Same script; different environment.

The *same script* is the point. Local dev, staging, prod — identical code path, parametrised by the secret key. This is what "manual once, scripted forever" actually looks like.

## Step 8 — Inspect what the script left behind

Open the Stripe dashboard → Products. Every price should now have:

- A **nickname** like `Plus monthly (seed)` — easier to identify than a bare ID.
- A **lookup key** in the details pane.
- A consistent set of fields across test and (eventually) live.

If a price is missing a nickname, it was created manually in Module 5.5 and the seed left it alone (the script's "doesn't mutate existing" rule). To clean that up: archive the manual price, re-run the seed, the script creates a fresh one with the nickname.

## Step 9 — A teammate-friendly README snippet

Add to `app/README.md` under a "Stripe" section:

```md
## Stripe setup

1. Copy `.env.example` to `.env` and fill in your test-mode keys from
   https://dashboard.stripe.com/test/apikeys.
2. Run `pnpm seed:stripe` to create the products/prices Contactly expects.
3. Run `pnpm stripe:listen` in a separate terminal to tunnel webhooks.

Or, for everything in one shot: `pnpm dev:all`.
```

Three steps, every command linked. This is the docs equivalent of `postinstall` — making the right thing impossible to miss.

## Verify

- `pnpm seed:stripe` exits 0 and matches every price.
- Archiving a price and re-running recreates it with the correct amount + lookup key.
- The `postinstall` hook runs on `pnpm install` (try deleting `node_modules` and running install).
- In dev, starting the app with no Stripe prices triggers the startup-time assertion.

## Common traps

- **Running the seed against live mode "to check."** Creates real Products in production. Archive-only clean-up afterward. Look at the `sk_` prefix before running.
- **Treating drift warnings as benign.** They mean your config and Stripe disagree. Decide which is right, take action, re-run until clean.
- **Depending on `postinstall` in CI.** CI should set `SKIP_SEED=1` so builds don't attempt to connect to Stripe. Production's Stripe is seeded out-of-band.
- **Deleting the seed script after "everything works."** You'll wipe test mode in three weeks to debug something, and the script will be gone. Keep it; re-run as needed.

Stripe is now populated by code, convergent, idempotent, wired into `postinstall`, and surfaced by a dev-time startup assertion. From here on the dashboard only *watches* what the script decides.
