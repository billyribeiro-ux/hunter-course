# 2.2 — Install Supabase SDKs & Generate Types

> Two packages, one codegen command. After this, your editor knows every column in every table.

## Why this matters

There are two Supabase packages we care about:

- **`@supabase/supabase-js`** — the core client. Talks to PostgREST, Auth, Storage, Realtime.
- **`@supabase/ssr`** — the SvelteKit/Next/Remix adapter. Handles cookies correctly on the server so your session survives a page refresh.

We also want **typed queries**. Without types, `supabase.from('contacts').select('*')` returns `any`. With types, it returns `Contact[]` and your editor autocompletes column names. This is the single biggest DX upgrade you can give yourself.

## The Principal Engineer lens

Codegen'd types are a contract between the database and the app. The contract lives in version control; it's regenerated whenever the schema changes; and CI fails the build if someone forgets to regenerate. That's how you prevent "oh I renamed that column three weeks ago" bugs.

## Step 1 — Confirm the packages are installed

We pinned these in Lesson 1.1. In `package.json`:

```json
{
  "dependencies": {
    "@supabase/ssr": "0.10.3",
    "@supabase/supabase-js": "2.106.2"
  }
}
```

If they're not there yet:

```bash
pnpm add @supabase/ssr@0.10.3 @supabase/supabase-js@2.106.2
```

(Exact pins — no `^`.)

## Step 2 — Make sure Supabase is running

Codegen reads your schema from the running local DB, so start it first:

```bash
pnpm supabase:start
```

## Step 3 — Generate the types

The `supabase` CLI ships a codegen command that introspects your DB and emits a single TypeScript file describing every table, view, enum, and function.

Run:

```bash
pnpm supabase:types
```

(Recall we added that script in Lesson 1.2: `supabase gen types typescript --local > src/lib/types/database.types.ts`.)

Open the generated file `src/lib/types/database.types.ts`. You'll see something like:

```ts
export type Database = {
	public: {
		Tables: {
			profiles: {
				Row: {
					id: string;
					full_name: string | null;
					updated_at: string;
				};
				Insert: {
					id: string;
					full_name?: string | null;
					updated_at?: string;
				};
				Update: {
					id?: string;
					full_name?: string | null;
					updated_at?: string;
				};
				Relationships: [
					/* ... FK info ... */
				];
			};
		};
		// ...
	};
};
```

This is the contract. Every query we write will be typed against this.

## Step 4 — Add a `Tables` helper

The raw `Database` type is verbose. A one-line helper makes it ergonomic. Create `src/lib/types/db.ts`:

```ts
// src/lib/types/db.ts
import type { Database } from './database.types';

export type Tables<T extends keyof Database['public']['Tables']> =
	Database['public']['Tables'][T]['Row'];

export type TablesInsert<T extends keyof Database['public']['Tables']> =
	Database['public']['Tables'][T]['Insert'];

export type TablesUpdate<T extends keyof Database['public']['Tables']> =
	Database['public']['Tables'][T]['Update'];

// Convenience re-exports:
export type Profile = Tables<'profiles'>;
```

Now in any file you can write:

```ts
import type { Profile } from '$lib/types/db';

const p: Profile = { id: '...', full_name: 'Ada', updated_at: new Date().toISOString() };
```

We'll add `Contact` to this file in Module 4, and `BillingCustomer` etc. in Module 7.

## Step 5 — Make codegen part of the workflow

Any time your schema changes, you regenerate. Don't rely on memory — we'll enforce it in CI (Module 12). For now, make it muscle memory:

```bash
pnpm supabase:reset        # apply migrations
pnpm supabase:types        # regenerate types
```

Do these two commands back-to-back every time.

## Step 6 — Prove it works

Create a throwaway file `src/lib/playground.ts`:

```ts
import type { Profile } from '$lib/types/db';

const p: Profile = {
	id: 'abc',
	full_name: 'ada',
	// @ts-expect-error — updated_at is required
	wrong_field: true
};

void p;
```

Run `pnpm check`. The `@ts-expect-error` should pass (meaning it correctly caught a bad field), and TypeScript should complain that `updated_at` is missing. Fix the file by adding `updated_at: new Date().toISOString()` or just delete it — we were only proving types work.

## Step 7 — Re-exclude the generated file from lint/format

Make sure `eslint.config.js` has the file in `ignores`:

```js
ignores: ['build/', '.svelte-kit/', 'dist/', 'src/lib/types/database.types.ts'];
```

And in `.prettierignore` (create it if missing):

```
src/lib/types/database.types.ts
.svelte-kit/
build/
```

Generated files are not your code; you shouldn't be formatting them.

## Verify

- `src/lib/types/database.types.ts` exists and contains `public.profiles`.
- `src/lib/types/db.ts` re-exports `Profile`.
- `pnpm check` passes.
- Re-running `pnpm supabase:types` is idempotent (no unexpected diff on identical schema).

## Common traps

- **"Table not found"** on `supabase gen types`. You forgot `pnpm supabase:start` or `pnpm supabase:reset` first.
- **Types out of date.** The fix is always `pnpm supabase:reset && pnpm supabase:types`. Never hand-edit `database.types.ts` — your change will be clobbered on the next regen.
- **Wrong DB in codegen.** `--local` is critical. Without it, the CLI tries to connect to a linked remote project and fails confusingly.

## Recap

You now have:

- The two Supabase packages installed.
- A generated types file reflecting your schema.
- A small `db.ts` helper making those types ergonomic.
