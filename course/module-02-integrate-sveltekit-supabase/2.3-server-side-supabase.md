# 2.3 — Server-Side Supabase

> Where `hooks.server.ts` earns its keep.

## Why this matters

Every request that hits your SvelteKit server needs a Supabase client **scoped to the current user**. Not a shared singleton — a fresh one per request, seeded with the user's cookie-backed session. That way:

- RLS enforces "only your rows" automatically.
- The user's JWT is refreshed when it's about to expire, via a `set-cookie` header on the response.
- Your app code can do `locals.supabase.from('contacts').select()` and it Just Works.

The magic lives in `hooks.server.ts`.

## The Principal Engineer lens

Three non-negotiables:

1. **One client per request**, created in a hook. Never cache Supabase clients across requests.
2. **Always verify the JWT**, don't trust the cookie's contents. Supabase's helper `getSession()` is fast but doesn't verify; `getUser()` hits their auth server and verifies. We call both.
3. **Keep the service-role client separate**, named `supabaseAdmin`, never conflated with the user client. Service-role bypasses RLS — one accidental `locals.supabase` / `locals.supabaseAdmin` swap is a privilege escalation bug.

## Step 1 — Tell TypeScript about `locals`

SvelteKit ships a type `App.Locals` in `src/app.d.ts`. Edit it:

```ts
// src/app.d.ts
import type { SupabaseClient, Session, User } from '@supabase/supabase-js';
import type { Database } from '$lib/types/database.types';

declare global {
	namespace App {
		interface Locals {
			supabase: SupabaseClient<Database>;
			supabaseAdmin: SupabaseClient<Database>;
			safeGetSession: () => Promise<{ session: Session | null; user: User | null }>;
			session: Session | null;
			user: User | null;
		}
		interface PageData {
			session: Session | null;
			user: User | null;
		}
		// interface Error {}
		// interface Platform {}
	}
}

export {};
```

Now `event.locals.supabase` is typed, and your editor autocompletes tables thanks to `<Database>`.

## Step 2 — Write the hook

Create or replace `src/hooks.server.ts`:

```ts
// src/hooks.server.ts
import { createServerClient } from '@supabase/ssr';
import { createClient } from '@supabase/supabase-js';
import { sequence } from '@sveltejs/kit/hooks';
import type { Handle } from '@sveltejs/kit';
import type { Database } from '$lib/types/database.types';
import { env } from '$lib/server/env';

const supabaseHandle: Handle = async ({ event, resolve }) => {
	// ── User-scoped client (respects RLS) ──────────────────────────────────
	event.locals.supabase = createServerClient<Database>(
		env.PUBLIC_SUPABASE_URL,
		env.PUBLIC_SUPABASE_ANON_KEY,
		{
			cookies: {
				getAll: () => event.cookies.getAll(),
				setAll: (cookies) => {
					for (const { name, value, options } of cookies) {
						event.cookies.set(name, value, { ...options, path: '/' });
					}
				}
			}
		}
	);

	// ── Admin client (service role — bypasses RLS) ─────────────────────────
	event.locals.supabaseAdmin = createClient<Database>(
		env.PUBLIC_SUPABASE_URL,
		env.SUPABASE_SERVICE_ROLE_KEY,
		{ auth: { persistSession: false, autoRefreshToken: false } }
	);

	// ── safeGetSession: verifies the JWT against Supabase Auth ─────────────
	event.locals.safeGetSession = async () => {
		const {
			data: { session }
		} = await event.locals.supabase.auth.getSession();
		if (!session) return { session: null, user: null };

		const {
			data: { user },
			error
		} = await event.locals.supabase.auth.getUser();
		if (error) return { session: null, user: null };

		return { session, user };
	};

	// Hydrate event.locals for downstream handlers
	const { session, user } = await event.locals.safeGetSession();
	event.locals.session = session;
	event.locals.user = user;

	return resolve(event, {
		filterSerializedResponseHeaders: (name) => name === 'content-range' || name === 'x-supabase-api-version'
	});
};

export const handle = sequence(supabaseHandle);
```

Key ideas:

- `createServerClient` is from `@supabase/ssr`; it knows how to read/write auth cookies using SvelteKit's cookie API.
- `createClient` (not `createServerClient`) is used for the admin client because we don't want cookie handling — we want a raw service-role connection.
- `safeGetSession` is our own name for "get a session we actually trust." We call `getUser()` to force a round-trip to Supabase Auth and verify the JWT signature. Without that, a forged cookie would be accepted.
- `sequence(...)` will matter once we add more handles (rate limiting, CSP, etc.).

## Step 3 — Expose session to pages via `+layout.server.ts`

Create `src/routes/+layout.server.ts`:

```ts
// src/routes/+layout.server.ts
import type { LayoutServerLoad } from './$types';

export const load: LayoutServerLoad = async ({ locals: { session, user } }) => {
	return { session, user };
};
```

That's it. Every page now receives `data.session` and `data.user` via the layout load chain. We'll use this to show "Log in" vs. user menu in the nav.

## Step 4 — Expose session to components via `+layout.svelte`

Edit `src/routes/+layout.svelte`:

```svelte
<script lang="ts">
	import '../app.css';
	let { data, children } = $props();
</script>

{@render children()}
```

For now we're just proving the pipeline works. We'll build the real layout (nav, theme toggle, toasts) in Module 3.

## Step 5 — Smoke test

Spin up dev server:

```bash
pnpm dev
```

Open the browser devtools → **Application → Cookies → localhost:5173**. Even before you log in, you may see zero cookies (because you have no session). Good.

Now add a temporary debug page. Create `src/routes/debug/+page.server.ts`:

```ts
import type { PageServerLoad } from './$types';

export const load: PageServerLoad = async ({ locals }) => {
	const { data, error } = await locals.supabase.from('profiles').select('*');
	return { profiles: data ?? [], err: error?.message ?? null };
};
```

And `src/routes/debug/+page.svelte`:

```svelte
<script lang="ts">
	let { data } = $props();
</script>

<pre>{JSON.stringify(data, null, 2)}</pre>
```

Visit `http://localhost:5173/debug`. You should see:

```json
{
	"profiles": [],
	"err": null
}
```

Empty array, no error — exactly what we want. RLS is blocking any row a non-authenticated user would see (there are none yet anyway). Delete the `debug/` folder before committing — debug routes must not ship.

## Step 6 — Why we hit `getUser()` on every request

You'll see articles online that say "just use `getSession()`, it's fast." That's true, but unsafe: `getSession()` reads whatever is in the cookie and returns it. A malicious client could craft a cookie with an expired or forged JWT, and `getSession()` would hand it back happily.

`getUser()` asks Supabase Auth to verify the JWT, at the cost of a ~50ms round-trip. We trade that latency for correctness. For a SaaS app this is the right default; for a blog with 10M page views you might revisit it.

## Verify

- `src/app.d.ts` declares typed `locals`.
- `src/hooks.server.ts` sets up both clients.
- `+layout.server.ts` returns `session` and `user`.
- `pnpm check` passes.

## Common traps

- **Setting cookies with wrong `path`.** Always `path: '/'` — otherwise subpage reloads lose the session.
- **Using `locals.supabaseAdmin` in a page load.** If you need admin access from a page, stop and think. Probably you need a different RLS policy, not an admin bypass.
- **Returning the raw `supabase` client from a load.** Never. The client wraps the fetch handler; returning it will serialize to `{}`.
- **Shipping the full Supabase `User` to the browser.** `return { session, user }` from `+layout.server.ts` is convenient, but `user` is a fat object — `phone`, `app_metadata`, `confirmation_sent_at`, `recovery_sent_at`, `aud`, `role`, `last_sign_in_at`. None of that is needed for rendering, and *every* extra field is gratuitous attack surface in a JS payload that an attacker can inspect via DevTools. Project to a `SafeUser` shape at the serialization boundary:

	```ts
	// src/routes/+layout.server.ts
	export const load: LayoutServerLoad = async ({ locals: { session, user } }) => {
		return {
			session,
			user: user
				? { id: user.id, email: user.email ?? null, fullName: user.user_metadata?.full_name ?? null }
				: null
		};
	};
	```

	Server-side `locals.user` keeps the full object for code that legitimately needs `user_metadata` or `app_metadata`. Only this narrowed projection crosses the wire. Principal-Engineer rule: minimise what crosses any trust boundary, even an internal one.

## Recap

Your server now creates a per-request Supabase client, verifies the session, and exposes both to the rest of the app through `locals` and the layout load. In the next lesson we'll build the matching browser-side client for cases where we need it.
