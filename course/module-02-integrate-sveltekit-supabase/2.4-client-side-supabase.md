# 2.4 — Client-Side Supabase

> For the two or three things the server can't do for you.

## Why this matters

With SvelteKit remote functions and `+page.server.ts`, 95% of our data access happens on the server. So why do we need a browser client at all? Two reasons:

1. **Auth flows.** `signInWithPassword`, `signUp`, `signOut` need the client because they write cookies the browser owns.
2. **Realtime subscriptions.** When we add "live contact list" in Module 13, the server can't push websockets — the browser subscribes directly.

That's it. For queries and mutations, the server is canonical. If you find yourself reaching for `supabase.from('contacts').select()` in a `.svelte` file, stop and make it a remote `query()`.

## The Principal Engineer lens

**Data flows downward from the server.** The browser consumes it; it doesn't fetch it. This gives us:

- RLS enforcement without relying on browser auth (which can be tampered with).
- Simpler stores (no client-side cache invalidation — remote function `.refresh()` handles it).
- A clean test story (mock the server; the browser can be a thin view layer).

But for *authentication* — sign-in, sign-out — the browser needs its own client because the session lives in `document.cookie`.

## Step 1 — Create the browser client factory

Create `src/lib/supabase/client.ts`:

```ts
// src/lib/supabase/client.ts
import { createBrowserClient } from '@supabase/ssr';
import type { Database } from '$lib/types/database.types';
import { PUBLIC_SUPABASE_URL, PUBLIC_SUPABASE_ANON_KEY } from '$env/static/public';

let _client: ReturnType<typeof createBrowserClient<Database>> | null = null;

/**
 * Get (or lazily create) the singleton browser Supabase client.
 * Safe to call from any component on the browser only.
 */
export function getSupabaseBrowserClient() {
	if (typeof window === 'undefined') {
		throw new Error('getSupabaseBrowserClient called on the server');
	}
	if (!_client) {
		_client = createBrowserClient<Database>(PUBLIC_SUPABASE_URL, PUBLIC_SUPABASE_ANON_KEY);
	}
	return _client;
}
```

Why singleton?

- Supabase's realtime socket should be opened once, not per-component.
- Auth state listeners are shared — if every component created its own client they'd each fire separate `onAuthStateChange` events.

Why the `typeof window === 'undefined'` guard?

- `createBrowserClient` assumes it's in a browser (reads `document.cookie`). If we SSR a component that calls it, we'd blow up. Making the failure explicit is better than a cryptic reference error.

## Step 2 — Where *not* to use it

Our rule: **`supabase` client appears exactly three places:**

1. `hooks.server.ts` — per-request user client + service role (done in 2.3).
2. Server-side code in `src/lib/server/` — rarely, only when a hook isn't enough.
3. `src/lib/supabase/client.ts` — the browser client, for auth + realtime only.

If you find yourself importing `@supabase/*` anywhere else, pause and ask whether a remote function would do the job instead.

## Step 3 — Think through auth state sync

Here's a subtle bug: the server knows the user is logged in (it read the cookie). The browser also knows (it has the cookie). But the two are separate objects. If you sign out on the browser, the server's `locals.session` for an in-flight request won't know until the browser sends its next request with updated cookies.

`@supabase/ssr` handles this for us: it shares cookie reads/writes between server and browser. We just have to remember to:

- **Call auth methods from the browser client** on signed-in/signed-out transitions.
- **Reload the server layout** after those calls, so the server re-reads cookies.

SvelteKit's `invalidateAll()` is how we trigger the reload. We'll use it in Module 3 inside the actual sign-in/sign-out forms.

## Step 4 — A tiny example for muscle memory

Here's the skeleton we'll expand in Module 3. Don't create this file yet — just read it:

```svelte
<!-- src/routes/login/+page.svelte (preview of Module 3) -->
<script lang="ts">
	import { goto, invalidateAll } from '$app/navigation';
	import { getSupabaseBrowserClient } from '$lib/supabase/client';

	let email = $state('');
	let password = $state('');
	let error = $state<string | null>(null);

	async function handleSubmit(e: SubmitEvent) {
		e.preventDefault();
		const supabase = getSupabaseBrowserClient();
		const { error: err } = await supabase.auth.signInWithPassword({ email, password });
		if (err) {
			error = err.message;
			return;
		}
		await invalidateAll();
		await goto('/contacts');
	}
</script>

<!-- ...form markup... -->
```

Three things worth noting for when you see this again:

- `$state(...)` is Svelte 5's rune for reactive local state. Replaces `let x = ...` + reactivity tricks.
- `invalidateAll()` re-runs every server load, so the server sees the new session cookie.
- We `goto` after `invalidateAll` — not before — so the destination route gets the fresh session.

## Step 5 — Dual-layer auth rule

> **Always verify on the server.**

Even though the browser client is aware of auth, any route that shows sensitive data must verify on the server — because the browser is controlled by the user and can't be trusted.

For us, "verify on the server" means `locals.user` in a `+page.server.ts` or remote `getRequestEvent().locals.user` in a `.remote.ts`. If `user` is `null`, we redirect to `/login`.

We'll codify this as a helper in Module 3 (`requireUser(locals)`), so every server function that needs an authenticated user gets a one-liner.

## Step 6 — Realtime: a sneak peek

In Module 13 we'll add live updates to the contacts list. The code will look like:

```ts
// Later in module 13
const channel = supabase
	.channel('contacts-changes')
	.on(
		'postgres_changes',
		{ event: '*', schema: 'public', table: 'contacts', filter: `user_id=eq.${user.id}` },
		() => void getContacts().refresh()
	)
	.subscribe();
```

That's the *one* scenario where the browser's Supabase client does meaningful querying. And even then, it's a subscription, not a SELECT — the actual data still flows from our `getContacts` remote query.

## Verify

- `src/lib/supabase/client.ts` exists and exports `getSupabaseBrowserClient`.
- It's not imported anywhere yet — we'll wire it into `/login` and `/register` in Module 3.
- `pnpm check` passes.

## Common traps

- **Creating a fresh client in every component.** You'll end up with multiple websocket connections, multiple auth listeners, weird race conditions. The singleton avoids this.
- **Using the browser client in a `+page.server.ts`.** `createBrowserClient` reads `document.cookie`; there's no `document` on the server. Always use `locals.supabase`.
- **Forgetting `invalidateAll()`** after `signIn` / `signOut`. Symptom: UI shows you're logged in, but server-rendered data still thinks you're a guest.

## Recap

You now have the two sides of the Supabase pipeline:

- **Server**: per-request user client + admin client, wired into `locals` in `hooks.server.ts`.
- **Browser**: lazy singleton used only for auth + realtime.

With that, we're ready to build the auth flow — sign up, sign in, sign out, password reset, user menu.
