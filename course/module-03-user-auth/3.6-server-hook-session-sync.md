# 3.6 — Server Hook & Session Sync

> The quiet infrastructure work that prevents "why am I logged out?" bugs.

## Why this matters

We already built `hooks.server.ts` in Lesson 2.3. This lesson is about the *other* hook: the client-side one that keeps the browser's auth state in lockstep with the server's cookies, especially across tabs and long-lived sessions.

Here's the subtle bug we're preventing: a user has two tabs open. They sign out in tab A. Tab B still thinks they're logged in — until it does a navigation. You click a "protected" button, the `command()` returns "not authenticated," and the user sees a confusing error instead of a graceful redirect.

The fix is two small pieces:

1. A root `+layout.svelte` listener that calls `invalidateAll()` on any Supabase auth state change.
2. A `getSupabaseBrowserClient()` singleton (already built in 2.4) that all tabs share via cookies.

Together, sign-out in tab A → cookies clear → tab B's next SSR refresh sees no user → UI reflows to match.

## The Principal Engineer lens

**Keep state authoritative in one place.** The server is the source of truth for "who is this user." The browser doesn't *decide* — it *listens*. This is the opposite of the old SPA pattern where the client owns auth and tells the server. Modern SSR/edge apps reverse that: cookies are canonical, client just reacts.

## Step 1 — Update the root layout server load

We already have `src/routes/+layout.server.ts` returning `{ session, user }`. We'll add one more thing — a stable-ish "session timestamp" we can use to detect changes:

```ts
// src/routes/+layout.server.ts
import type { LayoutServerLoad } from './$types';

export const load: LayoutServerLoad = async ({ locals, depends }) => {
	depends('supabase:auth');
	return {
		session: locals.session,
		user: locals.user
	};
};
```

`depends('supabase:auth')` marks this load as depending on a synthetic key. We can later call `invalidate('supabase:auth')` to re-run *just this load*, not every loader in the app.

## Step 2 — Wire up the client listener

Edit `src/routes/+layout.svelte`:

```svelte
<script lang="ts">
	import '../app.css';
	import { onMount } from 'svelte';
	import { invalidate } from '$app/navigation';
	import { getSupabaseBrowserClient } from '$lib/supabase/client';

	let { data, children } = $props();

	onMount(() => {
		const supabase = getSupabaseBrowserClient();
		const {
			data: { subscription }
		} = supabase.auth.onAuthStateChange((_event, newSession) => {
			// Only invalidate if the session *actually* changed (different token).
			if (newSession?.access_token !== data.session?.access_token) {
				void invalidate('supabase:auth');
			}
		});
		return () => subscription.unsubscribe();
	});
</script>

{@render children()}
```

What this does:

- **`onAuthStateChange`** fires whenever the browser Supabase client sees a sign-in, sign-out, or token refresh.
- **Access-token comparison** — without it, we'd invalidate on *every* refresh (the token rotates periodically), causing extra server round-trips for nothing.
- **`invalidate('supabase:auth')`** re-runs only the root layout load — cheap and targeted.
- **Cleanup** unsubscribes when the component unmounts.

## Step 3 — Why not `invalidateAll()`?

`invalidateAll()` re-runs every load in the app. It's correct, but heavy: if you have 10 loads on the current page and only the layout session matters, you'll thrash 9 unnecessary queries. With the named dependency, we invalidate precisely what we care about.

## Step 4 — Test cross-tab sync

```bash
pnpm dev
```

1. Open `http://localhost:5173/login` in two tabs.
2. Sign in on tab A. Navigate to `/contacts` (or wherever).
3. In tab B, hit refresh — or just wait and navigate. You should also be logged in.
4. Click "Sign out" in tab A.
5. In tab B, do any navigation (even clicking the logo). You should be bounced to `/login`.

Without the `onAuthStateChange` listener, tab B would show stale UI until you manually refreshed. With it, any auth-state event fires across tabs via the shared cookies + local-storage Supabase uses.

## Step 5 — Token refresh, explained

JWTs expire. Supabase sessions live for 1 hour (`jwt_expiry = 3600`). When the token is near expiry, the browser client silently refreshes it using the long-lived refresh token.

With our listener:
- Refresh fires → `onAuthStateChange('TOKEN_REFRESHED', newSession)`.
- New `access_token` ≠ previous `access_token` → `invalidate('supabase:auth')`.
- Root layout reloads → `locals.user` is re-verified with the fresh token → no one notices.

Without the listener you'd still stay logged in (cookies are updated), but long-lived pages might miss downstream effects that depend on the user object being fresh. The listener closes that gap.

## Step 6 — What about SSR errors when the user signs out?

If you're on a page that runs a protected load and the session disappears mid-request, the load should throw a redirect (to `/login`). SvelteKit handles that cleanly — the browser follows the redirect, no error shown.

If you're using a `query()` remote function on the page and the user signs out, the next `.refresh()` will get a 401-ish error. In Module 4 we'll wrap those in a small helper that redirects to login instead of throwing. For now, just know the hook is in place.

## Step 7 — Protect against "someone deleted the user in the DB"

Edge case: an admin deletes the user row in Supabase Studio while the user is active. Their cookie is still valid (JWT is signed and not expired), but `auth.users` has no record. `getUser()` will return an error — and our `safeGetSession` already handles that by returning `{ session: null, user: null }`. The next request-gated page will redirect to `/login`. Good.

## Verify

- Sign-out in tab A causes tab B's next navigation to redirect.
- Token refreshes don't invalidate the layout spuriously (check devtools Network — you should *not* see a reload every minute).
- `pnpm check` clean.

## Common traps

- **Calling `invalidateAll()` in `onAuthStateChange`.** Works, but fires way too often. Use `invalidate('supabase:auth')`.
- **Forgetting to compare `access_token`.** Without it, every token refresh re-queries the layout. Waste.
- **Putting the listener in an `(app)` layout instead of root.** Users on `/login` (outside `(app)`) wouldn't react to a sign-in event. Root layout is the right scope.

## Recap

Auth is fully wired. Sign-up, sign-in, sign-out, password reset, and cross-tab synchronization. Every protected route is gated by `requireUser` (explicit) and RLS (implicit). You can ship a SaaS with this much.
