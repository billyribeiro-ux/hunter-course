# 3.3 — Register a New Account

> Same pattern as login, plus three twists: password confirmation, profile creation, and "already signed in."

## Why this matters

Sign-up is the top of your funnel. Every friction you add costs conversion. Every friction you *remove* without adding a security gap is a free win. We'll keep it to four fields and zero gotchas — and we'll let the database trigger we built in Lesson 1.4 handle profile creation for us.

## The Principal Engineer lens

**Don't duplicate work across layers.** We already have an `auth.users → public.profiles` trigger. So the registration handler does *not* insert into `profiles` — the trigger does. The handler's only job is: validate, call `signUp`, redirect. If the trigger breaks, we fix the trigger; we don't paper over it with app code.

## Step 1 — Add the remote function

Create `src/routes/(auth)/register/auth.remote.ts`:

```ts
// src/routes/(auth)/register/auth.remote.ts
import { form, getRequestEvent } from '$app/server';
import { redirect } from '@sveltejs/kit';
import { z } from 'zod';

const RegisterSchema = z
	.object({
		full_name: z.string().trim().min(1, 'Your name is required').max(100),
		email: z.string().email('Enter a valid email address'),
		password: z.string().min(8, 'Use at least 8 characters').max(128),
		confirm: z.string(),
		next: z.string().optional()
	})
	.refine((data) => data.password === data.confirm, {
		message: "Passwords don't match",
		path: ['confirm']
	});

export const register = form(RegisterSchema, async ({ full_name, email, password, next }) => {
	const { locals } = getRequestEvent();

	const { error } = await locals.supabase.auth.signUp({
		email,
		password,
		options: {
			data: { full_name } // stored in auth.users.raw_user_meta_data; the trigger reads it into profiles.full_name
		}
	});

	if (error) {
		return { ok: false as const, message: error.message };
	}

	// With email confirmations off (local dev), the user is signed in immediately.
	// With confirmations on (prod), they'd be redirected to a "check your inbox" screen.
	const dest = next && next.startsWith('/') && !next.startsWith('//') ? next : '/contacts';
	throw redirect(303, dest);
});
```

A few subtleties:

- **`z.object(...).refine(...)`** is how Zod does cross-field validation (password === confirm). The `path: ['confirm']` makes the error attach to the `confirm` field so we can highlight the right input.
- **`options.data.full_name`** passes user metadata into `auth.users.raw_user_meta_data`. Our Lesson 1.4 trigger reads it out and copies it into `profiles.full_name`. One handoff, no double-write.
- **Trimming** `full_name`: users paste leading/trailing spaces. Strip them at the boundary so everything downstream can trust the data.

## Step 4 — Try it

```bash
pnpm dev
```

Visit `http://localhost:5173/register`:

- Submit with mismatched passwords → inline "Passwords don't match" error.
- Submit with a 6-char password → "Use at least 8 characters."
- Submit with all good values → redirected to `/contacts` (still 404 pending Module 4).

Then confirm the trigger did its thing. Hit the Supabase Studio SQL editor:

```sql

```

You should see your new user's profile row with the full_name you typed.

## Step 5 — Email confirmations in production

In local dev, `enable_confirmations = false` so signups complete instantly. In production, we'll turn them on (Module 12). With confirmations on:

- `signUp` doesn't sign the user in; it sends a confirmation email.
- We redirect to `/register/check-email` instead of `/contacts`.
- The trigger still fires on `auth.users` insert, so the profile is created at signup time (not at confirmation time).

We'll build the "check email" screen in Module 12. Don't branch on environment yet — keep local dev simple.

## Step 6 — What about "already registered"?

Supabase returns a clear error: `"User already registered"`. Our `{ ok: false, message: error.message }` handles it generically. If you want a dedicated "Sign in instead" CTA for that case, you can add:

```svelte
{#if result && 'message' in result && !result.ok}
	{#if result.message.includes('already registered')}
		<div class="rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-sm text-text-1">
			That email is already in use. <a href="/login" class="text-brand-500 hover:underline">Log in instead</a>.
		</div>
	{:else}
		<div role="alert" class="rounded-lg border border-red-500/30 bg-red-500/10 px-3 py-2 text-sm text-red-500">
			{result.message}
		</div>
	{/if}
{/if}
```

Nice polish, not required.

## Verify

- Register form shows, validates, and submits.
- Bad inputs show helpful errors.
- Successful signup creates a `profiles` row via the trigger.

## Common traps

- **Skipping the trigger and inserting into `profiles` manually from the handler.** Now you have *two* places that create profiles. One will drift. Stop.
- **Forgetting `options.data`.** Without it, `raw_user_meta_data` is empty and the trigger copies an empty `full_name`.
- **Allowing `full_name` to be blank and "fixing it in the UI."** Validate once, at the boundary. Trim, min(1), done.
