# 3.1 — User Registration

> Our first real form: the auth layout, the signup form, and the `form()` remote function pattern we'll reuse all over the app.

## Why this matters

Sign-up is the top of your funnel. Every friction you add costs conversion. Every friction you *remove* without adding a security gap is a free win. We'll keep it to four fields, validate cleanly with Zod, and let the database trigger we built in Lesson 1.4 create the profile row for us.

Along the way we'll introduce SvelteKit's **remote `form()` function** — the May 2026 pattern that replaces traditional `+page.server.ts` actions for 95% of forms.

## The Principal Engineer lens

Three design calls that will carry through every form in this course:

1. **Zod at the boundary.** Validate before you touch the database or auth server.
2. **Don't duplicate work.** Our `auth.users → public.profiles` trigger already creates the profile row. The signup handler does not insert into `profiles`.
3. **Progressive enhancement by default.** Remote forms work with JS disabled. Ship resilience, don't bolt it on.

## Step 1 — Create the auth route group

We want `/login`, `/register`, `/forgot-password` to share a common shell (logo, card, branding) but not share it with the app. SvelteKit's route groups do this: a folder in parentheses — `(auth)` — groups routes under a layout without adding anything to the URL.

```bash
mkdir -p src/routes/\(auth\)/register
```

Design notes:

- `min-h-svh` — viewport height using the small-viewport unit, so mobile browser chrome doesn't push content offscreen.
- `bg-surface-0`, `text-text-1` — CSS-variable-backed design tokens defined in `app.css`. They automatically swap for dark mode.
- `$props()` with `{ children }` is Svelte 5's way to receive layout children. `{@render children()}` mounts them into the slot.

## Step 3 — Write the registration remote function

Create `src/routes/(auth)/register/auth.remote.ts`:

```ts
// src/routes/(auth)/register/auth.remote.ts
import { form, getRequestEvent } from '$app/server';
import { redirect } from '@sveltejs/kit';
import { z } from 'zod';

const RegisterSchema = z
	.object({
		full_name: z.string().trim().min(1, 'Your name is required').max(100),
		email: z.string().email('Enter a valid email address'),
		password: z.string().min(8, 'Use at least 8 characters').max(128),
		confirm: z.string(),
		next: z.string().optional()
	})
	.refine((data) => data.password === data.confirm, {
		message: "Passwords don't match",
		path: ['confirm']
	});

// Constant response, used whether or not the email is already registered.
// Without this, Supabase's "User already registered" error leaks account
// existence — a credential-stuffing prerequisite.
const GENERIC_OK = {
	ok: true as const,
	message: "If that email isn't already registered, check your inbox to confirm."
};

export const register = form(RegisterSchema, async ({ full_name, email, password, next }) => {
	const { locals } = getRequestEvent();

	const { data, error } = await locals.supabase.auth.signUp({
		email,
		password,
		options: {
			// Written to auth.users.raw_user_meta_data.
			// Our Lesson 1.4 trigger reads it into public.profiles.full_name.
			data: { full_name }
		}
	});

	if (error) {
		// Collapse the "already exists" class of error into the generic response
		// so attackers can't enumerate registered emails.
		const isEnumerationLeak =
			error.code === 'user_already_exists' || /already/i.test(error.message);
		if (isEnumerationLeak) return GENERIC_OK;
		return { ok: false as const, message: error.message };
	}

	// With email confirmations off in local dev, signUp leaves us signed in.
	// In production we redirect to a "check your inbox" page.
	if (data.session) {
		const dest = next && next.startsWith('/') && !next.startsWith('//') ? next : '/contacts';
		throw redirect(303, dest);
	}
	return GENERIC_OK;
});
```

Unpacking:

- **`form(Schema, handler)`** — the first arg is a Standard Schema (Zod 4 is Standard Schema compliant). The validator becomes the handler's input type.
- **`getRequestEvent()`** — remote functions don't receive `event` as an argument; this helper returns it. Same shape as a page load's `event`.
- **`options.data.full_name`** — passes metadata to Supabase Auth, which stores it on `auth.users.raw_user_meta_data`. The trigger copies it into `profiles`.
- **Redirect safety** — `next.startsWith('/') && !next.startsWith('//')` blocks `//evil.com` open-redirects.
- **User-enumeration defense** — returning the same `GENERIC_OK` for both success and "email already registered" prevents an attacker from probing which emails have accounts. They get the same response either way; the legitimate user finds the confirm email in their inbox; the attacker is told nothing.

> **303, not 302.** A 303 means "see other — GET this URL." It's the correct code after a POST so the browser doesn't pester the user with "resubmit form?" on back-navigation.

## Step 4 — Build the form

Create `src/routes/(auth)/register/+page.svelte`:

```svelte
<script lang="ts">
	import { page } from '$app/state';
	import { register } from './auth.remote';

	const next = $derived(page.url.searchParams.get('next') ?? '');
	const result = $derived(register.result);
</script>

<h1 class="text-2xl font-semibold text-text-1">Create your account</h1>
<p class="mt-2 text-sm text-text-2">Start organizing your contacts in under a minute.</p>

<form method="POST" {...register} class="mt-8 space-y-4">
	<input type="hidden" name="next" value={next} />

	<label class="block text-sm">
		<span class="mb-1 block text-text-2">Full name</span>
		<input
			name="full_name"
			autocomplete="name"
			required
			class="w-full rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-brand-500"
		/>
	</label>

	<label class="block text-sm">
		<span class="mb-1 block text-text-2">Email</span>
		<input
			type="email"
			name="email"
			autocomplete="email"
			required
			class="w-full rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-brand-500"
		/>
	</label>

	<label class="block text-sm">
		<span class="mb-1 block text-text-2">Password</span>
		<input
			type="password"
			name="password"
			autocomplete="new-password"
			required
			minlength="8"
			class="w-full rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-brand-500"
		/>
		<span class="mt-1 block text-xs text-text-2">At least 8 characters.</span>
	</label>

	<label class="block text-sm">
		<span class="mb-1 block text-text-2">Confirm password</span>
		<input
			type="password"
			name="confirm"
			autocomplete="new-password"
			required
			class="w-full rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-brand-500"
		/>
	</label>

	{#if result && 'message' in result && !result.ok}
		<div
			role="alert"
			class="rounded-lg border border-red-500/30 bg-red-500/10 px-3 py-2 text-sm text-red-500"
		>
			{result.message}
		</div>
	{/if}

	<button
		type="submit"
		class="w-full rounded-lg bg-brand-500 px-3 py-2.5 text-sm font-medium text-white hover:bg-brand-600 focus:outline-none focus:ring-2 focus:ring-brand-500 focus:ring-offset-2 focus:ring-offset-surface-1 disabled:opacity-60"
	>
		Create account
	</button>
</form>

<p class="mt-6 text-center text-sm text-text-2">
	Already have an account?
	<a
		href="/login{next ? '?next=' + encodeURIComponent(next) : ''}"
		class="text-brand-500 hover:underline">Log in</a
	>
</p>
```

Stuff worth staring at:

- **`{...register}`** — spreads the remote form's generated `method`, `action`, and progressive-enhancement handler onto the form element. This is the secret sauce.
- **`register.result`** — reactive state the remote form maintains. After each submission it holds whatever the handler returned (or `undefined` before submit).
- **`page` from `$app/state`** — the May 2026 replacement for `$app/stores`. It's a rune; no `$page` prefix.
- **`autocomplete="new-password"`** — tells browsers/password managers this is a fresh password, not a login.

## Step 6 — Email confirmations in production

In `config.toml` we have `enable_confirmations = false`. That's right for local dev — no waiting for clicks. In production, we'll turn it on (Module 12) and the signup flow changes slightly:

- `signUp` no longer signs the user in; it sends a confirmation email.
- We redirect to `/register/check-email` instead of `/contacts`.
- The trigger still fires on `auth.users` insert, so the profile exists before confirmation.

We'll build `/register/check-email` in Module 12. For now, the simple flow.

## Step 7 — "Already registered" polish (optional)

Supabase returns a specific error: `"User already registered"`. The inline red block handles it generically, but a dedicated CTA improves UX:

```svelte
			That email is already in use.
			<a href="/login" class="text-brand-500 hover:underline">Log in instead</a>.
		</div>

		<div
			role="alert"
			class="rounded-lg border border-red-500/30 bg-red-500/10 px-3 py-2 text-sm text-red-500"

			{result.message}
		</div>

{/if}
```

## Common traps

- **Skipping the trigger and inserting into `profiles` from the handler.** Now you have two places that create profiles. One will drift. Don't.
- **Forgetting `options.data`.** Without it, `raw_user_meta_data` is empty and the trigger copies an empty `full_name`.
- **Forgetting `{...register}`** on the `<form>`. Without it, the form posts normally but without remote-function magic — no result state, no progressive enhancement.
