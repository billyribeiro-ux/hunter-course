# 3.5 — Account Page

> Build the `/account` page itself. Sections for profile, security, subscription, and danger.

## Why this matters

Every SaaS needs an account page. Users *will* try to change their name, email, password, or cancel their subscription. If the page is an afterthought they'll churn. We'll put together a clean, sectioned `/account` route now, with placeholder forms we'll wire up in 3.6. Subscription + billing sections get their real content in Module 9.

## The Principal Engineer lens

**Sections, not tabs.** Tabs hide complexity — users don't know where to look. A single long page with clear section headings beats a tabbed page every time unless you're dealing with dozens of settings. We have maybe six.

**Read data on the server.** The page's server load fetches the profile row from Postgres. Forms inside the page use remote `form()` functions in 3.6. No direct Supabase calls from `.svelte` files.

## Step 1 — Create the route

```bash
mkdir -p src/routes/\(app\)/account
```

`/account` is under `(app)`, so the `requireUser` guard from 3.3 already protects it. No extra work.

## Step 2 — The server load

Create `src/routes/(app)/account/+page.server.ts`:

```ts
// src/routes/(app)/account/+page.server.ts
import type { PageServerLoad } from './$types';
import { error } from '@sveltejs/kit';

export const load: PageServerLoad = async ({ locals }) => {
	// requireUser in the (app) layout guarantees locals.user exists.
	// But TypeScript doesn't know that, so we narrow here:
	const user = locals.user;
	if (!user) throw error(401, 'Not authenticated');

	const { data: profile, error: profileErr } = await locals.supabase
		.from('profiles')
		.select('id, full_name, updated_at')
		.eq('id', user.id)
		.single();

	if (profileErr) throw error(500, profileErr.message);

	return {
		email: user.email,
		profile
	};
};
```

Notes:

- **Why re-check `locals.user` in the load?** The layout guard ran first, so in practice it's never null. But TypeScript doesn't know about `requireUser`'s side effect. The `if (!user) throw error` is a two-line narrower that also serves as defense in depth.
- **`.single()`** — tells PostgREST to return a single object (or error). Without it you get `data[]`.
- **`user.email` from `auth.users`, `profile.full_name` from `profiles`.** Email is auth's job; name is the profile's. Don't duplicate email into `profiles`.

## Step 3 — The page shell

Create `src/routes/(app)/account/+page.svelte`:

```svelte
<script lang="ts">
	import ProfileSection from './ProfileSection.svelte';
	import EmailSection from './EmailSection.svelte';
	import PasswordSection from './PasswordSection.svelte';
	import SubscriptionSection from './SubscriptionSection.svelte';
	import DangerZone from './DangerZone.svelte';

	let { data } = $props();
</script>

<div class="mx-auto max-w-2xl space-y-10 py-4">
	<header>
		<h1 class="text-2xl font-semibold text-text-1">Account</h1>
		<p class="mt-1 text-sm text-text-2">Manage your profile, security, and subscription.</p>
	</header>

	<ProfileSection profile={data.profile} />

	<EmailSection email={data.email} />

	<PasswordSection />

	<SubscriptionSection />

	<DangerZone />
</div>
```

Each section is its own component for two reasons:

- **Smaller mental scope.** You can open `PasswordSection.svelte` and it's only about passwords.
- **Testable in isolation.** We'll have Playwright tests that only exercise one section at a time.

## Step 6 — Why sections and not a single long form?

You *could* have one big form with all the fields and one "Save" button. Don't. Here's why:

- **Independent saves.** Changing your name shouldn't require re-typing your password to save.
- **Progressive disclosure.** If you don't care about your email today, it's just a card.
- **Error isolation.** A validation error in the password section doesn't visually wipe out the rest of the page.
- **Auth reauthorization.** Changing email or password often requires re-entering the current password. Section-scoped forms let you prompt for it only where needed.

Each section is a mini-form with its own submit, its own loading state, its own result. That's the pattern we'll wire up in 3.6.

## Common traps

- **Returning the whole `user` object** from the load. User includes fields we don't need on the page (app metadata, identities, factors). Return only what you use — smaller payload, tighter contract.
- **Fetching the profile with `supabaseAdmin` "because it's just yours."** Use the user-scoped client so RLS enforces the owner check. Otherwise you'd silently mask a policy bug.
- **Hard-coding the user ID** instead of using `user.id`. Don't — you'd ship a page that only shows *your* profile. This really happens in reviewer-submitted code.
