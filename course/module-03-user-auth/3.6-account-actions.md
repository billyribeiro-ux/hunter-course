# 3.6 — Account Actions

> Real mutations: update profile, change email, change password, delete account. The full remote-function playbook.

## Why this matters

Placeholders are one thing — working forms are another. In this lesson we'll wire each section to a remote `form()`, handle server validation, reflect success/error state in the UI, and integrate Supabase Auth for the sensitive actions (email + password).

We'll also introduce two new patterns we'll reuse constantly:

- **Toast notifications** for success feedback ("Profile saved.").
- **Single-flight mutation pattern** for refreshing after a write (`void getX().refresh()`).

## The Principal Engineer lens

**Three things every mutation needs** (from the Introduction — these are not optional):

1. **Validation** — Zod schema at the boundary.
2. **Authorization** — explicit `requireUser(event)` inside every handler.
3. **Idempotency awareness** — forms that submit twice (double-click, retry) should not corrupt state. Our updates are naturally idempotent ("set name to X"); destructive actions (delete account) must be gated carefully.

## Step 1 — The remote functions file

Create `src/routes/(app)/account/account.remote.ts`:

```ts
// src/routes/(app)/account/account.remote.ts
import { form, getRequestEvent } from '$app/server';
import { redirect } from '@sveltejs/kit';
import { z } from 'zod';
import { requireUser } from '$lib/server/auth';

// ── Profile ──────────────────────────────────────────────────────────────────
const ProfileSchema = z.object({
	full_name: z.string().trim().min(1, 'Your name is required').max(100)
});

export const updateProfile = form(ProfileSchema, async ({ full_name }) => {
	const event = getRequestEvent();
	const user = requireUser(event);

	const { error } = await event.locals.supabase
		.from('profiles')
		.update({ full_name, updated_at: new Date().toISOString() })
		.eq('id', user.id);

	if (error) return { ok: false as const, message: error.message };
	return { ok: true as const, message: 'Profile saved.' };
});

// ── Email ────────────────────────────────────────────────────────────────────
const EmailSchema = z.object({
	email: z.string().email('Enter a valid email address')
});

export const updateEmail = form(EmailSchema, async ({ email }) => {
	const event = getRequestEvent();
	requireUser(event);

	const { error } = await event.locals.supabase.auth.updateUser({ email });
	if (error) return { ok: false as const, message: error.message };
	return {
		ok: true as const,
		message: 'Confirmation emails sent to both addresses. Click the link to finish the change.'
	};
});

// ── Password ─────────────────────────────────────────────────────────────────
const PasswordSchema = z
	.object({
		password: z.string().min(8, 'Use at least 8 characters').max(128),
		confirm: z.string()
	})
	.refine((d) => d.password === d.confirm, { message: "Passwords don't match", path: ['confirm'] });

export const updatePassword = form(PasswordSchema, async ({ password }) => {
	const event = getRequestEvent();
	requireUser(event);

	const { error } = await event.locals.supabase.auth.updateUser({ password });
	if (error) return { ok: false as const, message: error.message };
	return { ok: true as const, message: 'Password updated.' };
});

// ── Danger: delete account ───────────────────────────────────────────────────
const DeleteSchema = z.object({
	confirm: z.string()
});

export const deleteAccount = form(DeleteSchema, async ({ confirm }) => {
	const event = getRequestEvent();
	const user = requireUser(event);

	if (confirm !== user.email) {
		return {
			ok: false as const,
			message: 'Type your email exactly to confirm.'
		};
	}

	// Service-role client is required to delete an auth user.
	const { error } = await event.locals.supabaseAdmin.auth.admin.deleteUser(user.id);
	if (error) return { ok: false as const, message: error.message };

	// Sign out (clears cookies), then redirect home.
	await event.locals.supabase.auth.signOut();
	throw redirect(303, '/');
});
```

Important details:

- **Profile update uses the user-scoped client** → RLS enforces the ownership check. Even if we forgot `.eq('id', user.id)`, the policy would block unauthorized rows.
- **Email change via `supabase.auth.updateUser`** triggers Supabase's confirmation email flow. Don't write the new email directly into `auth.users` or `profiles`.
- **Delete account requires the email as a confirmation string** — a classic "are you really sure?" check. And it uses `supabaseAdmin.auth.admin.deleteUser` because deleting a user is a privileged op.
- **Cascade cleanup** — remember, our profile row has `on delete cascade` from `auth.users(id)`. When the admin deletes the auth user, the profile (and eventually contacts, billing rows) vanishes automatically.

## Step 2 — Wire the Profile section

Replace `src/routes/(app)/account/ProfileSection.svelte`:

```svelte
<script lang="ts">
	import { updateProfile } from './account.remote';

	interface Props {
		profile: { full_name: string | null };
	}
	let { profile }: Props = $props();

	const result = $derived(updateProfile.result);
</script>

<section class="rounded-xl border border-border-1 bg-surface-1 p-6">
	<h2 class="text-base font-semibold text-text-1">Profile</h2>
	<p class="mt-1 text-sm text-text-2">Your display name.</p>

	<form method="POST" {...updateProfile} class="mt-4 flex flex-col gap-3 sm:flex-row sm:items-end">
		<label class="flex-1 text-sm">
			<span class="mb-1 block text-text-2">Full name</span>
			<input
				name="full_name"
				defaultValue={profile.full_name ?? ''}
				required
				class="w-full rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-brand-500"
			/>
		</label>
		<button
			type="submit"
			class="rounded-lg bg-brand-500 px-4 py-2 text-sm font-medium text-white hover:bg-brand-600"
		>
			Save
		</button>
	</form>

	{#if result}
		<div
			class={[
				'mt-3 rounded-lg px-3 py-2 text-sm',
				result.ok ? 'bg-green-500/10 text-green-500' : 'bg-red-500/10 text-red-500'
			]}
		>
			{result.message}
		</div>
	{/if}
</section>
```

Two Svelte 5 details:

- **`defaultValue={...}`** on an `<input>` (not `value={...}`) — we want the input to be editable, not locked to a reactive value. `defaultValue` seeds the initial state; the user's edits take over.
- **`result.ok`-driven classes** — dynamic green for success, red for errors, dormant otherwise. No component lib needed.

## Step 5 — Wire the Danger Zone

Replace `src/routes/(app)/account/DangerZone.svelte`:

```svelte
<script lang="ts">
	import { deleteAccount } from './account.remote';
	const result = $derived(deleteAccount.result);
</script>

<section class="rounded-xl border border-red-500/30 bg-red-500/5 p-6">
	<h2 class="text-base font-semibold text-red-500">Danger zone</h2>
	<p class="mt-1 text-sm text-text-2">
		Deleting your account removes all of your data permanently. This cannot be undone.
	</p>

	<form method="POST" {...deleteAccount} class="mt-4 space-y-3">
		<label class="block text-sm">
			<span class="mb-1 block text-text-2">Type your email to confirm</span>
			<input
				name="confirm"
				required
				placeholder="you@example.com"
				class="w-full rounded-lg border border-red-500/30 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-red-500"
			/>
		</label>
		<button
			type="submit"
			class="rounded-lg border border-red-500/40 bg-red-500/10 px-4 py-2 text-sm font-medium text-red-500 hover:bg-red-500/20"
		>
			Delete my account
		</button>
	</form>

	{#if result && !result.ok}
		<div role="alert" class="mt-3 rounded-lg bg-red-500/10 px-3 py-2 text-sm text-red-500">
			{result.message}
		</div>
	{/if}
</section>
```

A few notes:

- **Type-to-confirm** is a much stronger gate than a "yes I'm sure" checkbox. It creates friction proportional to the danger.
- **Success case redirects** (via `throw redirect`), so we only render `result` when it's `!ok`.
- **Styling is distinctly red.** Users should *feel* this is different before they even read the heading.

## Step 7 — Where does password reset live?

If you noticed we don't have a "forgot password" link here — you're right. That flow lives in the `(auth)` group at `/forgot-password`, because the user can't reach `/account` if they forgot their password. We'll build that page in Module 12 alongside the email-confirmation production flow. For now, a user who forgets their password can sign in with a test password and change it here.

## Common traps

- **Deleting the auth user via `locals.supabase` (user-scoped).** That'd fail — only service-role can delete users. Use `locals.supabaseAdmin`.
- **Forgetting to `signOut()` after delete.** Without it, the browser has a stale cookie pointing at a deleted user. Next request → `getUser()` errors → the UI gets weird. Always sign out.
- **Letting "Update email" write directly to `profiles` instead of going through `supabase.auth.updateUser`.** We'd bypass confirmation and desynchronize `auth.users.email` from whatever we stored.
