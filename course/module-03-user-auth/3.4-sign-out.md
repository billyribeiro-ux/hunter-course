# 3.4 — Sign Out + App Shell

> The main navigation, a user menu, and a working sign-out command.

## Why this matters

Now that users can sign in and sign up, they need a place to live inside the app — a shell with a logo, navigation, and an obvious way to sign out. This shell is shared across every authenticated page: `/contacts`, `/account`, `/pricing`, etc. Build it once, use it forever.

We'll also introduce the **`command()` remote function** — the cousin of `form()` for "do a thing" actions that aren't tied to a form submission, like sign-out.

## The Principal Engineer lens

**Separate authenticated layout from public layout.** The marketing home at `/` has different chrome than the in-app `/contacts`. Don't conflate them. Use a second route group `(app)` for authenticated pages; the root `+layout.svelte` stays minimal (just imports CSS + renders children).

## Step 1 — Create the `(app)` group

```bash
mkdir -p src/routes/\(app\)
```

And move whatever authenticated routes we'll build (contacts, account) under it in later modules. For now just create the layout files.

## Step 2 — Build the app shell layout

Create `src/routes/(app)/+layout.svelte`:

```svelte
<script lang="ts">
	import { page } from '$app/state';
	import UserMenu from '$lib/components/UserMenu.svelte';
	import ThemeToggle from '$lib/components/ThemeToggle.svelte';
	import Toaster from '$lib/components/Toaster.svelte';

	let { data, children } = $props();

	const navItems = [
		{ href: '/contacts', label: 'Contacts' },
		{ href: '/pricing', label: 'Pricing' },
		{ href: '/account', label: 'Account' }
	];

	function isActive(href: string) {
		return page.url.pathname === href || page.url.pathname.startsWith(href + '/');
	}
</script>

<div class="min-h-svh bg-surface-0 text-text-1">
	<header class="sticky top-0 z-30 border-b border-border-1 bg-surface-0/80 backdrop-blur">
		<div class="mx-auto flex h-14 max-w-6xl items-center gap-4 px-4">
			<a href="/contacts" class="flex items-center gap-2">
				<span class="grid h-7 w-7 place-items-center rounded-lg bg-brand-500 text-xs font-bold text-white">C</span>
				<span class="text-sm font-semibold tracking-tight">Contactly</span>
			</a>

			<nav class="ml-4 hidden gap-1 sm:flex">
				{#each navItems as item (item.href)}
					<a
						href={item.href}
						class="rounded-md px-3 py-1.5 text-sm transition-colors"
						class:bg-surface-1={isActive(item.href)}
						class:text-text-1={isActive(item.href)}
						class:text-text-2={!isActive(item.href)}
					>
						{item.label}
					</a>
				{/each}
			</nav>

			<div class="ml-auto flex items-center gap-2">
				<ThemeToggle />
				<UserMenu user={data.user} />
			</div>
		</div>
	</header>

	<main class="mx-auto max-w-6xl px-4 py-8">
		{@render children()}
	</main>

	<Toaster />
</div>
```

Design notes:

- **Sticky, translucent header with `backdrop-blur`** — classic modern SaaS chrome.
- **Route-aware nav highlight.** `isActive` compares against `page.url.pathname`. Using `page` from `$app/state` means the highlight updates without a page reload.
- **`max-w-6xl`** — readable width. Tall, wide apps are harder to use than focused ones.

## Step 3 — The sign-out command

Create `src/lib/server/auth.remote.ts`:

```ts
// src/lib/server/auth.remote.ts
import { command, getRequestEvent } from '$app/server';
import { redirect } from '@sveltejs/kit';
import { z } from 'zod';

/** Sign the current user out. */
export const signOut = command(z.void(), async () => {
	const { locals } = getRequestEvent();
	await locals.supabase.auth.signOut();
	throw redirect(303, '/login');
});
```

What's a `command()`? It's the third kind of remote function:

- **`query()`** — GET-like. Reads data, cacheable, refreshable. No side effects.
- **`form()`** — POST-like, tied to a `<form>`. Handles progressive enhancement automatically.
- **`command()`** — POST-like, triggered from JS (button click, keystroke). No form.

Sign-out fits `command()`: we're not submitting a form, just triggering a server action from a button.

## Step 4 — The UserMenu component

Create `src/lib/components/UserMenu.svelte`:

```svelte
<script lang="ts">
	import type { User } from '@supabase/supabase-js';
	import { signOut } from '$lib/server/auth.remote';

	interface Props {
		user: User | null;
	}
	let { user }: Props = $props();

	let open = $state(false);
	let menuRef = $state<HTMLDivElement | null>(null);

	function initials(u: User): string {
		const name = (u.user_metadata?.full_name as string | undefined) ?? u.email ?? '?';
		return name
			.split(/\s+/)
			.slice(0, 2)
			.map((s) => s[0]?.toUpperCase() ?? '')
			.join('');
	}

	$effect(() => {
		if (!open) return;
		function onDocClick(e: MouseEvent) {
			if (menuRef && !menuRef.contains(e.target as Node)) open = false;
		}
		document.addEventListener('click', onDocClick);
		return () => document.removeEventListener('click', onDocClick);
	});

	async function handleSignOut() {
		await signOut();
	}
</script>

{#if !user}
	<a href="/login" class="rounded-md px-3 py-1.5 text-sm text-text-1 hover:bg-surface-1"
		>Log in</a
	>
{:else}
	<div bind:this={menuRef} class="relative">
		<button
			type="button"
			class="grid h-8 w-8 place-items-center rounded-full bg-brand-500 text-xs font-semibold text-white"
			aria-haspopup="menu"
			aria-expanded={open}
			onclick={() => (open = !open)}
		>
			{initials(user)}
		</button>

		{#if open}
			<div
				role="menu"
				class="absolute right-0 mt-2 w-56 overflow-hidden rounded-xl border border-border-1 bg-surface-1 shadow-lg"
			>
				<div class="border-b border-border-1 px-3 py-2 text-xs text-text-2">
					Signed in as
					<div class="truncate text-sm text-text-1">{user.email}</div>
				</div>
				<a href="/account" class="block px-3 py-2 text-sm text-text-1 hover:bg-surface-0" role="menuitem"
					>Account</a
				>
				<a href="/pricing" class="block px-3 py-2 text-sm text-text-1 hover:bg-surface-0" role="menuitem"
					>Upgrade</a
				>
				<button
					type="button"
					class="w-full border-t border-border-1 px-3 py-2 text-left text-sm text-text-1 hover:bg-surface-0"
					onclick={handleSignOut}
					role="menuitem"
				>
					Sign out
				</button>
			</div>
		{/if}
	</div>
{/if}
```

What's worth studying:

- **`$state<HTMLDivElement | null>(null)`** — runes-based element refs. `bind:this` sets them.
- **`$effect(() => { ... return cleanup; })`** — side effects tied to reactive deps. We only bind the document click listener *while* the menu is open, and clean up when it closes.
- **`onclick={...}`** — Svelte 5's event syntax. No more `on:click`; just regular HTML attributes.
- **ARIA roles (`menu`, `menuitem`, `haspopup`, `expanded`)** — screen-reader friendly dropdowns.

## Step 5 — Gate the `(app)` group server-side

Create `src/routes/(app)/+layout.server.ts`:

```ts
import type { LayoutServerLoad } from './$types';
import { requireUser } from '$lib/server/auth';

export const load: LayoutServerLoad = async (event) => {
	requireUser(event);
	return {};
};
```

Now every `/contacts`, `/account`, etc. route that lives under `(app)/` will redirect to `/login?next=...` if there's no session. One line of code, applied to the entire app. Defense in depth — plus our RLS policies — means even if this load is bypassed somehow, the DB still returns nothing.

## Step 6 — Use the sign-out command from anywhere

Because `signOut` is a remote command, you can call it from *any* component:

```svelte
<script>
	import { signOut } from '$lib/server/auth.remote';
</script>

<button onclick={() => signOut()}>Leave</button>
```

No `fetch`, no route, no plumbing. That's the remote-function superpower.

## Verify

- App shell renders with sticky nav.
- Avatar shows initials; menu opens/closes properly.
- Sign-out redirects to `/login`.
- Direct navigation to `(app)` routes while logged out redirects to `/login?next=...`.

## Common traps

- **Running the shell's sign-out from the browser-only Supabase client.** It works, but then you have to remember to `invalidateAll()` to sync the server. Using the `command()` keeps auth state changes server-authoritative.
- **Forgetting the `requireUser` in the `(app)` layout.** Your RLS will still protect data, but users will see a broken UI with no data. Layer 1 of defense.
- **Putting public routes (pricing/landing) inside `(app)`.** They shouldn't require login. Keep them at the root or in a `(marketing)` group.
