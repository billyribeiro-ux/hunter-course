# 3.5 — Password Reset

> Two pages, one email, zero account-enumeration leaks.

## Why this matters

Users forget passwords. A missing or broken reset flow is the #1 support ticket driver for any SaaS. Getting it right means:

- A request page (`/forgot-password`) that emails a reset link.
- A callback page (`/auth/callback`) that exchanges the token from the link for a session.
- A new-password page (`/reset-password`) the user lands on after exchange.

Plus one security subtlety: **don't leak which emails exist.** The request form should respond the same whether the email matches a real account or not.

## The Principal Engineer lens

**Security at the edges, UX in the middle.** Users hate error messages that say "user not found" because (a) they might typo their own email and be confused, and (b) it's a gift to attackers enumerating your user list. So the request form always says "if an account exists, we sent an email." Same message, every time.

On the *callback*, though, we need clear errors: expired link, already used, wrong token. The user clicked from their own inbox — no enumeration risk.

And the remote function, `src/routes/(auth)/forgot-password/auth.remote.ts`:

```ts
// src/routes/(auth)/forgot-password/auth.remote.ts
import { form, getRequestEvent } from '$app/server';
import { z } from 'zod';
import { env } from '$lib/server/env';

const Schema = z.object({
	email: z.string().email('Enter a valid email address')
});

export const requestPasswordReset = form(Schema, async ({ email }) => {
	const { locals } = getRequestEvent();

	// We intentionally do NOT return whether the email exists.
	// Supabase logs the attempt but returns a generic success even if the user doesn't exist.
	await locals.supabase.auth.resetPasswordForEmail(email, {
		redirectTo: `${env.PUBLIC_APP_URL}/auth/callback?next=/reset-password`
	});

	return { ok: true as const };
});
```

Points:

- **`redirectTo`** is where Supabase sends the user after they click the email link. We route through `/auth/callback`, which exchanges the token for a session, then forwards to `/reset-password`.
- **No branching on the user's existence.** Supabase does the right thing here; we just don't second-guess its response.

## Step 2 — The callback route

Supabase puts the reset token in the URL hash (`#access_token=...`), but newer flows use query params with a `code`. We handle both via the standard exchange.

Create `src/routes/auth/callback/+server.ts`:

```ts
// src/routes/auth/callback/+server.ts
import { redirect } from '@sveltejs/kit';
import type { RequestHandler } from './$types';

export const GET: RequestHandler = async ({ url, locals }) => {
	const code = url.searchParams.get('code');
	const next = url.searchParams.get('next') ?? '/';

	if (code) {
		const { error } = await locals.supabase.auth.exchangeCodeForSession(code);
		if (error) {
			throw redirect(303, `/login?error=${encodeURIComponent(error.message)}`);
		}
	}

	// Only allow redirects to paths on our origin
	const dest = next.startsWith('/') && !next.startsWith('//') ? next : '/';
	throw redirect(303, dest);
};
```

This `+server.ts` is a plain SvelteKit route handler (not a page). When Supabase Auth calls back, we exchange the `code` (or confirm the implicit session) and forward to `next`.

> **Why the redirect-safety check?** Without it, a crafted `?next=//evil.com` could bounce the user off your origin after auth. Always verify redirects are relative same-origin paths.

```svelte
	<button
		type="submit"
		class="w-full rounded-lg bg-brand-500 px-3 py-2.5 text-sm font-medium text-white hover:bg-brand-600"
	>
		Update password
	</button>
</form>
```

And `src/routes/(auth)/reset-password/auth.remote.ts`:

```ts
// src/routes/(auth)/reset-password/auth.remote.ts
import { form, getRequestEvent } from '$app/server';
import { redirect } from '@sveltejs/kit';
import { z } from 'zod';

const Schema = z
	.object({
		password: z.string().min(8, 'Use at least 8 characters').max(128),
		confirm: z.string()
	})
	.refine((d) => d.password === d.confirm, { message: "Passwords don't match", path: ['confirm'] });

export const updatePassword = form(Schema, async ({ password }) => {
	const { locals } = getRequestEvent();

	// The callback route has already exchanged the token and put us in a session.
	// If there's no session here, they bypassed the email link — bail.
	const { user } = await locals.safeGetSession();
	if (!user) {
		return { ok: false as const, message: 'Your reset link expired. Request a new one.' };
	}

	const { error } = await locals.supabase.auth.updateUser({ password });
	if (error) {
		return { ok: false as const, message: error.message };
	}

	throw redirect(303, '/contacts');
});
```

## Step 4 — Guarding `/reset-password`

If someone lands here with no session, we *don't* redirect them to login — they came from an email link, and we want them to see a clear "request a new one" prompt. The handler already returns that message if there's no session. That's enough.

## Step 5 — View the email in Inbucket

You don't need a real SMTP server in local dev. Supabase ships Inbucket — a fake mail server at `http://127.0.0.1:54324`. After submitting the forgot-password form:

1. Go to `http://127.0.0.1:54324`.
2. Find the inbox for the email you requested (e.g. `demo@contactly.app`).
3. Open the latest email, click the link.
4. You're bounced through `/auth/callback` → `/reset-password`.
5. Set a new password, get redirected to `/contacts`.

Full flow, no external services.

## Step 6 — Production email

In production you'll configure Supabase to send through a real provider (Resend, Postmark, SendGrid). The code doesn't change; only Supabase's dashboard SMTP settings do. We'll cover that in Module 12.

## Verify

- Request form always says "if an account exists, we sent a link" — never leaks existence.
- Inbucket shows the email.
- Clicking the link exchanges the code and lands on `/reset-password`.
- Submitting a valid new password signs you in and redirects to `/contacts`.
- Typos in confirm show "Passwords don't match."

## Common traps

- **Returning the Supabase "user not found" error from the request form.** That's enumeration. Return the same generic success string always.
- **Hardcoding `http://localhost:5173` in `redirectTo`.** Use `env.PUBLIC_APP_URL` — production needs the real origin, and Supabase's allow-list in `config.toml` has to match.
- **Skipping the same-origin check in the callback.** Open redirect vulnerabilities are an easy self-own.

## Recap

Users can now recover their passwords. Two forms, one callback handler, and Inbucket handling local email. Next: a tiny gotcha — the "middleware" (server hook) detail that makes sure sessions stay fresh.
