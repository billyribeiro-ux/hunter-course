# 3.3 — Protecting Auth Routes

> The helpers that gate every protected route in your app — plus the client-side glue that keeps tabs in sync.

## Why this matters

Two scenarios we want to handle correctly:

1. **Guest on protected page.** User visits `/contacts` without a session. Don't 404, don't show empty UI — redirect to `/login?next=/contacts` so they come right back after signing in.
2. **User on auth page.** User already signed in visits `/login` or `/register`. Don't show them the form — redirect to `/contacts`.

We'll solve both with tiny helpers: `requireUser` and `requireGuest`. Then we'll wire an `(app)` route group so *every* authenticated route inherits the guard without per-file boilerplate.

Finally, we'll handle the cross-tab sync problem: if you sign out in tab A, tab B should notice.

## The Principal Engineer lens

**Defense in depth.**

- **Layer 1 — Route guards.** `requireUser` in layout loads → redirect guests. Fast, catches 99% of cases.
- **Layer 2 — RLS.** Even if a guard is forgotten, the database returns nothing to an unauthenticated query.
- **Layer 3 — Remote function gates.** Inside each `form()`/`command()`, re-check `locals.user`. A handler should never trust its caller.

Each layer has different failure modes. Together, it's extremely hard to ship a leak.

## Step 1 — Write the guard helpers

Create `src/lib/server/auth.ts`:

```ts
// src/lib/server/auth.ts
import { redirect } from '@sveltejs/kit';
import type { RequestEvent } from '@sveltejs/kit';

/** Require an authenticated user; redirect to /login if missing. */
export function requireUser(event: Pick<RequestEvent, 'locals' | 'url'>) {
	if (!event.locals.user) {
		const next = encodeURIComponent(event.url.pathname + event.url.search);
		throw redirect(303, `/login?next=${next}`);
	}
	return event.locals.user;
}

/** Require *no* authenticated user; redirect to /contacts if one is present. */
export function requireGuest(event: Pick<RequestEvent, 'locals'>) {
	if (event.locals.user) {
		throw redirect(303, '/contacts');
	}
}
```

Key design calls:

- **`throw redirect(...)`** — SvelteKit's way of signaling a redirect from server code. It short-circuits the rest of the load/action/handler.
- **`next=...`** — we encode the pathname + query so users land back where they were trying to go. `/login?next=%2Fcontacts%2Fnew` → after sign-in they hit `/contacts/new`.
- **`Pick<RequestEvent, 'locals' | 'url'>`** — we only need `locals` and `url`. Narrower types are easier to mock in tests.

## Step 2 — Gate the entire `(app)` group

We want all authenticated routes (`/contacts`, `/account`, `/pricing` when logged in, etc.) to live under one guard. Create the route group:

```bash
mkdir -p src/routes/\(app\)
```

And its server load, `src/routes/(app)/+layout.server.ts`:

```ts
// src/routes/(app)/+layout.server.ts
import type { LayoutServerLoad } from './$types';
import { requireUser } from '$lib/server/auth';

export const load: LayoutServerLoad = async (event) => {
	const user = requireUser(event);
	return { user };
};
```

Now any route placed under `src/routes/(app)/` inherits the guard. Forgot to add the guard? You just can't — the layout is structural.

We'll move `/contacts`, `/account`, and `/pricing` under this group in Modules 4 and 8.

## Step 3 — Gate the auth pages against signed-in users

Each auth page gets a tiny `+page.server.ts`.

`src/routes/(auth)/register/+page.server.ts`:

```ts
import type { PageServerLoad } from './$types';
import { requireGuest } from '$lib/server/auth';

export const load: PageServerLoad = async (event) => {
	requireGuest(event);
	return {};
};
```

`src/routes/(auth)/login/+page.server.ts`:

```ts
import type { PageServerLoad } from './$types';
import { requireGuest } from '$lib/server/auth';

export const load: PageServerLoad = async (event) => {
	requireGuest(event);
	return {};
};
```

Why not put `requireGuest` in the `(auth)` layout itself? Because the forgot-password flow (Module 12) lives in `(auth)` too, and a user might be logged in there (we'll let them change email). Per-page guards keep semantics explicit.

## Step 4 — Use `requireUser` inside remote functions

Route guards protect page loads, but our `form()` and `command()` functions have their own entry points. Any remote function that mutates data should re-check auth. A pattern:

```ts
// Example for Module 4
import { form, getRequestEvent } from '$app/server';
import { z } from 'zod';
import { requireUser } from '$lib/server/auth';

export const createContact = form(Schema, async (input) => {
	const event = getRequestEvent();
	const user = requireUser(event);
	// ...proceed with user.id
});
```

This is defense in depth: the `(app)` layout already blocks guests from *navigating* to the page, but a bored attacker could POST directly to the remote endpoint. The handler-level check closes that loophole. Plus RLS would stop the query anyway — but don't rely on any single layer.

## Step 5 — Make the root layout session-aware

Edit `src/routes/+layout.server.ts` to expose `session` + `user` and mark the load dependency:

```ts
// src/routes/+layout.server.ts
import type { LayoutServerLoad } from './$types';

export const load: LayoutServerLoad = async ({ locals, depends }) => {
	depends('supabase:auth');
	return {
		session: locals.session,
		user: locals.user
	};
};
```

The `depends('supabase:auth')` registers a named invalidation key. We can later call `invalidate('supabase:auth')` to re-run *just this load* — cheaper than `invalidateAll()`.

## Step 6 — Cross-tab sync via `onAuthStateChange`

The problem: you have two tabs open. You sign out in tab A. Tab B still thinks you're logged in — until it navigates. Click a protected button there, and you get a confusing failure.

The fix: an `onAuthStateChange` listener on the browser Supabase client invalidates the root layout whenever auth state changes.

Edit `src/routes/+layout.svelte`:

```svelte
<script lang="ts">
	import '../app.css';
	import { onMount } from 'svelte';
	import { invalidate } from '$app/navigation';
	import { getSupabaseBrowserClient } from '$lib/supabase/client';

	let { data, children } = $props();

	onMount(() => {
		const supabase = getSupabaseBrowserClient();
		const {
			data: { subscription }
		} = supabase.auth.onAuthStateChange((_event, newSession) => {
			// Only invalidate if the session actually changed (different access token).
			if (newSession?.access_token !== data.session?.access_token) {
				void invalidate('supabase:auth');
			}
		});
		return () => subscription.unsubscribe();
	});
</script>

{@render children()}
```

Line-by-line:

- **`onAuthStateChange`** fires on sign-in, sign-out, and token refresh.
- **Access-token comparison** — without it we'd invalidate on every silent refresh, causing useless server round-trips every ~55 minutes.
- **`invalidate('supabase:auth')`** re-runs the root layout load (which re-reads `locals.user` from the fresh cookies).
- **Cleanup** unsubscribes when the layout unmounts.

## Step 7 — Why not `invalidateAll()`?

`invalidateAll()` re-runs *every* load in the tree. Correct, but heavy — if your current page has ten loads and only the layout session matters, you've done nine wasted queries. The named dependency targets exactly what we need.

## Step 8 — Test it

```bash
pnpm dev
```

1. Open `/login` in two tabs.
2. Sign in on tab A, navigate to `/contacts` (temporarily create a throwaway `src/routes/(app)/contacts/+page.svelte` with `<h1>contacts</h1>` to see the shell).
3. In tab B, refresh — you're also signed in.
4. Sign out in tab A (we'll build the button in 3.4; for now, open devtools → Application → Cookies → delete the `sb-*` cookies, then hit any route).
5. In tab B, click any link — redirected to `/login`.

## Step 9 — Token refresh sanity

JWTs expire (`jwt_expiry = 3600`). The browser client silently refreshes before expiry. With our listener:

- Refresh fires → `onAuthStateChange('TOKEN_REFRESHED', newSession)`.
- New `access_token` ≠ old → `invalidate('supabase:auth')`.
- Layout reloads → `safeGetSession()` re-verifies with the fresh token.

You should *not* see a full reload every minute. Check devtools Network; auth invalidations happen roughly hourly, not constantly.

## Verify

- `/register` while logged in → redirects to `/contacts`.
- `/contacts` while logged out → redirects to `/login?next=%2Fcontacts`.
- Sign-in → back on `/contacts`.
- `pnpm check` clean.

## Common traps

- **Putting guards in the layout `+layout.svelte` instead of `+layout.server.ts`.** Client-side redirects flash content first — guards must run on the server.
- **Forgetting to compare `access_token`** in the state-change listener. Constant invalidations will feel like "my app is reloading on its own."
- **Relying only on the layout guard and skipping handler-level `requireUser`.** Guests can hit remote-function endpoints directly. Belt *and* suspenders.

## Recap

You have:

- `requireUser` / `requireGuest` helpers.
- An `(app)` route group guarded by `+layout.server.ts`.
- Per-page guards on `/login` and `/register`.
- Cross-tab session sync via `onAuthStateChange` + targeted invalidation.
