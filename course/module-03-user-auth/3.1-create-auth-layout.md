# 3.1 — Create the Auth Layout

> One shell. Two forms. Consistent branding. Zero duplication.

## Why this matters

Login and register share more than they differ: a logo, a card, a pair of inputs, a submit button, a link to the other screen. If you build them as two standalone pages, you'll maintain two copies of every tweak. We'll do it the SvelteKit way: a nested layout at `src/routes/(auth)/+layout.svelte` wraps `/login` and `/register` in a shared shell.

## The Principal Engineer lens

**Layouts are for what doesn't change.** Not "might not change later." What actually doesn't change now. If `/login` needs a subtle difference — like a "remember me" checkbox — add it *in the page*, not as a prop threaded through the layout. When the difference is real, inline it; when it's cosmetic, layout it.

We'll also use SvelteKit's **route groups** (the `(auth)` parenthesized folder). The parens don't show up in the URL; they just group routes under one layout. `/login` and `/register` both live at the root of the URL, but they share a layout under the hood.

## Step 1 — Create the route group

In `app/`:

```bash
mkdir -p src/routes/\(auth\)/login
mkdir -p src/routes/\(auth\)/register
```

Your routes tree should now include:

```
src/routes/
├── +layout.server.ts
├── +layout.svelte
└── (auth)/
    ├── +layout.svelte       ← the auth shell
    ├── login/
    │   └── +page.svelte
    └── register/
        └── +page.svelte
```

## Step 2 — The auth layout

Create `src/routes/(auth)/+layout.svelte`:

```svelte
<script lang="ts">
	let { children } = $props();
</script>

<div class="min-h-svh flex items-center justify-center px-4 py-10 bg-surface-0">
	<div class="w-full max-w-md">
		<a href="/" class="mb-8 flex items-center justify-center gap-2 text-text-1 hover:text-brand-500">
			<span class="grid h-9 w-9 place-items-center rounded-xl bg-brand-500 text-white font-bold">C</span>
			<span class="text-xl font-semibold tracking-tight">Contactly</span>
		</a>

		<div class="rounded-2xl border border-border-1 bg-surface-1 p-8 shadow-xl shadow-black/5">
			{@render children()}
		</div>

		<p class="mt-6 text-center text-sm text-text-2">
			By continuing you agree to our
			<a href="/terms" class="underline hover:text-text-1">Terms</a>
			and
			<a href="/privacy" class="underline hover:text-text-1">Privacy Policy</a>.
		</p>
	</div>
</div>
```

What's going on:

- `min-h-svh` — full viewport height, using `svh` (small-viewport-height) so mobile address bars don't push content offscreen.
- Color tokens like `bg-surface-0`, `text-text-1` — these resolve to CSS variables defined in `app.css` and automatically swap for dark mode. We set them up in the scaffold; if you open `app.css` you'll see the palette.
- `rounded-2xl`, `shadow-xl shadow-black/5` — soft, modern card. Not too bold, not too flat.
- `$props()` with `{ children }` — Svelte 5's way to receive layout/component children. Renders via `{@render children()}`.

## Step 5 — Keep layouts dumb

The auth layout has *zero* server code. No `+layout.server.ts` sitting next to it. That's deliberate:

- Auth pages don't need a pre-existing session (if you're on `/login`, you're not logged in).
- In fact, if you *are* logged in, we'll redirect you away from `/login` — but we'll do that per-page, not per-layout, so the redirect decision is visible at the URL we're redirecting from.

## Step 6 — Dedupe the "already logged in, go away" redirect

Both `login` and `register` will do the same thing: if `locals.user` exists, redirect to `/contacts`. Write a helper now. Create `src/lib/server/auth.ts`:

```ts
// src/lib/server/auth.ts
import { redirect } from '@sveltejs/kit';
import type { RequestEvent } from '@sveltejs/kit';

/** Require an authenticated user; redirect to /login if missing. */
export function requireUser(event: Pick<RequestEvent, 'locals' | 'url'>) {
	if (!event.locals.user) {
		const next = encodeURIComponent(event.url.pathname + event.url.search);
		throw redirect(303, `/login?next=${next}`);
	}
	return event.locals.user;
}

/** Require *no* authenticated user; redirect to /contacts if one is present. */
export function requireGuest(event: Pick<RequestEvent, 'locals'>) {
	if (event.locals.user) {
		throw redirect(303, '/contacts');
	}
}
```

We'll use `requireGuest` in `/login` and `/register` load functions so signed-in users never see the auth screens.

> **Why do we pass `next=...`?** So if someone clicks a protected link while logged out, they land on `/login?next=/contacts/new`, and after signing in we can drop them back exactly where they tried to go. It's a UX polish that costs one line.

## Verify

- `http://localhost:5173/login` and `/register` render the shell.
- `pnpm check` clean.
- `src/lib/server/auth.ts` exists and exports both helpers.

## Common traps

- **Forgot to wrap with parens.** `src/routes/auth/login` would make the URL `/auth/login`, not `/login`. Parens are SvelteKit's "group without path segment."
- **Put form state in the layout.** Don't. Each page has its own form; the layout is decoration.
- **Tried to redirect from the layout.** Redirect per-page. Makes URL behavior explicit.
