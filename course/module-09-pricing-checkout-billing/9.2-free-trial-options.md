# 9.2 — Free Trial Options

> Two flavours of free trial, one tier config, zero `if` branches at the call site.

## Why this matters

Trials are the single most-used acquisition lever in B2B SaaS. Stripe supports them out of the box, but the choice isn't just "yes / no." It's:

- **With a card** — user enters a payment method now, gets 14 days free, Stripe charges automatically on day 15.
- **Without a card** — user starts trialing immediately, no card collected, Stripe nags them to add one before the trial ends and cancels if they don't.

The right answer is tier-specific and business-specific. Plus is our conversion workhorse — we want low-friction trials to hook users. Pro is for serious buyers — we want them to commit with a card. Contactly offers a 14-day trial on Plus (card required), no trial on Pro.

This lesson makes both modes configurable per tier and adds the single line to `createCheckoutSessionForLookupKey` that reads the config and passes it to Stripe. No ad-hoc `if (lookupKey === 'plus_monthly')` at the call site.

## The Principal Engineer lens

**Trials are marketing configuration, not business logic.** The moment you find yourself writing `if (tier === 'plus')` in a checkout handler, stop. That branch belongs in `pricing.ts` — the declarative source of truth for "what we sell." The handler should read configuration, not embody it.

Corollary: **the "card-required vs. card-optional" choice is a policy, not a UX detail.** A card-optional trial is a different business model (freemium-timed) from a card-required trial (upgrade-funnel). Treat the policy as data, pass the data to Stripe, don't let the difference leak into five different files.

## Step 1 — Extend the tier config

Open `src/lib/config/pricing.ts` and add an optional trial spec:

```ts
// src/lib/config/pricing.ts
export type TierId = 'free' | 'plus' | 'pro';
export type Interval = 'monthly' | 'yearly';

export interface TrialConfig {
	days: number;
	requirePaymentMethod: boolean;
}

export interface TierConfig {
	id: TierId;
	name: string;
	description: string;
	contactLimit: number | null;
	prices: Partial<Record<Interval, string>>;
	trial?: TrialConfig; // absent = no trial
}

export const TIERS: TierConfig[] = [
	{
		id: 'free',
		name: 'Free',
		description: 'Get started with basic contact management.',
		contactLimit: 5,
		prices: {}
	},
	{
		id: 'plus',
		name: 'Plus',
		description: 'More contacts, priority email support.',
		contactLimit: 25,
		prices: { monthly: 'plus_monthly', yearly: 'plus_yearly' },
		trial: { days: 14, requirePaymentMethod: true }
	},
	{
		id: 'pro',
		name: 'Pro',
		description: 'Unlimited contacts, premium support.',
		contactLimit: null,
		prices: { monthly: 'pro_monthly', yearly: 'pro_yearly' }
		// no trial
	}
];
```

One field, `trial?: TrialConfig`. Absence means "no trial." Presence means "this tier has a trial with these parameters." No booleans, no nulls — just "is it there."

## Step 2 — Why Plus gets a trial and Pro doesn't

Pricing psychology dressed up as product policy:

- **Plus ($10/mo, broad audience.)** A 14-day trial removes the "do I really want to pay $10?" objection. Conversion rates on Plus trials are the number we tune marketing against.
- **Pro ($20/mo, small-teams / power users.)** These buyers are evaluating capability, not price. A trial adds a decision-delay without adding signal. We'd rather the user pays, uses it for a month, and cancels if it's wrong than trials it, forgets, and converts to nothing.

Your business might disagree. That's what the config is *for*. If Pro should have a no-card trial starting tomorrow, it's one object literal change in `pricing.ts`.

## Step 3 — Read the trial config in checkout

Back in `src/lib/server/billing/checkout.ts`, extend `createCheckoutSessionForLookupKey`:

```ts
// src/lib/server/billing/checkout.ts (additions shown)
import type Stripe from 'stripe';
import { TIERS } from '$lib/config/pricing';

// ... inside the function, after resolving `match`:

const tierConfig = TIERS.find((t) => t.id === match.tier.id);
const trial = tierConfig?.trial;

const subscriptionData: Stripe.Checkout.SessionCreateParams.SubscriptionData = {
	metadata: { user_id: userId, lookup_key: lookupKey }
};

const sessionParams: Stripe.Checkout.SessionCreateParams = {
	mode: 'subscription',
	customer: customerId,
	line_items: [{ price: priceId, quantity: 1 }],
	success_url: `${env.PUBLIC_APP_URL}/billing/success?session_id={CHECKOUT_SESSION_ID}`,
	cancel_url: `${env.PUBLIC_APP_URL}/pricing`,
	allow_promotion_codes: true,
	client_reference_id: userId,
	metadata: { user_id: userId, lookup_key: lookupKey },
	subscription_data: subscriptionData
};

if (trial) {
	subscriptionData.trial_period_days = trial.days;
	if (!trial.requirePaymentMethod) {
		sessionParams.payment_method_collection = 'if_required';
	}
}

const session = await stripe.checkout.sessions.create(sessionParams, {
	idempotencyKey: `checkout:${userId}:${lookupKey}`
});
```

One conditional. Both trial flavours differ by a single Stripe field. If `trial` is absent, neither field is set and you get a regular paid subscription with immediate billing — the 9.1 behaviour unchanged.

## Step 4 — What the two trial flavours actually do

**Card required (Plus):**

- User fills the card form on Checkout.
- Stripe creates the subscription with `status: 'trialing'`, `trial_end` 14 days out.
- On day 15, Stripe attempts the first charge. Success → `status: 'active'` + `invoice.paid`. Failure → `status: 'past_due'` + `invoice.payment_failed` (Module 9.5 handles this).
- If the user cancels during the trial, they're billed nothing.

**Card not required (hypothetical Pro-trial):**

- `payment_method_collection: 'if_required'` tells Checkout "only show the card form if the plan needs one on day one." Since `trial_period_days > 0` defers the first charge, the card form is skipped.
- User lands on the app immediately with `status: 'trialing'`.
- Day 11 (3 days before trial end), Stripe fires `customer.subscription.trial_will_end`. We nudge the user (Module 12 wires the email).
- Day 14: if no card has been added, `default_payment_method` is null. The sub transitions to `status: 'incomplete'`, Stripe attempts charge once, fails, and per our dunning config (Module 9.6) cancels soon after.

Both arrive through the same webhook path. The subscription row in `stripe_subscriptions` reflects whichever state Stripe is in.

## Step 5 — `trial_will_end` in the webhook handler

The 3-days-before warning event is worth logging now, wiring to email later. Extend the webhook switch from 6.3 / 7.4:

```ts
// src/routes/api/webhooks/stripe/+server.ts (addition)
case 'customer.subscription.trial_will_end': {
	const sub = event.data.object as Stripe.Subscription;
	console.log('[stripe webhook] trial_will_end', sub.id, 'ends at', sub.trial_end);
	// Module 12: send an email.
	break;
}
```

Add the trigger to `package.json`:

```json
{
	"scripts": {
		"stripe:trigger:trial-will-end": "stripe trigger customer.subscription.trial_will_end"
	}
}
```

Firing it now logs the intent. When we build the email pipeline, the hook point is already there.

The marketing page should mention the trial. Extend `PRICING_PRESENTATION` in `src/lib/config/pricing-page.ts`:

{

	highlighted: true,

Two small but important things:

- **The CTA says "Start 14-day free trial" for free-tier viewers.** The link still goes to `/app/upgrade?lookup=plus_monthly`; Stripe handles the trial server-side. UI and server read the same config.
- **The bullets mention the trial.** Users shouldn't discover a 14-day trial only at the Checkout page — that's a trust violation. Say it on the card.

## Step 7 — Server-side assertion: UI matches config

If a PM edits `pricing-page.ts` to claim "21 days" but `pricing.ts` still says `days: 14`, users will feel cheated. Catch the drift at startup. Add a lightweight check in `listPricingPageTiers`:

```ts
// src/lib/server/billing/pricing-page.ts (addition)
import { TIERS } from '$lib/config/pricing';

// ...inside listPricingPageTiers, after building `out`:
if (import.meta.env.DEV) {
	for (const entry of out) {
		const cfg = TIERS.find((t) => t.id === entry.tier.id);
		const days = cfg?.trial?.days;
		const mentionsTrial = entry.presentation.bullets.some((b) => /trial/i.test(b));
		if (days && !mentionsTrial) {
			console.warn(
				`[pricing-page] tier ${entry.tier.id} has ${days}-day trial but no bullet mentions it`
			);
		}
		if (!days && mentionsTrial) {
			console.warn(`[pricing-page] tier ${entry.tier.id} markets a trial it does not have`);
		}
	}
}
```

Dev-only, warning-level. Not a blocker, just a nudge to keep the two files honest. Production skips the check entirely.

## Step 8 — Verify the trialing status in the DB

After paying on a Plus checkout with test card `4242 4242 4242 4242`:

```sql
select id, status, trial_end, current_period_end
from stripe_subscriptions
where user_id = (select id from auth.users where email = 'demo@contactly.app');
```

You should see:

- `status = 'trialing'` (not `'active'`)
- `trial_end` ≈ 14 days from now
- `current_period_end` = `trial_end` (the trial is the current period)

`getUserTier` from 7.4 already treats `'trialing'` as "on this tier," so the user gets Plus access immediately. That was the whole point of including `trialing` in `LIVE_STATUSES`.

## Step 9 — Trial as a business decision, surfaced honestly

A few conventions worth adopting now:

- **Never shorten a trial silently.** If you change Plus from 14 days to 7 days, only new sign-ups get the 7-day trial. Existing trialers keep theirs. Stripe enforces this automatically — the trial is stamped on the subscription at creation time.
- **Never extend a trial silently either.** Extensions should be deliberate, per-customer, and logged (Module 13 covers the admin side of this).
- **Mention the trial on both the pricing page and the checkout page.** Stripe's Checkout UI shows the trial period natively when `trial_period_days` is set. The redundancy reassures users.

## Verify

- `pnpm dev` + go to `/pricing`, click "Start 14-day free trial" on Plus.
- Stripe Checkout page reads "14 days free, then $10.00/month."
- Paying with `4242 4242 4242 4242` completes. You land on `/app`.
- `stripe_subscriptions.status = 'trialing'`, `trial_end ≈ now + 14d`.
- `getUserTier(admin, user.id)` returns `'plus'` — the app treats trialing users as Plus.
- `pnpm stripe:trigger:trial-will-end` logs the event at 200.
- Temporarily flip Plus to `requirePaymentMethod: false`, restart, click Upgrade — no card form on Checkout, sub starts trialing without a payment method.
- `pnpm check` clean; no `any` introduced.

## Common traps

- **Setting `trial_period_days` at the session top-level instead of `subscription_data.trial_period_days`.** Stripe silently ignores it. The subscription won't trial. Always nest it under `subscription_data`.
- **Using `payment_method_collection: 'if_required'` without a trial.** It does nothing — the plan requires payment immediately — and confuses future readers. Only set it when a trial could defer the first charge.
- **Hardcoding trial days at the checkout call site.** Every time marketing wants to A/B a 7-day vs 14-day trial you'll be editing the handler. Keep it in config.
- **Trusting client-side "is this a trial?" to gate features.** The DB has `status` and `trial_end`. The server decides. UI shows what the server says.
- **Forgetting to include `trialing` in the "active" status list.** Then trialing users are locked out of the tier they're paying (not) for. Check `LIVE_STATUSES` in 7.4 if in doubt.

## Recap

One field in `pricing.ts` drives both trial existence and trial flavour. The checkout helper reads it, passes it to Stripe, and nothing else in the app knows about trials except the pricing page copy and the webhook logger.
