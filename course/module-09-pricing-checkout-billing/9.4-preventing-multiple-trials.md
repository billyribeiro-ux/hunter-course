# 9.4 — Preventing Multiple Trials

> "Sign up, trial, cancel, sign up again, trial again, forever." Close the loop.

## Why this matters

A 14-day trial is a marketing gift. It's also, left alone, a trivially abusable one. The pattern:

1. User trials Plus, cancels on day 13.
2. User comes back next month, clicks "Start 14-day free trial," gets another 14 days free.
3. Repeat.

Nothing in what we built in 9.1–9.3 stops this. Stripe does *not* track "has this customer ever trialed before"; as far as Stripe's concerned, each new subscription is its own thing with its own trial.

This lesson adds the server-side block: before creating a Checkout Session *with a trial*, check our DB for any prior trial. If there was one, create the session without the trial — the user can still upgrade, they just pay from day one. The pricing-page UI also learns to stop advertising "14 days free" to returning users, so the Checkout page isn't a surprise.

## The Principal Engineer lens

**The server is the enforcement point. The UI is the communication layer.** Hiding the trial badge without a server check is a UX lie that falls apart the second someone constructs the URL by hand. A server check without UI updates is honest but feels like a bait-and-switch ("wait, the page said free for 14 days"). You need both.

Corollary: **know the scope of the defence you're building.** This check blocks same-account reuse. It does *not* block email-hopping — a user who signs up with a second email can still trial again. True defence there requires either Stripe Radar rules on payment method fingerprint or collecting a card even for "card-optional" trials. Both are deeper solutions that belong in Modules 12/13. We're doing the 80% case today, explicitly.

## Step 1 — Add `hasUsedTrial` to the subscriptions service

Open `src/lib/server/billing/subscriptions.ts` and add:

```ts
// src/lib/server/billing/subscriptions.ts (append)

export async function hasUsedTrial(admin: Admin, userId: string): Promise<boolean> {
	const { count, error } = await admin
		.from('stripe_subscriptions')
		.select('id', { count: 'exact', head: true })
		.eq('user_id', userId)
		.not('trial_end', 'is', null);

	if (error) throw error;
	return (count ?? 0) > 0;
}
```

A few deliberate choices:

- **`.not('trial_end', 'is', null)`** — we're asking "has this user ever had a subscription row where Stripe set a `trial_end`?" A subscription that never trialed has `trial_end = null`; one that did always has a timestamp, even after the trial ends or the sub is cancelled.
- **`head: true, count: 'exact'`** — no payload, just a count. Cheap: one row's worth of network, a fast index lookup in Postgres.
- **Admin client.** The table is RLS-locked; this check runs in contexts that may not have a user JWT attached. Pass admin explicitly — same pattern as 7.3.

## Step 2 — Why not use `getActiveSubscription`

The wrong version:

```ts
// ❌ The trap
const active = await getActiveSubscription(admin, userId);
if (active) {
	// ...skip the trial
}
```

`getActiveSubscription` only returns subs with status `trialing`, `active`, or `past_due` (from 7.4). A user who trialed for 14 days and cancelled on day 13 has a subscription with `status = 'canceled'` — which is *exactly the user we need to block from re-trialing*. They're not currently active, but they've consumed their trial allowance.

`hasUsedTrial` looks at *any* historical sub, regardless of current status. That's the right filter.

## Step 3 — Gate the trial in checkout

Back in `src/lib/server/billing/checkout.ts`:

```ts
// src/lib/server/billing/checkout.ts (additions shown)
import { hasUsedTrial } from './subscriptions';

// ...inside createCheckoutSessionForLookupKey, replace the trial block:

if (trial) {
	const used = await hasUsedTrial(admin, userId);
	if (!used) {
		subscriptionData.trial_period_days = trial.days;
		if (!trial.requirePaymentMethod) {
			sessionParams.payment_method_collection = 'if_required';
		}
	}
	// If `used` is true: fall through without setting any trial fields.
	// User pays from day one; the upgrade still works.
}
```

The branch is intentionally un-dramatic. Returning users silently don't get a trial. No error, no message, no redirect — the Checkout page just shows "$10.00/month, billed immediately" instead of "14 days free." That's the right default: a user who clicks "Upgrade" has consented to pay.

## Step 4 — Communicate the state to the pricing page

We don't want a returning user to see "14-day free trial" on the pricing card and then get surprised at Checkout. Pass the "has used trial" flag to the page loader and branch the presentation.

First, expose it on `PageData` from the pricing loader. Open `src/routes/(marketing)/pricing/+page.server.ts`:

```ts
// src/routes/(marketing)/pricing/+page.server.ts (modified)
import type { PageServerLoad } from './$types';
import { listPricingPageTiers } from '$lib/server/billing/pricing-page';
import {
	getActiveSubscription,
	hasUsedTrial,
	tierIdFromLookupKey
} from '$lib/server/billing/subscriptions';

export const load: PageServerLoad = async ({ locals, setHeaders }) => {
	const pageTiers = await listPricingPageTiers();

	let currentTierId: 'free' | 'plus' | 'pro' = 'free';
	let trialUsed = false;
	if (locals.user) {
		const sub = await getActiveSubscription(locals.supabaseAdmin, locals.user.id);
		currentTierId = tierIdFromLookupKey(sub?.price_lookup_key ?? null);
		trialUsed = await hasUsedTrial(locals.supabaseAdmin, locals.user.id);
	}

	if (!locals.user) {
		setHeaders({ 'Cache-Control': 'public, max-age=60, s-maxage=300' });
	}

	return { pageTiers, currentTierId, trialUsed };
};
```

Then let the card read it. In `src/routes/(marketing)/pricing/TierCard.svelte`, extend props:

```svelte
<script lang="ts">
	import type { Tier, TierPrice } from '$lib/server/billing/types';
	import type { PricingTierPresentation } from '$lib/config/pricing-page';
	import type { TierId } from '$lib/config/pricing';
	import { TIERS } from '$lib/config/pricing';

	type Props = {
		tier: Tier;
		presentation: PricingTierPresentation;
		interval: 'monthly' | 'yearly';
		currentTierId: TierId;
		trialUsed: boolean;
		formatPerMonth: (cents: number, interval: 'monthly' | 'yearly') => string;
	};
	let { tier, presentation, interval, currentTierId, trialUsed, formatPerMonth }: Props =
		$props();

	let price = $derived<TierPrice | undefined>(
		tier.prices.find((p) => p.interval === interval)
	);

	let tierConfig = $derived(TIERS.find((t) => t.id === tier.id));
	let offersTrial = $derived(Boolean(tierConfig?.trial) && !trialUsed);

	let cta = $derived(
		currentTierId === tier.id
			? presentation.ctaCurrent
			: currentTierId === 'free'
				? offersTrial
					? presentation.ctaFree
					: `Upgrade to ${tier.name}`
				: presentation.ctaOther
	);

	// ... rest of existing script unchanged (isCurrent, href)
</script>
```

And in the template, guard the trial bullet:

```svelte
<ul class="mt-6 space-y-2 text-sm flex-1">
	{#each presentation.bullets as bullet (bullet)}
		{#if !(/trial/i.test(bullet)) || offersTrial}
			<li class="flex items-start gap-2">
				<span aria-hidden="true" class="mt-0.5 text-primary">✓</span>
				<span>{bullet}</span>
			</li>
		{/if}
	{/each}
</ul>
```

Filter out trial-mentioning bullets when the viewer isn't eligible. Swap the CTA from "Start 14-day free trial" to "Upgrade to Plus" in the same case. Both behaviours flow from one boolean.

Finally, update `+page.svelte` to pass `trialUsed` down:

```svelte
<!-- src/routes/(marketing)/pricing/+page.svelte (just the TierCard invocation) -->
<TierCard
	tier={entry.tier}
	presentation={entry.presentation}
	{interval}
	currentTierId={data.currentTierId}
	trialUsed={data.trialUsed}
	{formatPerMonth}
/>
```

## Step 5 — Why "filter bullets that mention 'trial'" is OK here

Pattern-matching on copy is usually a smell. In this case it's a feature:

- The trial-mention rule is coupled to the `trial` field on the tier config (Step 1 in 9.2 added the dev-mode check that asserts the two stay in sync).
- The alternative — tagging each bullet as `{ label: string; showIfTrialEligible?: boolean }` — is more machinery than the problem deserves for one conditional bullet per tier.
- If tomorrow we have three conditional bullets, we'll upgrade the data shape. Today's YAGNI.

The dev assertion from 9.2 catches the case where a PM adds "trial" to a non-trialing tier. Together, the two rules are enough.

## Step 6 — Test it end-to-end with a test clock

From 9.3, you know how:

```bash
# 1. Fresh clock user
pnpm stripe:clock:user
# (sign in, go to /pricing as this user — Plus shows "Start 14-day free trial")
# (upgrade, complete checkout, land on /app)

# 2. Cancel immediately (via Stripe dashboard or Customer Portal in 9.8), then advance.
pnpm stripe:clock advance-days clock_... 30
# The sub is now in status 'canceled' in stripe_subscriptions.

# 3. Re-visit /pricing as the same user.
# - No more "14-day free trial" bullet under Plus.
# - CTA reads "Upgrade to Plus" instead of "Start 14-day free trial".

# 4. Click Upgrade.
# - Stripe Checkout shows "$10.00 due today" — no 14-day free header.
```

Each step is observable in the UI and in the DB. If any of them skips, the defence is incomplete.

## Step 7 — What this doesn't block

Two known gaps, documented honestly:

### Email-hopping

User cancels, registers a new Supabase account with `alt+1@...`, trials again. Our `hasUsedTrial` is keyed on `user_id`; the new user has no prior subs. They trial. Defences that *would* catch this:

- **Stripe Radar rules on payment method fingerprint.** Each card has a stable `fingerprint`. Block or flag when the same fingerprint appears across two "first trial" customers. (Module 13 material.)
- **Force card collection even for card-optional trials.** Then Radar can see *something*. We don't have card-optional trials today, so this doesn't apply — but would if we added one.
- **Rate-limit trials by signup IP.** Cheap, trivially defeated, unfriendly to NAT'd users. Don't.

### Chargebacks / refunds as trial

A user who trialed, was charged on day 15, and disputed the charge within the billing window can effectively get a free trial paid out. This is a Stripe-side concern — disputes are handled in the dashboard with evidence. Module 13 covers the operational workflow.

Neither gap is a reason to skip the account-level check. It's the 80% block with 10 lines of code. Keep it.

## Step 8 — Preserving the old trial window across plan changes

One subtle point. A user who trialed Plus for 14 days, converted, was active for 3 months, then downgrades to Pro (hypothetical): our check says they've used a trial, so the Pro checkout won't offer one. Desired? In our business, yes — the trial is per-customer, not per-tier. Stripe's own conventions agree: a trial is a one-time onboarding nudge, not a "try each tier" buffet.

If you ever want per-tier trials, `hasUsedTrial` grows a `lookupKey` filter and `price_lookup_key` gets checked too. Easy extension; we don't need it.

## Verify

- A brand-new clock user with no prior subs: `hasUsedTrial` returns `false`, pricing page shows "Start 14-day free trial" on Plus, Checkout shows the free-trial header.
- After that user trials + cancels: `hasUsedTrial` returns `true`, pricing page shows "Upgrade to Plus" on Plus (no trial bullet), Checkout shows "$10.00 due today" with no trial header.
- A user who pays Pro directly (no trial) from day one: `hasUsedTrial` stays `false` because `trial_end` is null on that sub. They can still trial Plus later if we ever add that flow.
- `pnpm check` clean; no `any` in the new code; no leaked Stripe types in the UI.

## Common traps

- **Querying with `status = 'canceled'` to find past trialers.** Misses users who are currently active (they trialed *and* stayed). Use `trial_end IS NOT NULL`.
- **Checking on the client.** The UI can show the right thing, but the server must enforce. Never rely on the hidden-bullet to stop abuse — someone will just land on `/app/upgrade?lookup=plus_monthly` directly.
- **Returning an error when a returning user tries to trial again.** Awful UX and legally questionable — you're offering a product, they're trying to buy it. Silently drop the trial and let them pay.
- **Hardcoding the trial bullet list index to hide.** Fragile; re-ordering the bullets breaks it. Filter by content (or by a proper config field if it grows).
- **Claiming this is complete abuse protection.** It isn't, and saying so sets up the next engineer to under-invest in Radar when growth makes the gap visible.

## Recap

A 10-line DB check, wired into one checkout helper, backed by one UI prop that conditionally hides the trial bullet and swaps the CTA. Same-account trial abuse closed. Email-hopping and payment-method tricks remain, explicitly, for later modules. Next we'll look at what happens when a legitimate customer's *card* fails.
