# 9.5 — Test Cards & Failed Payments

> Five to fifteen percent of card charges fail somewhere in their life. Treat it as a first-class state, not an exception.

## Why this matters

Card payments are not a boolean. A charge can: succeed cleanly, require 3DS authentication, fail because the issuer declined it, fail because of insufficient funds, attach fine but fail on the first charge, succeed now and fail at renewal, or start as a soft decline and retry to success.

Most of our Module 9 work so far assumed the happy path. This lesson rehearses the unhappy ones using Stripe's test card cheat sheet, inspects how Stripe's dunning (retry) pipeline reflects those failures in our `stripe_subscriptions` table, and builds the small UI affordance that tells a user "your card failed — update it" *before* their subscription is cancelled.

Contactly's rule: a user whose active subscription is `past_due` sees a banner the moment they land on the app. One click opens the Customer Portal (Module 9.7/9.8) and lets them fix it.

## The Principal Engineer lens

**Failed payments are not errors. They are states.** An error gets a try/catch, a log line, maybe a Sentry alert. A state gets a row in a table, a UI, a journey. Treating `past_due` as an exception is how you end up with a 2 AM incident where "subscription data looks wrong" and nobody remembers whether Stripe or our DB is the source of truth.

Corollary: **the window between first failure and final cancellation is your best reactivation funnel.** Stripe retries for days; dunning is a giveable. If your app is silent during that window, the user only finds out when Pro features stop working. By then, the muscle memory of "this is a thing I pay for" has weakened. Surface it at the first failed charge, not the last.

## Step 1 — Stripe's test cards, the short list

Stripe test mode accepts these card numbers with any expiry in the future and any CVC. They trigger deterministic outcomes:

| Card number | Outcome |
|---|---|
| `4242 4242 4242 4242` | Succeeds. |
| `4000 0025 0000 3155` | Requires 3DS authentication; succeeds if user completes the challenge. |
| `4000 0000 0000 9995` | Attaches, *charge* fails immediately with `insufficient_funds`. |
| `4000 0000 0000 0341` | Attaches fine, *first charge* fails with `generic_decline`. Fails at renewal too. |
| `4000 0000 0000 0002` | Always declined (`generic_decline`). |
| `4000 0000 0000 0069` | Expired card. |
| `4100 0000 0000 0019` | Flagged as fraudulent. |

Full cheat sheet: `https://docs.stripe.com/testing#cards`. Keep this table open in a tab during development; you'll reach for it often.

## Step 2 — Walk through `0341` end-to-end

The most instructive test case. Create a fresh clock user (Module 9.3), go through Plus checkout with the Plus trial enabled, but use card `4000 0000 0000 0341`. Two phases matter.

**During trial (days 0–14).** No charge attempt yet. Subscription starts at `trialing`, `trial_end` 14 days out. Our DB reflects it normally. The card's problem doesn't surface until Stripe tries to actually bill it.

**At trial end (day 15).**

```bash
pnpm stripe:clock advance-days clock_... 15
```

Watch the webhook log:

1. `customer.subscription.trial_will_end` — 3 days before end, logged at day 12.
2. `invoice.created` — day 14, Stripe prepares the first invoice.
3. `invoice.payment_failed` — day 15, the `0341` card rejects the charge.
4. `customer.subscription.updated` — status transitions `trialing` → `past_due`.

`stripe_subscriptions` row now has `status = 'past_due'`. The user still has access (7.4's `LIVE_STATUSES` includes `past_due` for exactly this reason) — but their card is broken and Stripe will retry.

Advance further (the retry schedule is configured in 9.6; default is roughly 3 attempts across 2 weeks):

```bash
pnpm stripe:clock advance-days clock_... 7
# → invoice.payment_failed again, still past_due.

pnpm stripe:clock advance-days clock_... 14
# → final retry fails, Stripe gives up per dunning policy.
# → customer.subscription.deleted, status → 'canceled'.
```

`stripe_subscriptions.status = 'canceled'`. `getUserTier` returns `free`. Access revoked.

That whole arc — 21 days of real time, 30 seconds of test-clock time — is what the UI needs to handle gracefully.

## Step 3 — The past-due banner

Add `src/lib/components/PastDueBanner.svelte`:

```svelte
<!-- src/lib/components/PastDueBanner.svelte -->
<script lang="ts">
	interface Props {
		manageUrl: string;
	}
	let { manageUrl }: Props = $props();
</script>

<div
	role="alert"
	class="flex flex-wrap items-center justify-between gap-3 rounded-lg border border-red-500/40 bg-red-500/10 px-4 py-3 text-sm"
>
	<div class="text-red-600 dark:text-red-400">
		<strong class="font-semibold">Your last payment failed.</strong>
		Update your card to keep your subscription active.
	</div>
	<a
		href={manageUrl}
		class="rounded-md bg-red-600 px-3 py-1.5 text-sm font-medium text-white hover:bg-red-700"
	>
		Update payment method
	</a>
</div>
```

Hard rules for this component:

- **Visible above the fold on `/app` and on `/account`.** Any page a paying user naturally lands on.
- **High contrast, red.** This is the one place we break from neutral UI. Failed payments are the one thing a user should *never* miss.
- **Action included inline.** Never a banner that says "your payment failed" with no link. Every banner is also a button.

## Step 4 — Compute `status === 'past_due'` server-side

The banner decision must be on the server, not the client. Open the top-level protected layout `src/routes/(app)/+layout.server.ts` and extend:

```ts
// src/routes/(app)/+layout.server.ts (modified)
import type { LayoutServerLoad } from './$types';
import { requireUser } from '$lib/server/auth';
import { getActiveSubscription } from '$lib/server/billing/subscriptions';

export const load: LayoutServerLoad = async (event) => {
	const user = requireUser(event);

	const sub = await getActiveSubscription(event.locals.supabaseAdmin, user.id);
	const isPastDue = sub?.status === 'past_due';

	return { user, isPastDue };
};
```

And consume it in `src/routes/(app)/+layout.svelte`:

```svelte
<script lang="ts">
	import PastDueBanner from '$lib/components/PastDueBanner.svelte';
	import type { LayoutData } from './$types';
	import type { Snippet } from 'svelte';

	let { data, children }: { data: LayoutData; children: Snippet } = $props();
</script>

<div class="mx-auto max-w-4xl px-4 py-6">
	{#if data.isPastDue}
		<div class="mb-4">
			<PastDueBanner manageUrl="/app/billing/portal" />
		</div>
	{/if}
	{@render children()}
</div>
```

A single `isPastDue` boolean in layout data, everywhere a protected page renders. One source of truth; no per-page flag juggling.

## Step 5 — Why `past_due` stays inside `LIVE_STATUSES`

Revisit 7.4's definition:

```ts
const LIVE_STATUSES = ['trialing', 'active', 'past_due'] as const;
```

`past_due` is "the user is our customer, the charge hasn't landed yet." Stripe is retrying. If we demoted them to Free the moment the first charge failed:

- **Users who fixed their card within minutes** would still be locked out until the next retry.
- **The billing dashboard would lie about MRR** (they're paying, probabilistically).
- **Retention flows would flag them as churned** when they haven't churned.

Keep them as paid customers during dunning. Revoke only when Stripe gives up (`canceled`). That's the graceful path.

## Step 6 — Reading the retry schedule from Stripe

Our app doesn't *configure* retries — that lives in the Stripe dashboard (Module 9.6). But it should *observe* them:

```ts
// src/lib/server/billing/subscriptions.ts (append)
import type Stripe from 'stripe';
import { stripe } from '$lib/server/stripe';

export async function nextRetryAt(
	stripeSubscriptionId: string
): Promise<Date | null> {
	const sub = await stripe.subscriptions.retrieve(stripeSubscriptionId, {
		expand: ['latest_invoice']
	});
	const inv = sub.latest_invoice;
	if (!inv || typeof inv === 'string') return null;
	if (!inv.next_payment_attempt) return null;
	return new Date(inv.next_payment_attempt * 1000);
}
```

`next_payment_attempt` is Stripe's authoritative "we will retry at this Unix timestamp or not at all." Useful for showing "We'll try your card again on Thu, Apr 25" instead of a vague "we're retrying." We won't wire this into the banner today — keep it minimal for 9.5; Module 13 polishes.

## Step 7 — What happens on recovery

Say the user updates their card via the Customer Portal on day 17 (two days into `past_due`). Stripe attempts the charge immediately with the new card. On success:

- `invoice.paid` fires.
- `customer.subscription.updated` fires, status `past_due` → `active`.

Our webhook handler syncs the sub, `isPastDue` becomes `false`, the banner disappears next request. No special recovery code to write — we already re-upsert on every sub event (7.4's "no deltas" rule).

Verify on a test clock:

```bash
pnpm stripe:clock advance-days clock_... 16
# Past-due. Banner visible on /app.

# (update card to 4242... via portal)

pnpm stripe:clock advance-days clock_... 1
# Stripe retries on the period boundary.
# Webhook logs: invoice.paid, customer.subscription.updated.
# status: active. Banner gone.
```

## Step 8 — What the UI deliberately doesn't do

- **Doesn't show the raw Stripe decline code.** `"generic_decline"` is meaningless to users. "Update your card" is enough.
- **Doesn't enumerate retry attempts ("this is retry 2 of 3").** Uncomfortable pressure; Stripe's own emails say this already.
- **Doesn't auto-email the user.** Stripe's "Payment failed" customer email is enabled in 9.6. We don't double-email; we surface in-app.
- **Doesn't block app functionality.** The user is still paid-up as far as our tier logic is concerned; they keep Plus features. The banner is the only diff. Cutting features mid-dunning is a self-inflicted churn wound.

Every restraint is a decision to trust Stripe's dunning and let the user keep working.

## Step 9 — Minimal observability

A couple of log lines you'll be glad to have:

```ts
// src/routes/api/webhooks/stripe/+server.ts (inside switch, existing cases extended)
case 'invoice.payment_failed': {
	const inv = event.data.object as Stripe.Invoice;
	console.warn(
		'[stripe webhook] invoice.payment_failed',
		inv.id,
		'customer:', inv.customer,
		'attempt:', inv.attempt_count,
		'next_attempt:', inv.next_payment_attempt
	);
	break;
}
case 'invoice.paid': {
	const inv = event.data.object as Stripe.Invoice;
	console.log('[stripe webhook] invoice.paid', inv.id, 'amount:', inv.amount_paid);
	break;
}
```

Not analytics-grade. Enough to grep the logs when a user asks "did my payment go through?"

## Verify

- Upgrading with card `4000 0000 0000 0341`, then advancing the clock past the trial, produces `invoice.payment_failed` and flips `stripe_subscriptions.status` to `past_due`.
- `/app` shows the red "Update payment method" banner.
- Clicking the banner navigates to `/app/billing/portal` (stubbed today, fully wired in 9.8).
- Updating the card to `4242 4242 4242 4242` via Portal + advancing the clock one day flips status to `active` and removes the banner.
- Advancing far enough to exhaust retries flips status to `canceled`, `getUserTier` returns `free`, banner removed (the user isn't past-due anymore — they're ex-customer).
- `pnpm check` clean; no `any` introduced.

## Common traps

- **Hiding the `past_due` state entirely.** Then the user finds out when their sub is cancelled and their `invoice.payment_failed` emails from Stripe looked like spam. Surface in-app, always.
- **Demoting to Free as soon as `past_due` arrives.** Mid-dunning users are still customers. Keep tier access; just tell them to fix the card.
- **Building a custom retry scheduler.** Stripe's dunning is better than yours. Configure it (9.6); don't rewrite it.
- **Showing the Stripe error code in the UI.** "generic_decline" means nothing. Use plain language.
- **Forgetting to restart `pnpm stripe:listen` between test cases.** Each `stripe listen` is its own forwarding session; if it's down, the webhook fires but your app never sees it.
- **Testing only with `4242...`.** The happy path hides every interesting bug. Run through `0341` at least once per release.

## Recap

`past_due` is a first-class state. A single server-computed boolean drives a single banner component that appears wherever authenticated users land. Stripe's dunning handles the retries; our app honestly tells the user what's happening and gives them one click to fix it. Next we'll configure the dunning policies and customer emails that make this behaviour feel consistent.
