# 9.3 — Stripe Test Clocks

> A time machine for Stripe customers. The "come back in 14 days" bug becomes a "run this script" bug.

## Why this matters

You just added 14-day trials. How do you test what happens on day 15? The naïve answer — wait two weeks — obviously doesn't scale. The slightly-less-naïve answer — manually set `trial_end` to a past timestamp and poke things — produces fragile tests that only exercise one event at a time.

Stripe's answer: **test clocks**. A test clock is a Stripe object you attach to a test-mode Customer. The customer's entire lifecycle runs against the clock's "frozen time" rather than wall-clock. When you `advance` the clock by N days, Stripe replays *every* event that would have happened in those N days — trial end, payment attempt, renewal, dunning, everything — and returns only after every event has been generated. If your webhook handler is listening, you see them land in order, for real.

This lesson sets up a tiny script with three subcommands (`create`, `advance-days`, `destroy`) that lets you rehearse every billing edge case in seconds. Every subsequent lesson in Module 9 leans on it.

## The Principal Engineer lens

**If you can't test a code path in under a minute, you will not test it.** Billing lifecycles are full of "what happens on day X" branches. A test clock collapses them into a one-line invocation. Your willingness to write the handler for `trial_will_end` correctly is directly proportional to how quickly you can re-trigger it.

Corollary: **separate the clock customer from your dev identity.** Your normal `demo@contactly.app` user lives on real (unfrozen) time and hits real webhooks on real schedules. A test-clock customer lives on frozen time. Mixing them leaks state: a "14 days later" advance will mutate your demo user's subscription and you'll spend an afternoon wondering why your dev account looks weird. Use a throwaway user tied to a fresh clock, and destroy the clock when you're done.

## Step 1 — What a test clock is, precisely

From Stripe's perspective, a test clock is a scheduling sandbox:

- It has a `frozen_time` (Unix seconds) that represents "now" for attached customers.
- Creating a customer with `{ test_clock: clockId }` binds that customer to the clock. The customer's subscriptions, invoices, and renewals all use the clock's time instead of wall-clock.
- Calling `stripe.testHelpers.testClocks.advance(clockId, { frozen_time: t })` moves the clock forward to `t`. Stripe then runs every scheduled job up to `t` — `customer.subscription.trial_will_end`, `invoice.created`, `invoice.paid`, renewals, everything — and only resolves the API call after they've all been generated.
- The call returns the test clock object with `status: 'ready'`. If you're polling events, they've already fired.

Test clocks only work in test mode. You cannot attach one to a live-mode customer.

## Step 2 — The helper module

Create `src/lib/server/billing/test-clock.ts`:

```ts
// src/lib/server/billing/test-clock.ts
import { stripe } from '$lib/server/stripe';

export async function createTestClock(frozenAt: Date = new Date()): Promise<string> {
	const clock = await stripe.testHelpers.testClocks.create({
		frozen_time: Math.floor(frozenAt.getTime() / 1000),
		name: `contactly-dev-${frozenAt.toISOString()}`
	});
	return clock.id;
}

export async function advanceTestClockByDays(clockId: string, days: number): Promise<void> {
	const clock = await stripe.testHelpers.testClocks.retrieve(clockId);
	const target = clock.frozen_time + days * 24 * 60 * 60;

	await stripe.testHelpers.testClocks.advance(clockId, { frozen_time: target });
	// The SDK resolves once Stripe has finished generating every scheduled event
	// up to `target`. Callers can assume webhooks have been delivered (or
	// attempted) by the time this returns.
}

export async function destroyTestClock(clockId: string): Promise<void> {
	// Deletes the clock AND all customers attached to it.
	await stripe.testHelpers.testClocks.del(clockId);
}
```

Three functions, one responsibility each. Nothing surprising — the whole lesson is mostly about *using* them.

## Step 3 — The CLI script

Create `app/scripts/stripe-clock.ts`:

```ts
// app/scripts/stripe-clock.ts
import {
	createTestClock,
	advanceTestClockByDays,
	destroyTestClock
} from '../src/lib/server/billing/test-clock';

async function main(): Promise<void> {
	const [cmd, ...rest] = process.argv.slice(2);

	switch (cmd) {
		case 'create': {
			const id = await createTestClock();
			console.log(id);
			return;
		}
		case 'advance-days': {
			const [clockId, daysRaw] = rest;
			if (!clockId || !daysRaw) {
				throw new Error('usage: stripe-clock advance-days <clockId> <days>');
			}
			const days = Number(daysRaw);
			if (!Number.isFinite(days) || days <= 0) {
				throw new Error('days must be a positive number');
			}
			await advanceTestClockByDays(clockId, days);
			console.log(`advanced ${clockId} by ${days} day(s)`);
			return;
		}
		case 'destroy': {
			const [clockId] = rest;
			if (!clockId) throw new Error('usage: stripe-clock destroy <clockId>');
			await destroyTestClock(clockId);
			console.log(`destroyed ${clockId}`);
			return;
		}
		default:
			console.error('usage: stripe-clock <create|advance-days|destroy> [...args]');
			process.exit(1);
	}
}

main().catch((err: unknown) => {
	console.error(err);
	process.exit(1);
});
```

Wire it into `app/package.json`:

```json
{
	"scripts": {
		"stripe:clock": "tsx scripts/stripe-clock.ts"
	}
}
```

Why a CLI instead of a UI button:

- **Fast iteration.** `pnpm stripe:clock advance-days clk_... 15` fits in muscle memory.
- **Scriptable.** Playwright tests in Module 11 can shell out to this same script.
- **No clock state in the app.** The clock is Stripe's, not ours. The app stays oblivious.

## Step 4 — Creating a clock-bound customer

A test clock is useless without a customer attached. Stripe doesn't let you retrofit an existing customer onto a clock — the attachment is set at creation time. Which means for clock-based testing, you create a *new* customer (and, here, a new user).

Create a one-shot helper script `app/scripts/stripe-clock-user.ts`:

```ts
// app/scripts/stripe-clock-user.ts
import { stripe } from '../src/lib/server/stripe';
import { createTestClock } from '../src/lib/server/billing/test-clock';
import { supabaseAdmin } from '../src/lib/server/supabase-admin';

async function main(): Promise<void> {
	const email = `clock-${Date.now()}@contactly.test`;
	const password = 'Password123!';

	// 1. Create a Supabase auth user.
	const { data: authData, error: authErr } = await supabaseAdmin.auth.admin.createUser({
		email,
		password,
		email_confirm: true
	});
	if (authErr || !authData.user) throw authErr ?? new Error('no user');

	// 2. Create a test clock.
	const clockId = await createTestClock();

	// 3. Create a Stripe customer attached to the clock, mirrored into our DB.
	const customer = await stripe.customers.create({
		email,
		metadata: { user_id: authData.user.id },
		test_clock: clockId
	});

	const { error: mirrorErr } = await supabaseAdmin
		.from('stripe_customers')
		.insert({ user_id: authData.user.id, stripe_customer_id: customer.id });
	if (mirrorErr) throw mirrorErr;

	console.log(
		JSON.stringify(
			{
				email,
				password,
				userId: authData.user.id,
				stripeCustomerId: customer.id,
				clockId
			},
			null,
			2
		)
	);
}

main().catch((err: unknown) => {
	console.error(err);
	process.exit(1);
});
```

And a script entry:

```json
{
	"scripts": {
		"stripe:clock:user": "tsx scripts/stripe-clock-user.ts"
	}
}
```

Running `pnpm stripe:clock:user` prints a JSON blob with everything you need to sign in, upgrade, and advance:

```json
{
	"email": "clock-1713520000000@contactly.test",
	"password": "Password123!",
	"userId": "a12b...",
	"stripeCustomerId": "cus_Nq...",
	"clockId": "clock_Nq..."
}
```

Sign in at `/login`, upgrade to Plus, then start time-travelling.

## Step 5 — The rehearsal scripts

Open three terminals:

```bash
# A: app
pnpm dev

# B: webhook forwarder
pnpm stripe:listen

# C: clock controls
```

Then walk through each scenario.

### Scenario 1 — Trial end, payment method present

```bash
pnpm stripe:clock:user
# (sign in as the printed email, upgrade to Plus with test card 4242..., takes the 14-day trial)

# Advance 15 days: trial ends, renewal charge succeeds.
pnpm stripe:clock advance-days clock_... 15
```

In Terminal A you should see, in order:

- `[stripe webhook] customer.subscription.trial_will_end` (fires 3 days before trial end, even during the advance)
- `[stripe webhook] invoice.created`
- `[stripe webhook] invoice.paid`
- `[stripe webhook] customer.subscription.updated` (status `trialing` → `active`)

`stripe_subscriptions.status` in your DB: `active`. Renewal done.

### Scenario 2 — Trial end, payment method missing

Requires flipping Plus to `requirePaymentMethod: false` in `pricing.ts`, restarting, and re-running the user flow (the Checkout page won't collect a card).

```bash
pnpm stripe:clock advance-days clock_... 15
```

Expected events:

- `trial_will_end`
- `invoice.created`
- `invoice.payment_failed` (no card on file)
- `customer.subscription.updated` (status `trialing` → `incomplete`)
- Shortly after, per your retry config: `customer.subscription.deleted` (status `canceled`).

`stripe_subscriptions.status` in your DB: `canceled`. The tier-gating logic from Module 10 will put this user back on Free.

### Scenario 3 — Monthly renewal (card works)

Start from an already-`active` Plus sub (you can fake this by advancing past trial as in Scenario 1). Then:

```bash
pnpm stripe:clock advance-days clock_... 30
```

Expected: one `invoice.paid`, one `customer.subscription.updated` with a new `current_period_end`. That's the normal monthly renewal.

### Scenario 4 — Renewal with a declining card

Rebuild the clock user with test card `4000 0000 0000 0341` (attaches fine, fails on charge):

```bash
pnpm stripe:clock advance-days clock_... 30
```

Expected:

- `invoice.created`
- `invoice.payment_failed`
- `customer.subscription.updated` (status `active` → `past_due`)
- (If you advance further into your retry schedule) eventual `canceled`.

This is the scenario Module 9.5 builds the UI for.

### Scenario 5 — Cancel at period end

Upgrade, then in the Stripe dashboard set the sub to cancel at period end (or use the Customer Portal after 9.8). Advance 30 days:

```bash
pnpm stripe:clock advance-days clock_... 30
```

Expected: `customer.subscription.deleted` (status `canceled`). The user is back on Free automatically.

## Step 6 — Clean up religiously

A test clock created and never destroyed lingers in your Stripe account forever, attached to a real customer. Two problems:

- The Stripe dashboard accumulates `clock-2026-04-...` entries that nobody remembers creating.
- Every subsequent clock customer is a unique email in `auth.users`, slowly bloating Supabase.

After each scenario:

```bash
pnpm stripe:clock destroy clock_...
# Also delete the Supabase auth user — one SQL call or Studio click.
```

Or make destruction part of your test teardown. In Module 11, Playwright tests will spin up a clock in `beforeAll` and destroy it in `afterAll`. Same discipline.

## Step 7 — One clock, many advances

A clock can be advanced repeatedly. The rule: **time only moves forward.** You can go `frozen_time=t` → `t + 1 day` → `t + 10 days`, but not back. If you want to rehearse "what happens on day 3, then day 5" separately, you need two clocks.

Stripe also rate-limits how far you can advance in one call — historically up to 2 simulated days per wall-clock second of advance. For Contactly's purposes (30-day-ish jumps) this is seconds of real time. Don't advance a year in one call; do it in chunks.

## Step 8 — What test clocks don't do

A few things they deliberately don't simulate:

- **Email delivery.** Stripe's "customer email" settings (Module 9.6) aren't triggered during clock advances in a way your inbox sees. You'll see the event; the email itself is suppressed.
- **Bank-side authorization delays.** Real cards sometimes take minutes to post. Clock advances are synchronous.
- **Webhooks retrying on your side.** If your webhook handler errors on a clock-fired event, Stripe queues a retry — but it's against wall-clock retry intervals, not clock intervals. Your retry won't happen during the advance call itself.

These are minor. Test clocks cover >95% of what you need to verify.

## Verify

- `pnpm stripe:clock:user` creates a user, a clock, and a clock-bound Stripe customer, and prints the IDs.
- Signing in as that user, upgrading to Plus, and advancing 15 days fires `trial_will_end`, `invoice.paid`, and `subscription.updated` with `status='active'`.
- `pnpm stripe:clock destroy clock_...` deletes the clock (check the dashboard to confirm).
- After destroy, advancing the same clock ID errors out ("no such test clock").
- The normal `demo@contactly.app` account is untouched — its subscription is on wall-clock, not the test clock.

## Common traps

- **Advancing past `trial_end` but not far enough to trigger dunning.** You'll see `past_due` and nothing else, and conclude the retry schedule is broken. It isn't — you just need another advance. Check Stripe's dashboard retry settings to know how far to jump.
- **Attaching the clock to `demo@contactly.app`.** You can't, and even if you could, you'd regret mixing frozen and wall-clock times on a single user. Always create a fresh user per clock.
- **Hardcoding the clock ID in your app code.** The clock is a dev/test artifact. The app should have no idea it exists. Pass the ID via the script args, never store it.
- **Forgetting to run `pnpm stripe:listen` during advances.** You'll see the DB state update (via Stripe's own retries to wherever your webhook endpoint points), but your local logs will be empty. Both terminals, every time.
- **Using a test clock in live mode.** The SDK call will 400 immediately. If you see that error, check your `STRIPE_SECRET_KEY` — you're on the wrong key.

## Recap

Two helpers (`createTestClock`, `advanceTestClockByDays`, `destroyTestClock`), one CLI, one setup script for clock-bound users, five rehearsed scenarios. You can now test any 14-day-or-30-day billing path in seconds. The rest of Module 9 assumes this tool exists and uses it.
