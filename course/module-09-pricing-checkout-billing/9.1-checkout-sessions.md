# 9.1 — Checkout Sessions

> Click "Upgrade," end up on Stripe's checkout page, come back a paid customer. One server function and two routes.

## Why this matters

Module 8 left a dangling link: the pricing page's paid-tier CTA points at `/app/upgrade?lookup=plus_monthly`, a route that doesn't exist yet. This lesson makes that click *work*.

Stripe Checkout is Stripe's hosted payment page. You create a Checkout Session on your server (secret key required), redirect the user to the URL Stripe returns, and Stripe handles the card form, 3DS, receipts, taxes, fraud, SCA, and every other "I'm glad someone else is solving this" problem. When the user pays, Stripe fires `checkout.session.completed` and `customer.subscription.created` webhooks at the endpoint you built in Module 6.3, and our upsert in 7.4 mirrors the subscription into Postgres.

This lesson is the bridge between the CTA and the webhook: one `createCheckoutSessionForLookupKey` helper, one `/app/upgrade` route that creates a session and redirects, one `/billing/success` landing route that confirms and sends the user on. After this, Contactly can actually take money.

## The Principal Engineer lens

**The server is the only thing that's allowed to create a Checkout Session.** The API requires the Stripe secret key. Stripe.js + `redirectToCheckout` from the client is a different (older) path that also works, but adds a round-trip and a JavaScript dependency for a flow that's fundamentally "go to this URL." One `redirect(303, ...)` on the server is faster, simpler, and degrades gracefully if JS fails to load.

Corollary: **every external ID Stripe gives you — customer, session, subscription — is an ID you should immediately bind to an internal one.** We set `client_reference_id: userId` *and* `metadata.user_id` on the session, *and* `subscription_data.metadata.user_id` on the subscription that will be created. Three copies of the same fact. Redundant on the happy path, lifesaving when a webhook arrives for something your DB didn't mirror yet.

## Step 1 — The checkout helper

Create `src/lib/server/billing/checkout.ts`:

```ts
// src/lib/server/billing/checkout.ts
import type { SupabaseClient } from '@supabase/supabase-js';
import type Stripe from 'stripe';
import { stripe } from '$lib/server/stripe';
import { env } from '$lib/server/env';
import type { Database } from '$lib/types/db';
import { getOrCreateStripeCustomer } from './customers';
import { findTierByLookupKey } from './products';

type Admin = SupabaseClient<Database>;

export interface CreateCheckoutArgs {
	admin: Admin;
	userId: string;
	email: string;
	lookupKey: string;
}

export async function createCheckoutSessionForLookupKey(
	args: CreateCheckoutArgs
): Promise<Stripe.Checkout.Session> {
	const { admin, userId, email, lookupKey } = args;

	// 1. Resolve lookup key → Stripe price ID. Throws on unknown key.
	const match = await findTierByLookupKey(lookupKey);
	if (!match) throw new Error(`No tier for lookup key: ${lookupKey}`);
	const priceId = match.price.stripePriceId;

	// 2. Get-or-create the customer. Idempotent per user.
	const customerId = await getOrCreateStripeCustomer(admin, userId, email);

	// 3. Create the Checkout Session.
	const session = await stripe.checkout.sessions.create(
		{
			mode: 'subscription',
			customer: customerId,
			line_items: [{ price: priceId, quantity: 1 }],
			success_url: `${env.PUBLIC_APP_URL}/billing/success?session_id={CHECKOUT_SESSION_ID}`,
			cancel_url: `${env.PUBLIC_APP_URL}/pricing`,
			allow_promotion_codes: true,
			client_reference_id: userId,
			metadata: {
				user_id: userId,
				lookup_key: lookupKey
			},
			subscription_data: {
				metadata: {
					user_id: userId,
					lookup_key: lookupKey
				}
			}
		},
		{
			// Two clicks of the upgrade button within 24h land on the same session.
			idempotencyKey: `checkout:${userId}:${lookupKey}`
		}
	);

	return session;
}
```

Every field is load-bearing.

## Step 2 — Why `mode: 'subscription'`

Stripe Checkout has three modes: `payment` (one-off), `subscription` (recurring), `setup` (save a card for later). Picking `'subscription'` tells Stripe "this session, when it succeeds, should create a `Stripe.Subscription` backed by the given price." The resulting subscription is what our Module 7.4 sync path picks up.

Pick `'payment'` and you'd get a `PaymentIntent` with no subscription — and no renewal. Not what we sell.

## Step 3 — Why `customer: customerId` (not `customer_email`)

You can start a Checkout Session with just `customer_email` and Stripe will create a fresh Customer each time. That's the trap we warned about in 7.3. Passing an explicit `customer` ties this session to the one Customer record we already own for this user. One user → one Stripe customer → many subscriptions over time.

## Step 4 — Why `allow_promotion_codes: true`

Adds a "Have a promo code?" field on Checkout. Stripe validates codes against coupons you've defined in the dashboard. Zero app code, and marketing can ship a promo in ten minutes without waiting on us. Turn it off if you don't want it visible — don't leave it default-true without thinking.

## Step 5 — Why three copies of `user_id`

- **`client_reference_id`** — top-level on the session, survives to `checkout.session.completed`. Easy to read off the event.
- **`metadata.user_id` on the session** — same info, different channel; arrives on `checkout.session.completed` too.
- **`subscription_data.metadata.user_id`** — propagates onto the `Stripe.Subscription` itself, visible on every future `customer.subscription.*` event *without* needing to join back through the checkout session.

The third is the most important. Webhook handlers for subscription events shouldn't have to fetch the session that created the sub just to find out which user it belongs to. Stamp the user on the sub, once, forever.

## Step 6 — Why `idempotencyKey: checkout:${userId}:${lookupKey}`

A user who double-clicks "Upgrade to Plus" within 24 hours sees one Checkout Session, not two. Without the key, they'd see two hosted pages (if both requests raced) and potentially start two subscriptions. With the key, Stripe returns the cached session to the second request.

The key is per `(user, lookupKey)` so a legitimate "upgrade to Pro after starting Plus" creates a distinct session.

## Step 7 — The `/app/upgrade` route

Create `src/routes/(app)/app/upgrade/+page.server.ts`:

```ts
// src/routes/(app)/app/upgrade/+page.server.ts
import { error, redirect } from '@sveltejs/kit';
import type { PageServerLoad } from './$types';
import { requireUser } from '$lib/server/auth';
import { createCheckoutSessionForLookupKey } from '$lib/server/billing/checkout';

export const load: PageServerLoad = async (event) => {
	const user = requireUser(event);

	const lookupKey = event.url.searchParams.get('lookup');
	if (!lookupKey) throw error(400, 'Missing lookup key');

	const session = await createCheckoutSessionForLookupKey({
		admin: event.locals.supabaseAdmin,
		userId: user.id,
		email: user.email!,
		lookupKey
	});

	if (!session.url) throw error(500, 'Stripe did not return a checkout URL');
	throw redirect(303, session.url);
};
```

Notes:

- **It's a `+page.server.ts` with no `+page.svelte`.** The load function always throws (either a `redirect` or an `error`), so the page never renders. SvelteKit handles this cleanly.
- **`redirect(303, ...)`** — "See Other." Correct for a POST-like transition where the client should issue a fresh GET. Browsers follow it automatically.
- **`session.url!`** — TypeScript doesn't know the URL is always present for `mode: 'subscription'`. We assert and fall back to a 500 if Stripe somehow lied.
- **No body parsing.** The lookup key is a URL parameter. The user is authenticated via the `(app)` guard from 3.3 *plus* the handler-level `requireUser` call — belt and braces.

The pricing page from Module 8.4 already links here: `href={`/app/upgrade?lookup=${price.lookupKey}`}`. No change needed there.

## Step 8 — The `/billing/success` route

When the user pays, Stripe redirects them back to `success_url`. We want to confirm the payment actually completed (not just that Stripe bounced them somewhere) before telling them "you're upgraded." Create `src/routes/(app)/billing/success/+page.server.ts`:

```ts
// src/routes/(app)/billing/success/+page.server.ts
import { redirect } from '@sveltejs/kit';
import type { PageServerLoad } from './$types';
import { requireUser } from '$lib/server/auth';
import { stripe } from '$lib/server/stripe';

export const load: PageServerLoad = async (event) => {
	requireUser(event);

	const sessionId = event.url.searchParams.get('session_id');
	if (!sessionId) throw redirect(303, '/app');

	const session = await stripe.checkout.sessions.retrieve(sessionId);

	// A completed session means Stripe has accepted payment (or started a trial).
	// The subscription webhook has either fired or is in flight; our DB may or
	// may not reflect the row yet. That's fine — /app reads the latest.
	if (session.status !== 'complete') {
		throw redirect(303, '/pricing');
	}

	throw redirect(303, '/app');
};
```

Why this is separate from the upgrade route:

- **It's the single landing point after payment.** One URL is easier to debug, easier to link to, and easier to analytics-instrument.
- **We don't mirror the subscription here.** That's the webhook's job. Relying on the webhook keeps one canonical write path and prevents double-writes.
- **We don't show a success page.** The user's answer to "did it work?" is the `/app` UI reflecting their new tier. In-page celebration screens (Module 13.2) are polish; the core flow is redirect → app → use it.

## Step 9 — Why not Stripe.js redirectToCheckout

A common alternative:

```ts
// ❌ The older path
const stripe = await loadStripe(PUBLIC_STRIPE_PUBLISHABLE_KEY);
await stripe.redirectToCheckout({ sessionId: data.sessionId });
```

Trade-offs:

- **Extra bundle.** Stripe.js adds ~40 KB to the client bundle for a one-time redirect.
- **JS-required.** If Stripe.js fails to load (adblock, flaky network), the upgrade button dies silently.
- **Two round-trips.** Server creates session → returns ID to client → client loads Stripe.js → Stripe.js redirects. Our server-redirect version is one round-trip.

The only reason to prefer `redirectToCheckout` is if you need Stripe.js in the browser *anyway* (e.g., for a custom Elements form on the same page). We don't. Hosted Checkout it is.

## Step 10 — Stripe types at the boundary only

Notice `createCheckoutSessionForLookupKey` returns `Stripe.Checkout.Session`. That's fine inside `src/lib/server/**` because this code is already server-only, already deeply tied to Stripe. The callers in `+page.server.ts` pull only `session.url` off it and let it go. Nothing Stripe-shaped ever crosses into `+page.svelte` or any client-visible type.

If you're tempted to return `{ url, id }` from the helper to "decouple," don't. The Stripe types *are* the decoupling: anyone reading `checkout.ts` sees exactly which Stripe fields we use, and `tsc` will yell if Stripe changes them on an SDK upgrade. The boundary is the `+page.server.ts` file, not the helper.

## Verify

- Clicking "Upgrade to Plus" on `/pricing` (as a logged-in user) lands you on `checkout.stripe.com` with the Plus product and $10 total.
- Paying with test card `4242 4242 4242 4242` redirects to `/billing/success?session_id=cs_test_...` and then forwards to `/app`.
- In another terminal, `pnpm stripe:listen` shows `customer.subscription.created` and `checkout.session.completed` at 200.
- `select * from stripe_subscriptions` shows one row, `status='active'`, `price_lookup_key='plus_monthly'`.
- Double-clicking the upgrade link within 24h lands on the *same* Checkout Session URL (copy it and compare `cs_test_...` IDs) — idempotency working.
- A logged-out visit to `/app/upgrade?lookup=plus_monthly` redirects to `/login` via the `(app)` guard.

## Common traps

- **Using `customer_email` instead of `customer`.** Creates a fresh Stripe Customer per checkout. You end up with duplicates and a painful reconciliation.
- **Leaving `success_url` or `cancel_url` at localhost in production.** Stripe redirects to whatever you pass. Always derive from `PUBLIC_APP_URL` so staging/prod get the right hostnames.
- **Forgetting `{CHECKOUT_SESSION_ID}` in `success_url`.** Without it, the success page has no ID to retrieve, and you can't confirm the session status.
- **Writing the subscription row on the success route.** Looks like defence-in-depth; is actually a race with the webhook and a second write path to keep in sync. Let the webhook own it.
- **Creating the Checkout Session from a client-side `fetch()`.** Requires exposing the secret key or building a tiny endpoint that does exactly what our `+page.server.ts` already does. Just use the server load.
- **Hardcoding the price ID in `line_items`.** We already have `findTierByLookupKey`. Never name a price by its ID in billing code.

## Recap

One helper creates a Checkout Session; one route redirects to it; one success route confirms and forwards to the app. The pricing page's existing link is now a working upgrade flow. Webhooks mirror the subscription, RLS gates what the user can see, and every user_id/lookup_key pairing is stamped on the session, the subscription, and our DB.
