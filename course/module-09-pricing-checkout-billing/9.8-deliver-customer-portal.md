# 9.8 — Deliver Customer Portal

> One URL, three entry points, zero UI duplication. The final bolt on Contactly's billing surface.

## Why this matters

Lesson 9.7 configured the Portal dashboard-side. This lesson wires it into our app: a server helper that creates a per-user portal session, one route that redirects the user to it, and three UI entry points that all funnel through that same route. When we're done:

- The `/account` page has a "Manage subscription" panel with a link.
- The pricing page's CTA for a user's current tier reads "Manage subscription" and links in.
- The past-due banner from 9.5 links in for emergency card updates.

All three targets resolve to `/app/billing/portal`. One URL means: one place to change the redirect logic, one place to add rate-limiting, one place to add logging. If you build three parallel paths, you'll have to fix every future bug in all three.

## The Principal Engineer lens

**Funnel entry points; don't fan them out.** Every additional place in the UI that says "take me to billing" is a fine thing; every additional *implementation* of "create a Portal session and redirect" is one more place to get the customer ID wrong. The seam between "user wants to manage billing" and "user lands on Stripe's hosted page" belongs in exactly one server handler.

Corollary: **never accept a customer ID from the request.** The portal-session call takes a Stripe customer ID. If you let the client tell you which customer to redirect, a curious user can paste someone else's `cus_...` into the URL and update *their* payment method. Always look up the customer keyed by the authenticated user.

## Step 1 — The portal helper

Create `src/lib/server/billing/portal.ts`:

```ts
// src/lib/server/billing/portal.ts
import type { SupabaseClient } from '@supabase/supabase-js';
import { stripe } from '$lib/server/stripe';
import { env } from '$lib/server/env';
import type { Database } from '$lib/types/db';
import { getOrCreateStripeCustomer } from './customers';

type Admin = SupabaseClient<Database>;

export async function createPortalSession(
	admin: Admin,
	userId: string,
	email: string,
	returnUrl: string = `${env.PUBLIC_APP_URL}/account`
): Promise<string> {
	// Always resolve the customer from our DB, keyed by the authenticated user.
	// Never accept a customer ID from the caller.
	const customerId = await getOrCreateStripeCustomer(admin, userId, email);

	const session = await stripe.billingPortal.sessions.create({
		customer: customerId,
		return_url: returnUrl
	});

	return session.url;
}
```

Three deliberate shapes.

### Why `getOrCreateStripeCustomer` and not `findUserIdByStripeCustomer`

The user might not have a Stripe customer yet (free-tier user who never trialed). Calling `findUserIdByStripeCustomer` returns null; we'd have to branch. `getOrCreateStripeCustomer` is already idempotent — calling it for a free user creates a Customer with no subscriptions, which is fine. The Portal will render with a "No active subscription" message and a list of past invoices (empty). Better UX than a 404.

### Why `returnUrl` is a parameter with a default

The three entry points in this lesson all want `/account` as the return URL, because that's where billing context lives after the trip. But if Module 13 adds a "Manage subscription" button from a specific feature's upsell, we may want the user back on that feature's page. Parameterise now; callers pick.

### Why no `idempotencyKey`

Portal sessions are cheap, short-lived (their URL expires in an hour), and not a mutation of billing state. Duplicates cost nothing. `idempotencyKey` matters for customer creation and checkout; for portal sessions it's noise.

## Step 2 — The route

Create `src/routes/(app)/app/billing/portal/+page.server.ts`:

```ts
// src/routes/(app)/app/billing/portal/+page.server.ts
import { error, redirect } from '@sveltejs/kit';
import type { PageServerLoad } from './$types';
import { requireUser } from '$lib/server/auth';
import { createPortalSession } from '$lib/server/billing/portal';

export const load: PageServerLoad = async (event) => {
	const user = requireUser(event);

	const url = await createPortalSession(
		event.locals.supabaseAdmin,
		user.id,
		user.email!
	);

	if (!url) throw error(500, 'Stripe did not return a portal URL');
	throw redirect(303, url);
};
```

Same shape as `/app/upgrade` from 9.1. A `+page.server.ts` whose `load` always throws, so no `+page.svelte` is needed. The user hits the URL, we mint a session, they're on Stripe within one round-trip.

## Step 3 — Why a route, not a remote command

A reasonable alternative:

```ts
// src/lib/server/billing/portal.remote.ts
import { command, getRequestEvent } from '$app/server';
import { requireUser } from '$lib/server/auth';
import { createPortalSession } from './portal';

export const goToPortal = command(async () => {
	const event = getRequestEvent();
	const user = requireUser(event);
	const url = await createPortalSession(event.locals.supabaseAdmin, user.id, user.email!);
	return { url };
});
```

Then in the UI, call `goToPortal()`, read `result.url`, `window.location.href = result.url`. It works. It also:

- Requires client-side JS (form submissions to a remote command use fetch).
- Hides the redirect intent behind a command, which is idiomatic for mutations but odd for "go somewhere."
- Doesn't degrade: a user with JS disabled clicks nothing.

A plain `<a href="/app/billing/portal">` on an anchor tag:

- Is a regular link. No JS required.
- Has native middle-click / Cmd-click / "open in new tab" behaviour, which users expect for navigation.
- Is one less abstraction to explain.

Use the route. Keep remote commands for actual state mutations.

## Step 7 — Three entry points, one journey

Map it out explicitly:

| Entry point | URL clicked | Resolves to |
|---|---|---|
| `/account` → "Manage subscription" | `/app/billing/portal` | Stripe portal session, return to `/account` |
| `/pricing` → current-tier CTA | `/app/billing/portal` | Stripe portal session, return to `/account` |
| Past-due banner on `/app` | `/app/billing/portal` | Stripe portal session, return to `/account` |

Three links, same URL, same handler, same helper, same `return_url`. If tomorrow we want the return URL to be dynamic (banner returns to wherever the user was), the change is one function in one file.

## Step 8 — What happens when the user comes back

The Portal page has a "Back to Contactly" button that uses the `return_url` we passed. When the user clicks it — or closes the tab and navigates back manually — they land on `/account` with whatever they did reflected in the DB *eventually*.

"Eventually" is key. The Portal doesn't call back to our app. It mutates Stripe. Stripe fires webhooks. Our webhook handler (Module 6.3 / 7.4) syncs the subscription. That all takes one to a few seconds.

Consequence: if the user changes plan in the Portal and is back on `/account` before the webhook lands, the page shows the *old* tier. Two mitigations, in order of preference:

1. **Do nothing for now.** The webhook lands in seconds. A small "Your subscription was updated. Refresh if you don't see changes." hint on `/account` is enough if users complain.
2. **In Module 13, add a query param to `return_url` (e.g., `?billing=updated`) and a small loader on `/account` that refreshes data after 2 seconds when that param is present.** Solves the race visually without changing the real data path.

Don't be tempted to call `stripe.subscriptions.retrieve` on the return page and write the row yourself. Same argument as in 9.1: two write paths = drift.

## Step 9 — What the Portal doesn't expose to us directly

A few things to be aware of for completeness:

- **We can't restrict what an individual user sees in the Portal.** It's per-Stripe-account configuration. A user who clicks "Manage subscription" sees the same flows as every other user, including ones on the same tier. If you need per-tier UI (e.g., "Pro users see an invoice PDF button, Plus users don't"), the Portal is the wrong tool.
- **We can't embed the Portal in our UI.** It's always a redirect to `billing.stripe.com`. If you want an embedded experience, Stripe Elements + custom forms is the path — and you lose most of the "free hours" we celebrated in 9.7.
- **Portal URLs expire after roughly an hour.** Treat them as single-use, per-click. Never cache them in your DB or paste them into emails.

## Verify

- `/app/billing/portal` (logged in): redirects to `billing.stripe.com/session/...` within a second.
- On the Portal: update card to `4242 4242 4242 4242`. Click "Back to Contactly." Land on `/account`.
- Webhook terminal shows `customer.subscription.updated` and/or `payment_method.attached`. DB row reflects the current state.
- `/pricing` as a Plus subscriber: the Plus card CTA reads "Manage subscription" and links to `/app/billing/portal`.
- `/account` as a Plus subscriber: the Subscription section reads "Plus — renews Apr 30, 2026" (or similar), with a "Manage subscription" button that links to `/app/billing/portal`.
- Using test card `0341` to induce `past_due`: the red banner on `/app` links to `/app/billing/portal`; updating the card there clears the banner after the next webhook.
- A free-tier user hitting `/app/billing/portal` directly: Stripe creates a customer (via `getOrCreateStripeCustomer`) and the Portal shows "No active subscription" with invoice history. They can still navigate back.
- A logged-out request to `/app/billing/portal`: redirected to `/login` by the `(app)` guard from 3.3.
- `pnpm check` clean; no `any` introduced; no Stripe types leaking into any `.svelte`.

## Common traps

- **Accepting `customer_id` as a query parameter.** Ever. The customer is derived from the authenticated user, always.
- **Hardcoding the Portal URL base in your app.** Stripe owns `billing.stripe.com`; you never generate it manually. Always read `session.url`.
- **Caching portal URLs.** They're short-lived and user-specific. A cached URL handed to a different user or an hour later is a 410 waiting to happen.
- **Writing state when the user returns.** The webhook is authoritative. Return pages only *read* state; they never *write* it.
- **Creating the portal session with `locals.supabase` instead of `locals.supabaseAdmin`.** The `stripe_customers` table is RLS-locked; the get-or-create helper (and by extension, portal creation) needs the service-role client. See 7.3 on why.
- **Putting three different "go to portal" URLs across the app.** One route. One helper. Three links.

## Recap

One helper, one route, three entry points. Card updates, plan changes, cancellations, invoice downloads — all delivered via Stripe's hosted UI with a single `redirect(303, ...)` on our side. Module 9 is done: Contactly can take money, trial the right way, block the wrong way, survive payment failures, and let users self-serve everything else.
