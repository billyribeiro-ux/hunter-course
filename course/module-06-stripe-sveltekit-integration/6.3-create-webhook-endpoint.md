# 6.3 — Create Webhook Endpoint

> A `+server.ts` that verifies, parses, switches, and returns 200 faster than a heartbeat.

## Why this matters

This is the first piece of Stripe code that handles real traffic. Get it right and the rest of the billing surface (checkout, portal, subscriptions) just plugs into it. Get it wrong and you ship an endpoint that either rejects Stripe's own requests (signature fails, you never know about renewals) or accepts forged ones (attacker sends fake "subscription created" and unlocks Pro for free).

We're not wiring the database yet. That lands in Module 7 when we have the tables to write to. For now the handler proves three things:

- The raw body reaches the verifier intact.
- The signature check passes for real Stripe events and fails for anything else.
- We return 200 on success and 400 on signature failure, with sensible logs in between.

If you can `pnpm stripe:trigger:sub-created` and watch your server log "Received customer.subscription.created evt_1Nq...", the integration backbone works. The rest of the module is wiring.

## The Principal Engineer lens

**This endpoint is the trust boundary between Stripe and your app.** Everything below it is assumed to have a verified payload; everything above it has to prove who it is. Two rules follow:

1. **Read the raw body exactly once, before anything else touches it.** `await request.text()` first, then hand that string to `constructEvent`. Never `request.json()` — JSON parsing reorders whitespace and breaks the HMAC.
2. **No user context lives here.** A webhook has no session cookie. `locals.supabase` (the user-scoped client) would try to enforce RLS against a null user and fail. When we eventually do DB writes, they go through `locals.supabaseAdmin` — the service-role client we set up in Lesson 2.3.

Corollary: a webhook handler is the one place a `+server.ts` is correct over a remote function. Remote functions assume the caller is *your* UI and carry a session. Webhooks have neither.

## Step 1 — Create the route

From `app/`:

```bash
mkdir -p src/routes/api/webhooks/stripe
```

Structurally:

- `src/routes/api/` — anything here is a raw endpoint, not a page.
- `webhooks/stripe/` — one subfolder per webhook provider. If we ever add Postmark or Resend webhooks, they'd be siblings.

## Step 2 — Write the handler

Create `src/routes/api/webhooks/stripe/+server.ts`:

```ts
// src/routes/api/webhooks/stripe/+server.ts
import { json, type RequestHandler } from '@sveltejs/kit';
import type Stripe from 'stripe';
import { stripe } from '$lib/server/stripe';
import { env } from '$lib/server/env';

export const POST: RequestHandler = async ({ request }) => {
	// 1. Read the raw body as a string — exact bytes, no parsing.
	const rawBody = await request.text();

	// 2. Pull the signature header Stripe attached to the request.
	const signature = request.headers.get('stripe-signature');
	if (!signature) {
		return new Response('Missing stripe-signature header', { status: 400 });
	}

	// 3. Verify the signature and parse the event. Throws on any mismatch.
	let event: Stripe.Event;
	try {
		event = stripe.webhooks.constructEvent(rawBody, signature, env.STRIPE_WEBHOOK_SECRET);
	} catch (err) {
		const message = err instanceof Error ? err.message : 'unknown error';
		console.warn('[stripe webhook] signature verification failed:', message);
		return new Response(`Webhook Error: ${message}`, { status: 400 });
	}

	// 4. Dispatch. For now we just log; real DB writes land in Module 7.
	switch (event.type) {
		case 'checkout.session.completed':
			console.log('[stripe webhook]', event.type, event.id);
			break;
		case 'customer.subscription.created':
		case 'customer.subscription.updated':
		case 'customer.subscription.deleted':
			console.log('[stripe webhook]', event.type, event.id);
			break;
		case 'invoice.paid':
		case 'invoice.payment_failed':
			console.log('[stripe webhook]', event.type, event.id);
			break;
		default:
			// Unknown events: acknowledge so Stripe stops retrying.
			console.log('[stripe webhook] (ignored)', event.type, event.id);
			break;
	}

	// 5. Always return 2xx for events we successfully verified.
	return json({ received: true });
};
```

Every block earns its place:

- **`await request.text()`** — the single most important line. SvelteKit's `Request` is a standard web `Request`, and `.text()` gives you the body as it came off the wire. Do this *before* touching the headers or calling anything async that might consume the body. The body can only be read once.
- **`signature` header check** — a missing header is not necessarily malicious; it might be a health-check or a curious developer. We return 400 with a helpful message.
- **`stripe.webhooks.constructEvent(...)`** — verifies HMAC, checks timestamp freshness, parses JSON. Three jobs, one call.
- **`Stripe.Event` type** — imported as a type-only import so nothing from the Stripe SDK ends up in runtime bundles except via the `stripe` singleton we built in 6.1.
- **Switch with explicit cases per event we care about** — deliberately boring. One day a teammate will `Cmd+F` for `customer.subscription.created` and find this line immediately. That's the whole point.
- **`default: log + 200`** — don't make Stripe retry events we don't handle. Log so you can notice if a new relevant event type starts arriving (e.g. you enable test clocks and see `invoiceitem.created`).
- **`return json({ received: true })`** — body is informational; Stripe only cares about the status code. The `json({ ... })` helper sets `Content-Type: application/json` for us.

## Step 3 — Why the raw-body detour matters

A tempting wrong version:

```ts
// ❌ Broken
const body = await request.json();
const event = stripe.webhooks.constructEvent(body, signature, env.STRIPE_WEBHOOK_SECRET);
```

Two problems:

1. `constructEvent` expects a **string or Buffer**, not a parsed object. Passing an object will throw immediately.
2. Even if we stringified the parsed object before passing it in, `JSON.stringify(JSON.parse(x))` is *not* guaranteed to equal `x`. Whitespace, key order, number precision — all can shift. HMAC is byte-sensitive. The verification will fail for valid requests, randomly.

Rule: **raw body, exactly once, string or Buffer, before anything else.**

## Step 4 — Why not `locals.supabase`?

In CRUD lessons we always reached for `event.locals.supabase` (user-scoped, RLS-enforcing). Here we don't, because **there is no user**. Webhooks aren't triggered by a logged-in customer; they're triggered by Stripe's servers on its own timetable. `locals.user` is `null`. Any query we make through `locals.supabase` either returns zero rows (RLS hides everything) or errors (can't insert without a user).

Once we start persisting in Module 7, we'll reach for `event.locals.supabaseAdmin`. The authorisation that justifies service-role here isn't a user JWT — it's Stripe's signature on the payload. We reviewed this rationale in Lesson 4.4.

## Step 5 — Test with `stripe listen`

Two terminals (or one, after Lesson 6.3.1):

```bash
# Terminal A
pnpm dev

# Terminal B
pnpm stripe:listen
```

`stripe listen` prints its webhook signing secret on startup:

```
> Ready! Your webhook signing secret is whsec_...
```

Paste that into `app/.env` as `STRIPE_WEBHOOK_SECRET`, then restart `pnpm dev` so the typed env re-reads it.

> Each fresh `stripe listen` session generates a new secret. If you keep seeing signature failures after a restart, the first suspect is a stale `STRIPE_WEBHOOK_SECRET`.

In a third terminal, fire an event:

```bash
pnpm stripe:trigger:sub-created
```

Watch Terminal A. You should see:

```
[stripe webhook] customer.subscription.created evt_1Nq...
```

And terminal B (`stripe listen`) shows a `2xx` status for the forwarded request. Both green means signature verification worked and your handler returned 200.

Now try the failure path. Stop `stripe listen`, change `STRIPE_WEBHOOK_SECRET` in `.env` to garbage, restart `pnpm dev`, then from your browser or `curl`:

```bash
curl -X POST http://localhost:5173/api/webhooks/stripe \
	-H 'stripe-signature: t=1,v1=bogus' \
	-d '{"not":"valid"}'
```

You should see a 400 in the terminal and `[stripe webhook] signature verification failed: ...` in the logs. Restore the real secret afterwards.

## Step 6 — The complete event menu, for reference

Our switch handles five cases across six event types (the three subscription events share a case, and checkout + both invoice events are their own). You can add new cases later as your app grows. Keep the pattern:

- One `case` per event.
- Inside the case, either inline work (fast, trivial) or a call to a service function (named, greppable, testable).
- Never `await` a long operation in the case body — queue it.

In Module 7 the body of each case will look like:

```ts
case 'customer.subscription.created':
case 'customer.subscription.updated':
	await upsertSubscriptionFromEvent(event);
	break;
```

For now, `console.log` is enough.

## Step 8 — Replay protection: `stripe_events`

Stripe delivers webhooks **at-least-once**. The same event id can land on your endpoint twice — network blips, Stripe retries on a 5xx, your function cold-starts and times out before responding. Every handler we'll write in Module 7 is an `upsert`, so a duplicate happens to be idempotent today. But "happens to be" is not a security property. The day you add an email-sender or a credit-debit side effect, the second delivery double-fires.

The fix: a tiny dedup table, a unique-violation check at the top of the handler, and a rollback on handler failure so Stripe's retry actually re-runs (instead of hitting the dedupe and silently passing).

Create `supabase/migrations/<timestamp>_stripe_events.sql`:

```sql
create table public.stripe_events (
    id            text primary key,
    type          text not null,
    received_at   timestamptz not null default now()
);

alter table public.stripe_events enable row level security;
-- No policies → no one but service role can read or write. That's the point.
```

Then in the webhook handler, **after** signature verification but **before** any handler runs:

```ts
// Replay guard. Insert the event id; PK conflict means already-processed.
const { error: dupErr } = await event.locals.supabaseAdmin
	.from('stripe_events')
	.insert({ id: stripeEvent.id, type: stripeEvent.type });

if (dupErr) {
	const isDuplicate =
		(dupErr as { code?: string }).code === '23505' ||
		/duplicate key/i.test(dupErr.message);
	if (isDuplicate) {
		return new Response(JSON.stringify({ received: true, duplicate: true }), {
			status: 200,
			headers: { 'content-type': 'application/json' }
		});
	}
	console.error('[webhook] could not record event id:', dupErr);
	error(500, 'Could not record event');
}
```

And on the handler-failure path:

```ts
} catch (err) {
	console.error(`[webhook] ${stripeEvent.type} failed:`, err);
	// Roll back the replay-guard row so Stripe's retry re-runs the handler.
	await event.locals.supabaseAdmin
		.from('stripe_events')
		.delete()
		.eq('id', stripeEvent.id);
	error(500, 'Webhook handler error');
}
```

Three properties this buys you:

- **Idempotent by design**, not by luck. The dedupe runs before the side effect, so the side effect can be anything — sending an email, charging a card, posting to Slack — without double-firing.
- **Failure still retries.** The rollback on the `catch` branch means a transient handler failure doesn't permanently mark the event as processed. Stripe retries; the second delivery re-runs the handler with a clean slate.
- **Service-role isolated.** `stripe_events` has RLS enabled with zero policies — only the service-role client can touch it. Clients can't probe which events have been received.

## Verify

- `POST /api/webhooks/stripe` with a valid signature logs the event type and returns 200.
- `POST` with a missing or wrong signature returns 400 and logs a warning.
- Unknown event types (triggered via `stripe trigger payment_intent.created` if you like) log `(ignored)` and still return 200.
- Each of the six event types logged from `pnpm stripe:trigger:*` scripts appears in the server terminal.
- **Replay test:** `stripe trigger customer.subscription.updated`, note the event id in the log, then `stripe events resend <event_id>`. The second delivery returns `{ received: true, duplicate: true }` and the handler does not re-fire.
- `pnpm check` passes — no type errors on `event.type` narrowing.

## Common traps

- **Calling `await request.json()` instead of `await request.text()`.** Verification will fail silently for every real request. Symptom: "it works in `curl`, why doesn't it work with Stripe?"
- **Using `event.locals.supabase` in the handler.** There's no user. Writes will fail under RLS. Use `event.locals.supabaseAdmin` (from Module 7 onward).
- **Returning 500 on unknown event types.** Stripe retries for three days. Return 200 with a "ignored" log and move on.
- **Forgetting to restart `pnpm dev` after changing `STRIPE_WEBHOOK_SECRET`.** `$env/static/private` is read at build/startup. A stale env means every signature looks wrong. Restart, always.
- **Putting this handler in a remote function.** Remote functions assume a session. Webhooks are the opposite — the single, legitimate reason to use `+server.ts` in this app.
- **Skipping the dedupe rollback in the catch branch.** A handler that throws *and* leaves the `stripe_events` row in place permanently marks the event as processed — Stripe's retry will hit the dedupe and return 200 without ever re-running the handler. The mirror silently drifts from Stripe and nobody notices until a customer complains.

## Recap

A signed, raw-body, fast-returning webhook endpoint with PK-dedup replay protection. Six handled event types, one default-acknowledge case, clean 400/200 semantics, and a guarantee that no handler ever runs twice for the same event.
