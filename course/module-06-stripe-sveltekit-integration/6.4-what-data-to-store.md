# 6.4 — What Data to Store

> Stripe is the source of truth. Your database is a read cache. Mirror less, re-fetch when in doubt.

## Why this matters

The instinct when you first see a Stripe webhook payload is to save everything. The event gives you a subscription with twenty fields, an invoice with line items, a customer with address and default payment method — why not store it all? You'll "need it eventually," right?

This instinct is the second-worst mistake you can make with a billing system. (The worst is not storing *anything* and calling Stripe on every page load.) Overstoring creates a second source of truth that drifts. Customer updates their card? Your mirror is stale. Stripe changes the shape of `invoice.lines`? Your column breaks. You now maintain a billing schema forever, as a read-only byproduct of the real one.

The right move is to store the smallest amount of data that lets your app render and make decisions, and reach back to Stripe's API for everything else. This lesson defines that minimum — enough detail for you to understand Module 7's migrations before you run them.

## The Principal Engineer lens

**Mirror for entitlement and display. Nothing else.**

Three questions decide whether a Stripe field earns a column:

1. **Do we need it to render a page in under 50ms?** (Yes → mirror. It's a display cache.)
2. **Do we need it to authorise an action?** (Yes → mirror. It's an entitlement check that must not depend on a slow external call.)
3. **Is it historical detail Stripe already keeps?** (Yes → don't mirror. Link out or re-fetch.)

Corollary: **when Stripe and your DB disagree, Stripe wins.** This is the contract of every piece of billing code we write. A user's `/account` page pulls from your DB for speed, but any action that changes state (upgrade, cancel, resume trial) is done via a Stripe API call and the resulting webhook is what updates your DB. You never edit your DB directly for billing.

## Step 1 — The three tables (preview)

Module 7 creates three tables. Here is the plan, so you can see the shape before we commit to migrations.

### `stripe_customers`

One row per user that has ever touched Stripe.

| Column | Type | Notes |
|---|---|---|
| `user_id` | `uuid` PK, FK → `auth.users.id` ON DELETE CASCADE | The row's primary key is the user ID. One customer per user. |
| `stripe_customer_id` | `text` UNIQUE NOT NULL | The `cus_...` ID from Stripe. |
| `created_at` | `timestamptz` DEFAULT now() | When we first minted the customer. |

That's it. Three columns. We don't mirror the customer's email (it's on `auth.users`), the default payment method (re-fetch when needed), or the billing address (Stripe stores it, Customer Portal edits it).

### `stripe_subscriptions`

One row per subscription. A user might have zero, one, or — edge case — more than one (e.g. a dormant cancelled row plus an active current row).

| Column | Type | Notes |
|---|---|---|
| `id` | `text` PK | The Stripe subscription ID (`sub_...`). Stripe-issued, unique, stable. |
| `user_id` | `uuid` NOT NULL, FK → `auth.users.id` ON DELETE CASCADE | Ownership. Lets RLS scope by `user_id`. |
| `status` | `text` NOT NULL | `active`, `trialing`, `past_due`, `canceled`, `incomplete`, etc. |
| `price_lookup_key` | `text` NOT NULL | From Lesson 5.6 — `plus_monthly`, `pro_yearly`. |
| `current_period_end` | `timestamptz` | When the current paid period ends. |
| `cancel_at_period_end` | `boolean` NOT NULL DEFAULT false | "Cancel at end of period" flag. |
| `trial_end` | `timestamptz` | When (or if) the trial ends. |
| `created_at` | `timestamptz` DEFAULT now() | When we first saw it. |
| `updated_at` | `timestamptz` DEFAULT now() | Touched on every webhook upsert. |

The interesting choices:

- **`price_lookup_key`, not `price_id`.** This is the Module 5.6 lookup-keys pattern applied at the storage layer. We never want a `price_1Nq7Bz...` in our DB, for the same reason we don't want one in code: environment-portability and "change the price without migrating rows." When the webhook arrives, we read `subscription.items.data[0].price.lookup_key` and store that.
- **`current_period_end` and `trial_end` as `timestamptz`.** These are what the UI renders ("Your Pro plan renews on May 12") and what the entitlement code checks. Store them natively, not as Unix seconds.
- **`cancel_at_period_end`** — needed for the "Cancels on X" banner on the account page. A single boolean that flips when the customer hits "Cancel" in the Customer Portal.
- **No `quantity`, no `metadata`, no `items` array.** Contactly has per-user subscriptions with a single item. If we ever support multi-seat we'll add a `seat_count` column.

### `stripe_events`

The idempotency ledger introduced in Lesson 6.2. One row per Stripe event ID we have ever processed.

| Column | Type | Notes |
|---|---|---|
| `id` | `text` PK | The Stripe event ID (`evt_...`). |
| `type` | `text` NOT NULL | Stored mostly for forensics. |
| `received_at` | `timestamptz` DEFAULT now() | When our handler first saw it. |
| `processed_at` | `timestamptz` | Stamped after the real work completes. |

The PK is the check-and-set. Insert → if conflict, we've handled this event; if not, we haven't, so do the work and stamp `processed_at`. No race, no double-insert.

You might ask: why keep old events forever? Two reasons. First, storage is free (we'll process a few hundred events per day at most — kilobytes per year). Second, it's a debugging gold mine: "when did you first mark me past due?" → `select * from stripe_events where type = 'invoice.payment_failed' and received_at > ...`.

If the table ever gets uncomfortably big, a scheduled job can prune anything older than 90 days. Not a Module 6 concern.

## Step 2 — What we explicitly do *not* store

This list is as important as the tables above. Each omission is a deliberate call.

- **Payment method details.** Last-four digits, card brand, expiry. Stripe stores them, the Customer Portal renders them, and if we really need to show "•••• 4242" on our own pages we can fetch it on demand. Any copy we keep is guaranteed to be wrong the moment the customer updates their card.
- **Invoice line items.** Full invoice breakdowns with tax, discounts, and metadata. Stripe has them, with a permalink we can surface. We store none of it.
- **Product images / marketing text.** Hosted in Stripe, referenced by lookup key. The pricing page in Module 8 fetches them at build time or via SSR — not a database mirror.
- **Receipt URLs.** Stripe hosts receipts forever at stable URLs. We never need to mirror.
- **Stripe customer email / name / address.** `auth.users` has the email. The Customer Portal handles name/address. No duplication.
- **Full invoice history.** We don't need to list "every charge this user ever made" — the Customer Portal does that. If we ever do, it's a paginated call to `stripe.invoices.list({ customer })`, not a table.

The discipline behind every row of that list is the same: **if Stripe already has it, and we can fetch it on demand for the one page that renders it, we don't mirror it.**

## Step 3 — What we *always* hit Stripe for

A corollary — the things we don't mirror necessarily mean some code paths always talk to Stripe live:

- **Creating a Checkout session.** `stripe.checkout.sessions.create(...)` on demand. No mirror involved.
- **Creating a Customer Portal session.** `stripe.billingPortal.sessions.create(...)`. Same pattern.
- **Listing invoices for "my billing history".** If we add that page (it's optional — the portal already has it), we call `stripe.invoices.list` server-side and render the response directly.
- **Retrieving a subscription to resolve a disagreement.** If our mirror says `active` and a user claims they cancelled, we `stripe.subscriptions.retrieve(id)` to confirm. Stripe wins.

These operations are usually single-user and single-request — a few hundred milliseconds of Stripe latency is invisible inside a page navigation. The real-time reads that would kill us (is this user's plan active?) are always served by the mirror.

## Step 4 — Why lookup keys propagate all the way to the DB

This deserves its own beat, because it's the biggest structural decision here.

The obvious choice is to store `price_id` (the `price_1Nq7Bz...` value). It's what the Stripe event gives you. It's a foreign key to a "prices" concept. It's *correct*.

It's also fragile. A price gets archived and replaced — which happens the moment you raise prices from $10 to $12 — and now your DB has rows pointing at an archived ID. New checkouts use a new ID. The "which tier is this user on?" query turns into a case statement across both IDs, forever.

Lookup keys solve it:

- `price_lookup_key = 'plus_monthly'` means "Plus, billed monthly" — **regardless of which underlying Price ID is currently active.**
- Grandfathered customers on the old $10 price still have `price_lookup_key = 'plus_monthly'`. Their Stripe subscription references the old Price ID (and Stripe continues to bill them $10, which is Stripe's promise). Our app sees them as "on the Plus plan" — correct.
- New subscribers get the $12 price, same lookup key, same entitlement code path.

When the webhook arrives, we extract the lookup key from the nested price object:

```ts
const lookupKey = event.data.object.items.data[0].price.lookup_key;
```

And persist *that*. The Price ID never enters our schema.

## Step 5 — RLS considerations

All three tables will have RLS enabled in Module 7. The policies will look like:

- **`stripe_customers`** — user can `SELECT` their own row (`user_id = auth.uid()`). No one can `INSERT`, `UPDATE`, `DELETE` from the client — those only happen via the service-role webhook handler.
- **`stripe_subscriptions`** — same: user can `SELECT` their own, no client writes.
- **`stripe_events`** — no policies, no client access. This table is invisible to the app; only the webhook service touches it.

The webhook handler uses `locals.supabaseAdmin` (the service-role client from Lesson 2.3), which bypasses RLS. That's the only code path that writes to these tables. User-facing reads go through `locals.supabase` and see exactly their own rows.

## Common traps

- **Storing the full Stripe event payload in a `json` column "just in case".** You'll grow a ten-gigabyte table of stale snapshots that nobody queries. If you need forensics, use Stripe's dashboard or the `stripe events retrieve evt_...` CLI.
- **Mirroring the default payment method.** Your copy will be wrong within a month of going live. The Customer Portal shows the live one; your app doesn't need to.
- **Storing `price_id` alongside `price_lookup_key`.** Now you have two fields that can disagree. Pick the lookup key and trust it.
- **Using the DB as the authority for "is this user on Pro?".** You're right 99.9% of the time. The 0.1% is the bug that costs you a customer. For anything mutating (upgrade, feature unlock), also revalidate via Stripe when it's not too expensive.
- **Skipping `stripe_events` because "the other tables' unique constraints will handle dedupe."** They won't — a subscription `upsert` succeeds the second time too, silently, quietly making timestamps drift. The ledger is the only mechanism that tells you "we've already processed this one."

## Recap

Three small tables, one principle: mirror for speed and entitlement, never for history. Lookup keys in the DB, no payment-method detail, an events ledger to keep webhook delivery honest. Module 7 builds these tables and the services that fill them — and by the end of it, `pnpm stripe:trigger:sub-created` will land a real row in your local database.
