# 6.1 — Setup Stripe Node Client

> One server-only Stripe instance, pinned and typed. Imported everywhere, constructed once.

## Why this matters

You can't talk to Stripe without a client. Up until now we've been on the dashboard side: creating products, pinning lookup keys, running `stripe listen`. That was preparation. From this lesson forward every Stripe interaction — checkout sessions, customer portal links, subscription lookups, webhook verification — flows through a single `stripe` object imported from `$lib/server/stripe.ts`.

Get this file right once and every following lesson reads like "call `stripe.somethingSomething()`." Get it wrong — wrong API version, wrong import path, wrong place — and you'll spend hours chasing ghosts: missing fields on objects, secret keys leaking to the browser, production and local running against different Stripe behaviour. Five minutes of discipline now saves weeks later.

## The Principal Engineer lens

**One client. Server-only. Pinned version. Never `latest`.**

Stripe's Node SDK is stateless; constructing it is cheap. You still only do it once, in one file, because a single import path makes every grep find every caller. Pinning the API version — both in the `package.json` and in the `new Stripe(..., { apiVersion })` call — means Stripe can ship a breaking change tomorrow and your app won't notice until *you* decide to upgrade. Unpinned Stripe is a remote-controlled time bomb on someone else's release cadence.

Corollary: **no factory, no dependency-injection wrapper, no `getStripe()` helper.** The Stripe client isn't the kind of dependency you mock — in tests we'll hit Stripe's test mode directly (it's the whole point of test mode). Extra indirection here is ceremony with no payoff.

## Step 1 — Install the SDK (pinned)

From `app/`:

```bash
pnpm add stripe@22.0.2
```

Note the exact version, no caret. Open `app/package.json` and confirm:

```json
{
	"dependencies": {
		"stripe": "22.0.2"
	}
}
```

If pnpm added a `^` prefix (older pnpm configs do), strip it. The `save-prefix` we set in Lesson 1.1 should already default to exact versions.

Why this version? It's the latest stable Stripe Node SDK as of April 2026, and it's the one that types the `2026-03-25.dahlia` API version we'll pin below. Upgrade it when you *decide* to, not when npm decides for you.

## Step 2 — Add the env vars

Open `src/lib/server/env.ts` and confirm the three Stripe vars are already in the typed `env` object. We added them back in Lesson 2.1 as placeholders; they should look like this:

```ts
// src/lib/server/env.ts
import {
	PUBLIC_SUPABASE_URL,
	PUBLIC_SUPABASE_ANON_KEY,
	PUBLIC_APP_URL,
	PUBLIC_STRIPE_PUBLISHABLE_KEY
} from '$env/static/public';
import {
	SUPABASE_SERVICE_ROLE_KEY,
	STRIPE_SECRET_KEY,
	STRIPE_WEBHOOK_SECRET
} from '$env/static/private';

function required(name: string, value: string | undefined): string {
	if (!value || value.length === 0) {
		throw new Error(`Missing required env var: ${name}`);
	}
	return value;
}

export const env = {
	PUBLIC_SUPABASE_URL: required('PUBLIC_SUPABASE_URL', PUBLIC_SUPABASE_URL),
	PUBLIC_SUPABASE_ANON_KEY: required('PUBLIC_SUPABASE_ANON_KEY', PUBLIC_SUPABASE_ANON_KEY),
	PUBLIC_APP_URL: required('PUBLIC_APP_URL', PUBLIC_APP_URL),
	PUBLIC_STRIPE_PUBLISHABLE_KEY: required(
		'PUBLIC_STRIPE_PUBLISHABLE_KEY',
		PUBLIC_STRIPE_PUBLISHABLE_KEY
	),
	SUPABASE_SERVICE_ROLE_KEY: required('SUPABASE_SERVICE_ROLE_KEY', SUPABASE_SERVICE_ROLE_KEY),
	STRIPE_SECRET_KEY: required('STRIPE_SECRET_KEY', STRIPE_SECRET_KEY),
	STRIPE_WEBHOOK_SECRET: required('STRIPE_WEBHOOK_SECRET', STRIPE_WEBHOOK_SECRET)
} as const;
```

Notice `PUBLIC_STRIPE_PUBLISHABLE_KEY` imports from `$env/static/public` — that's the one Stripe key that is *meant* to reach the browser (it's used to render Stripe Elements if we ever add them). The other two — `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` — come from `$env/static/private` and never leave the server.

Make sure `app/.env` has real values:

```bash
STRIPE_SECRET_KEY=sk_test_51Ab...
STRIPE_WEBHOOK_SECRET=whsec_...
PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_test_51Ab...
```

And `app/.env.example` lists them with empty values (committed to git). You did this in Lesson 5.7 — double-check.

## Step 3 — Create `src/lib/server/stripe.ts`

This file is the entire setup. Create it:

```ts
// src/lib/server/stripe.ts
import Stripe from 'stripe';
import { env } from '$lib/server/env';

export const stripe = new Stripe(env.STRIPE_SECRET_KEY, {
	apiVersion: '2026-03-25.dahlia',
	typescript: true,
	appInfo: {
		name: 'Contactly',
		version: '0.1.0'
	}
});
```

Four things, each load-bearing:

- **`apiVersion: '2026-03-25.dahlia'`** — pin the wire format. Without this, you'd inherit whatever default version your Stripe account has set in the dashboard. That default can drift. By pinning in code you lock behaviour to what you tested.
- **`typescript: true`** — tells the SDK to prefer the most specific TypeScript types over the older `any`-heavy fallbacks. This lights up autocomplete for the pinned API version.
- **`appInfo`** — Stripe echoes this string in their logs. If you ever open a support ticket, they can grep their logs for "Contactly 0.1.0" and find your calls. Low effort, high payoff on the one day you need it.
- **Location: `$lib/server/`** — SvelteKit enforces that anything under `$lib/server/` *cannot* be imported into browser code. If you accidentally `import { stripe } from '$lib/server/stripe'` in a `.svelte` file, the build fails. That's the tripwire that keeps your secret key on the server.

That's the whole file. No factory, no `getStripe()`, no initialisation guard. Top-level `new Stripe(...)` runs once per server process and then you import `stripe` wherever you need it.

## Step 4 — A sanity check you can delete after

Drop a temporary file to prove the client works. Create `src/routes/(app)/debug-stripe/+page.server.ts`:

```ts
import type { PageServerLoad } from './$types';
import { stripe } from '$lib/server/stripe';

export const load: PageServerLoad = async () => {
	const prices = await stripe.prices.list({
		lookup_keys: ['plus_monthly'],
		active: true,
		limit: 1
	});
	return {
		found: prices.data.length,
		id: prices.data[0]?.id ?? null,
		amount: prices.data[0]?.unit_amount ?? null
	};
};
```

And `src/routes/(app)/debug-stripe/+page.svelte`:

```svelte
<script lang="ts">
	let { data } = $props();
</script>

<pre>{JSON.stringify(data, null, 2)}</pre>
```

Run `pnpm dev`, log in, visit `http://localhost:5173/debug-stripe`. You should see:

```json
{
	"found": 1,
	"id": "price_...",
	"amount": 1000
}
```

That confirms:

- The secret key is readable from `env`.
- The SDK can reach Stripe.
- The lookup key `plus_monthly` resolves to your $10 Plus price from Module 5.5.

Delete the `debug-stripe/` folder before committing. Debug routes must never ship — same rule as the Supabase debug page in Lesson 2.3.

## Step 5 — Why not a factory?

If you've seen "professional" Node tutorials, you might expect something like:

```ts
// ❌ Don't do this
export function getStripe() {
	return new Stripe(env.STRIPE_SECRET_KEY, { apiVersion: '2026-03-25.dahlia' });
}
```

Or worse, a dependency-injection container with a provider. Resist both.

- **We never need two clients.** There's one Stripe account, one secret key, one API version.
- **We never need to mock it.** Test mode is a real Stripe with real behaviour. Our integration tests hit it.
- **A singleton is trivially replaceable.** If we ever *do* need a factory (e.g. Stripe Connect with per-merchant keys), `sed -i 's/stripe/getStripe()/g'` takes ten seconds.

Premature abstraction in the wrong place is worse than no abstraction.

## Verify

- `pnpm list stripe` prints `stripe 22.0.2` (no caret, exact match).
- `src/lib/server/stripe.ts` exists and exports `stripe`.
- The debug page returns your `plus_monthly` price with `amount: 1000`.
- `pnpm check` passes with no type errors.
- Removing the `STRIPE_SECRET_KEY` value from `.env` and restarting dev gives a loud `Missing required env var: STRIPE_SECRET_KEY` — same pattern as Lesson 2.1.

## Common traps

- **Importing `stripe` in a `.svelte` or `+page.ts` file.** The build will fail because of the `$lib/server/` rule, but if you disable that protection (don't) or reach for `$env/dynamic/private` in a component (definitely don't), your secret key will ship to the browser. One leak, game over.
- **Skipping `apiVersion`.** The SDK will use whatever the SDK author hardcoded as "default," which changes when you upgrade. Your code works, then the SDK bumps a default, and now `subscription.items.data[0].price` has a new shape.
- **Using `process.env.STRIPE_SECRET_KEY` directly.** Works, bypasses the typed env layer, silently succeeds on empty strings. Use `env.STRIPE_SECRET_KEY` from `$lib/server/env` — always.
- **Installing `stripe` with a caret.** `^22.0.2` lets pnpm pull `22.9.0` on the next `install`, which could change types and break your build. Pin exact.
- **Constructing a fresh `new Stripe()` inside every handler.** Works, wastes no real resources, but scatters configuration. One file, one instance, imported.
