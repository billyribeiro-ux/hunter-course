# 6.2 — Stripe Webhooks & Events

> Stripe is the source of truth. Webhooks are how the truth reaches you.

## Why this matters

Customers will subscribe at 3 AM, cancel at 9 AM on a Saturday, and have their cards decline on a Tuesday at lunch. You need to know each of those happened without being awake, watching a dashboard, or polling Stripe every 30 seconds. Stripe's answer is webhooks: when something important happens, Stripe `POST`s a JSON payload to a URL you own. Your server updates its own database. Your app reflects reality.

Without webhooks you'd have two choices, both bad: poll Stripe's API constantly (expensive, slow, rate-limited) or believe whatever your local UI said last (wrong, because Stripe can change state on its own — payment failures, renewals, cancellations from the customer portal).

This lesson is conceptual. No code changes. We'll build the actual endpoint in 6.3, but the mental model has to be right first — webhooks are one of the two or three places where beginners consistently ship a real bug that only fires in production.

## The Principal Engineer lens

**Stripe owns the billing state. Your database owns a read cache of it.**

Your tables exist so your `/account` page can render in 20ms without hitting Stripe. They are not the authority. When there's a disagreement between your DB and Stripe, Stripe wins — always. The webhook is how you keep the cache close enough to reality that the disagreement never becomes visible to a user.

Corollary: **every webhook handler is idempotent, signature-verified, and fast.** Miss any of those three and you have a bug. We'll enforce each explicitly.

## Step 1 — What a webhook actually is

A webhook is "Stripe calls your URL." That's it. When an event happens on Stripe's side (subscription created, invoice paid, card declined), Stripe sends an HTTP `POST` to the endpoint URL you configured.

The request body is JSON — a Stripe `Event` object:

```json
{
	"id": "evt_1Nq7BzKJxYzAbcDef",
	"type": "customer.subscription.created",
	"created": 1714521600,
	"data": {
		"object": {
			"id": "sub_1Nq7...",
			"status": "active",
			"customer": "cus_O...",
			"items": { "data": [{ "price": { "lookup_key": "plus_monthly" } }] }
		}
	},
	"livemode": false
}
```

- **`id`** — unique event ID. Critical for idempotency (Step 4).
- **`type`** — the name of the thing that happened.
- **`data.object`** — the Stripe object in its new state, at the moment the event fired.
- **`livemode`** — `false` in test mode, `true` in live. Our `stripe listen` events are always `false`.

## Step 2 — The events Contactly cares about

Stripe fires hundreds of event types. We only handle six:

| Event type | What it means | What we do |
|---|---|---|
| `checkout.session.completed` | A customer finished Checkout. | Record the Stripe customer ID against our user. |
| `customer.subscription.created` | A new subscription exists. | Insert a row in `stripe_subscriptions`. |
| `customer.subscription.updated` | Status, price, or trial state changed. | Update the existing row. |
| `customer.subscription.deleted` | Subscription ended (cancelled, churned). | Mark the row `status: 'canceled'`. |
| `invoice.paid` | A renewal (or first charge) succeeded. | Optional: update `current_period_end`. |
| `invoice.payment_failed` | A card declined or bank bounced. | Flag the subscription as past-due. |

Everything else (disputes, payouts, customer updates) we ignore for now. We can add handlers later without changing the subscription UI — that's the nice thing about event-driven systems.

Why these six?

- `checkout.session.completed` is how we learn the Stripe `customer_id` for a user (more on this in Module 7).
- The three `customer.subscription.*` events give us the full lifecycle.
- The two `invoice.*` events cover renewals and the single worst UX moment in SaaS: a customer's card fails and we don't notice until they complain.

## Step 3 — Signature verification

Stripe's webhook URL is public. That means anyone on the internet can `POST` to it. So how do you know a request really came from Stripe and not from a curious attacker sending fake "subscription created" events to unlock Pro features?

Every webhook request has a `Stripe-Signature` header:

```
Stripe-Signature: t=1714521600,v1=abc123def456...
```

That signature is an HMAC-SHA256 of `${timestamp}.${rawBody}` using your `STRIPE_WEBHOOK_SECRET`. You compute the same HMAC on your side. If they match, the request is from Stripe and the body wasn't tampered with. If they don't, you reject it with a 400.

The Stripe SDK does this for you:

```ts
const event = stripe.webhooks.constructEvent(rawBody, signatureHeader, env.STRIPE_WEBHOOK_SECRET);
```

This one line does three things: verifies the signature, checks the timestamp is recent (within 5 minutes by default — rejects replays), and parses the JSON into a typed `Stripe.Event`. If any step fails, it throws.

Two things you must get right for this to work, both of which we'll see in 6.3:

- **The raw body, byte-for-byte.** HMAC hashes bytes. If SvelteKit parses the JSON before you get to hash it, the signature won't match. In 6.3 we use `await request.text()`, never `await request.json()`.
- **The correct secret.** The `whsec_...` from `stripe listen` is different from the one Stripe prints for a registered production endpoint. They don't interoperate. `.env` points to whichever one matches your current setup.

## Step 4 — Idempotency

Stripe delivers every event **at least once**, not exactly once. That means the same event ID might `POST` to your endpoint twice, or three times, or (in rare bad days) fifty times. Network retries, Stripe's internal retries after a 500 response, load balancer hiccups — all cause redeliveries.

If your handler is not idempotent, the same `customer.subscription.created` event creates three subscription rows, or the same `invoice.paid` bumps the period end three times. Neither is acceptable.

The fix is a small ledger. We'll build a table in Module 7:

```
stripe_events
  id          text primary key   -- the Stripe event id (evt_...)
  type        text
  received_at timestamptz
  processed_at timestamptz
```

The handler flow:

1. Start a transaction.
2. Try to insert the `event.id` into `stripe_events`. If it conflicts (already there), commit and return `200 OK`. We've seen this one before.
3. Otherwise, do the actual work (upsert the subscription row, etc.).
4. Stamp `processed_at`. Commit.

The primary-key conflict is the atomic check-and-set. No races, no double-writes, no "what if two webhook deliveries arrive at exactly the same time" worries.

In 6.3 we'll skip the ledger for now (we're just `console.log`-ing). It lands in Module 7 when we wire the real storage.

## Step 5 — The at-least-once mental model

Internalise this phrasing for the rest of the course:

> "My webhook handler will receive this event at least once. Writing it correctly means it produces the same outcome whether it's called 1 time or 100."

Pair this with the signature check and you've defeated both accidental duplicates and intentional replays.

Related: Stripe also supports an `Idempotency-Key` header on *outgoing* API calls (Checkout creation, etc.), to protect against double-charges when *we* retry. That's a separate mechanism; we'll meet it in Module 9.

## Step 6 — Handle fast, return 2xx quickly

Stripe considers a delivery "successful" if your endpoint returns any 2xx response within their timeout (roughly 30 seconds, depending on the event, but treat anything over a few seconds as trouble). Longer and Stripe retries with exponential backoff. Lots of retries mean your endpoint is flagged and eventually disabled.

The implication: **your webhook handler does the minimum amount of work, then returns 200.** If the work is expensive (send an email, regenerate a PDF, warm a cache), you put it on a queue and acknowledge the webhook immediately.

For Contactly, every handler is a single database upsert. That runs in 5–20ms. We'll return 200 synchronously and never think about queues. If the app grew — say we start emailing customers on failed payments — we'd introduce a background job. Not today.

## Step 7 — What happens when you return non-2xx

- **200–299**: Stripe marks the event delivered. Done.
- **400**: Usually signature verification failed. Stripe gives up *immediately* — no retries. This is what we want on a bad signature, because retries won't help a forged request.
- **500+ (or timeout)**: Stripe retries with exponential backoff for up to 3 days. After that the event goes into the "failed" bucket in the dashboard and a human has to replay it.

Our endpoint in 6.3 returns 400 on bad signature, 200 on everything else — *including* event types we don't handle. That last bit matters: if we returned 500 on "unknown type," Stripe would hammer us for three days over an event we're never going to care about. Acknowledge, log, move on.

## Step 8 — The event catalog as living documentation

Keep a flat list in your head — or better, a comment in the webhook handler — of exactly which events you handle and what they do. When a future you wonders "where do we handle `invoice.payment_failed`?", the answer should be `Cmd+F` away.

We'll structure 6.3's switch statement to make this impossible to miss: one `case` per event we care about, explicit, with a comment per case. No clever loops or dispatch tables — just boring code that reads like the table in Step 2.

## Common traps

- **Assuming webhooks fire exactly once.** They fire *at least* once. If your handler isn't idempotent you will double-insert on your first busy day.
- **Trusting `data.object` as the current state.** It's the state *at the moment the event fired*. If three updates happen in quick succession, the events may arrive out of order. For critical reads, re-fetch with `stripe.subscriptions.retrieve(id)` or use the `created` timestamp as a tiebreaker.
- **Skipping signature verification in dev because "it's just localhost."** Then production ships without it. Use it everywhere, including with `stripe listen` (which issues a real `whsec_` for you).
- **Returning 500 on "unknown event type."** Stripe will retry for three days. Return 200 and log.
- **Long-running work inside the handler.** Email sending, PDF generation, heavy queries — push to a job queue and return 200 first.

## Recap

Webhooks are Stripe's mechanism for pushing state changes to your server. You verify the signature, dedupe by event ID, do the minimum necessary work, and return 200. Six events matter to Contactly. With that mental model in place, the actual SvelteKit endpoint is fifty lines of code — and that's what we build next.
