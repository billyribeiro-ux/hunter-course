# 12.2 — Supabase to Production

> A new Supabase project. The same migrations. Secrets in the right places. Nothing clever.

## Why this matters

Our whole schema, RLS policies, and triggers live in `supabase/migrations/`. That directory is the blueprint. Production Supabase needs to be built from it — not from a manual "I'll recreate the tables in the dashboard" ritual. Anything that diverges between local and prod is a bug waiting to ship.

This lesson creates the production project, links it to the repo, and pushes every migration to it. Done right, you'll never click "New table" in the production dashboard.

## The Principal Engineer lens

**Migrations are the only way to change production.** Every schema change — always — goes through a migration file, PR review, CI, and then applied on merge. Never the dashboard. Never a one-off psql session. The migration log in git *is* the schema.

Corollary: **two Supabase projects, not two databases.** Production and local are separate Supabase *projects*, each with their own URL, anon key, service-role key, and JWT secret. The code never connects to both at once.

## Step 1 — Create the production project

- Go to https://supabase.com/dashboard → **New project**.
- Organisation: your personal one (you can upgrade to a team later).
- **Project name**: `contactly-prod`.
- **Database password**: generate a strong one; store it in your password manager (not `.env`).
- **Region**: closest to your primary user base.
- **Pricing plan**: Free tier is fine to start.

Creation takes ~2 minutes (Supabase provisions a dedicated Postgres instance). Leave the tab open.

## Step 2 — Capture the credentials

Once provisioned, grab three values from **Project Settings → API**:

- **URL** — e.g. `https://abcdefghij.supabase.co`. Save as `PUBLIC_SUPABASE_URL`.
- **anon public key** — the JWT that frontend code uses. `PUBLIC_SUPABASE_ANON_KEY`.
- **service_role key** (shown under "Service role — revealed only here") — `SUPABASE_SERVICE_ROLE_KEY`. This is the admin key; guard it.

And from **Settings → Database → Connection string** (direct connection, not pooler): `DATABASE_URL`. We'll need this to run migrations.

Paste them into a temporary scratch file — *not* into any `.env`. The values will be copied into Vercel (Module 12.3) and GitHub Actions (Module 12.4) secrets storage, never a checked-in file.

## Step 3 — Link the local repo to the prod project

From `app/`:

```bash
npx supabase@2.0.6 link --project-ref abcdefghij
# enter the DB password from Step 1 when prompted
```

Replace `abcdefghij` with the project ref (the subdomain before `.supabase.co`). This stores a `.temp/project-ref` file under `supabase/` locally; don't commit it.

Verify:

```bash
npx supabase projects list
# → contactly-prod should be marked as linked
```

## Step 4 — Dry-run the migration push

Before applying anything, see what *would* change:

```bash
npx supabase db push --dry-run
```

This prints every migration the CLI would apply. On a brand-new project, that's every file in `supabase/migrations/` in order. No errors expected.

If it errors — "migration X is out of order," for instance — investigate. A dry-run failure always beats a production failure.

## Step 5 — Apply the migrations

```bash
npx supabase db push
```

This runs every migration against the production DB. For our project that's:

1. `202X-01-XX_profiles_table.sql`
2. `202X-01-XX_contacts_table.sql`
3. `202X-01-XX_set_updated_at_function.sql`
4. `20260420000000_billing_tables.sql`

And a handful more depending on how you've organised them. All applied atomically per-file.

Verify by opening the Supabase dashboard → **Table editor** → `public` schema. You should see: `profiles`, `contacts`, `stripe_customers`, `stripe_subscriptions`, `stripe_events`, plus any you added along the way.

## Step 6 — Sanity-check RLS

Open `contacts` → **Policies** tab. You should see four policies (select, insert, update, delete), all scoped to `auth.uid() = user_id`. Repeat for `profiles` and `stripe_*`.

This is the one thing I verify *every time* I deploy a new environment. A migration that applies cleanly without its RLS policies is terrifying — the table exists, looks normal, and leaks data. Quick visual check averts a catastrophe.

## Step 7 — Enable email confirmations in production

Local dev has email confirmations disabled for convenience (Module 1.2). Production should require confirmation — otherwise your signup form becomes a spam vector.

In Supabase dashboard → **Authentication → Providers → Email**:

- Enable **Confirm email**: ON.
- **Site URL**: `https://contactly.app` (your production domain; we set this in 12.6).
- **Redirect URLs**: add `https://contactly.app/**` so confirmation emails route back correctly.

For the first week of operation, check the Authentication → Users list daily — confirm emails are being sent (Supabase has a default provider for small volumes) and users are actually confirming.

## Step 8 — Create the storage bucket (if needed)

Contactly core doesn't use Supabase Storage yet (contact avatars are deferred to an Extras lesson), but if we ever do, create the bucket in prod manually — it's the one piece not in migrations (yet; Supabase is adding storage-as-code for migrations).

**Storage → New bucket → `avatars` → Public**. Or skip until an Extras lesson actually needs it.

## Step 9 — Write down the production credentials, safely

Before closing the tab, confirm you've stored these four values in a password manager (1Password, Bitwarden, etc.) under a single entry named "Contactly — Supabase Production":

- Project URL
- Anon public key
- Service role key
- Database password
- Database connection string

Losing the service-role key means "rotate it in the dashboard." Losing the DB password means "reset it via dashboard → Database." Neither is catastrophic, but the rotation is a Thursday-afternoon task you'd rather not unplanned.

## Step 10 — What we deliberately did NOT do

- **Copy-pasted SQL into the Supabase SQL editor.** One-off SQL bypasses the migration log. The migration file *is* the change; running it via `supabase db push` is how it gets to production.
- **Re-used local credentials.** `PUBLIC_SUPABASE_URL` in production must point at `contactly-prod`, not `localhost:54321`. Obvious, easy to miss, catastrophic.
- **Enabled pooler mode for the app.** SvelteKit's server-side Supabase client uses the direct connection (session mode). Pooler mode (transaction mode) breaks `onAuthStateChange`. If you see weird auth dropouts in prod, double-check you're on session mode.
- **Set up Supabase branching (beta).** Their Git-linked branch databases are a great pattern but still evolving. We'll revisit once stable.

## Verify

- `npx supabase projects list` shows `contactly-prod` linked.
- `npx supabase db push --dry-run` prints "no migrations to apply."
- Supabase dashboard shows all expected tables in `public`.
- RLS is enabled on `profiles`, `contacts`, and all three `stripe_*` tables, each with the correct policies.
- Email confirmations are ON in prod auth settings.

## Common traps

- **Using the pooler URL in Vercel env vars.** Session-mode connections break; switch to the direct connection string.
- **Forgetting to enable email confirm.** Open signups become spam magnets within a week.
- **Rotating keys but not updating Vercel.** The app keeps trying old keys and fails silently. Rotate + update in lock-step.
- **Running `supabase db push` against local by accident.** Check `supabase projects list` first; confirm the linked project before pushing.

## Recap

Production Supabase exists, all migrations applied, RLS verified, email confirmations on, credentials stored. The DB is ready for app traffic. Next: the app itself, on Vercel.
