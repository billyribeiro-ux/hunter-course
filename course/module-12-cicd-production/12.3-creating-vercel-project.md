# 12.3 — Creating Vercel Project

> Connect the repo, paste env vars, set the adapter. Ten minutes to first deploy.

## Why this matters

Vercel is where SvelteKit's serverless runtime shines. The build adapter produces edge-friendly functions, the deploy model is atomic, and PR previews come for free once the repo is linked. Getting this right means every subsequent deploy is `git push` and waiting 90 seconds.

## The Principal Engineer lens

**Pick the runtime once, stick with it.** Vercel supports Node, Edge, and (for SvelteKit) a few hybrid modes. We pick Node for SSR routes and Edge for static — the defaults for `@sveltejs/adapter-vercel`. Don't customise until you measure a reason to.

Corollary: **env vars have three scopes (Production / Preview / Development).** Use all three. A live-mode Stripe key in Preview is a bug waiting to happen.

## Step 1 — Install the adapter

In `app/`:

```bash
pnpm add -D @sveltejs/adapter-vercel@5.5.4
```

Edit `svelte.config.js`:

```js
import adapter from '@sveltejs/adapter-vercel';
import { vitePreprocess } from '@sveltejs/vite-plugin-svelte';

export default {
	preprocess: vitePreprocess(),
	kit: {
		adapter: adapter({
			runtime: 'nodejs20.x'
		})
	}
};
```

The `nodejs20.x` pin matches what Vercel currently defaults to but lets us stay deterministic when they upgrade defaults.

## Step 2 — Create the Vercel project

- https://vercel.com/new → pick the GitHub repo `hunter-course` (or your fork).
- **Project name**: `contactly`.
- **Framework preset**: SvelteKit (should auto-detect).
- **Root directory**: `app/` — Vercel needs this because our app isn't at the repo root. Click **Edit** and set it.
- **Build command**: `pnpm build` (default).
- **Install command**: `pnpm install` (default).
- **Output directory**: (leave default — the adapter handles it).

Click **Deploy**. It will fail on the first try because env vars aren't set. That's fine — we fix that next.

## Step 3 — Wire up env vars

**Project → Settings → Environment Variables**. Add each one with the correct scope:

| Name | Production | Preview | Value source |
|---|---|---|---|
| `PUBLIC_SUPABASE_URL` | ✓ | ✓ | Module 12.2 prod project URL |
| `PUBLIC_SUPABASE_ANON_KEY` | ✓ | ✓ | Module 12.2 anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | ✓ | ✓ | Module 12.2 service role key |
| `DATABASE_URL` | ✓ | ✓ | Module 12.2 direct DB URL |
| `STRIPE_SECRET_KEY` | ✓ (`sk_live_`) | ✓ (`sk_test_`) | Dashboard → API keys |
| `STRIPE_WEBHOOK_SECRET` | ✓ (prod webhook) | ✓ (preview webhook) | Set after Module 12.5 |
| `PUBLIC_STRIPE_PUBLISHABLE_KEY` | ✓ (`pk_live_`) | ✓ (`pk_test_`) | Dashboard |
| `PUBLIC_APP_URL` | ✓ (`https://contactly.app`) | ✓ (`https://contactly-preview.vercel.app`) | Your domain |

Critical: **Production gets `sk_live_`; Preview gets `sk_test_`.** This is the single most important split in the whole table. Live keys on previews = real customers billed from test branches.

## Step 4 — The `PUBLIC_APP_URL` nuance

For preview deploys, Vercel assigns a unique URL per deployment (`contactly-git-feat-xyz-yourteam.vercel.app`). That URL is specific to one deploy. If we set `PUBLIC_APP_URL` to a fixed preview URL, every preview deploy misroutes callbacks.

Two options:

- **Accept the imprecision.** Set `PUBLIC_APP_URL` to a stable preview-environment URL like `contactly-preview.vercel.app` (the "latest preview" alias Vercel auto-assigns on every push). Stripe success URLs will route to that stable alias rather than the specific deploy. Works for most flows.
- **Compute at runtime.** Use `VERCEL_URL` (auto-injected) at server runtime as a fallback:

```ts
// src/lib/server/env.ts
export const env = {
	// ...
	PUBLIC_APP_URL:
		process.env.VERCEL_ENV === 'preview'
			? `https://${process.env.VERCEL_URL}`
			: required('PUBLIC_APP_URL', PUBLIC_APP_URL)
};
```

We recommend the second approach. A few lines of conditional logic gives per-deploy-accurate URLs for Stripe callbacks.

## Step 5 — Redeploy

Back in Vercel → Deployments → **⋯ → Redeploy** on the failed build. With env vars in place it should succeed.

Wait for "Ready." The deploy URL is `https://contactly-xxx.vercel.app`. Open it. You should see:

- The landing page (if we have one) or `/pricing` if that's the default.
- DevTools → Network: requests to `https://abcdefghij.supabase.co`, not localhost.
- No console errors referencing env vars.

## Step 6 — Attach a custom domain

Skip until you have one. When you do (Module 12.6), Vercel → Project → Settings → Domains → Add. Update the A/CNAME records at your registrar. Vercel auto-provisions TLS.

## Step 7 — Configure SvelteKit build output

Open Vercel → Deployments → latest → **Build Logs**. Skim for warnings. Two to act on if they appear:

- **"Large serverless function."** Look for accidental bundling of server-only deps into client code. Usually caused by an import path missing `$lib/server/`.
- **"Edge runtime is not supported for this route."** Our setup uses Node for all SSR, so this shouldn't occur. If it does, check `export const config` exports on `+page.server.ts` files — remove any `runtime: 'edge'` overrides.

## Step 8 — Preview deploy on next push

Go back to your local repo, make any small change (edit a README comment), push to a feature branch. Within 60 seconds Vercel creates a preview deploy and reports its URL as a GitHub status check on the PR.

Click through the preview URL. Log in with a test account. Create a contact. Everything should work against the production Supabase and test-mode Stripe.

This is the moment it all comes together — a PR can be reviewed against a live preview of the code.

## Step 9 — Protect the `main` branch

GitHub → Settings → Branches → **Add rule** for `main`:

- Require pull request reviews: 1 approval.
- Require status checks: Vercel preview deployment + (soon) GitHub Actions CI.
- Require branches to be up to date before merging.
- Include administrators (yes — you want the same rules for yourself).

This is the gate that makes the pipeline binding. Without it, anyone with push access can shove broken code to `main`.

## Step 10 — What we deliberately did NOT do

- **Use Vercel's built-in database.** It's Postgres-as-a-service, but our workflow is tied to Supabase. Two databases = twice the chances of drift.
- **Self-host.** Vercel's free tier is generous and the DX is outstanding. Self-hosting is an optimisation for usage levels we're years away from.
- **Enable Vercel Analytics.** Paid feature; Sentry or Plausible are better standalone options. Revisit when you have ~1k monthly users.

## Verify

- Production deploy is green and opens at `https://contactly-xxx.vercel.app`.
- A push to a feature branch produces a preview deploy URL.
- The preview deploy uses `sk_test_` for Stripe (inspect the HTML for `PUBLIC_STRIPE_PUBLISHABLE_KEY` — it should start with `pk_test_`).
- The production deploy uses `sk_live_` and `pk_live_`.
- `main` is branch-protected and requires the Vercel check to pass.

## Common traps

- **Forgetting to set the root directory to `app/`.** Vercel will look for `package.json` at repo root and fail.
- **Live Stripe keys in Preview scope.** Real customers billed from test branches. Double-check the scope column in the env var list.
- **Using `VERCEL_URL` in client code.** It's server-only. Client code gets `PUBLIC_APP_URL` from SvelteKit's `$env/static/public`.
- **Skipping branch protection on `main`.** Within a week someone — you or a collaborator — pushes directly. The rule is the guardrail.

## Recap

Vercel is live, env vars are scoped correctly, preview deploys are automatic, and `main` is protected. The app can deploy; the CI piece connecting GitHub Actions hasn't been wired yet — that's the next lesson.
