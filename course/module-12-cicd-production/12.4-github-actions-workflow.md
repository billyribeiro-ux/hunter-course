# 12.4 — GitHub Actions Workflow

> One YAML file. Typecheck, lint, build, e2e tests, migrate DB on main. Green before merge, green all the way to prod.

## Why this matters

Vercel already builds and deploys on every push. What it *doesn't* do: run your Playwright suite, your typecheck, your linter, or your migration dry-runs. GitHub Actions fills that gap. The workflow in this lesson is a load-bearing piece of your production safety net — it catches the regressions Vercel's build alone cannot.

## The Principal Engineer lens

**Fast feedback beats exhaustive coverage.** A 20-minute CI job gets ignored; a 3-minute job gets respected. Cache aggressively, parallelise where safe, skip what isn't worth the wall-clock time. Every second over 4 minutes is a second developers will work around.

Corollary: **test what you'll deploy.** The CI job should use the same Node version, same pnpm version, same lockfile as Vercel. If CI and Vercel disagree, something's off.

## Step 1 — The file layout

Create `.github/workflows/ci.yml` at the repo root:

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verify:
    runs-on: ubuntu-24.04
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v5

      - uses: pnpm/action-setup@v5
        with:
          version: 11.5.0

      - uses: actions/setup-node@v6
        with:
          node-version: 24.16.0
          cache: pnpm
          cache-dependency-path: app/pnpm-lock.yaml

      - name: Install deps
        working-directory: app
        run: pnpm install --frozen-lockfile
        env:
          SKIP_SEED: '1'

      - name: Typecheck
        working-directory: app
        run: pnpm check

      - name: Lint
        working-directory: app
        run: pnpm lint

      - name: Build
        working-directory: app
        run: pnpm build
        env:
          PUBLIC_SUPABASE_URL: http://localhost:54321
          PUBLIC_SUPABASE_ANON_KEY: ${{ secrets.TEST_SUPABASE_ANON_KEY }}
          PUBLIC_STRIPE_PUBLISHABLE_KEY: pk_test_dummy
          PUBLIC_APP_URL: http://localhost:5173
          SUPABASE_SERVICE_ROLE_KEY: ${{ secrets.TEST_SUPABASE_SERVICE_ROLE_KEY }}
          STRIPE_SECRET_KEY: ${{ secrets.TEST_STRIPE_SECRET_KEY }}
          STRIPE_WEBHOOK_SECRET: whsec_dummy

  e2e:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    needs: verify
    steps:
      - uses: actions/checkout@v5

      - uses: pnpm/action-setup@v5
        with:
          version: 11.5.0

      - uses: actions/setup-node@v6
        with:
          node-version: 24.16.0
          cache: pnpm
          cache-dependency-path: app/pnpm-lock.yaml

      - name: Install Supabase CLI
        run: |
          curl -fsSL https://github.com/supabase/cli/releases/download/v2.102.0/supabase_linux_amd64.tar.gz \
            | tar xz && sudo mv supabase /usr/local/bin

      - name: Start Supabase
        working-directory: app
        run: supabase start

      - name: Install app deps
        working-directory: app
        run: pnpm install --frozen-lockfile
        env:
          SKIP_SEED: '1'

      - name: Install Playwright browsers
        working-directory: app
        run: pnpm exec playwright install --with-deps chromium

      - name: Run e2e
        working-directory: app
        run: pnpm test
        env:
          PUBLIC_SUPABASE_URL: http://localhost:54321
          PUBLIC_SUPABASE_ANON_KEY: ${{ secrets.TEST_SUPABASE_ANON_KEY }}
          SUPABASE_SERVICE_ROLE_KEY: ${{ secrets.TEST_SUPABASE_SERVICE_ROLE_KEY }}
          PUBLIC_STRIPE_PUBLISHABLE_KEY: ${{ secrets.TEST_STRIPE_PUBLISHABLE_KEY }}
          STRIPE_SECRET_KEY: ${{ secrets.TEST_STRIPE_SECRET_KEY }}
          STRIPE_WEBHOOK_SECRET: whsec_dummy
          PUBLIC_APP_URL: http://localhost:5173

      - name: Upload Playwright report on failure
        if: failure()
        uses: actions/upload-artifact@v5
        with:
          name: playwright-report
          path: app/playwright-report
          retention-days: 7
```

Ten steps across two jobs. Let's walk through the interesting ones.

## Step 2 — Why two jobs, not one

The `verify` job is quick (~2 min): typecheck, lint, build. These catch 80% of regressions and produce fast feedback.

The `e2e` job is slower (~5-8 min): it spins up local Supabase, installs Chromium, runs the full Playwright suite. We gate it on `needs: verify` so a trivially broken PR fails fast without paying for Playwright.

Splitting jobs also lets us parallelise later if either gets slow (the verify job could split into typecheck-vs-build-vs-lint with near-zero overhead).

## Step 3 — `concurrency: cancel-in-progress`

When you push three commits to a PR in quick succession, GitHub by default starts three CI runs. Two of them are wasted — you only care about the latest. `cancel-in-progress: true` kills the earlier runs automatically. Saves minutes of wall-clock and a non-trivial amount of Actions budget.

## Step 4 — The secrets

Add these to GitHub → **Settings → Secrets and variables → Actions → New repository secret**:

- `TEST_SUPABASE_ANON_KEY` — the anon key printed by `supabase start` locally. Copy it once; it's stable across projects.
- `TEST_SUPABASE_SERVICE_ROLE_KEY` — same source.
- `TEST_STRIPE_SECRET_KEY` — a `sk_test_...` key. Safe to commit-adjacent in the sense that test-mode keys can't bill real money. Still, secret storage is correct.
- `TEST_STRIPE_PUBLISHABLE_KEY` — the `pk_test_...` companion.

Note: **we never put `sk_live_...` in GitHub secrets.** CI has no business touching live keys. Production deploy happens on Vercel, which has its own secrets.

## Step 5 — Pin everything

Every version in the YAML is pinned:

- `ubuntu-24.04` (not `ubuntu-latest`).
- `pnpm 11.5.0`.
- `node-version: 24.16.0`.
- `supabase 2.102.0`.
- Action versions (`@v5`, `@v6`, `@v5`, etc.).

`latest` is a time bomb. The day GitHub rotates `ubuntu-latest` to 24.04, apt package names change and your workflow mysteriously fails. Pin and upgrade deliberately.

## Step 6 — The build step's env vars

The `build` step needs env vars even though it's not *running* — SvelteKit validates at build time whether certain `$env/static/*` imports are valid, and the typed `env` wrapper (Module 2.1) throws on missing values at load time.

For CI we pass dummy-but-valid-shaped values. A fake `whsec_dummy` is fine because no webhook verification runs during build. Real values are in Vercel and are used at runtime there.

## Step 7 — Required status checks

Back in GitHub → **Settings → Branches → main → Edit rule → Require status checks**. Add:

- `CI / verify`
- `CI / e2e`
- `Vercel – contactly` (the preview deploy check)

Now a PR can't merge unless all three are green. The pipeline from 12.1 becomes binding.

## Step 8 — The production deploy path

On a merge to `main`, Vercel deploys to prod automatically. We want to *also* push migrations before the app rolls out.

Add a third job to `ci.yml`, gated on `main`:

```yaml
  migrate-prod:
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-24.04
    needs: [verify, e2e]
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v5

      - name: Install Supabase CLI
        run: |
          curl -fsSL https://github.com/supabase/cli/releases/download/v2.102.0/supabase_linux_amd64.tar.gz \
            | tar xz && sudo mv supabase /usr/local/bin

      - name: Apply migrations to prod
        working-directory: app
        run: |
          supabase link --project-ref ${{ secrets.PROD_SUPABASE_PROJECT_REF }} \
            --password "${{ secrets.PROD_SUPABASE_DB_PASSWORD }}"
          supabase db push --include-all
        env:
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
```

Two new secrets:

- `PROD_SUPABASE_PROJECT_REF` — the `abcdefghij` subdomain from 12.2.
- `PROD_SUPABASE_DB_PASSWORD` — the DB password from 12.2.
- `SUPABASE_ACCESS_TOKEN` — personal access token from https://supabase.com/dashboard/account/tokens.

Migrations apply *before* Vercel finishes the prod deploy, so new code meets a ready schema. If migration fails, the job fails — Vercel still deploys, but with the old schema. Not ideal, but the *next* deploy will retry the migration. For safer ordering, move migration to a pre-deploy Vercel hook (Vercel calls this feature "Build Hook"); overkill for us right now.

## Step 9 — Post-deploy smoke test

Add a final job:

```yaml
  smoke:
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    needs: migrate-prod
    runs-on: ubuntu-24.04
    timeout-minutes: 3
    steps:
      - name: Wait for Vercel
        run: sleep 60
      - name: Hit health endpoint
        run: |
          curl --fail --retry 10 --retry-delay 6 \
            https://contactly.app/api/health
```

The `sleep 60` is a coarse wait for Vercel's build to finish (Vercel's build usually completes in under a minute for our app). The `curl --fail` explodes on non-2xx; the workflow fails. The health endpoint itself is Module 12.6 material.

## Step 10 — What's in the `.github/` dir once this module ends

```
.github/
└── workflows/
    ├── ci.yml          # this file
    └── preview-comment.yml  # optional: auto-comments preview URL on PRs
```

Some teams add a Dependabot config next (`.github/dependabot.yml`) to auto-bump deps. Nice-to-have; not in scope for this module.

## Verify

- Push a branch with a trivial change → `verify` + `e2e` jobs run → both green → Vercel preview deploy works.
- Introduce a type error in a component → `verify` fails in ~90 seconds.
- Introduce a broken RLS policy → `e2e` fails (the cross-user isolation test from Module 11.3).
- Merge a green PR to `main` → `migrate-prod` and `smoke` run, both green, Vercel shows production deployed.

## Common traps

- **Using `ubuntu-latest`.** Ghost failures on GitHub runner updates. Pin the version.
- **Forgetting `--frozen-lockfile` in CI.** pnpm might fetch newer deps than your lockfile records, and CI green ≠ your production dep tree. Always frozen.
- **Sharing a `TEST_STRIPE_SECRET_KEY` with local dev.** Isolating them means a rotation in CI doesn't disrupt your laptop.
- **No concurrency group.** Five pushes to a PR = five parallel runs, all charging Actions minutes.
- **Skipping the smoke test.** A green deploy that doesn't actually serve is invisible until a user complains.

## Recap

`ci.yml` is ~120 lines and does everything: verify, test, migrate, smoke. Every PR is gated; every merge deploys. The pipeline is now the gatekeeper. Next: Stripe and Supabase in production mode.
