# 12.1 — CI/CD Pipeline Overview

> Every push runs every check. Every merge ships. Zero surprises in production.

## Why this matters

Shipping without CI/CD is a series of small fires you learn to live with: forgotten migrations, unrun tests, mismatched env vars, "it works on my machine." Shipping *with* a well-tuned pipeline is boring — and that's exactly the point. A boring deploy is a correct one.

Before we build the pipeline, we need to agree on what it *does*. This lesson is a whiteboard sketch: the stages, the systems they touch, and the points where things can go wrong. The next five lessons implement it.

## The Principal Engineer lens

**The pipeline is the runbook you don't have to run.** Everything a human would manually verify — migrations apply cleanly, tests pass, types compile, the app boots — is codified as a CI check. Humans review code; the pipeline reviews correctness.

Corollary: **one pipeline, two environments: preview and production.** Every pull request spins up a preview; every merge to `main` promotes to production. No separate "staging" environment — it's cost, duplication, and drift. If you need more isolation, spin up more preview branches.

## Step 1 — The systems involved

Contactly's production stack, end-to-end:

- **GitHub** — source of truth for code.
- **GitHub Actions** — runs CI (typecheck, tests, lint, build).
- **Vercel** — hosts the SvelteKit app (preview + production).
- **Supabase Cloud** — hosts Postgres + Auth for production (and staging if we add it).
- **Stripe (live mode)** — handles payments in production.

Every deploy touches four of these. The pipeline is the glue.

## Step 2 — The stages

```
push → PR opened ──► [checks] ──► reviewer approves ──► merge to main ──► [production deploy]
                    │                                                    │
                    ├─ typecheck (pnpm check)                            ├─ supabase db push
                    ├─ lint (pnpm lint)                                   ├─ vercel deploy --prod
                    ├─ unit tests (pnpm test:unit, if any)               └─ smoke test prod
                    ├─ e2e tests (Playwright)
                    └─ preview deploy (Vercel)
```

Every box is a required GitHub status check. If any fails, merging is blocked. That's the only mechanism that keeps things honest.

## Step 3 — The migration question

Supabase migrations are the scariest part of any deploy. Get a migration wrong and you've either:

- Locked a table for 5 minutes during peak hours.
- Added a NOT NULL column to a table with existing data and broken inserts.
- Forgotten to update RLS policies and leaked data.

Our pipeline defends in three ways:

1. **Every migration runs in CI against a fresh Supabase first** (via the e2e step). If the migration fails, CI fails before the merge.
2. **Migrations are applied on `main` merge, BEFORE the app deploys.** If the migration fails in prod, the old app keeps running — no broken new code meets a broken new schema.
3. **Every migration is reversible or idempotent.** See Module 7.1's rollback note. For risky changes (dropping a column, changing a constraint), we ship the change in two steps: "new column added" in PR N, "old column removed" in PR N+1. Never both at once.

## Step 4 — The environment matrix

Four environments, from laptops to production:

| Environment | Supabase | Stripe | Vercel |
|---|---|---|---|
| Local dev | `supabase start` (Docker) | Test mode | `pnpm dev` |
| CI | `supabase start` (GitHub Actions) | Test mode | Headless Playwright |
| Preview | Branch DB (Supabase Cloud) | Test mode | Preview URL |
| Production | Prod DB (Supabase Cloud) | Live mode | `contactly.app` |

Notice: **only production talks to Stripe live mode.** Everything else uses test mode, including previews. The test/live split at Stripe means we can't accidentally bill real customers from a preview branch.

## Step 5 — Secrets management

Each environment needs different secrets. The principle: **secrets live in their environment's dashboard, never in code, never in a shared place.**

- Local dev → `app/.env` (gitignored).
- CI → GitHub Actions secrets (encrypted, scoped to the repo).
- Preview → Vercel env vars (scoped to Preview environments).
- Production → Vercel env vars (scoped to Production environment).

One rule: **no secret is ever pasted into more than one of those four places.** If the same `STRIPE_SECRET_KEY` is in both GitHub Actions and Vercel, you've got two copies that can drift. Instead: CI uses a test-mode key; Vercel preview uses a test-mode key; Vercel production uses the live key. All different.

## Step 6 — Deploy cadence

On `main`:

1. GitHub Actions runs the full CI suite (same as on PRs).
2. If CI passes, the workflow calls `supabase db push` against the production DB.
3. Then it triggers `vercel deploy --prod`.
4. A final step hits `https://contactly.app/api/health` and fails the pipeline if the response isn't 200. (The health endpoint is a 5-line `+server.ts` returning `{ ok: true }` plus a trivial DB query to prove the DB connection works.)

Four steps. Every one of them is observable in GitHub's UI. If anything looks off post-deploy, the log tells you which step did it.

## Step 7 — Rollback

Vercel ships atomically: every deploy is a new immutable artifact. Rolling back is one click in Vercel's dashboard — promote the previous deploy to production.

Rolling back the *database* is harder. Postgres doesn't undo a migration automatically. Our mitigation: migrations are reviewed, run in CI first, and risky ones are split across PRs. Still, if a bad migration lands, we restore from Supabase's automatic daily backup (retention: 7 days on the free tier, longer on paid tiers).

Takeaway: **code rollback is a click; schema rollback is a backup restore.** Design for it by shipping schema changes conservatively.

## Step 8 — Observability

Every deploy emits a GitHub Deployment event, which Vercel status-checks. After the deploy we want:

- **Error tracking** (Sentry, or Vercel's built-in error monitoring). Not covered in this course; add once you have real users.
- **Stripe dashboard** — for payment events. Already covered.
- **Supabase logs** — for DB query issues. Built-in.

For our first production deploy, GitHub + Vercel + Supabase + Stripe dashboards together are enough. Add Sentry on the day you have paying customers.

## Step 9 — What we're NOT doing

Things big orgs have that we don't need:

- **Separate staging environment.** PR previews fill the role.
- **Blue-green deploys.** Vercel's atomic deploys are instant; the window for partial failure is milliseconds.
- **Feature flags.** Clear commits + small PRs keep reversibility high. Add flags when you have runtime-critical toggles.
- **Canary releases.** Same — not worth the complexity for a two-digit-user app.
- **A dedicated SRE playbook.** The Vercel dashboard + Supabase dashboard + this pipeline *is* the playbook.

Every one of these becomes valuable at scale. Adding them now is premature ops.

## Common traps

- **Conflating CI and CD.** CI is "does this code build + test clean?" CD is "deploy it." Separate stages, separate failure modes.
- **Sharing secrets across environments "to save time."** Inevitably one of them gets a different value and you spend an afternoon debugging env drift.
- **Skipping the post-deploy health check.** A deploy that builds but doesn't actually serve is invisible until a user complains.
- **Designing for 100-developer team rituals while building a 1-developer app.** Optimise for the team size you *have*.
