# 7.3 — Customers Service

> Every user becomes a Stripe customer exactly once, exactly when they need to.

## Why this matters

Before a user can pay, Stripe needs a `Customer` record for them. You have three choices when to create it:

1. **At signup.** Every new user immediately gets a Stripe customer.
2. **At first checkout.** Create lazily, only when they click "Upgrade."
3. **Never explicitly — let `checkout.sessions.create` do it.** Stripe will create a customer and attach them.

Option 3 is the trap: Stripe will create a *new* customer every time, and you end up with duplicates for the same user. Option 1 burns Stripe API calls on users who'll never pay. Option 2 is the sweet spot — lazy creation, one customer per user, and a service function that's safe to call any number of times.

This lesson builds that function.

## The Principal Engineer lens

**Idempotent "get-or-create" is the most common billing primitive.** It appears at checkout, at portal creation, at webhook handling ("did we already mirror this customer?"). Write it once, carefully, and never again.

Corollary: **concurrency is a real risk.** If a user double-clicks "Upgrade," two requests can try to create a customer in parallel. Your function has to survive that without duplicating the Stripe customer or the DB row.

## Step 1 — The contract

Create `src/lib/server/billing/customers.ts`:

```ts
// src/lib/server/billing/customers.ts
import { stripe } from '$lib/server/stripe';
import type { SupabaseClient } from '@supabase/supabase-js';
import type { Database } from '$lib/types/db';

type Admin = SupabaseClient<Database>;

export async function getOrCreateStripeCustomer(
	admin: Admin,
	userId: string,
	email: string
): Promise<string> {
	// 1. Fast path: already mirrored.
	const existing = await admin
		.from('stripe_customers')
		.select('stripe_customer_id')
		.eq('user_id', userId)
		.maybeSingle();

	if (existing.error) throw existing.error;
	if (existing.data) return existing.data.stripe_customer_id;

	// 2. Slow path: create in Stripe.
	const customer = await stripe.customers.create(
		{
			email,
			metadata: { user_id: userId }
		},
		{
			// Idempotency-Key on Stripe's side: if two concurrent requests
			// use the same key, Stripe returns the *same* customer, not two.
			idempotencyKey: `create-customer:${userId}`
		}
	);

	// 3. Mirror to DB. Unique constraint on stripe_customer_id protects
	//    against the rare double-insert race.
	const inserted = await admin
		.from('stripe_customers')
		.insert({ user_id: userId, stripe_customer_id: customer.id })
		.select('stripe_customer_id')
		.single();

	if (inserted.error) {
		// Likely another request won the race and inserted first.
		// Re-read.
		const retry = await admin
			.from('stripe_customers')
			.select('stripe_customer_id')
			.eq('user_id', userId)
			.single();
		if (retry.error) throw retry.error;
		return retry.data.stripe_customer_id;
	}

	return inserted.data.stripe_customer_id;
}
```

Three defences against concurrency, stacked.

## Step 2 — Defence #1: `idempotencyKey` on Stripe

Stripe honours an `Idempotency-Key` header on every write request. If two requests arrive with the same key within 24 hours, Stripe runs the operation once and returns the same result to both.

Our key is `create-customer:${userId}`. Any two concurrent "get-or-create for user X" calls share the key → Stripe returns the same Customer object to both → we only ever have one Customer per user *on Stripe's side*.

This is the most important line in the file. Without it, two clicks of "Upgrade" at the exact same moment can create two customers, and you're now in duplicate-cleanup land.

## Step 3 — Defence #2: DB unique constraint

From Module 7.1's migration:

```sql
create table public.stripe_customers (
	user_id uuid primary key references auth.users(id) on delete cascade,
	stripe_customer_id text not null unique,
	...
);
```

`user_id primary key` + `stripe_customer_id unique`. If both racing requests somehow survive Stripe's idempotency (e.g. clock skew, cache miss), one of the two INSERTs hits a unique violation and errors. We catch the error, re-SELECT, and return the other request's winner.

## Step 4 — Defence #3: Fast-path SELECT first

Before hitting Stripe at all, we check our DB. For 99.9% of "repeat" calls (every checkout after the first), we return in a single SELECT without touching Stripe.

Order matters: **cheapest defence first.** SELECT → Stripe (with idempotency) → INSERT (with unique) → re-SELECT (on conflict).

## Step 5 — Why we pass the `admin` client in

The service takes `admin: SupabaseClient` as an argument rather than importing it. Three reasons:

- **Testability.** In Module 11 we can pass a mock admin client.
- **Explicit trust.** The caller is stating "I have a service-role client and I'm authorising this write." If the function imported `locals.supabaseAdmin` internally, it'd be unclear whether it's safe to call from RLS-respecting contexts.
- **Webhook compatibility.** Webhook handlers have their own `admin` client (the user-scoped one doesn't exist there — no session). Passing it in makes both call-sites work the same way.

## Step 6 — Mirroring customers created by webhooks

Not every customer is created by our `getOrCreateStripeCustomer`. Sometimes a webhook arrives for a customer we haven't mirrored yet — e.g., a customer created via Stripe Dashboard manually, or by a migration script. Add a symmetric helper:

```ts
// src/lib/server/billing/customers.ts (append)

export async function upsertStripeCustomer(
	admin: Admin,
	userId: string,
	stripeCustomerId: string
): Promise<void> {
	const { error } = await admin
		.from('stripe_customers')
		.upsert(
			{ user_id: userId, stripe_customer_id: stripeCustomerId },
			{ onConflict: 'user_id' }
		);
	if (error) throw error;
}
```

This is used in the webhook handler when we see `customer.created` and the metadata has a `user_id`. Simple, idempotent, fire-and-forget from the webhook's perspective.

## Step 7 — Looking up a user from a Stripe customer ID

Webhooks arrive with `stripe_customer_id` but not `user_id`. We need the reverse lookup:

```ts
// src/lib/server/billing/customers.ts (append)

export async function findUserIdByStripeCustomer(
	admin: Admin,
	stripeCustomerId: string
): Promise<string | null> {
	const { data, error } = await admin
		.from('stripe_customers')
		.select('user_id')
		.eq('stripe_customer_id', stripeCustomerId)
		.maybeSingle();

	if (error) throw error;
	return data?.user_id ?? null;
}
```

If this returns `null`, we've got a webhook for an unknown customer — either from a different environment (misconfigured webhook) or a customer created outside our flow. The webhook handler logs and returns 200 (don't let Stripe retry a lost cause forever).

## Step 8 — What we deliberately did NOT do

- **Store the customer's email.** Supabase `auth.users.email` already has it. Mirroring means updating on email change — avoid.
- **Store the customer's billing address.** Stripe manages it. If we ever need to render it (e.g., on an invoice preview), we fetch on demand.
- **Create a customer at signup.** Feels tidy, but most users never upgrade. We'd be padding Stripe's customer count and burning API quota for nothing.

Every "I won't mirror that" decision is a future migration we don't have to write.

## Step 9 — A realistic call-site

When the user clicks "Upgrade to Plus" in Module 9, the server-side handler starts like this:

```ts
import { getOrCreateStripeCustomer } from '$lib/server/billing/customers';

export const startCheckout = command(schema, async ({ lookupKey }) => {
	const { user, supabaseAdmin } = await requireUser(getRequestEvent());
	const customerId = await getOrCreateStripeCustomer(
		supabaseAdmin,
		user.id,
		user.email!
	);
	// ...create Checkout Session with `customer: customerId`
});
```

Three lines. All the concurrency and idempotency complexity is in the service, invisible here.

## Verify

- Calling `getOrCreateStripeCustomer` twice in a row for the same user returns the same ID.
- Calling it concurrently (e.g., `Promise.all([...])`) returns the same ID to all callers.
- A row appears in `public.stripe_customers` with the expected `user_id`.
- The Stripe dashboard's Customers tab shows exactly one customer per local user, with `metadata.user_id` set.
- Deleting a Supabase user also deletes the `stripe_customers` row (thanks to `on delete cascade`). (The Stripe customer remains — intentional; Stripe retains for auditing.)

## Common traps

- **Skipping `idempotencyKey`.** Double-click → two customers → reconciliation hell. This one header is non-negotiable.
- **Using the user-scoped Supabase client here.** RLS blocks writes to `stripe_customers` for end users (we deliberately omitted the INSERT policy). Use admin.
- **Throwing on unique-violation instead of re-reading.** The violation means "someone else won the race" — that's a success condition, not an error.
- **Storing `user.email` in the DB row.** Supabase has it. One source of truth per field.

## Recap

`getOrCreateStripeCustomer` is 20 lines with three concurrency defences. Most billing bugs happen when people skip one of them. With customers sorted, the last service piece is subscriptions — the thing customers actually pay for.
