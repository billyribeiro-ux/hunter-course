# 7.2 — Products Service

> The thin layer that turns "what tiers do we offer?" into a single, cached function call.

## Why this matters

The pricing page, the upgrade buttons, the "You're on Plus" indicator — they all ask the same question: *what are our current tiers and their prices?* The lazy approach: call `stripe.prices.list()` from wherever you need it. That's 3–5 network hops per pricing-page render, rate limits in your future, and four slightly-different transformations of the same data scattered across the codebase.

The principled approach: **one function, one shape, one cache.** Everyone asks the service; the service handles Stripe and caching. Swap Stripe for Paddle tomorrow? Change one file.

## The Principal Engineer lens

**Services own the translation between "Stripe's world" and "our app's world."** Stripe's `Price` has 40 fields; we need 6. Stripe nests `recurring.interval` two levels deep; our UI wants a flat `interval: 'monthly' | 'yearly'`. The service is where we pay that translation cost exactly once.

Corollary: **no Stripe types leak into UI components.** If a `+page.svelte` file imports from `'stripe'`, something's wrong. The service returns our types, components render them.

## Step 1 — Define the DTO

"DTO" = Data Transfer Object. A small, purpose-built shape for crossing layers. Create `src/lib/server/billing/types.ts`:

```ts
// src/lib/server/billing/types.ts
import type { TierId, Interval } from '$lib/config/pricing';

export interface TierPrice {
	lookupKey: string;         // e.g. 'plus_monthly'
	interval: Interval;         // 'monthly' | 'yearly'
	unitAmount: number;         // cents, e.g. 1000 for $10.00
	currency: string;           // 'usd'
	stripePriceId: string;      // 'price_...' — used only when creating checkout sessions
}

export interface Tier {
	id: TierId;                 // 'free' | 'plus' | 'pro'
	name: string;
	description: string;
	contactLimit: number | null; // null = unlimited
	prices: TierPrice[];        // [] for free, [monthly, yearly] otherwise
}
```

A few deliberate choices:

- **Amounts are in cents (integers).** Floats and money don't mix. `1000` means $10.00. The UI formats; never the service.
- **We do surface `stripePriceId`.** The one place code needs it is `stripe.checkout.sessions.create({ line_items: [{ price }] })` — that `price` must be a Stripe ID. This is the single authorised leak.
- **`contactLimit: null` for unlimited.** Pro tier. Module 10's gating code checks `limit == null || count < limit`.

## Step 2 — Write the service

Create `src/lib/server/billing/products.ts`:

```ts
// src/lib/server/billing/products.ts
import { stripe } from '$lib/server/stripe';
import { TIERS, type Interval, type TierId } from '$lib/config/pricing';
import type { Tier, TierPrice } from './types';

// In-process cache — fine for a single Node server.
// Module 12 discusses edge-runtime caching.
let cache: { value: Tier[]; expiresAt: number } | null = null;
const TTL_MS = 5 * 60 * 1000; // 5 minutes

export async function listTiers(): Promise<Tier[]> {
	if (cache && cache.expiresAt > Date.now()) return cache.value;

	const allLookupKeys = TIERS
		.flatMap((t) => Object.values(t.prices))
		.filter(Boolean);

	const prices = allLookupKeys.length
		? (
				await stripe.prices.list({
					lookup_keys: allLookupKeys,
					active: true,
					expand: ['data.product']
				})
			).data
		: [];

	const byLookup = new Map(prices.map((p) => [p.lookup_key!, p]));

	const tiers: Tier[] = TIERS.map((t) => ({
		id: t.id,
		name: t.name,
		description: t.description,
		contactLimit: t.contactLimit,
		prices: Object.entries(t.prices)
			.map(([interval, lookupKey]): TierPrice | null => {
				const p = byLookup.get(lookupKey);
				if (!p) return null;
				return {
					lookupKey,
					interval: interval as Interval,
					unitAmount: p.unit_amount ?? 0,
					currency: p.currency,
					stripePriceId: p.id
				};
			})
			.filter((x): x is TierPrice => x !== null)
	}));

	cache = { value: tiers, expiresAt: Date.now() + TTL_MS };
	return tiers;
}

export async function findTierByLookupKey(
	lookupKey: string
): Promise<{ tier: Tier; price: TierPrice } | null> {
	const tiers = await listTiers();
	for (const tier of tiers) {
		const price = tier.prices.find((p) => p.lookupKey === lookupKey);
		if (price) return { tier, price };
	}
	return null;
}

export function findTierById(id: TierId, tiers: Tier[]): Tier | undefined {
	return tiers.find((t) => t.id === id);
}

export function invalidateTiersCache(): void {
	cache = null;
}
```

Worth stopping on a few lines.

## Step 3 — Why cache for 5 minutes

Stripe's `prices.list` is cheap (tens of ms) but not free. On a pricing page with 1,000 concurrent visitors, 1,000 calls/sec is wasteful *and* counts toward Stripe's rate limit (100 read ops/sec in test mode).

A 5-minute in-process cache means:

- Each server instance calls Stripe at most once per 5 minutes for this data.
- Price changes propagate within 5 minutes — acceptable; price changes are planned events.
- If a price urgently needs to propagate (e.g., a bug fix), call `invalidateTiersCache()` from a webhook handler.

**Don't over-engineer the cache.** A `Map` with a timestamp is enough until you have multiple server instances needing coherence. When you do (Module 12), a 5-minute stale cache with a `revalidate-if-webhook` fallback beats Redis-of-death.

## Step 4 — Why we don't cache on the Stripe side

Stripe's SDK doesn't cache by design — it assumes every call is fresh. That's the right default for an SDK. Caching is a *domain* concern (how fresh does *this* app need *this* data?), so it belongs in our service, not in the client.

## Step 5 — The "build from `TIERS`, hydrate with Stripe" pattern

Notice we start from our static `TIERS` config (Module 5.5) and look up Stripe prices *by lookup key*. Not the other way round ("list all Stripe prices, match to tiers").

Why: **our app's pricing shape is intentional; Stripe's is emergent.** A Stripe account might have orphaned test prices lying around. Our `TIERS` array is the declaration of what we offer today. Starting from it means:

- Missing lookup keys surface as missing `prices[]` entries — the UI can show "temporarily unavailable" or we can throw.
- Orphaned Stripe prices are invisible to our app.

If `prices.length === 0` for a paid tier, something's wrong with the seed. Module 8.2's seed script has to be run (or re-run).

## Step 6 — Add a guard for "no paid tier available"

In `src/lib/server/billing/products.ts`, export a helper:

```ts
export async function assertAllPaidTiersSeeded(): Promise<void> {
	const tiers = await listTiers();
	for (const t of tiers) {
		if (t.id === 'free') continue;
		const expected = Object.keys(
			TIERS.find((x) => x.id === t.id)?.prices ?? {}
		).length;
		if (t.prices.length !== expected) {
			throw new Error(
				`Tier ${t.id} expected ${expected} prices, got ${t.prices.length}. ` +
					`Did you run pnpm seed:stripe?`
			);
		}
	}
}
```

Call this at app boot (in `hooks.server.ts`, non-blocking) so the first pricing page render doesn't 500. Module 8 ties this into a startup diagnostic.

## Step 7 — Use it from a remote query

The pricing page (Module 8.4) will ask for tiers via a `query()` remote function:

```ts
// src/lib/server/billing/tiers.remote.ts
import { query } from '$app/server';
import { listTiers } from './products';

export const tiers = query(async () => {
	return await listTiers();
});
```

That `query` is public — no auth required. We return DTOs, Stripe types never cross the wire.

## Verify

- `listTiers()` returns three tiers in order: free, plus, pro.
- Each paid tier has exactly two prices (monthly + yearly).
- `unitAmount` is in cents (1000 for $10.00, not 10 or 10.00).
- No `'stripe'` import appears anywhere outside `src/lib/server/`.
- Second call within 5 minutes doesn't hit Stripe (add a temporary `console.log` inside the cache miss path to confirm).

## Common traps

- **Returning Stripe's `Price` object to the UI.** It'll work until a Stripe field changes shape. DTOs are the bulkhead.
- **Caching *forever* and forgetting to invalidate on webhook.** 5-min TTL is a safety net; the belt is a `price.updated` webhook calling `invalidateTiersCache()`.
- **Storing `unitAmount` as a float.** `10.00` and `10.0000000001` are not the same number. Cents are integers. Always.
- **Putting the cache in module-global state then running multiple Node processes.** Coherence issue. Fine for single-instance dev/staging; Module 12 addresses multi-instance prod.

## Recap

One service, one DTO, one 5-minute cache, zero Stripe types leaking outward. The pricing page, upgrade flows, and tier gating will all call `listTiers()` and be happy. Next: the Customers service — the piece that maps Supabase users to Stripe customers.
