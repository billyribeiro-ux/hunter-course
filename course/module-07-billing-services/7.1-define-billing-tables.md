# 7.1 — Define Billing Tables

> Three tables, the right columns, RLS on from day one.

## Why this matters

In Module 6 we previewed what Stripe data we mirror locally. Now we create it for real. These three tables — `stripe_customers`, `stripe_subscriptions`, `stripe_events` — are the *entire* billing cache for Contactly. Every upgrade, downgrade, trial, renewal, and cancellation will land in these rows via webhook handlers.

Get the columns right now and Modules 9/10 (checkout + tier gating) become a series of simple SELECTs. Get them wrong and you'll be running reconciliation scripts at midnight. The principle: **narrow, typed, RLS-protected**.

## The Principal Engineer lens

**Only store what your app reads on the hot path.** Every column we add is a column we have to keep in sync with Stripe. If we wouldn't read it during a request, we don't mirror it. Payment methods? No — Stripe shows those in the Customer Portal. Invoice PDFs? No — Stripe hosts the URLs. Line items? No — if you need to audit a charge, open Stripe.

Corollary: **migrations for billing tables go through the same review as any other schema change.** They're not "Stripe stuff, YOLO" — they're load-bearing user data. PR review, RLS review, rollback plan.

## Step 1 — Write the migration

Create `app/supabase/migrations/20260420000000_billing_tables.sql`:

```sql
-- ============================================================
-- stripe_customers
-- One row per user, created the first time they check out.
-- ============================================================

create table public.stripe_customers (
	user_id uuid primary key references auth.users(id) on delete cascade,
	stripe_customer_id text not null unique,
	created_at timestamptz not null default now(),
	updated_at timestamptz not null default now()
);

create trigger stripe_customers_set_updated_at
before update on public.stripe_customers
for each row execute function public.set_updated_at();

alter table public.stripe_customers enable row level security;

-- A user can read their own Stripe customer row.
create policy "stripe_customers_select_own"
on public.stripe_customers for select
to authenticated
using (auth.uid() = user_id);

-- No INSERT / UPDATE / DELETE policies for end users.
-- Only the service-role client (webhooks) writes here.


-- ============================================================
-- stripe_subscriptions
-- One row per Stripe subscription. A user may have multiple
-- (historical cancelled + active), so NOT keyed on user_id.
-- ============================================================

create table public.stripe_subscriptions (
	id text primary key, -- Stripe subscription id (sub_xxx)
	user_id uuid not null references auth.users(id) on delete cascade,
	status text not null,
	price_lookup_key text not null,
	current_period_end timestamptz not null,
	cancel_at_period_end boolean not null default false,
	trial_end timestamptz,
	created_at timestamptz not null default now(),
	updated_at timestamptz not null default now()
);

create index stripe_subscriptions_user_id_idx
on public.stripe_subscriptions (user_id);

create index stripe_subscriptions_status_idx
on public.stripe_subscriptions (status)
where status in ('trialing', 'active', 'past_due');

create trigger stripe_subscriptions_set_updated_at
before update on public.stripe_subscriptions
for each row execute function public.set_updated_at();

alter table public.stripe_subscriptions enable row level security;

create policy "stripe_subscriptions_select_own"
on public.stripe_subscriptions for select
to authenticated
using (auth.uid() = user_id);


-- ============================================================
-- stripe_events
-- Idempotency ledger. One row per Stripe event id we've seen.
-- No user scoping — this is ops data, not user data.
-- ============================================================

create table public.stripe_events (
	id text primary key, -- Stripe event id (evt_xxx)
	type text not null,
	received_at timestamptz not null default now(),
	processed_at timestamptz
);

create index stripe_events_type_received_idx
on public.stripe_events (type, received_at desc);

alter table public.stripe_events enable row level security;

-- No SELECT policy — end users never read this table.
-- Service-role (webhooks) bypasses RLS and is the only writer/reader.
```

A lot of decisions packed in there. Let's walk through the tricky ones.

## Step 2 — Why `user_id` is the primary key of `stripe_customers`

A Stripe customer represents a *person who can pay*. In Contactly, a user has exactly one payment identity — there's no team billing, no multi-tenant madness (yet). So `user_id → stripe_customer_id` is a 1:1 relationship, and the cleanest representation is `user_id` as primary key.

If we ever added teams (Module 13-or-beyond material), we'd introduce a `teams` table and move `stripe_customer_id` onto that. For now, simplicity wins.

The `unique` constraint on `stripe_customer_id` guards against double-creation bugs (a genuine hazard: two concurrent checkout sessions for the same user can each try to create a customer). The DB will reject the second insert; we handle it by doing a SELECT first in the service layer.

## Step 3 — Why `stripe_subscriptions.id` is the Stripe ID itself

Unlike `contacts` (where we generate our own `uuid`), a subscription's natural key *is* the Stripe ID. It's globally unique in Stripe, won't collide across environments (test vs live are separate accounts anyway), and using it directly means our webhook handler can `upsert` without a lookup step.

This is a general pattern worth internalising: **if an external system owns the identity, use their ID as your primary key.** It eliminates mapping tables and ID-translation bugs.

## Step 4 — Why `price_lookup_key` instead of `price_id`

From Module 5.6: lookup keys are stable; IDs change when you replace a price. Storing `plus_monthly` instead of `price_1Nq7Bz...` means:

- When we archive the old $10 price and create a new $12 price with the same lookup key, existing `stripe_subscriptions` rows don't suddenly point at an invalid (archived) price.
- Our tier-gating code in Module 10 can do `if (sub.price_lookup_key === 'plus_monthly' || sub.price_lookup_key === 'plus_yearly') grantPlus()` — human-readable, doesn't need to know Stripe IDs.

The trade-off: we have to *derive* the lookup key from the subscription's current price when the webhook fires. Tiny cost — we fetch the Price along with the Subscription in the webhook handler anyway.

## Step 5 — Why the partial index on `status`

```sql
create index stripe_subscriptions_status_idx
on public.stripe_subscriptions (status)
where status in ('trialing', 'active', 'past_due');
```

The vast majority of queries we run are "does this user have a live-ish subscription?" — that's `status in ('trialing', 'active', 'past_due')`. Cancelled and expired subs pile up forever but we rarely filter by them. A **partial index** keeps only the hot rows, smaller and faster. Postgres 12+ picks it up automatically when your `WHERE` matches.

If you've only ever written full indexes, try this one in production and watch p99 query time drop.

## Step 6 — Why no `updated_at` on `stripe_events`

The ledger is write-once: insert on arrival, set `processed_at` when handling finishes, done. There's no logical "update" to an event — it's an immutable record of something that happened. No trigger needed.

## Step 7 — Generate types + apply

```bash
cd app
pnpm supabase:migrate   # applies 20260420000000_billing_tables.sql locally
pnpm supabase:types      # regenerates src/lib/types/db.ts
```

In `src/lib/types/db.ts` you should now see `stripe_customers`, `stripe_subscriptions`, `stripe_events` as keys of `Database['public']['Tables']`.

Export convenience aliases next to the existing `Profile` export:

```ts
// src/lib/types/db.ts (append)
export type StripeCustomer = Tables<'stripe_customers'>;
export type StripeSubscription = Tables<'stripe_subscriptions'>;
export type StripeEvent = Tables<'stripe_events'>;
```

Now any service can `import type { StripeSubscription } from '$lib/types/db'` without touching the raw `Tables<...>` helper.

## Step 8 — A note on the lack of INSERT/UPDATE RLS policies

You might expect symmetry: every table in Module 4 has four policies (select/insert/update/delete). These billing tables have only a `select` policy. On purpose.

**Users never directly write to billing tables.** They trigger Stripe flows (checkout, portal), Stripe fires a webhook, and our webhook handler — running with the service-role key, which bypasses RLS — writes. Having no INSERT policy means that *even if* a bug somewhere caused a user-scoped client to attempt a write, Postgres would reject it. The RLS absence is a safety rail.

This is the "defense in depth" stance: bugs will happen; RLS makes them non-catastrophic.

## Step 9 — Migration rollback plan

Every migration should be reversible. Ours is:

```sql
-- hypothetical rollback (do not commit)
drop table public.stripe_events;
drop table public.stripe_subscriptions;
drop table public.stripe_customers;
```

In practice Supabase's migration system handles rollback by running the *next* migration that removes things, not by reversing the previous one. But it's worth thinking through: if we had to un-ship this tomorrow, the only "lost data" would be webhook cache — Stripe still has the truth.

## Verify

- `pnpm supabase:migrate` runs cleanly (no SQL errors).
- Three new tables visible in the Supabase Studio table editor.
- `select * from public.stripe_subscriptions;` as an end-user returns 0 rows (RLS is on, no matching rows yet).
- `src/lib/types/db.ts` regenerated with `stripe_customers`, `stripe_subscriptions`, `stripe_events`.
- `StripeCustomer`, `StripeSubscription`, `StripeEvent` exports work in `$lib/types/db`.

## Common traps

- **Storing `price_id` instead of `price_lookup_key`.** You'll regret this the first time you archive a price — explained in Module 5.6.
- **Adding an `INSERT` policy "just in case."** Then a future bug is one `.insert()` call away from corruption. RLS absence is a *feature* here.
- **Forgetting the `unique` on `stripe_customer_id`.** Two racing webhooks can both create customers for the same user; the DB should refuse the second, not silently duplicate.
- **Using a full index on `status`.** Works, but grows linearly with cancelled subs forever. Partial index keeps it proportional to *active* subs.

## Recap

Three tables, lean columns, RLS locked down to read-only for users, service-role writes on the webhook path. With this schema in place, the next three lessons build the services that fill it: Products, Customers, Subscriptions.
