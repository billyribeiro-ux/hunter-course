# 7.4 — Subscriptions Service

> One function the webhook calls on every event. Another the app calls to ask "what's this user paying for?"

## Why this matters

Subscriptions are the noisiest object in Stripe. A single user might generate twenty events in their first hour: `customer.subscription.created`, `trial_will_end`, `updated`, `invoice.paid`, `updated` again. Our webhook handler (Module 6.3) routes each one; the subscriptions service is where they *land*.

Two call-sites matter:

- **Write**: `syncSubscriptionFromStripe(admin, stripeSubscription)` — called from every subscription-related webhook. Upserts the row with current Stripe truth.
- **Read**: `getActiveSubscription(admin, userId)` — called from the app to check entitlement.

That's it. Keep those two crisp and the rest of the app gets simple.

## The Principal Engineer lens

**Re-fetch on every event, don't patch deltas.** When a `customer.subscription.updated` event arrives, it carries a full subscription payload. Don't try to figure out "which field changed." Just upsert the whole thing. Simpler, idempotent, impossible to drift.

Corollary: **status is a machine-owned field.** Your code never writes a custom status ("upgrading", "pending"). You reflect Stripe's `status` exactly: `trialing`, `active`, `past_due`, `canceled`, `unpaid`, `incomplete`, `incomplete_expired`. Any business question ("can this user access Pro features?") is a *derivation*, not a status.

## Step 1 — The write path

Create `src/lib/server/billing/subscriptions.ts`:

```ts
// src/lib/server/billing/subscriptions.ts
import type Stripe from 'stripe';
import type { SupabaseClient } from '@supabase/supabase-js';
import type { Database, StripeSubscription } from '$lib/types/db';
import { findUserIdByStripeCustomer } from './customers';

type Admin = SupabaseClient<Database>;

export async function syncSubscriptionFromStripe(
	admin: Admin,
	sub: Stripe.Subscription
): Promise<StripeSubscription | null> {
	// Stripe's `customer` field can be string or Customer — we want the id.
	const stripeCustomerId =
		typeof sub.customer === 'string' ? sub.customer : sub.customer.id;

	const userId = await findUserIdByStripeCustomer(admin, stripeCustomerId);
	if (!userId) {
		// Webhook for an unknown customer — log & skip.
		console.warn(`[subs] unknown customer ${stripeCustomerId}, skipping sync`);
		return null;
	}

	// A subscription can technically carry multiple line items / prices.
	// We only ever attach one, so grab it.
	const item = sub.items.data[0];
	const lookupKey = item?.price.lookup_key;
	if (!lookupKey) {
		console.warn(`[subs] subscription ${sub.id} has no lookup_key, skipping`);
		return null;
	}

	const row = {
		id: sub.id,
		user_id: userId,
		status: sub.status,
		price_lookup_key: lookupKey,
		current_period_end: new Date(sub.current_period_end * 1000).toISOString(),
		cancel_at_period_end: sub.cancel_at_period_end,
		trial_end: sub.trial_end
			? new Date(sub.trial_end * 1000).toISOString()
			: null
	};

	const { data, error } = await admin
		.from('stripe_subscriptions')
		.upsert(row, { onConflict: 'id' })
		.select()
		.single();

	if (error) throw error;
	return data;
}
```

Three decisions worth spelling out.

## Step 2 — Why `upsert` on `id`

Stripe subscription IDs are stable for the lifetime of the sub. We might see the same ID across `created`, `updated`, `deleted` events. `upsert(..., { onConflict: 'id' })` handles all three idempotently:

- First `created` event: INSERT.
- Subsequent `updated` events: UPDATE.
- `deleted` event: UPDATE status to `canceled` (Stripe doesn't actually delete the sub; it just sets `status: 'canceled'`).

One code path. No branches. No accidental duplicates.

## Step 3 — Why we convert timestamps

Stripe delivers timestamps as Unix seconds (integer). Postgres expects `timestamptz`. The conversion `new Date(sub.current_period_end * 1000).toISOString()` is the bridge. Forgetting this is a classic bug: the row gets `1704067200` literally into a text column, everything "works" until you try to filter by date, and then `WHERE current_period_end > now()` returns nothing.

## Step 4 — Why we guard on `lookupKey`

If a price in Stripe somehow lacks a lookup key (a bug in the seed, a manually-created price without one), we refuse to mirror the subscription. Better to have no row than a row with `price_lookup_key = ''` that the tier-gating logic in Module 10 has to special-case.

We log + skip; the sub exists in Stripe and keeps billing; a human sees the warning and fixes the seed.

## Step 5 — The read path

The app needs to answer "which (if any) subscription is this user currently on?" An "active-ish" subscription is any with status `trialing`, `active`, or `past_due` (the last means "we haven't successfully collected yet but haven't given up"). A user can have multiple historical subs; we want the current one.

```ts
// src/lib/server/billing/subscriptions.ts (append)

const LIVE_STATUSES = ['trialing', 'active', 'past_due'] as const;

export async function getActiveSubscription(
	admin: Admin,
	userId: string
): Promise<StripeSubscription | null> {
	const { data, error } = await admin
		.from('stripe_subscriptions')
		.select('*')
		.eq('user_id', userId)
		.in('status', LIVE_STATUSES as unknown as string[])
		.order('current_period_end', { ascending: false })
		.limit(1)
		.maybeSingle();

	if (error) throw error;
	return data;
}
```

`maybeSingle()` over `single()` matters: a free user has no active subscription, and that's *not* an error. `maybeSingle` returns `null`; `single` throws.

## Step 6 — Deriving the tier

Given an active subscription (or lack thereof), what *tier* is the user on?

```ts
// src/lib/server/billing/subscriptions.ts (append)

import { TIERS, type TierId } from '$lib/config/pricing';

export function tierIdFromLookupKey(lookupKey: string | null): TierId {
	if (!lookupKey) return 'free';
	for (const t of TIERS) {
		if (Object.values(t.prices).includes(lookupKey)) return t.id;
	}
	return 'free';
}

export async function getUserTier(
	admin: Admin,
	userId: string
): Promise<TierId> {
	const sub = await getActiveSubscription(admin, userId);
	return tierIdFromLookupKey(sub?.price_lookup_key ?? null);
}
```

Three levels of abstraction stacked cleanly:

- `stripe_subscriptions` row → `price_lookup_key` → `TierId`.
- Any one of the layers can be tested in isolation.
- `getUserTier` is the one most callers want. The others exist for more specific needs.

## Step 7 — Preventing multiple concurrent subscriptions

A business rule: a Contactly user has at most one live subscription at a time. If they upgrade from Plus to Pro, Stripe's Customer Portal handles it as an *update* to the existing subscription — same subscription ID, new price. Our upsert reflects that correctly.

But what if a user somehow checks out twice in parallel (race condition, bug in our UI)? They could end up with two `active` rows in `stripe_subscriptions`. We deal with this in two layers:

1. **Checkout-time guard** (Module 9.4). Before creating a Checkout Session, call `getActiveSubscription`. If there's one, redirect to the Portal instead.
2. **Defensive read.** `getActiveSubscription` already `.limit(1).order(...desc)`, so even if two rows exist, the app picks the newer one and never crashes.

Layer 1 prevents the problem; layer 2 contains it if it happens.

## Step 8 — Wire into the webhook handler

Back in Module 6.3 we had a skeleton webhook handler that only logged events. Now we can fill in the subscription cases:

```ts
// src/routes/api/webhooks/stripe/+server.ts (additions)
import {
	syncSubscriptionFromStripe
} from '$lib/server/billing/subscriptions';
import { upsertStripeCustomer } from '$lib/server/billing/customers';

// ...inside the switch statement:
case 'customer.subscription.created':
case 'customer.subscription.updated':
case 'customer.subscription.deleted':
	await syncSubscriptionFromStripe(
		locals.supabaseAdmin,
		event.data.object as Stripe.Subscription
	);
	break;

case 'customer.created': {
	const c = event.data.object as Stripe.Customer;
	const userId = c.metadata?.user_id;
	if (userId) {
		await upsertStripeCustomer(locals.supabaseAdmin, userId, c.id);
	}
	break;
}
```

For every sub event, re-sync. No deltas, no state machines, just "reflect Stripe." That's the whole service.

## Step 9 — What about `invoice.paid` and `invoice.payment_failed`?

Those don't *directly* mutate our tables — the subscription events that accompany them carry the same state. But they're useful for:

- Triggering an email ("payment failed — update card").
- Analytics ("how often do cards fail on renewal?").

Module 9 wires emails; Module 11 adds tests. For now we log them and move on.

## Verify

- Triggering `stripe trigger customer.subscription.created` inserts a row in `stripe_subscriptions` with the correct `user_id`, `price_lookup_key`, and `current_period_end` in the future.
- Triggering `customer.subscription.updated` updates the same row (no duplicate).
- `getActiveSubscription(admin, userId)` returns that row.
- `getUserTier(admin, userId)` returns `'plus'` or `'pro'` accordingly.
- Deleting the sub (`stripe trigger customer.subscription.deleted`) sets status to `canceled` on the existing row; `getUserTier` now returns `'free'`.

## Common traps

- **Forgetting `* 1000` on the timestamp conversion.** You'll store a date in 1970, everything "works" until renewal logic fails silently.
- **Using `.single()` instead of `.maybeSingle()` for the active-sub lookup.** Free users crash the app.
- **Writing a custom status like `'upgrading'`.** Stripe's enum is the enum. If you need a UI-side state, keep it in the component.
- **Re-deriving `tier` from `unit_amount`.** Lookup key is the stable identifier. Amounts can change.
- **Calling `syncSubscriptionFromStripe` from user-scoped code.** It writes to an RLS-locked table. Admin client only.

## Recap

Two functions handle the whole subscription lifecycle: `syncSubscriptionFromStripe` writes, `getActiveSubscription` / `getUserTier` read. Stripe's events flow in, your DB reflects current state, your app asks simple questions. Module 8 uses this to build the actual pricing page.
