# 5.3.1 — Stripe CLI on WSL

> If you're on Windows + WSL, one extra step avoids an hour of "why doesn't my webhook arrive?" pain.

## Why this matters

Most of our course assumes macOS or Linux. Windows users typically run WSL2 (Ubuntu) for dev. `stripe listen` *mostly* works on WSL — with one gotcha: by default, `localhost` inside WSL and `localhost` in Windows aren't the same thing, and Stripe CLI's default tunnel target depends on which side it's installed on.

The fix is easy: **install and run the Stripe CLI inside WSL**, not on Windows.

## The Principal Engineer lens

**Keep your dev environment unified.** Jumping between "I need to run this in PowerShell, and this in WSL, and this in Docker Desktop" creates fragile state. When in doubt, pick one shell — WSL — and install everything there.

## Step 1 — Install the CLI *inside WSL*

Open your WSL terminal (Ubuntu). Don't install Stripe CLI via `winget` or in PowerShell for this flow.

```bash
# Add Stripe's Bintray GPG + repo (one-time)
curl -s https://packages.stripe.dev/api/security/keypair/stripe-cli-gpg/public | \
  sudo gpg --dearmor -o /usr/share/keyrings/stripe.gpg

echo "deb [signed-by=/usr/share/keyrings/stripe.gpg] https://packages.stripe.dev/stripe-cli-debian-local stable main" | \
  sudo tee -a /etc/apt/sources.list.d/stripe.list

sudo apt update
sudo apt install stripe
```

Verify:

```bash
stripe --version
```

## Step 2 — Confirm `localhost` resolves correctly

When `pnpm dev` runs inside WSL on port 5173, visiting `http://localhost:5173` in a Windows browser works because WSL2 forwards localhost both ways — *usually*. From a terminal inside WSL, `curl http://localhost:5173` must return a response. Check:

```bash
pnpm dev &                     # in another WSL terminal
curl -I http://localhost:5173/
```

Should be `HTTP/1.1 200 OK` (or similar). If not, your WSL network setup is off — see https://learn.microsoft.com/en-us/windows/wsl/networking.

## Step 3 — Run `stripe listen` in WSL

```bash
stripe listen --forward-to http://localhost:5173/api/webhooks/stripe
```

Trigger an event from another WSL terminal:

```bash
stripe trigger customer.subscription.created
```

In the `stripe listen` terminal, you should see the event forward with a 4xx from the (not-yet-built) endpoint. That's success — the tunnel works.

## Step 4 — If `localhost` doesn't work, use the WSL host IP

Rare fallback: if WSL2's localhost forwarding is broken on your machine, point the CLI at WSL's network IP:

```bash
ip addr show eth0 | grep inet         # copy the IPv4 address (e.g., 172.18.0.2)

stripe listen --forward-to http://172.18.0.2:5173/api/webhooks/stripe
```

Run your dev server with `--host 0.0.0.0` so it binds that interface:

```bash
pnpm dev --host 0.0.0.0
```

This is the escape hatch; try `localhost` first.

## Step 5 — Don't install Stripe CLI on both sides

If you've got `stripe.exe` on Windows *and* `stripe` in WSL, you'll confuse yourself about which one's running. Pick one, remove the other. We recommend WSL — it matches the rest of our toolchain.

## Verify

- `stripe --version` inside WSL.
- `stripe login` succeeds (browser opens on Windows, redirects back).
- `stripe listen --forward-to http://localhost:5173/...` runs and tunnels to your WSL dev server.

## Common traps

- **Installing CLI on Windows, dev server on WSL.** `localhost` on Windows is *not* the same as `localhost` in WSL. Tunnels will succeed at Stripe's end but never hit your app.
- **Corporate VPN intercepting outbound TLS.** If `stripe login` fails at the first fetch, suspect VPN SSL inspection.
- **Running `pnpm dev` without `--host` when using WSL IP.** The default binding is `127.0.0.1` inside WSL, which only accepts loopback traffic.

## Recap

If you use WSL: install the CLI *inside* WSL and use `localhost` by default. Fall back to the WSL IP only if the loopback forwarding is broken on your machine.
