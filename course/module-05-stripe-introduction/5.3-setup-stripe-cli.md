# 5.3 — Setup Stripe CLI

> One tool to log in, tail events, forward webhooks, and trigger test payloads.

## Why this matters

The Stripe CLI is how you do local Stripe development. Its killer feature is `stripe listen`: it opens a tunnel from Stripe's servers to your local machine, so webhook events sent by Stripe reach your `http://localhost:5173/api/webhooks/stripe` endpoint with real signatures. No ngrok, no public URL, no hacks.

It also lets you trigger synthetic events (`stripe trigger customer.subscription.created`) so you can test your webhook handler without clicking through Checkout ten times.

## The Principal Engineer lens

**Local = production, minus the money.** Stripe's design rewards you for testing locally — real signatures, real idempotency keys, real event shapes. If your local webhook handler works, your production handler will work. We'll exploit this by testing every Stripe integration locally before ever deploying.

## Step 1 — Install the CLI

Pick your OS:

- **macOS**: `brew install stripe/stripe-cli/stripe`
- **Ubuntu/Debian**: follow https://docs.stripe.com/stripe-cli#install → apt repo.
- **Windows**: `scoop install stripe` (with Scoop) or download from releases.

If you're on WSL, see the next lesson (5.3.1).

Verify:

```bash
stripe --version
```

Should print something like `stripe version 1.29.0` (or newer — any 1.x works).

## Step 2 — Log in

```bash
stripe login
```

Your browser opens, you confirm in the Stripe dashboard, and the CLI stores a token in `~/.config/stripe/` (macOS/Linux) or `%APPDATA%\stripe\` (Windows).

Default mode is **test**. Confirm:

```bash
stripe config --list
```

You should see your `test_mode_api_key` set.

## Step 3 — Listen for webhook events

Even without our backend built yet, we can practice:

```bash
stripe listen --forward-to http://localhost:5173/api/webhooks/stripe
```

You'll see:

```
> Ready! Your webhook signing secret is whsec_... (^C to quit)
```

That `whsec_...` is crucial — it's the **webhook signing secret** your backend uses to verify events. It rotates each time you run `stripe listen` unless you pin it. Save it to `.env` as `STRIPE_WEBHOOK_SECRET`.

Leave the command running in a terminal. It'll display every event Stripe sends + the response code from your endpoint (404 for now, since we haven't built it yet).

## Step 4 — Trigger a test event

In a second terminal, trigger one:

```bash
stripe trigger customer.subscription.created
```

You should see:

- The trigger command print "Setting up fixture for customer.subscription.created."
- In your first terminal (`stripe listen`), a new event arrive and forward to your endpoint.
- A 404 reply (expected — no handler yet).

That's the whole dev loop. No Stripe dashboard clicking, no external tunnel, real-looking events on demand.

## Step 5 — Pin the webhook secret for stability

Each `stripe listen` rotates the secret, which means you'd have to update `.env` every time. Pin it with:

```bash
stripe listen --forward-to http://localhost:5173/api/webhooks/stripe --skip-verify --print-secret
```

Or better, once you have a secret, pass it back:

```bash
stripe listen --forward-to http://localhost:5173/api/webhooks/stripe --events customer.subscription.created,customer.subscription.updated,customer.subscription.deleted,invoice.paid,invoice.payment_failed,checkout.session.completed
```

Narrowing `--events` reduces noise; we'll configure exactly the events we handle in Module 6.

## Step 6 — Add package scripts for convenience

In `app/package.json`:

```json
{
	"scripts": {
		"stripe:listen": "stripe listen --forward-to http://localhost:5173/api/webhooks/stripe",
		"stripe:trigger:sub-created": "stripe trigger customer.subscription.created",
		"stripe:trigger:checkout-completed": "stripe trigger checkout.session.completed"
	}
}
```

Then you can just `pnpm stripe:listen` and remember less.

## Step 7 — Log out (only if you switch accounts)

```bash
stripe logout
```

Not something you usually do. But if you work on multiple Stripe accounts, you'll need to `stripe login --account [account-id]` or logout/login to swap.

## Verify

- `stripe --version` runs.
- `stripe login` succeeds; `stripe config --list` shows a test-mode token.
- `stripe listen --forward-to ...` prints a `whsec_...` and stays running.
- `stripe trigger customer.subscription.created` sends an event that hits your local endpoint (404 is fine for now).

## Common traps

- **Forgetting to re-run `stripe listen` after a reboot.** It has to be running during dev to receive events.
- **Using a stale `STRIPE_WEBHOOK_SECRET`.** Match whatever `stripe listen` currently prints.
- **Firewall / VPN blocking the tunnel.** If events don't arrive, the culprit is almost always a firewall between your machine and Stripe.
