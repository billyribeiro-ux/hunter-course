# 5.7 — Cleanup

> A tidy Stripe account pays you back every single week of your project.

## Why this matters

By the end of this course you'll have poked Stripe dozens of times: trial products, misnamed prices, leftover customers from an experiment, webhooks pointed at a dead endpoint. None of it hurts — test mode is disposable — but a cluttered dashboard makes it genuinely hard to see what you care about. And once you're in live mode, clutter becomes *embarrassing* (customers see product names on invoices).

Spend 10 minutes now building good habits. You'll thank yourself in Module 9 when you need to verify a checkout flow and your dashboard shows exactly what you expect.

## The Principal Engineer lens

**Treat your test-mode dashboard like source code.** If something's there, it should be there on purpose. If it's not on purpose, delete/archive it. The same discipline you bring to a codebase — "no dead imports, no commented-out blocks" — applies to external services. A dashboard that reflects reality is a debugging superpower.

Corollary: **never delete anything in live mode**. Archive instead. Stripe retains history for auditing, refunds, and tax. The "delete" button is for test mode only.

## Step 1 — Archive vs. delete

Two verbs matter:

- **Archive** (`active: false`). Hides the object from the default dashboard view, prevents new uses (e.g., can't start a subscription on an archived price), but preserves it for historical reference. Works in both test and live.
- **Delete** (dashboard trash icon or `.del()` API). Irreversible. Only available for objects that have no dependents. Use in test mode for cleanup; basically never in live.

Rule of thumb: **archive in live, delete in test.**

## Step 2 — Clean up Products

Go to **Products** in the dashboard (test mode).

You should see Plus and Pro from Module 5.5. If you also see:

- "Test Product" from when you clicked around in 5.1 — **delete** it.
- Duplicate Plus/Pro from accidental double-creation — archive duplicates (right-click → Archive), keep the one with the correct lookup keys.

After this, Products shows exactly: `Plus (2 prices)`, `Pro (2 prices)`. Nothing else.

## Step 3 — Clean up Prices

For each product, click in and review the Prices list:

- Exactly one monthly, one yearly, per product.
- Lookup keys match: `plus_monthly`, `plus_yearly`, `pro_monthly`, `pro_yearly`.
- Amounts: $10, $96, $20, $192 USD.

If a price exists without a lookup key, either add one (Advanced options → Lookup key) or archive it.

## Step 4 — Clean up Customers

**Customers** tab. In test mode you may have a stray customer from when Stripe CLI triggered a subscription event. The `stripe trigger customer.subscription.created` command from 5.3 actually creates a real test customer in your account.

For test mode, you can safely delete any customer whose email starts with something like `guest-…@example.com` or that you don't recognise. In production you'd never do this — customers stay forever.

## Step 5 — Clean up Webhook endpoints

**Developers → Webhooks**. You won't have any registered endpoints yet (that comes in Module 6), but check anyway. If there's a stale `https://something.ngrok.io` or similar from past experiments, delete it. Webhook endpoints are cheap; keep only what you actively use.

For `stripe listen` (the CLI tunnel), no dashboard entry is created — it's a temporary session. Nothing to clean there.

## Step 6 — Double-check the API version

**Developers → API version**. Stripe shows two values:

- **Default** — what your account uses when an API call doesn't specify a version.
- **Upcoming** — the next scheduled version.

We pin the version in our code (Module 5.2), so the "Default" value is mostly cosmetic. But: make sure it's reasonably current. If it's more than a year behind today's version, click **Upgrade** (safe in test mode) so the dashboard's behaviour matches what our code does.

## Step 7 — Verify environment isolation

Toggle **Live mode** in the top-right. You should see:

- A completely empty dashboard (no products, no customers, no webhooks, no API keys). That's correct — we've only touched test mode so far.
- A banner saying your account hasn't been activated for live payments. That's also correct — we won't activate until Module 12.

Toggle back to **Test mode**. Confirm you're in test for the rest of the course by glancing at the dashboard header. Every expensive mistake in Stripe dev history started with "wait, was I in live mode?"

## Step 8 — Protect your API keys

**Developers → API keys**. Two things:

- **Publishable key** (starts with `pk_test_...`) — safe in client code, but for our app it lives in `PUBLIC_STRIPE_PUBLISHABLE_KEY` anyway (we barely use it; Checkout is server-driven).
- **Secret key** (`sk_test_...`) — **never commit this**. Lives in `.env` as `STRIPE_SECRET_KEY`. If it ever leaks, click **Roll secret key** in the dashboard *immediately* — old key dies, new one issued, update `.env`, restart server.

Stripe's secret-scanning will also automatically roll a key if it detects a leak on GitHub. This has saved thousands of engineers. Don't rely on it, but know it's there.

## Step 9 — A `.env` sanity pass

Open `app/.env` and confirm:

```bash
# Supabase (from Module 2)
PUBLIC_SUPABASE_URL=https://xxx.supabase.co
PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOi...
DATABASE_URL=postgresql://...

# Stripe (new this module)
STRIPE_SECRET_KEY=sk_test_51Ab...
STRIPE_WEBHOOK_SECRET=whsec_...        # from `stripe listen`
PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_test_51Ab...
```

And `app/.env.example` (committed to git) has the same keys, all with empty values:

```bash
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
PUBLIC_STRIPE_PUBLISHABLE_KEY=
```

New teammates clone, copy `.env.example` → `.env`, fill in values. No secrets ever in git.

## Step 10 — One last gut check

Before we move on, ask yourself:

- Could a teammate clone this repo and get a working Stripe test setup by reading this module plus the `.env.example`? If not, fix the docs.
- If my laptop died tomorrow, could I re-create the same Stripe test config in 10 minutes? (Answer should be yes, because Module 8's seed script will do it automatically.)

If both answers are yes, you're ready for Module 6 — wiring this into code.

## Verify

- Products dashboard shows exactly Plus and Pro; 4 prices total with correct lookup keys.
- No stray customers or webhook endpoints in test mode.
- Live mode is empty and unactivated.
- `.env` has Stripe keys; `.env.example` lists them with empty values.

## Common traps

- **Deleting things in live mode to "clean up."** You'll break historical invoices, tax reports, and refunds. Archive only.
- **Committing the secret key once and rolling it later.** Rolling doesn't un-leak — treat every commit as permanent. Rotate *and* scrub the history if you must.
- **Leaving the webhook secret from an old `stripe listen` session in `.env`.** Each `stripe listen` rolls the secret; update `.env` + restart the server.
- **Archiving a price with active subscriptions on it.** Stripe allows this (subscribers keep paying), but it means the price no longer shows on your pricing page even though revenue is flowing. Pair archive with "create replacement and transfer lookup key" — never orphan.
