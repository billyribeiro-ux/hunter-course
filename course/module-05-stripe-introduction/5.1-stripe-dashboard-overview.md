# 5.1 — Stripe Dashboard Overview

> The map of the Stripe UI — so when your boss says "can you check if that payment succeeded?" you know where to click.

## Why this matters

The Stripe dashboard is where you'll spend 80% of your non-code Stripe time: checking payments, debugging a failed webhook, looking up a customer, creating a test card charge, pulling a report for your accountant. Before we write a line of Stripe code, we'll tour the dashboard so the rest of the module makes sense.

## The Principal Engineer lens

**Treat the dashboard as read-mostly.** In a production SaaS, we never create products, prices, or customers by hand in the dashboard — those are managed via code (`scripts/seed-stripe.ts` in Module 8) so the config is versioned and reproducible. The dashboard is for *observing* what your code + your users did: payment logs, disputes, webhook retries.

## Step 1 — Create your Stripe account

If you don't have one yet: https://dashboard.stripe.com/register. Use your real email — you'll need access to the Test environment and the dashboard's full feature set.

Stripe gives you two modes from day one:

- **Test mode** — sandbox, fake money. We'll use this for the entire course.
- **Live mode** — real money. We'll switch to live in Module 12 just before deploy.

The toggle is at the top of the sidebar. **Always** check which mode you're in before doing anything.

## Step 2 — The sidebar, top to bottom

You don't need to know every menu yet, but here's what each is for:

| Section | What's there | When you'll use it |
|---|---|---|
| **Home** | Snapshot — revenue, payments, failed charges. | Quick health check. |
| **Payments** | Every charge, refund, dispute. | Debugging a specific transaction. |
| **Balances** | Your Stripe balance, payouts. | Reconciliation, transfers to your bank. |
| **Customers** | All your Stripe Customer records. | Looking up "who is this user?" |
| **Products** | Your catalog. | Rarely — we seed via code in Module 8. |
| **Billing** | Subscriptions, invoices, plans. | Debugging a subscription state. |
| **Developers** | API keys, webhooks, events, logs. | Constantly. |
| **Tax / Radar / Connect** | Advanced features. | Not for this course. |

The section we'll live in is **Developers**. Everything else is read-mostly.

## Step 3 — The Developers tab

Click **Developers** (or press `G` then `D` — Stripe has vim bindings, it's great).

Sub-sections:

- **API keys** — your publishable + secret keys for test and live.
- **Webhooks** — HTTP endpoints Stripe posts events to. We'll register our local endpoint in Module 6.
- **Events** — a log of every event Stripe has emitted. Invaluable for debugging.
- **Logs** — every API request and response your code has made. If your webhook returned 500 and Stripe retried — you'll find the retry details here.

## Step 4 — Grab your test API keys (for later)

Go to **Developers → API keys**. You'll see:

- **Publishable key** — `pk_test_...`. Safe to expose in browser code. Identifies your account to Stripe's checkout UI.
- **Secret key** — `sk_test_...`. Server-only. Never commit. Never log. Never paste in Slack.

Click **Reveal test key** to see the secret. We'll put these in `.env` in Module 6.

> There's a "Restricted keys" option too. For production, we'll create a restricted key scoped to only the API calls we actually make. For local dev, the regular secret key is fine.

## Step 5 — Read-only tours: Customers, Payments, Subscriptions

Play with the dashboard to get comfortable:

- **Customers** → **+ Add test customer** → create one for yourself. Now refresh and you'll see a search/filter UI, a detail page with "payment methods," "invoices," "subscriptions" tabs. This is what a real support agent sees when helping a customer.
- **Payments** → you have none yet. Later, after a test checkout, come back here to see the charge + receipt URL + paid amount.
- **Billing → Subscriptions** → empty. After Module 9, you'll see your first test subscription here, complete with status, next-billing-date, cancel/reactivate controls.

## Step 6 — Bookmarks worth making

Three pages you'll hit a *lot*:

1. `https://dashboard.stripe.com/test/events` — recent webhook events.
2. `https://dashboard.stripe.com/test/logs` — recent API requests (yours).
3. `https://dashboard.stripe.com/test/customers` — lookup by email.

Bookmark them now. Future-you will thank you.

## Step 7 — Never trust the dashboard for business logic

Here's the boundary: the dashboard tells you what *is*, not what *should be*. If your user has a "Plus" subscription in Stripe but your app says they're on Free, your app is wrong (or your webhook is broken). You always fix it in code, not by hand-editing in the dashboard.

This is the Principal Engineer mindset we'll keep repeating: **Stripe is the source of truth, your DB is the cache, your UI reflects the cache**. The dashboard is a window into Stripe — not into your app.

## Verify

- You can log into the Stripe dashboard in test mode.
- You know where **Developers → API keys**, **Webhooks**, **Events**, **Logs** live.
- You can create a test customer manually and find them in the list.

## Common traps

- **Mixing test and live mode keys.** Your `.env` might have a test key; your production deploy uses a live key. Read the prefix: `sk_test_...` vs. `sk_live_...`.
- **Editing production data in the dashboard.** Almost every "quick fix" in live mode becomes a support ticket. Go through code + webhooks.
- **Assuming dashboard changes propagate to your DB.** They don't — unless the change triggers a webhook we handle. If you manually cancel a subscription in the dashboard, our webhook handler will still update our DB. Good. If you manually change the description of a product, nothing fires. We'll only mirror what we care about.
