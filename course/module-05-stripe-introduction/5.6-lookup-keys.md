# 5.6 — Lookup Keys

> The single design choice that separates painful Stripe integrations from calm ones.

## Why this matters

Most first-time Stripe integrations do this:

```ts
// ❌ The trap
const PRICE_PLUS_MONTHLY = 'price_1Nq7BzKJxYz...';
```

Then three months later: the price changes, you migrate environments, or a teammate re-seeds test mode — and every one of those constants is wrong. You're scanning code, copying IDs from the dashboard, pushing a "fix price IDs" commit. Forever.

A **lookup key** fixes this in one move. It's a human-readable, stable handle you attach to a Price. Your code asks Stripe "give me the price with lookup key `plus_monthly`" and Stripe resolves it to the current ID — test or live, old or new.

Once you internalise this, you stop thinking in IDs. You think in *names*. That's the shift.

## The Principal Engineer lens

**Stable names, mutable implementations.** This is the same principle as DNS, semantic versioning, and package names. The name is the contract; the underlying thing behind it can change. Hardcoding a Stripe price ID is like hardcoding an IP address — it works until it doesn't, and when it breaks it breaks in production.

Corollary: **every external ID in your code is a liability.** Price IDs, webhook endpoint IDs, product IDs — if you can replace them with a named handle, do. The only Stripe ID we'll store in *our* database is the Subscription ID (because it's unique per customer and created by Stripe, so there's no naming to do).

## Step 1 — What a lookup key actually is

On a Price object, `lookup_key` is just a field:

```json
{
	"id": "price_1Nq7BzKJxYzAbcDef",
	"object": "price",
	"product": "prod_OabcXYZ",
	"unit_amount": 1000,
	"currency": "usd",
	"recurring": { "interval": "month" },
	"lookup_key": "plus_monthly",
	"active": true
}
```

It must be unique among **active** prices in a given Stripe account + mode. You can have an archived `plus_monthly` and an active `plus_monthly` — Stripe's API lets you "transfer" the key from old to new when you create a replacement.

## Step 2 — Resolving a price by lookup key

The shape you'll use everywhere:

```ts
// src/lib/server/stripe.ts (sketch — real file in Module 6)
import Stripe from 'stripe';

const stripe = new Stripe(env.STRIPE_SECRET_KEY, {
	apiVersion: '2026-03-25.dahlia'
});

export async function getPriceByLookupKey(lookupKey: string) {
	const prices = await stripe.prices.list({
		lookup_keys: [lookupKey],
		active: true,
		expand: ['data.product']
	});
	const price = prices.data[0];
	if (!price) throw new Error(`No active price for lookup key: ${lookupKey}`);
	return price;
}
```

Three things worth noticing:

- **`active: true`** — ignore archived prices. When you replace one, the old one stays around forever; you want the live one.
- **`expand: ['data.product']`** — pulls the full Product object inline. One round-trip instead of two.
- **Throw if missing.** A typo in a lookup key is a programmer error, not a user error. Loud failure, early.

## Step 3 — Why this wins across environments

Imagine your pipeline has three Stripe *accounts* (or modes):

| Environment | Stripe mode | `plus_monthly` resolves to |
|---|---|---|
| Local dev | test | `price_1Nq7Bz...` |
| Staging | test (separate acct) | `price_1Mk9Tx...` |
| Production | live | `price_1Pz3Qw...` |

Your code is *identical* in all three. `getPriceByLookupKey('plus_monthly')` just works. No per-environment price ID table. No `if (env === 'production')` branches. No PR that adds a second hardcoded constant for live mode.

This is the biggest practical win. It's worth the ten seconds of typing a lookup key.

## Step 4 — Why this wins across price changes

Say Contactly raises Plus from $10/mo to $12/mo. Stripe's rule: you can't edit `unit_amount` on an existing Price. What you do instead:

1. Create a new Price on the same Product, `unit_amount: 1200`, **no lookup key yet** (Stripe rejects duplicate active keys).
2. Move the lookup key: call `stripe.prices.update(oldId, { lookup_key: null })` then `stripe.prices.update(newId, { lookup_key: 'plus_monthly', transfer_lookup_key: true })`.
3. Archive the old price: `stripe.prices.update(oldId, { active: false })`.

*Or, in one atomic operation:*

```ts
await stripe.prices.update(newPriceId, {
	lookup_key: 'plus_monthly',
	transfer_lookup_key: true
});
```

`transfer_lookup_key: true` does steps 1+2 atomically. Existing subscribers stay on the old price object (Stripe preserves their $10 forever, as Module 5.4 promised). New checkouts resolve `plus_monthly` and get $12. Your app code? Not a single change.

## Step 5 — Why this wins when you nuke test mode

At least once per project you'll want to wipe test mode — delete all the junk products you created while learning. After the wipe, your seed script runs, creates fresh Products + Prices with fresh IDs, and reattaches the lookup keys `plus_monthly` / `plus_yearly` / `pro_monthly` / `pro_yearly`. Your local app keeps working with zero code changes. That magic is the lookup key.

## Step 6 — Lookup keys we'll use

From Module 5.5 we created four:

| Lookup key | Product | Amount | Interval |
|---|---|---|---|
| `plus_monthly` | Plus | $10 | month |
| `plus_yearly` | Plus | $96 | year |
| `pro_monthly` | Pro | $20 | month |
| `pro_yearly` | Pro | $192 | year |

Naming convention: `{tier}_{interval}`. Short, predictable, greppable. Don't include currency (we're USD-only — when/if we add EUR, we'll likely have a separate Stripe account per region, not a suffix). Don't include version numbers (`plus_monthly_v2`) — versioning happens via the "archive + recreate" dance from Step 4, transparently to your code.

## Step 7 — Resolving a set of keys at once

For the pricing page we need all four prices in one shot:

```ts
export async function listActiveTierPrices() {
	const prices = await stripe.prices.list({
		lookup_keys: ['plus_monthly', 'plus_yearly', 'pro_monthly', 'pro_yearly'],
		active: true,
		expand: ['data.product']
	});
	// Returns an array of ≤4 prices. If any is missing, the seed didn't run.
	return prices.data;
}
```

`lookup_keys` accepts an array of up to 10. For Contactly, 4 fits. When we hit 11, we'd paginate or fetch per-tier; for most SaaS apps this never happens.

## Step 8 — Where our app writes lookup keys

Only two places touch lookup keys in writes:

1. **`scripts/seed-stripe.ts`** (Module 8). Reads `TIERS` from `pricing.ts`, creates missing products/prices, assigns the lookup keys. Idempotent — re-running is a no-op.
2. **Dashboard (manual, once).** We just did this in 5.5 to learn the fields. From here on, the script owns it.

Everywhere else (checkout, billing portal, webhook handler) lookup keys are *read-only*. The app reads; the seed writes.

## Step 9 — A common "gotcha" worth preempting

When you archive a price, its lookup key is *released*. That's how `transfer_lookup_key` works. But if you *first* create a new price with the same key, Stripe errors with `Duplicate lookup_key`. The order matters:

- ✅ Create new price → transfer key → archive old.
- ❌ Create new price with same key → *boom*.

We handle this in the seed script by using `transfer_lookup_key: true`, which internally does the dance for you. If you ever write this by hand, remember: one active lookup key at a time.

- You can explain (in one sentence) why lookup keys beat hardcoded IDs.
- You can write the Stripe call that resolves `plus_monthly` to a Price object.
- You know what `transfer_lookup_key: true` does, and why you'd want it.

## Common traps

- **Using IDs in code "temporarily."** Never temporary. Use lookup keys from day one.
- **Forgetting `active: true` on `prices.list`.** You'll get archived prices back and break renewals for customers who migrated.
- **Inventing lookup keys on the fly in templates.** Lookup keys are *data*, owned by the seed. Don't generate them in component code.
- **Assuming lookup keys are global.** They're scoped per Stripe account + mode. Test and live have independent namespaces — the same name in each resolves to different IDs. That's the feature.

## Recap

Lookup keys are the "name over address" move for Stripe. Your code references names; Stripe resolves them to current IDs. Result: the same codebase runs against test, staging, and live Stripe accounts, survives price changes, and shrugs off environment wipes.
