# 5.2 — Stripe API & Docs

> How to read Stripe's docs so you find answers in minutes, not hours.

## Why this matters

Stripe has arguably the best API documentation of any company. Once you know the structure, you can answer almost any question without asking a human. Miss the structure and you'll drown. We'll cover both the docs' layout and the API's core objects so that when we start calling the SDK in Module 6, you already know what you're pointing at.

## The Principal Engineer lens

**Read the object reference before reading the guide.** Guides are tutorials — useful but opinionated and often behind the latest features. The object reference is the source of truth: if a field exists in the API, it's in the reference. Start there; supplement with guides.

## Step 1 — The shape of stripe.com/docs

Open https://stripe.com/docs. Four main tabs:

- **Start** — marketing-flavored intro.
- **Guides** — multi-step tutorials (e.g., "Accept a payment").
- **API reference** — every object, every field, every method.
- **SDKs** — language-specific wrappers.

For our course we'll live in **API reference** and **SDKs → Node**.

## Step 2 — Core objects you need to know

Stripe's data model for subscription billing boils down to five objects:

| Object | What it is |
|---|---|
| **Customer** | A person or company. Holds payment methods + subscriptions. |
| **Product** | What you sell (e.g. "Plus plan"). |
| **Price** | How much and how often (e.g. "$10 / month"). |
| **Subscription** | A Customer's ongoing agreement to pay Prices. |
| **Invoice** | A single bill against a Subscription (or one-time charge). |

Two more you'll see constantly in webhooks:

| Object | What it is |
|---|---|
| **Checkout Session** | The hosted UI where a user actually pays. |
| **Event** | A thing that happened, posted to your webhook. |

That's the whole vocabulary. Every other object is a detail under one of these seven.

## Step 3 — How the objects relate

```
Customer ───┬──> PaymentMethod
            ├──> Subscription ──> Price ──> Product
            └──> Invoice ──────> Subscription
```

Spoken aloud: "A customer has payment methods and subscriptions. A subscription is pegged to a price. A price sells a product. An invoice attributes to a subscription."

When something goes wrong, always ask: which arrow did my code follow, and which arrow should it have followed?

## Step 4 — API versions

Stripe uses *dated* API versions. The latest when writing this course is `2026-03-25.dahlia`. Old versions keep working forever (they're that careful), but new fields only appear in newer versions.

Our Stripe client pins the version explicitly:

```ts
import Stripe from 'stripe';
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!, {
	apiVersion: '2026-03-25.dahlia'
});
```

Why pin? So a future Stripe API change doesn't silently alter your webhook payload at 3 AM.

## Step 5 — The API reference's layout

Open https://stripe.com/docs/api. Every object page follows the same structure:

- **The [object] object** — every field + its type.
- **Create / Retrieve / Update / Delete** — the REST methods.
- **List / Search** — filters, pagination.
- **Events** — list of webhook events this object emits.

Example flow: you want to know what fields are on a subscription when it renews. Open *Subscription* → scroll to *The subscription object* → find `current_period_end`. Done.

## Step 6 — Read-oriented vs. write-oriented fields

Some fields are **read-only** (set by Stripe): `id`, `created`, `current_period_end`. You can GET them, never POST.

Some are **write-only at create** (`success_url` on Checkout Sessions) — set them on creation and they're persisted, but you can't PATCH them.

Some are **mutable** (`metadata`, `cancel_at_period_end`) — update freely.

The API reference labels these. When in doubt: try it in test mode; Stripe rejects forbidden writes.

## Step 7 — Metadata is your friend

Every major Stripe object has a `metadata` field — a free-form `Record<string, string>` up to 50 keys. This is your bridge between Stripe and your app. Examples we'll use:

- On a Checkout Session: `metadata: { user_id: 'uuid', tier: 'plus' }` — so the webhook knows who's paying for what.
- On a Subscription: `metadata: { source: 'upgrade-from-free' }` — analytics breadcrumbs.
- On a Customer: `metadata: { user_id: 'uuid' }` — reverse lookup from Stripe to your DB.

We'll use metadata a lot. The key rule: **never use metadata as the source of truth** — if Stripe lost the metadata tomorrow, your app should still work from its own DB. Metadata is for convenience + analytics, not critical data.

## Step 8 — The dashboard ↔ API parity

A key aha moment for many devs: *everything* you see in the dashboard exists in the API. Every button in the dashboard calls an API method. When you click "Cancel subscription," the dashboard calls `stripe.subscriptions.update(id, { cancel_at_period_end: true })`. That's why we can replicate any support action via code — and why we can verify our code's behavior in the dashboard.

## Step 9 — How to search the docs productively

- **API reference** (`/docs/api`) has a Cmd+K search that only searches objects/fields. Use it first.
- **Guides** (`/docs`) has a broader search. Use it when "which object do I need?" is the question.
- **Stack Overflow + GitHub** for edge cases and error messages. Stripe's official forum is less active.

## Verify

- You can name the five core objects from memory.
- You know where the API version pin goes.
- You can find `current_period_end` on a Subscription in under 30 seconds.

## Common traps

- **Reading a Stripe guide from 2019.** Always check the date. API versions and best practices shift.
- **Using `latest` as your API version.** Don't. You want deterministic payloads. Pin a date.
- **Ignoring `metadata` and instead shoving IDs into `description`.** `description` is for humans (invoices, receipts). `metadata` is for code. Don't cross the streams.

## Recap

Stripe's API has five objects, a sensible REST surface, and unusually good docs. Pin the API version, lean on metadata, read the object reference first. Next we'll set up the Stripe CLI for local webhook testing.
