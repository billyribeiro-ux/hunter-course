# 1.4 — Profiles Table & RLS

> Your first real table. Your first RLS policy. Your first real database trigger.

## Why this matters

`auth.users` is managed by Supabase and opaque to your app. If you want to store domain data about a user — their display name, their avatar, their favorite sandwich — you need your own table. That table is almost always called `profiles` and it lives in `public` with RLS enabled.

## The Principal Engineer lens

Three design choices that feel small but pay off for years:

1. **Key `profiles.id` to `auth.users.id`.** Not a separate FK column. Same UUID, same PK. Fewer joins, impossible to get out of sync.
2. **Auto-create a profile via trigger.** Not from the app. If a user ever exists in `auth.users` without a profile, your joins break. Trigger guarantees the invariant.
3. **RLS from day one.** Not "we'll add it later." Later is the breach.

## Step 1 — Create a migration

Supabase tracks migrations in `supabase/migrations/` with a timestamp prefix. Create one:

```bash
pnpm supabase migration new profiles
```

That creates `supabase/migrations/<timestamp>_profiles.sql`. Replace its contents with:

```sql
-- ─────────────────────────────────────────────────────────────────────────────
-- Profiles table
--
-- One row per user. Keyed by auth.users.id. Populated automatically by a
-- trigger on auth.users so we never have an orphan auth row without a profile.
--
-- RLS: users can read/update only their own row.
-- ─────────────────────────────────────────────────────────────────────────────

create table public.profiles (
    id          uuid primary key references auth.users(id) on delete cascade,
    full_name   text,
    updated_at  timestamptz not null default now()
);

alter table public.profiles enable row level security;

create policy "Profiles are readable by owner"
    on public.profiles for select
    using (auth.uid() = id);

create policy "Profiles are updatable by owner"
    on public.profiles for update
    using (auth.uid() = id)
    with check (auth.uid() = id);

-- ── Auto-create a profile when a new auth user is inserted ───────────────────
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
    insert into public.profiles (id, full_name)
    values (new.id, coalesce(new.raw_user_meta_data ->> 'full_name', ''));
    return new;
end;
$$;

create trigger on_auth_user_created
    after insert on auth.users
    for each row
    execute function public.handle_new_user();
```

Line-by-line, the interesting bits:

- `references auth.users(id) on delete cascade` — if an auth user is deleted, their profile goes too. No orphans.
- `alter table ... enable row level security` — this is the magic sentence. Without it, policies are ignored and everything is readable.
- `auth.uid()` — Supabase's function that returns the current JWT's user ID (or NULL for anon). It's the linchpin of every RLS policy you'll write.
- `using (...)` controls SELECT, UPDATE, DELETE visibility. `with check (...)` controls INSERT/UPDATE values.
- `security definer set search_path = public` — the trigger runs with the table-owner's rights but with a fixed search path, preventing search-path attacks.

## Step 2 — Apply the migration

```bash
pnpm supabase:reset
```

This drops your dev DB, re-applies all migrations in order, and re-runs `seed.sql`. Should take ~3 seconds.

Open Studio at http://127.0.0.1:54323 → **Tables** → you should see `profiles`. Click **Policies** → you should see two policies.

## Step 3 — Test the trigger

We don't have an auth flow yet, but we can simulate it from the Studio SQL editor:

```sql
insert into auth.users (id, email, aud, role, instance_id)
values ('11111111-1111-1111-1111-111111111111', 'test@test.com', 'authenticated', 'authenticated', '00000000-0000-0000-0000-000000000000');

select * from public.profiles;
```

You should see one row with that exact ID. The trigger fired.

Clean up:

```sql
delete from auth.users where id = '11111111-1111-1111-1111-111111111111';
```

## Step 4 — Test the RLS

Still in Studio, switch the role (top-right dropdown) from `postgres` to `anon` (or `authenticated`). Try:

```sql
select * from public.profiles;
```

As `anon`: empty result (no policy allows it). As `authenticated` with no JWT: empty. As the actual user whose JWT matches `auth.uid()`: their row.

> **If this confuses you**, that's normal. RLS is genuinely one of the trickier parts of Postgres to internalize. Stare at it for a minute; then re-read [Supabase's RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security). It will click.

## Step 5 — Commit

```bash
git add supabase/migrations/
git commit -m "feat(db): add profiles table with RLS + auto-create trigger"
```

## Verify

```bash
pnpm supabase:reset
```

Should complete without errors and recreate the table.

## Common traps

- **Forgot `enable row level security`.** Your table is world-readable. This is the #1 Supabase mistake. Double-check with:
  ```sql
  select tablename, rowsecurity from pg_tables where schemaname = 'public';
  ```
  `rowsecurity` must be `t` for every app table.

- **Policy is on the wrong side.** `using` ≠ `with check`. For UPDATE we set both to the same expression; for INSERT you only need `with check`.

- **Trigger doesn't fire because search_path is wrong.** We set `set search_path = public` in the function — without that, `insert into public.profiles` would work but `insert into profiles` would fail under some extensions.

- **Supabase Auth email confirmation** is on. Signups don't finish (and the trigger doesn't fire) until the user clicks the confirmation link. That's why we turned it off locally.

## Recap

You have a `profiles` table, RLS that limits it to the owner, and a trigger that auto-creates a row on signup. Three concepts: migrations, policies, triggers. Every table you add from now on will follow this pattern.
