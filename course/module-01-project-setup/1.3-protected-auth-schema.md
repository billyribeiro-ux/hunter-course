# 1.3 — Protected Auth Schema

> Why your app should never expose the `auth` schema — and how to make sure it doesn't.

## Why this matters

Supabase auto-exposes schemas listed in `config.toml`'s `[api] schemas` to PostgREST. By default that's `public`. But Supabase Auth stores its tables in a schema called `auth` — users, sessions, tokens. If you accidentally expose it, anyone with your anon key can probe user rows (rate limits and RLS help, but you don't want to find out the hard way).

## The Principal Engineer lens

**Principle of least privilege.** Your app doesn't need direct SELECT access to `auth.users` — ever. It needs:

- Supabase Auth SDK calls (`signUp`, `signInWithPassword`, `getUser`) that use a secure session-aware endpoint.
- A way to *join* auth users to your domain tables (contacts, profiles). That's what foreign keys to `auth.users(id)` are for — and Postgres enforces them without exposing the table.

If you ever find yourself writing `select * from auth.users`, stop and ask: "am I reaching into a system schema because I modeled my own tables wrong?"

## Step 1 — Confirm your API schemas

In `supabase/config.toml`:

```toml
[api]
enabled = true
port = 54321
schemas = ["public"]
extra_search_path = ["public", "extensions"]
```

Only `public` is exposed. `auth`, `storage`, `realtime`, etc. are internal.

## Step 2 — Why `extra_search_path`?

Some Supabase features (gen_random_uuid(), vector, etc.) live in the `extensions` schema. Adding it to the search path lets you write `gen_random_uuid()` in migrations without typing `extensions.gen_random_uuid()`. You do **not** want to expose `extensions` over the API.

## Step 3 — A test that proves it

Let's poke the API with the anon key to confirm:

```bash
ANON=$(pnpm --silent supabase status | awk -F': ' '/anon key/ {print $2}')
curl -s "http://127.0.0.1:54321/rest/v1/users?select=*" \
  -H "apikey: $ANON" \
  -H "Authorization: Bearer $ANON" | jq .
```

You should get something like:

```json
{
  "code": "PGRST205",
  "message": "Could not find the table 'public.users' in the schema cache"
}
```

PostgREST tried to find `public.users`, not `auth.users`. Perfect.

## Step 4 — The one time you *do* touch auth.*

Triggers. When a user signs up via Supabase Auth, we want to auto-create a row in `public.profiles`. The trigger is defined on `auth.users`, but runs as `security definer` with a locked-down search path — which is exactly what we'll set up in Lesson 1.4.

Principal Engineer rule: triggers on auth tables are OK; queries are not.

## Step 5 — Remember this when you write CLI commands

Whenever you use `supabase db` commands, you're authenticating as `postgres` superuser — which bypasses RLS and schema restrictions. That's fine (it's a local dev tool), but it means *everything works in the Supabase Studio SQL editor too*. You need to keep the mental model: PostgREST (your app) is restricted; `psql`/Studio is not. Your RLS policies will be tested against the app, not Studio.

## Verify

Run the `curl` above. Any result that doesn't include actual auth user rows is correct.

## Common traps

- **Someone adds `"auth"` to `[api] schemas`**. This is almost always a mistake — there are legit tools that want it (e.g. admin dashboards built on Supabase), but for an app like ours, never.
- **You try `select *` on `auth.users` from a `+page.server.ts`**. It'll fail via the anon client (good). Don't "fix" it by reaching for the service-role client — fix the model instead (join through your own tables).

## Recap

The only schema your app talks to over PostgREST is `public`. Everything else is reachable via Supabase SDK methods that enforce their own auth rules. That's a boundary worth defending.
