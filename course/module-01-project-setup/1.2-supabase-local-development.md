# 1.2 — Supabase Local Development

> Run the entire Supabase stack on your laptop. No cloud needed for the next 10 modules.

## Why this matters

If your dev loop requires the internet, every test you write is a slow test, and every "quick fix" is a 10-minute wait for a migration to deploy. Supabase local changes that: Postgres, Auth, Realtime, Inbucket (mock SMTP), and Studio all run in Docker on your machine. You can reset the DB in 2 seconds. You can run CI against it. It's the *best* thing about the Supabase DX.

## The Principal Engineer lens

"Local first" isn't just convenient — it's a correctness statement. If your migrations run in local dev, they'll run in CI. If they run in CI, they'll run in production. A Principal Engineer never tests migrations against production Postgres; that's how databases get corrupted.

## Step 1 — Ensure Docker is running

```bash
docker info | head -3
```

If Docker isn't running, start Docker Desktop now. `supabase start` will download several GB of images on the first run — this is a one-time event.

## Step 2 — Initialize Supabase

From the `app/` directory:

```bash
pnpm supabase init
```

(We already installed `supabase` as a dev dependency; the `pnpm supabase` prefix uses that local binary.)

This creates a `supabase/` directory with:

```
supabase/
├── config.toml       # local-service configuration
├── migrations/       # your SQL migrations (empty for now)
└── seed.sql          # data to seed after `supabase db reset`
```

## Step 3 — Tune the config

Open `supabase/config.toml` and edit these sections:

```toml
project_id = "contactly"

[api]
enabled = true
port = 54321
schemas = ["public"]
extra_search_path = ["public", "extensions"]
max_rows = 1000

[db]
port = 54322
shadow_port = 54320
major_version = 17

[studio]
enabled = true
port = 54323

[auth]
enabled = true
site_url = "http://localhost:5173"
additional_redirect_urls = ["http://localhost:5173/auth/callback"]
jwt_expiry = 3600
enable_signup = true
enable_confirmations = false    # OFF for local dev; ON in production.

[auth.email]
enable_signup = true
double_confirm_changes = true
enable_confirmations = false

[inbucket]
enabled = true
port = 54324

[storage]
enabled = false                  # we don't need file storage
```

Two Principal-Engineer notes:

- **`enable_confirmations = false` in local only.** We don't want to wait for a confirmation click during rapid iteration. Production will re-enable it (Module 12).
- **`storage.enabled = false`.** If you don't use a service, don't run it. Fewer containers, faster startup.

## Step 4 — Start Supabase

```bash
pnpm supabase:start
```

First run downloads ~2 GB of images. Get a coffee. When done, you'll see:

```
   API URL: http://127.0.0.1:54321
  GraphQL URL: http://127.0.0.1:54321/graphql/v1
       DB URL: postgresql://postgres:postgres@127.0.0.1:54322/postgres
   Studio URL: http://127.0.0.1:54323
 Inbucket URL: http://127.0.0.1:54324
   anon key: eyJ...
service_role key: eyJ...
```

**Save these keys.** The anon key goes in `.env.local` next lesson; the service-role key also goes in `.env.local` but never leaves the server.

Verify:
- Studio at http://127.0.0.1:54323 — you should see a SQL editor and empty tables list.
- Inbucket at http://127.0.0.1:54324 — empty inbox.

## Step 5 — The day-to-day commands

```bash
pnpm supabase:status       # show URLs/keys again
pnpm supabase:stop         # gracefully stop containers
pnpm supabase:reset        # drop DB + re-run migrations + re-run seed
```

`supabase db reset` is the single most useful command you'll run during development. When something's weird, reset. When you merge a branch, reset. When tests misbehave, reset. It takes ~3 seconds.

## Step 6 — Scripts

Add these to your `package.json` scripts block:

```json
{
  "scripts": {
    "supabase:start": "supabase start",
    "supabase:stop": "supabase stop",
    "supabase:status": "supabase status",
    "supabase:reset": "supabase db reset",
    "supabase:types": "supabase gen types typescript --local > src/lib/types/database.types.ts"
  }
}
```

We'll use `supabase:types` in Lesson 2.2 to regenerate TypeScript types from our schema.

## Verify

```bash
pnpm supabase:status
```

Should print the same URLs/keys. `curl http://127.0.0.1:54321/rest/v1/` should return an empty object or a schema discovery response.

## Common traps

- **Port conflict.** If `54321` is taken (rare), change ports in `config.toml`. Keep them consistent with what you put in env vars.
- **Docker out of space.** Supabase images are big; `docker system prune -a` helps.
- **Changes to `config.toml` don't apply.** You must `supabase stop && supabase start` for config changes to take effect.
