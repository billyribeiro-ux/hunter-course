# 4.6 — Updating Contacts

> Reuse the form, add an ID, change the verb. Same pattern as create.

## Why this matters

If create is the hardest write (new row, new ID, new invariants), update is the easiest — all the hard stuff already exists. The worthwhile nuances are (a) making the form component do double duty for both create and update, and (b) picking an interaction model that's obvious: row → click → edit inline or in a dialog? We'll go with the dialog (same as create) for consistency.

## The Principal Engineer lens

**DRY the form, not the handler.** One `ContactForm` component, two remote functions (`createContact`, `updateContact`). Don't try to DRY the handlers — the shapes of insert and update are subtly different (update needs an ID; insert doesn't), and conflating them leads to `if mode === 'create'` branches.

## Step 1 — Add `updateContact` to the remote file

Extend `src/routes/(app)/contacts/contacts.remote.ts`:

```ts
// add to src/routes/(app)/contacts/contacts.remote.ts

const UpdateContactSchema = z.object({
	id: z.string().uuid('Invalid contact id'),
	full_name: z.string().trim().min(1, 'Name is required').max(100),
	email: z.string().trim().toLowerCase().email('Enter a valid email').or(z.literal('')).optional(),
	phone: z.string().trim().max(40).optional(),
	notes: z.string().trim().max(1000).optional()
});

export const updateContact = form(UpdateContactSchema, async ({ id, full_name, email, phone, notes }) => {
	const event = getRequestEvent();
	const user = requireUser(event);

	const { data, error } = await event.locals.supabase
		.from('contacts')
		.update({
			full_name,
			email: email || null,
			phone: phone || null,
			notes: notes || null
		})
		.eq('id', id)
		.eq('user_id', user.id) // ← defense-in-depth; RLS also enforces it
		.select()
		.single();

	if (error) return { ok: false as const, message: error.message };
	if (!data) return { ok: false as const, message: 'Contact not found.' };
	return { ok: true as const, contact: data };
});
```

Details:

- **`id: z.string().uuid(...)`** — the schema validates that the ID is a UUID, reducing the chance of garbage queries. (Postgres would error anyway, but catching it earlier gives a better UX.)
- **`.eq('id', id).eq('user_id', user.id)`** — two filters. The first targets the row; the second ensures the row is ours. If RLS fails (policy bug, admin bypass), the `user_id` filter is another layer.
- **`.select().single()` after update** — we get the new row back to update the UI atomically.

## Step 2 — Evolve `ContactForm` to handle both modes

Edit `src/routes/(app)/contacts/ContactForm.svelte`:

```svelte
<script lang="ts">
	import type { Contact } from '$lib/types/db';
	import { createContact, updateContact } from './contacts.remote';

	interface Props {
		contact?: Contact;
		onDone: (c: Contact | null) => void;
	}
	let { contact, onDone }: Props = $props();

	const isEdit = $derived(!!contact);
	const action = $derived(isEdit ? updateContact : createContact);
	const result = $derived(action.result);

	$effect(() => {
		if (result?.ok) onDone(result.contact);
	});
</script>

<form method="POST" {...action} class="space-y-3">
	{#if isEdit}
		<input type="hidden" name="id" value={contact!.id} />
	{/if}

	<label class="block text-sm">
		<span class="mb-1 block text-text-2">Full name</span>
		<input
			name="full_name"
			required
			autofocus
			defaultValue={contact?.full_name ?? ''}
			class="w-full rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-brand-500"
		/>
	</label>
	<label class="block text-sm">
		<span class="mb-1 block text-text-2">Email</span>
		<input
			type="email"
			name="email"
			defaultValue={contact?.email ?? ''}
			class="w-full rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-brand-500"
		/>
	</label>
	<label class="block text-sm">
		<span class="mb-1 block text-text-2">Phone</span>
		<input
			name="phone"
			defaultValue={contact?.phone ?? ''}
			class="w-full rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-brand-500"
		/>
	</label>
	<label class="block text-sm">
		<span class="mb-1 block text-text-2">Notes</span>
		<textarea
			name="notes"
			rows="3"
			defaultValue={contact?.notes ?? ''}
			class="w-full rounded-lg border border-border-1 bg-surface-0 px-3 py-2 text-text-1 focus:outline-none focus:ring-2 focus:ring-brand-500"
		></textarea>
	</label>

	{#if result && !result.ok}
		<div role="alert" class="rounded-lg border border-red-500/30 bg-red-500/10 px-3 py-2 text-sm text-red-500">
			{result.message}
		</div>
	{/if}

	<div class="flex items-center justify-end gap-2 pt-2">
		<button
			type="button"
			class="rounded-lg border border-border-1 px-3 py-2 text-sm text-text-1 hover:bg-surface-0"
			onclick={() => onDone(null)}
		>
			Cancel
		</button>
		<button
			type="submit"
			class="rounded-lg bg-brand-500 px-4 py-2 text-sm font-medium text-white hover:bg-brand-600"
		>
			{isEdit ? 'Save changes' : 'Save contact'}
		</button>
	</div>
</form>
```

Changes:

- **Optional `contact` prop** — absence means "create mode," presence means "edit mode."
- **`const action = $derived(isEdit ? updateContact : createContact)`** — pick the remote function based on mode.
- **`<input type="hidden" name="id" value={contact!.id}>`** — pass the ID in edit mode. Hidden field, not a JS-only thing; it survives no-JS submits.
- **`defaultValue={contact?.full_name ?? ''}`** — seeds the inputs when editing, leaves them empty when creating.

## Step 3 — Make a row clickable and show the edit dialog

Update `src/routes/(app)/contacts/ContactRow.svelte`:

```svelte
<script lang="ts">
	import type { Contact } from '$lib/types/db';

	interface Props {
		contact: Contact;
		onEdit: (c: Contact) => void;
	}
	let { contact, onEdit }: Props = $props();

	function initials(name: string) {
		return name
			.split(/\s+/)
			.slice(0, 2)
			.map((s) => s[0]?.toUpperCase() ?? '')
			.join('');
	}
</script>

<li>
	<button
		type="button"
		class="flex w-full items-center gap-4 px-4 py-3 text-left hover:bg-surface-0 focus:bg-surface-0 focus:outline-none"
		onclick={() => onEdit(contact)}
	>
		<span class="grid h-9 w-9 shrink-0 place-items-center rounded-full bg-brand-500/10 text-sm font-semibold text-brand-500">
			{initials(contact.full_name)}
		</span>
		<div class="min-w-0 flex-1">
			<p class="truncate text-sm font-medium text-text-1">{contact.full_name}</p>
			<p class="truncate text-xs text-text-2">{contact.email ?? contact.phone ?? '—'}</p>
		</div>
	</button>
</li>
```

Row is now a `<button>` — accessible, focusable with Tab, activatable with Enter/Space.

## Step 4 — Wire the edit dialog into the page

Update `src/routes/(app)/contacts/+page.svelte`:

```svelte
<script lang="ts">
	import Dialog from '$lib/components/Dialog.svelte';
	import ContactForm from './ContactForm.svelte';
	import ContactRow from './ContactRow.svelte';
	import { getContacts } from './contacts.remote';
	import type { Contact } from '$lib/types/db';

	let showCreate = $state(false);
	let editing = $state<Contact | null>(null);

	const contactsPromise = $derived(getContacts());
</script>

<div class="flex items-center justify-between">
	<h1 class="text-2xl font-semibold text-text-1">Contacts</h1>
	<button
		class="rounded-lg bg-brand-500 px-4 py-2 text-sm font-medium text-white hover:bg-brand-600"
		onclick={() => (showCreate = true)}
	>
		+ New contact
	</button>
</div>

{#await contactsPromise}
	<div class="mt-8 space-y-2">
		{#each { length: 3 } as _}
			<div class="h-14 animate-pulse rounded-lg bg-surface-1"></div>
		{/each}
	</div>
{:then contacts}
	{#if contacts.length === 0}
		<div class="mt-10 rounded-xl border border-dashed border-border-1 bg-surface-1 p-10 text-center">
			<p class="text-base text-text-1">No contacts yet</p>
			<p class="mt-1 text-sm text-text-2">Click "New contact" to add your first one.</p>
		</div>
	{:else}
		<ul class="mt-6 divide-y divide-border-1 overflow-hidden rounded-xl border border-border-1 bg-surface-1">
			{#each contacts as c (c.id)}
				<ContactRow contact={c} onEdit={(c) => (editing = c)} />
			{/each}
		</ul>
	{/if}
{:catch err}
	<div role="alert" class="mt-8 rounded-lg border border-red-500/30 bg-red-500/10 px-4 py-3 text-sm text-red-500">
		Couldn't load contacts: {err.message}
	</div>
{/await}

<Dialog open={showCreate} title="New contact" onClose={() => (showCreate = false)}>
	<ContactForm
		onDone={() => {
			showCreate = false;
			void getContacts().refresh();
		}}
	/>
</Dialog>

<Dialog open={editing !== null} title="Edit contact" onClose={() => (editing = null)}>
	{#if editing}
		<ContactForm
			contact={editing}
			onDone={() => {
				editing = null;
				void getContacts().refresh();
			}}
		/>
	{/if}
</Dialog>
```

Two dialogs, same `ContactForm`, different props. Refresh the list after either flow.

## Step 6 — Why not inline edit?

Inline editing (click a cell, edit in place) is a great UX but has real cost: focus management, Escape-to-cancel, Enter-to-save, optimistic updates, conflict handling. We punt on it because:

- Dialogs are lower risk and faster to ship.
- The same `ContactForm` works for both actions — single code path.
- Inline edit becomes worth it when you have dozens of cells per row. We have four.

If you want inline later, the model doesn't change; only the view.

## Verify

- Clicking a row opens the edit dialog with prefilled values.
- Saving updates the row in place.
- Cancel leaves it unchanged.
- Validation errors display inline, same as create.

## Common traps

- **Using `value={...}` on the inputs instead of `defaultValue={...}`.** `value` locks the input to the prop, so users can't type. `defaultValue` seeds and then steps aside.
- **Skipping the `user_id` filter in the update query.** RLS catches it, but belt-and-suspenders saves the day when policies get edited.
- **Updating `updated_at` manually in the handler.** Our trigger handles it. Don't double-write.
