# 4.7.1 — Close Modal on Cancel

> A tiny UX fix that prevents a whole category of "did it save?" confusion.

## Why this matters

This is a micro-lesson — shorter than the others — because the topic is small, but the bug it prevents is annoying: after clicking **Cancel** in the contact form, we want the dialog closed cleanly (no half-rendered form, no stale state). Same after clicking **Delete** in the edit dialog. And we want Escape and backdrop-click to behave identically.

## The Principal Engineer lens

**Consistent close semantics across every dismiss path.** The user should not have to remember which button closes the dialog vs. which just "dismisses the inner form." There's one dialog, one close, one mental model.

## Step 1 — Check all dismiss paths

Our dialogs have four ways to close:

1. **Escape key** — handled in `Dialog.svelte` via the `$effect` keyboard listener.
2. **Backdrop click** — handled in `Dialog.svelte` via `handleBackdrop`.
3. **X button** — explicit `onClose` button in `Dialog.svelte`.
4. **Cancel/Delete buttons inside the form** — calls `onDone(null)` or finishes the delete.

Paths 1–3 call the Dialog's `onClose` prop. Path 4 calls the *form's* `onDone`, which the parent page wires up to set `editing = null`.

If we wired those wrong (e.g., Cancel only hid the form but not the Dialog), we'd get ghost dialogs. Let's double-check.

## Step 2 — Audit the wiring in `+page.svelte`

From 4.6, the edit dialog reads:

```svelte
<Dialog open={editing !== null} title="Edit contact" onClose={() => (editing = null)}>
	{#if editing}
		<ContactForm
			contact={editing}
			onDone={() => {
				editing = null;
				void getContacts().refresh();
			}}
		/>
	{/if}
</Dialog>
```

- `onClose` → `editing = null` ✔
- `onDone` → `editing = null` + `getContacts().refresh()` ✔

The same logic applies to the create dialog (`showCreate`).

## Step 3 — Add a small teardown safeguard in `ContactForm`

When the dialog closes while the user is editing, we don't want any half-written `result` state to leak into the *next* opening. Remote function results live on the remote function itself (not per component), so repeated edits can show stale `result`s if we're not careful.

Update the start of `ContactForm.svelte` to reset the result on mount:

```svelte
<script lang="ts">
	import type { Contact } from '$lib/types/db';
	import {
		createContact,
		updateContact,
		deleteContact,
		getContacts
	} from './contacts.remote';
	import ConfirmDialog from '$lib/components/ConfirmDialog.svelte';
	import { onMount } from 'svelte';

	interface Props {
		contact?: Contact;
		onDone: (c: Contact | null) => void;
	}
	let { contact, onDone }: Props = $props();

	const isEdit = $derived(!!contact);
	const action = $derived(isEdit ? updateContact : createContact);
	const result = $derived(action.result);

	let confirmingDelete = $state(false);

	onMount(() => {
		// Clear any stale result from a previous mount so we don't flash an error
		// banner from a different contact/edit.
		createContact.result = undefined;
		updateContact.result = undefined;
	});

	$effect(() => {
		if (result?.ok) onDone(result.contact);
	});

	// …handleDelete unchanged…
</script>
```

> Why on mount? Because remote functions are *module-level*; their `.result` persists across navigations and re-opens. A fresh form should start empty.

## Step 4 — Double-check the confirm-dialog teardown

In `handleDelete` we have:

```ts
async function handleDelete() {
	if (!contact) return;
	await deleteContact({ id: contact.id });
	void getContacts().refresh();
	confirmingDelete = false;
	onDone(null);
}
```

If `deleteContact` throws, we don't reach `confirmingDelete = false` or `onDone(null)`. That's fine — the `ConfirmDialog`'s `busy` flag resets via the `finally` block, and the error surfaces via the unhandled promise rejection (we'll prettify with a toast in Module 13).

## Step 5 — Make sure Escape doesn't ambush the confirm dialog

Because the confirm dialog is rendered *inside* the ContactForm, which is itself *inside* the edit Dialog, we have nested dialogs. Escape on the confirm should close only the confirm — not both.

Good news: our `Dialog.svelte` is self-contained per instance and its `$effect` listener fires per mounted instance. When confirm is open, both listeners exist, but Escape calls each `onClose`. To avoid closing both at once, guard the outer:

Update `Dialog.svelte` to only handle Escape when it's the topmost open dialog. A simple-enough heuristic: stop Escape's propagation after handling:

```svelte
$effect(() => {
	if (!open) return;
	function onKey(e: KeyboardEvent) {
		if (e.key === 'Escape') {
			onClose();
			e.stopPropagation();
		}
	}
	window.addEventListener('keydown', onKey, { capture: false });
	return () => window.removeEventListener('keydown', onKey);
});
```

The capture order (last-mounted wins in bubbling phase) means the innermost dialog's listener fires first, calls `onClose`, then stops propagation — so the outer listener never sees the key. Works because we attach listeners in mount order.

> For a production app you might use a dialog-stack store, but for two levels of nesting this is fine.

## Step 6 — Smoke test all paths

```bash
pnpm dev
```

For each dismiss path, verify:

- **Create dialog**:
  - Open → Cancel → closed.
  - Open → Escape → closed.
  - Open → click backdrop → closed.
  - Open → X → closed.
  - Open → fill and Save → closed + row appears.
- **Edit dialog**:
  - Open from a row → Cancel → closed.
  - Open → Save changes → closed + row updated.
  - Open → Delete → confirm opens → Escape → confirm closed, edit dialog still open.
  - Open → Delete → confirm → Confirm → both dialogs closed + row gone.

If any combination misbehaves, trace the event and compare to the wiring above.

## Verify

- No combination of Escape/backdrop/buttons leaves a ghost dialog.
- The edit form doesn't show a stale "error" banner when opened for a different contact.
- Confirm dialog's Escape only closes the confirm.

## Common traps

- **Forgetting to clear `.result` on re-mount.** Users see a banner like "Contact not found" when opening a totally different contact.
- **Confusing `onDone` and `onClose`.** `onClose` = dismiss, no side effects. `onDone` = dismiss + the action completed. Keep them distinct.
- **Nested dialogs both listening for Escape without propagation control.** The outer closes unexpectedly, taking the inner with it.
