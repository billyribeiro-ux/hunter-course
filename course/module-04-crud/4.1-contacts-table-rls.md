# 4.1 — Contacts Table & RLS Policies

> The second table in your app. Same rigor as `profiles`, two more policies.

## Why this matters

`contacts` is the heart of Contactly. Every row belongs to a user, is only ever read or written by that user, and has a handful of simple fields — name, email, phone, notes. We'll model it carefully now because every other feature (the tier caps in Module 10, the pagination in Module 13, the E2E tests in Module 11) relies on this shape.

## The Principal Engineer lens

Three table-design habits we'll use forever:

1. **Own the primary key.** UUIDs (`gen_random_uuid()`), not bigints. Collisions are impossible across environments, and you can expose them in URLs without leaking row counts.
2. **`user_id` as a FK to `auth.users(id)` with cascade delete.** When a user leaves, their contacts leave too — zero orphans, zero manual cleanup.
3. **Four RLS policies, one per verb.** `select`, `insert`, `update`, `delete`. Don't collapse them into one "owner only" policy — separate policies make intent explicit and are easier to audit.

## Step 1 — Create a migration

```bash
pnpm supabase migration new contacts
```

Open the generated `supabase/migrations/<timestamp>_contacts.sql` and replace its contents:

```sql
-- ─────────────────────────────────────────────────────────────────────────────
-- Contacts table
--
-- One row per contact, owned by a single user. RLS enforces ownership.
-- ─────────────────────────────────────────────────────────────────────────────

create table public.contacts (
    id          uuid primary key default gen_random_uuid(),
    user_id     uuid not null references auth.users(id) on delete cascade,
    full_name   text not null,
    email       text,
    phone       text,
    notes       text,
    created_at  timestamptz not null default now(),
    updated_at  timestamptz not null default now()
);

-- Index for "my contacts ordered by most recent"
create index contacts_user_id_created_at_idx
    on public.contacts (user_id, created_at desc);

alter table public.contacts enable row level security;

-- ── RLS: a user can only see their own rows ──────────────────────────────────
create policy "Contacts: select own"
    on public.contacts for select
    using (auth.uid() = user_id);

create policy "Contacts: insert own"
    on public.contacts for insert
    with check (auth.uid() = user_id);

create policy "Contacts: update own"
    on public.contacts for update
    using (auth.uid() = user_id)
    with check (auth.uid() = user_id);

create policy "Contacts: delete own"
    on public.contacts for delete
    using (auth.uid() = user_id);

-- ── Maintain updated_at on UPDATE ────────────────────────────────────────────
create or replace function public.set_updated_at()
returns trigger
language plpgsql
as $$
begin
    new.updated_at := now();
    return new;
end;
$$;

create trigger contacts_set_updated_at
    before update on public.contacts
    for each row
    execute function public.set_updated_at();
```

Let's unpack the interesting parts:

- **`gen_random_uuid()`** is from the `pgcrypto` / `pgjwt` extensions, available via the `extensions` schema (which we added to `extra_search_path` in Lesson 1.2, so we don't need to qualify it).
- **`user_id` FK cascade delete** — user vanishes, contacts vanish.
- **Composite index `(user_id, created_at desc)`** — the exact shape of "my contacts, newest first." The index has to start with `user_id` because that's how we filter; `created_at desc` is the second key because that's how we order.
- **Four policies** — `select`/`delete` use `using`; `insert` uses `with check`; `update` uses *both* (`using` to control which rows are visible for UPDATE, `with check` to control what values you can set).
- **`updated_at` trigger** — Postgres doesn't auto-update the column on UPDATE. A trigger is the cleanest way to enforce "always current."

## Step 2 — Apply the migration

```bash
pnpm supabase:reset
```

Should take a few seconds. Open Supabase Studio at `http://127.0.0.1:54323`:

- **Tables** → `contacts` with 7 columns.
- **Database → Policies** → four policies on `contacts`.
- **Database → Functions** → `set_updated_at` function.

## Step 3 — Regenerate types

We changed the schema, so regenerate:

```bash
pnpm supabase:types
```

Open `src/lib/types/database.types.ts` — `contacts` is now a typed `Row`, `Insert`, `Update`. Add a convenience export in `src/lib/types/db.ts`:

```ts
// src/lib/types/db.ts
import type { Database } from './database.types';

export type Tables<T extends keyof Database['public']['Tables']> =
	Database['public']['Tables'][T]['Row'];
export type TablesInsert<T extends keyof Database['public']['Tables']> =
	Database['public']['Tables'][T]['Insert'];
export type TablesUpdate<T extends keyof Database['public']['Tables']> =
	Database['public']['Tables'][T]['Update'];

export type Profile = Tables<'profiles'>;
export type Contact = Tables<'contacts'>;
export type ContactInsert = TablesInsert<'contacts'>;
export type ContactUpdate = TablesUpdate<'contacts'>;
```

Now any file can `import type { Contact } from '$lib/types/db'` and get a full-fidelity type.

## Step 4 — Test RLS manually

Still in Studio SQL editor, first as `postgres` (bypasses RLS, always works):

```sql
insert into public.contacts (user_id, full_name, email)
values (
    (select id from auth.users where email = 'demo@contactly.app'),
    'Ada Lovelace',
    'ada@example.com'
);

select * from public.contacts;
```

You should see your new row.

Now switch the Studio role dropdown to `authenticated` **and** set the JWT for the demo user (Studio will prompt you). Or simulate via:

```sql
set local role authenticated;
set local request.jwt.claim.sub = '<demo user id>';

select * from public.contacts;   -- should return the row
delete from public.contacts;     -- should work (own row)
```

Try with a different `sub`:

```sql
set local request.jwt.claim.sub = '00000000-0000-0000-0000-000000000000';
select * from public.contacts;   -- empty — not your row
```

RLS working. Reset:

```sql
reset role;
```

## Step 5 — Why four policies instead of one

You'll see tutorials that do this:

```sql
-- NOT our approach
create policy "Owner only"
    on public.contacts for all
    using (auth.uid() = user_id)
    with check (auth.uid() = user_id);
```

It works, but:

- **Auditing is harder.** A reviewer can't tell at a glance that DELETE is permitted.
- **Granularity is lost.** What if you wanted "read is public, write is owner-only" later? You'd have to split the policy anyway.
- **Debugging is vaguer.** `pg_policies` shows one row; separate policies show you exactly which verb is firing.

Four policies is marginally more code and much more explicit. Pay the tax.

## Common traps

- **`for all` policy instead of four.** Works, but opaque. Split them.
- **Forgot `enable row level security`.** Your table is world-readable. Double-check with `select tablename, rowsecurity from pg_tables where schemaname = 'public';` — must be `t`.
- **`user_id` without `not null`.** A nullable FK means orphan rows are possible. Always `not null` on ownership columns.
