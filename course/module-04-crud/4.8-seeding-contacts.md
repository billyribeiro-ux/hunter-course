# 4.8 — Seeding Contacts

> A node script that pre-populates contacts for our demo users, so every fresh reset lands on a useful app.

## Why this matters

`supabase/seed.sql` runs SQL directly, which is great for static data. But we want seeded contacts with a bit of realism — names, emails, phone numbers, notes — and we want them scoped to each demo user. A tiny TypeScript script using the service-role client gives us per-user control and room to grow (next time we'll seed a pretend subscription, etc.).

We'll wire it to run automatically after `pnpm supabase:reset`, so the flow becomes: reset → seed → ready.

## The Principal Engineer lens

**Seed scripts are tests in disguise.** If the script runs, the schema accepted the inserts — meaning the columns are right, the types are right, the FKs line up. A failing seed is an early warning that a migration broke something.

Also: **idempotency**. Re-running the seed should not double-insert. Use `upsert` with a stable key so the script is safe to run twice.

## Step 1 — The script

Create `app/scripts/seed-contacts.ts`:

```ts
// app/scripts/seed-contacts.ts
import { createClient } from '@supabase/supabase-js';
import type { Database } from '../src/lib/types/database.types';

const SUPABASE_URL = process.env.PUBLIC_SUPABASE_URL ?? 'http://127.0.0.1:54321';
const SERVICE_ROLE = process.env.SUPABASE_SERVICE_ROLE_KEY;

if (!SERVICE_ROLE) {
	console.error('Missing SUPABASE_SERVICE_ROLE_KEY.');
	console.error("Run with:  env $(grep -v '^#' .env | xargs) pnpm seed:contacts");
	process.exit(1);
}

const supabase = createClient<Database>(SUPABASE_URL, SERVICE_ROLE, {
	auth: { persistSession: false, autoRefreshToken: false }
});

const demoUsers = {
	demo: '11111111-1111-1111-1111-111111111111',
	pro: '22222222-2222-2222-2222-222222222222'
};

const demoContacts = [
	{ full_name: 'Ada Lovelace', email: 'ada@analytical.engine', phone: '+44 20 7946 0958', notes: 'Early champion of mechanical computing.' },
	{ full_name: 'Grace Hopper', email: 'grace@navy.mil', phone: '+1 202 555 0188', notes: 'Invented the compiler. Never late.' },
	{ full_name: 'Alan Turing', email: 'alan@kings.cam.ac.uk', phone: '+44 122 334 5566', notes: 'Breakfast appointment: Thursday.' }
];

const proContacts = [
	{ full_name: 'Linus Torvalds', email: 'linus@kernel.org', phone: '+1 503 555 0112', notes: 'Rebase or revert.' },
	{ full_name: 'Guido van Rossum', email: 'guido@python.org', phone: '+31 20 555 0199', notes: 'Indentation matters.' },
	{ full_name: 'Margaret Hamilton', email: 'margaret@nasa.gov', phone: '+1 713 555 0118', notes: 'Shipped to the Moon.' },
	{ full_name: 'Brian Kernighan', email: 'brian@princeton.edu', phone: '+1 609 555 0166', notes: '"Hello, world!"' }
];

async function main() {
	// Verify the demo users exist before seeding contacts.
	const { data: users, error: userErr } = await supabase
		.from('profiles')
		.select('id')
		.in('id', Object.values(demoUsers));

	if (userErr) throw userErr;
	if (!users || users.length !== 2) {
		throw new Error('Demo users missing — run `pnpm supabase:reset` first.');
	}

	const rows = [
		...demoContacts.map((c) => ({ ...c, user_id: demoUsers.demo })),
		...proContacts.map((c) => ({ ...c, user_id: demoUsers.pro }))
	];

	// Upsert on (user_id, full_name) for idempotency.
	// Requires a unique index; we'll add that next.
	const { error } = await supabase
		.from('contacts')
		.upsert(rows, { onConflict: 'user_id,full_name' });

	if (error) throw error;

	console.log(`Seeded ${rows.length} contacts (${demoContacts.length} demo, ${proContacts.length} pro).`);
}

main().catch((err) => {
	console.error(err);
	process.exit(1);
});
```

Stuff to call out:

- **Admin client (service-role).** Bypasses RLS, which we need because we're writing contacts owned by two different users from one script. This is the classic legit use of admin from 4.4.
- **`upsert(... , { onConflict: 'user_id,full_name' })`** — requires a unique index on `(user_id, full_name)`. Adding it next.
- **`persistSession: false`** on the admin client — no cookies needed.
- **`process.env` values** — tsx will read these if we pipe `.env` in, or they can be passed explicitly.

## Step 2 — Add the unique index migration

```bash
pnpm supabase migration new contacts_unique
```

Contents:

```sql
-- supabase/migrations/<timestamp>_contacts_unique.sql
--
-- Unique index to support idempotent seeding via upsert.
-- Not a true business rule — users are welcome to create "John Doe" twice
-- with different emails — but seed uses stable (user_id, full_name) pairs.

create unique index if not exists contacts_user_full_name_seed_key
    on public.contacts (user_id, full_name);
```

> Strictly, this turns "two contacts with the same name" into a validation error for users. For a contact app, that's arguably fine (de-dup is a feature). If you disagree, change the seed to upsert by `(user_id, email)` or by a synthetic `seed_key` column. The lesson is about idempotency, not this specific index choice.

Apply:

```bash
pnpm supabase:reset
pnpm supabase:types
```

		"seed:contacts": "tsx scripts/seed-contacts.ts"

```

```

## Step 5 — Run it

Make sure your `.env` has `SUPABASE_SERVICE_ROLE_KEY` set (it does, from 2.1).

```bash
pnpm supabase:reset
```

You should see:

```
Finished running migrations.
Seeded 7 contacts (3 demo, 4 pro).
```

Log in as `demo@contactly.app` — three famous computer scientists in your list. Log in as `pro@contactly.app` — four more. RLS keeps them separate.

## Step 6 — Why not do it in `seed.sql`?

Three reasons:

- **We'd need raw SQL for the INSERTs**, which loses type safety.
- **Keeping node-driven seeds** means we can extend to Stripe, etc., in later modules, where only node can talk to Stripe.
- **Fail faster.** A broken migration is easier to debug when the script reports the error, rather than a cryptic `seed.sql` failure.

## Step 7 — Re-running is safe

Try it:

```bash
pnpm seed:contacts
```

Same output — no duplicates, no errors. The upsert's `onConflict` clause made the script idempotent. This matters during development: you can seed-then-test-then-break-and-seed-again without nuking your DB.

## Verify

- `pnpm supabase:reset` runs clean and ends with "Seeded ... contacts."
- Demo account has 3 contacts; Pro has 4.
- Re-running `pnpm seed:contacts` doesn't duplicate.
- Types still compile cleanly after schema change.

## Common traps

- **Forgetting `persistSession: false`** on the admin client — you'll see weird auth-related errors in logs.
- **Forgetting to add the unique index** — the upsert silently becomes regular insert, duplicates appear.
- **Running the script without `SUPABASE_SERVICE_ROLE_KEY` in env** — the script bails with a clear message. Don't commit the key.
