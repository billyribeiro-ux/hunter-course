# 4.7 — Deleting Contacts

> A destructive mutation: one remote `command()`, one confirmation dialog, one `refresh()` call.

## Why this matters

Deletes are the most dangerous mutations in any app — undo is hard, users are careless, and one missed confirmation step leads to support tickets. We'll build a delete flow that's small, obvious, and hard to misfire.

We'll also meet our second `command()` — since there's no form submission, just a "do it" button after confirmation, `command()` is the right primitive.

## The Principal Engineer lens

Three delete rules:

1. **Always confirm.** Even if the user is "sure." Click-to-delete without confirmation is a bug.
2. **Name what you're deleting** in the confirmation. Not "Delete this?" — "Delete Ada Lovelace?"
3. **Undo is a nice-to-have.** Optimistic delete with a "Undo" toast is polish; a confirm-then-delete is required. We'll skip undo for simplicity; add it later if you want.

## Step 1 — Add `deleteContact` command

Extend `src/routes/(app)/contacts/contacts.remote.ts`:

```ts
// add to src/routes/(app)/contacts/contacts.remote.ts
import { command } from '$app/server';

export const deleteContact = command(z.object({ id: z.string().uuid() }), async ({ id }) => {
	const event = getRequestEvent();
	const user = requireUser(event);

	const { error } = await event.locals.supabase
		.from('contacts')
		.delete()
		.eq('id', id)
		.eq('user_id', user.id);

	if (error) throw new Error(error.message);
});
```

Key points:

- **`command()` with `z.object({ id: z.string().uuid() })`** — a trivial schema, but it blocks malformed IDs from even reaching the database.
- **Explicit `eq('user_id', user.id)`** on the delete — we said this in 4.6, we'll say it every time.
- **`throw` on failure, return `void` on success.** Commands don't have a built-in `.result` like forms do; success/failure is promise resolution/rejection.

## Step 2 — A ConfirmDialog component

Rather than hand-roll a confirm for every destructive action, make it reusable. Create `src/lib/components/ConfirmDialog.svelte`:

```svelte
<script lang="ts">
	import Dialog from './Dialog.svelte';

	interface Props {
		open: boolean;
		title: string;
		message: string;
		confirmLabel?: string;
		destructive?: boolean;
		onConfirm: () => void | Promise<void>;
		onClose: () => void;
	}
	let {
		open,
		title,
		message,
		confirmLabel = 'Confirm',
		destructive = false,
		onConfirm,
		onClose
	}: Props = $props();

	let busy = $state(false);

	async function handleConfirm() {
		if (busy) return;
		busy = true;
		try {
			await onConfirm();
		} finally {
			busy = false;
		}
	}
</script>

<Dialog {open} {title} {onClose}>
	<p class="text-sm text-text-2">{message}</p>

	<div class="mt-6 flex items-center justify-end gap-2">
		<button
			type="button"
			class="rounded-lg border border-border-1 px-3 py-2 text-sm text-text-1 hover:bg-surface-0 disabled:opacity-60"
			disabled={busy}
			onclick={onClose}
		>
			Cancel
		</button>
		<button
			type="button"
			class="rounded-lg px-4 py-2 text-sm font-medium text-white disabled:opacity-60"
			class:bg-brand-500={!destructive}
			class:hover:bg-brand-600={!destructive}
			class:bg-red-500={destructive}
			class:hover:bg-red-600={destructive}
			disabled={busy}
			onclick={handleConfirm}
		>
			{busy ? 'Working…' : confirmLabel}
		</button>
	</div>
</Dialog>
```

Notes:

- **`busy` state** guards against double-click submissions — a real-world failure mode where the second click fires a redundant request.
- **`destructive` prop** swaps the primary button color from brand blue to red so users can't miss the gravity.

## Step 3 — Add a delete button in the edit dialog

We'll add a "Delete" action inside the edit form rather than a per-row "..." menu — keeps the UI simpler. Edit `src/routes/(app)/contacts/ContactForm.svelte` to add a delete button when editing:

```svelte
<script lang="ts">
	import type { Contact } from '$lib/types/db';
	import { createContact, updateContact, deleteContact, getContacts } from './contacts.remote';
	import ConfirmDialog from '$lib/components/ConfirmDialog.svelte';

	interface Props {
		contact?: Contact;
		onDone: (c: Contact | null) => void;
	}
	let { contact, onDone }: Props = $props();

	const isEdit = $derived(!!contact);
	const action = $derived(isEdit ? updateContact : createContact);
	const result = $derived(action.result);

	let confirmingDelete = $state(false);

	$effect(() => {
		if (result?.ok) onDone(result.contact);
	});

	async function handleDelete() {
		if (!contact) return;
		await deleteContact({ id: contact.id });
		void getContacts().refresh();
		confirmingDelete = false;
		onDone(null);
	}
</script>

<form method="POST" {...action} class="space-y-3">
	{#if isEdit}
		<input type="hidden" name="id" value={contact!.id} />
	{/if}

	<!-- ...the same input labels as before... -->

	<!-- (keep the full_name, email, phone, notes blocks unchanged) -->

	{#if result && !result.ok}
		<div role="alert" class="rounded-lg border border-red-500/30 bg-red-500/10 px-3 py-2 text-sm text-red-500">
			{result.message}
		</div>
	{/if}

	<div class="flex items-center justify-between pt-2">
		<div>
			{#if isEdit}
				<button
					type="button"
					class="rounded-lg px-3 py-2 text-sm text-red-500 hover:bg-red-500/10"
					onclick={() => (confirmingDelete = true)}
				>
					Delete
				</button>
			{/if}
		</div>
		<div class="flex items-center gap-2">
			<button
				type="button"
				class="rounded-lg border border-border-1 px-3 py-2 text-sm text-text-1 hover:bg-surface-0"
				onclick={() => onDone(null)}
			>
				Cancel
			</button>
			<button
				type="submit"
				class="rounded-lg bg-brand-500 px-4 py-2 text-sm font-medium text-white hover:bg-brand-600"
			>
				{isEdit ? 'Save changes' : 'Save contact'}
			</button>
		</div>
	</div>
</form>

{#if contact}
	<ConfirmDialog
		open={confirmingDelete}
		title="Delete contact"
		message={`Delete ${contact.full_name}? This cannot be undone.`}
		confirmLabel="Delete"
		destructive
		onClose={() => (confirmingDelete = false)}
		onConfirm={handleDelete}
	/>
{/if}
```

> Tip: keep your `<!-- ...input labels unchanged... -->` as actual code in your file — the comment above is for this lesson's brevity. You'll merge it into the existing form.

Behavior:

- **"Delete" button** on the left, separated from Cancel/Save — visual hierarchy matches severity.
- **Click Delete** → `ConfirmDialog` pops with the contact's name.
- **Confirm** → `deleteContact({ id })` runs, then we refresh the list and close the dialog.

## Step 4 — Try it

```bash
pnpm dev
```

1. Edit a contact.
2. Click **Delete** → confirm dialog, named.
3. Click **Cancel** in the confirm → nothing happens.
4. Click **Delete** in the confirm → the row is gone from the list, edit dialog closes.
5. Try deleting a contact that someone else created (you'd need to manually insert into Postgres as the other user). Your delete silently returns zero rows — RLS blocks it. No error thrown because `delete` with a filter that matches nothing is a legal no-op.

## Step 5 — What about bulk delete?

Good question — we punt. Bulk delete needs:

- Row-selection UI (checkboxes, shift-click ranges).
- A separate command with an array of IDs.
- Likely a skip-confirm-for-repeats pattern.

All doable; none essential for v1. We'll leave it as "a feature you could add in an afternoon" and move on.

## Step 6 — Don't leak delete state

Subtle bug: if we'd forgotten the `onDone(null)` call after delete, the edit dialog would stay open referencing a now-deleted `contact` object — leading to weird errors when the form tries to re-submit. Calling `onDone(null)` closes the outer edit dialog cleanly, and the next click on a row opens a fresh one.

This kind of teardown discipline matters as the app grows. Every opened UI should have a clear "I'm done now" path.

## Verify

- Delete button only appears in edit mode.
- Confirm dialog names the contact.
- Confirming actually deletes.
- List refreshes and the edit dialog closes.
- Clicking Cancel in the confirm preserves the row.

## Common traps

- **Deleting without a confirmation.** Don't. Even in internal tools. Users will cry.
- **Deleting via a page load (e.g. `/contacts/123/delete`) instead of a mutation.** That's a GET-does-a-write, which web crawlers and link prefetchers can trigger. Always POST/DELETE, never GET.
- **Forgetting `.eq('user_id', ...)`.** RLS saves you, but stacked defenses survive one broken layer.
