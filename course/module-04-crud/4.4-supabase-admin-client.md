# 4.4 — Supabase Admin Client

> The service-role client: a loaded weapon. When to reach for it, when to keep your hands off.

## Why this matters

We set up `locals.supabaseAdmin` in Lesson 2.3. It uses the `SUPABASE_SERVICE_ROLE_KEY`, which **bypasses RLS**. Every query you make with it runs as a superuser. That's dangerous — and occasionally necessary. This lesson is a short, disciplined look at when you're allowed to reach for it.

## The Principal Engineer lens

**Admin is a side door. Locked by default.** Every time you find yourself typing `supabaseAdmin`, ask: "Is the user-scoped client failing because RLS is correctly blocking this, or because I'm trying to do something RLS doesn't have a policy for?"

- If it's the first, change *what you're trying to do*, not your client.
- If it's the second — maybe you're handling a Stripe webhook with no user context, or deleting a user from the admin endpoint — then admin is the right tool.

## Step 1 — Inventory the legitimate uses

In our app, the list of places `supabaseAdmin` is acceptable:

| Use case | Why admin is needed |
|---|---|
| **Stripe webhooks** (Module 6) | No user session; we're processing a signed payload from Stripe. |
| **Account deletion** (3.6) | `auth.admin.deleteUser()` requires service-role. |
| **Tier lookups from untrusted contexts** | Not in our app, but common — e.g. a public "count of active subscribers" endpoint. |
| **Seed/migration scripts** | `seed.sql` runs as postgres which is fine; but node-side helpers use admin. |

**Everything else uses `locals.supabase`.** Listing contacts, creating contacts, updating profiles — all RLS-protected, all user-scoped.

## Step 2 — Quick re-confirm of the hook wiring

In `src/hooks.server.ts` we already have:

```ts
event.locals.supabaseAdmin = createClient<Database>(
	env.PUBLIC_SUPABASE_URL,
	env.SUPABASE_SERVICE_ROLE_KEY,
	{ auth: { persistSession: false, autoRefreshToken: false } }
);
```

Two settings worth a second look:

- **`persistSession: false`** — no cookies, no "who is logged in." This client has no concept of a user; it's just a superuser connection.
- **`autoRefreshToken: false`** — we're not using JWTs here, and there's nothing to refresh.

## Step 3 — Build a tiny audit helper

Because admin is dangerous, we want any admin use to be visible in code review. Convention: admin operations live in `src/lib/server/services/` in named functions, never inline. Create `src/lib/server/services/README.md` (optional but helpful):

```md
# Server services

Every file in this directory runs with the service-role Supabase client.
Review rules:

- No user input flows directly into a query without validation.
- Every admin operation documents *why* it needs to bypass RLS.
- Never export a service-level function to a .svelte file.
```

You don't need to create this file — it's a convention nudge. We'll actually add service files in Modules 6 and 7 for billing.

## Step 4 — Example: where admin isn't allowed

Let's imagine the wrong version of the contacts create handler:

```ts
// WRONG — don't do this
export const createContact = form(ContactSchema, async (input) => {
	const { locals } = getRequestEvent();
	await locals.supabaseAdmin.from('contacts').insert({
		user_id: input.user_id, // ← client-controlled, no RLS check!
		...input
	});
});
```

Two bugs:

1. Accepting `user_id` from the client lets an attacker write contacts as anyone.
2. Using `supabaseAdmin` means RLS can't save us if we forget the ownership check.

The version we wrote in 4.3 is correct: `user.id` from `locals`, `locals.supabase` (user-scoped) as the client. RLS would block an impersonation attempt even if the handler had a bug.

## Step 5 — Where admin *is* allowed: Stripe webhooks (preview)

Here's a snippet from Module 6 (don't build it yet) — it's the archetype of a legitimate admin use:

```ts
// src/routes/api/webhooks/stripe/+server.ts (preview)
export const POST: RequestHandler = async ({ request, locals }) => {
	const payload = await request.text();
	const sig = request.headers.get('stripe-signature') ?? '';

	// Verify the request is really from Stripe.
	const event = stripe.webhooks.constructEvent(payload, sig, env.STRIPE_WEBHOOK_SECRET);

	// There's no user session here. We use supabaseAdmin to mirror the event
	// into our billing_* tables. The payload was cryptographically verified.
	await mirrorStripeEvent(locals.supabaseAdmin, event);

	return new Response('ok');
};
```

The authorization isn't a user JWT — it's Stripe's signature on the payload. That's still authorization, just of a different kind. Admin-scoped writes are appropriate because:

- No user context exists.
- We verified the source cryptographically.
- The writes are strictly to tables the user can read via RLS but cannot write to.

## Step 6 — Self-audit checklist

Before merging any PR that uses `supabaseAdmin`, ask yourself:

1. **Is there no user session?** If there's a user, prefer user-scoped.
2. **Is the write to a `billing_*` or similar mirror table?** Good.
3. **Is the read a public aggregate (active subscriber count, etc.)?** OK, but SELECT a limited column set; don't SELECT `*`.
4. **Does every admin call write or read exactly one user's data based on a verified ID?** Good.
5. **Could an attacker manipulate any input into the admin query?** Unsafe; fix it.

If you fail question 5, stop and redesign.

## Step 7 — One practical rule

**`supabaseAdmin` never appears in a `+page.server.ts` load, a remote `query()`, or a remote `form()`.**

Those all run in the context of a signed-in user. The user-scoped client is correct there. Admin lives in:

- `+server.ts` webhook endpoints.
- `src/lib/server/services/` functions imported by webhooks or scripts.
- A specific account-deletion call in 3.6 (the one legit exception, because `auth.admin.deleteUser` requires it).

## Verify

There's nothing to "run" in this lesson — it's a design gate. But you can verify your discipline by grepping your repo:

```bash
grep -r "supabaseAdmin" src/
```

The results should look like:

- `src/hooks.server.ts` — where it's created.
- `src/routes/(app)/account/account.remote.ts` — the `deleteUser` call.
- Nothing else, for now.

In Module 6 we'll add webhook + services usage; that's also fine.

## Common traps

- **Reaching for admin because a query returns empty.** Empty usually means RLS is working and your filter is wrong. Never use admin to "fix" an RLS error in a user-context handler.
- **Using admin for "convenience reads" in SSR.** Yes, admin bypasses RLS so your queries always return rows. That's how leaks ship. Use the user client and trust the policies.
- **Importing `supabaseAdmin` directly in `.svelte` files.** SvelteKit will refuse (it's under `$lib/server/`), but you might be tempted to "just pass it down." Don't.

## Recap

`locals.supabaseAdmin` exists, is service-scoped, and is rationed to a handful of uses — all of which have strong non-user authorization (webhook signatures, verified user IDs). Everywhere else, `locals.supabase` + RLS is your default. Now, let's go read our contact list.
