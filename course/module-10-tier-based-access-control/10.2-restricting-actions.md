# 10.2 — Restricting Actions

> Server-side gating is the real fence. UI-side is the signpost.

## Why this matters

An entitlement check on a button alone is security theatre — a `curl` straight at the remote function bypasses it. Every tier-gated *mutation* must also be blocked on the server, in the remote function or `+server.ts` handler. The pattern: read `locals.tier`, call an entitlement helper from 10.1, throw if denied, proceed otherwise.

This lesson wires that pattern into `createContact` (our first concrete gated action). The same recipe applies to every future gated action; we write it once, clearly, and reuse.

## The Principal Engineer lens

**Server-side checks are non-negotiable. UI-side checks are a courtesy.** The server is the source of truth; the UI is a hint to the user. If you only have one of the two, always pick server-side. A pretty disabled button with an open endpoint behind it is worse than no gating at all, because it lulls you into false confidence.

Corollary: **the error the server throws should be machine-readable.** A structured error lets the UI display the upgrade CTA inline rather than a generic "something went wrong." We'll throw a typed `EntitlementError` that the remote-function boundary converts into a predictable HTTP response.

## Step 1 — The typed error

Create `src/lib/server/billing/errors.ts`:

```ts
// src/lib/server/billing/errors.ts
import type { TierId } from '$lib/config/pricing';

export class EntitlementError extends Error {
	readonly code = 'ENTITLEMENT_DENIED';
	readonly upgradeTo?: TierId;

	constructor(message: string, upgradeTo?: TierId) {
		super(message);
		this.name = 'EntitlementError';
		this.upgradeTo = upgradeTo;
	}
}
```

A dedicated error class lets both the server (which throws it) and the client (which catches it in the form response) discriminate it from generic errors.

## Step 2 — A tiny guard helper

Add to `entitlements.ts`:

```ts
// src/lib/server/billing/entitlements.ts (append)
import { EntitlementError } from './errors';

export function assertEntitlement(e: Entitlement): void {
	if (!e.allowed) {
		throw new EntitlementError(e.reason ?? 'Not allowed on your plan', e.upgradeTo);
	}
}
```

Three lines, but the ergonomics pay off at every call site.

## Step 3 — Wire it into `createContact`

Open `src/lib/server/contacts.remote.ts` (from Module 4.3). Current `createContact` looks roughly like:

```ts
// before
export const createContact = form(CreateContactSchema, async (data) => {
	const event = getRequestEvent();
	const { user, supabase } = await requireUser(event);

	const { data: row, error } = await supabase
		.from('contacts')
		.insert({ ...data, user_id: user.id })
		.select()
		.single();

	if (error) throw error;
	return row;
});
```

Extend it with the entitlement check:

```ts
// after
import { canAddContact, assertEntitlement } from '$lib/server/billing/entitlements';

export const createContact = form(CreateContactSchema, async (data) => {
	const event = getRequestEvent();
	const { user, supabase } = await requireUser(event);

	// 1. Count existing contacts for this user.
	const { count, error: countError } = await supabase
		.from('contacts')
		.select('*', { count: 'exact', head: true })
		.eq('user_id', user.id);
	if (countError) throw countError;

	// 2. Check entitlement.
	assertEntitlement(canAddContact(event.locals.tier, count ?? 0));

	// 3. Proceed with insert.
	const { data: row, error } = await supabase
		.from('contacts')
		.insert({ ...data, user_id: user.id })
		.select()
		.single();

	if (error) throw error;
	return row;
});
```

Four-line insert. The only structural change: a pre-insert count + entitlement check.

## Step 4 — Why not do the check in `canAddContact` using a DB call?

We could merge the count into the entitlement helper. We didn't because:

- **Purity.** The helper stays testable without a DB mock.
- **Callers know which DB to use.** Here we use `supabase` (user-scoped, RLS-enforced). Elsewhere — an admin script — the admin client might be appropriate. Decoupling the check from the query lets each call site pick.
- **Performance.** If a future caller already has the count, they shouldn't pay for a second query. Passing it in is explicit.

## Step 5 — A `head: true` count — worth explaining

`.select('*', { count: 'exact', head: true })` returns zero rows but populates `count`. Why not `select('id').then(...length)`? Because:

- `head: true` means Postgres returns *no rows* — just the count. On a user with 100,000 contacts (not Contactly's problem, but imagine), fetching all IDs would be wasteful.
- `count: 'exact'` forces a real count, not an estimate. Small tables, exact is fine; huge tables, switch to `'estimated'`. For us, exact is right.

## Step 6 — Surface the error to the client

Remote functions serialize thrown errors back to the client. Our error page / form component needs to recognise `EntitlementError` and render an upgrade prompt. In `contacts.remote.ts`, our thrown `EntitlementError` needs a specific shape when it crosses the wire — SvelteKit's `form()` transport wraps errors in a serialized envelope.

Update the remote function's thrown value to carry structured metadata. Use SvelteKit's `error()` helper with a custom payload:

```ts
import { error } from '@sveltejs/kit';
import { EntitlementError } from '$lib/server/billing/errors';

// Inside the form handler, replace `assertEntitlement(...)` with:
const ent = canAddContact(event.locals.tier, count ?? 0);
if (!ent.allowed) {
	throw error(402, {
		message: ent.reason ?? 'Not allowed on your plan',
		code: 'ENTITLEMENT_DENIED',
		upgradeTo: ent.upgradeTo
	});
}
```

Why HTTP 402 "Payment Required"? Exactly this scenario. It was invented for it and almost never used — but for us, it's semantically perfect. SvelteKit's `error()` sends a structured body the client can read.

The `assertEntitlement` helper from Step 2 is still useful for non-remote server code (admin scripts, webhook handlers). For remote functions we prefer `error(402, ...)` because SvelteKit already knows how to serialize it.

## Step 7 — The client-side catch

When `createContact` fails with a 402, our `ContactForm` component from Module 4.6 needs to render an upgrade prompt. The form's result object (`form.result`) surfaces the error:

```svelte
<script lang="ts">
	import { enhance } from '$app/forms';
	import { goto } from '$app/navigation';

	let { form: serverResult } = $props();

	// ...

	function handleSubmit({ formData }) {
		return async ({ result, update }) => {
			if (result.type === 'failure' && result.data?.code === 'ENTITLEMENT_DENIED') {
				// Show the upgrade modal rather than a form error.
				upgradeModalOpen = true;
				upgradeReason = result.data.message;
				upgradeTarget = result.data.upgradeTo;
				return;
			}
			await update(); // default behavior
		};
	}
</script>
```

The key pattern: inspect `result.data.code` first; if it's `ENTITLEMENT_DENIED`, branch to an upgrade modal. Everything else goes through the default form-failure path. Module 10.3 builds the `UpgradeModal` component; here we're just wiring the decision.

## Step 8 — Test the gate with a real user

End-to-end verification:

1. Sign in as a Free user who already has 5 contacts.
2. Try to create a 6th via the dashboard. The form submission returns 402; modal prompts "Upgrade to Plus."
3. Via DevTools → Network, inspect the failing request. The JSON body is `{ code: 'ENTITLEMENT_DENIED', upgradeTo: 'plus', message: '...' }`.
4. `curl` directly with a stolen cookie to confirm the server *also* 402s, not just the UI:

```bash
curl -i -X POST http://localhost:5173/?/contacts.remote.createContact \
	-H 'Cookie: sb-access-token=...' \
	-F 'full_name=Sixth'
```

Response: `HTTP/1.1 402 Payment Required`. The server enforces independent of the UI. That's the test that matters.

## Step 9 — Checklist for adding a new gated action

Future gated actions (CSV export, bulk-import, whatever) follow this recipe:

1. Write (or reuse) an entitlement helper in `entitlements.ts` returning `Entitlement`.
2. In the remote function or route handler, call the helper, `throw error(402, { code: 'ENTITLEMENT_DENIED', upgradeTo, message })` on denial.
3. In the UI, catch the `ENTITLEMENT_DENIED` response and show the upgrade CTA (Module 10.3).
4. Add a test that `curl`s the endpoint without the UI — pure server enforcement.

Four steps, every time. Predictable.

## Verify

- As a Free user with 5 contacts, `createContact` via the UI yields an upgrade modal.
- Direct POST to the remote endpoint returns `402` with the structured JSON body.
- Free user with 4 contacts can add a 5th (no 402).
- Plus user with 24 contacts can add a 25th but is blocked on the 26th.
- Pro user can add contacts indefinitely.

## Common traps

- **UI gating only.** A disabled button still has the endpoint behind it. Always pair UI + server.
- **Using HTTP 403 instead of 402.** 403 means "authenticated but lacking permission" — tier gating is closer to "payment required." Semantically clearer.
- **Letting the count drift.** If another tab just deleted three contacts, the count might be stale for a second. That's fine — the server recount in `createContact` uses the fresh number. Never *cache* the count on the client as truth.
- **Returning a plain 400 with a string message.** The UI has to parse human strings to decide what to do. Machine-readable codes > human strings.

## Recap

Server-side gating is four lines added to `createContact`: count, check, throw 402 on denial, proceed otherwise. The structured error lets the UI branch cleanly. Next: the UI side — disabled buttons, upgrade modals, inline prompts.
