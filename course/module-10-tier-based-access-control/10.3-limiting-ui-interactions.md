# 10.3 — Limiting UI Interactions

> The user should know what they can't do and why, *before* they try.

## Why this matters

Server-side gating (Module 10.2) stops abuse. UI-side gating prevents *confusion*. A Free user clicking "Add contact" on their 6th entry only to hit an error modal has wasted effort and learned nothing useful until the modal appeared. Much better: disable the button in the first place, show a tooltip explaining why, and link to the pricing page.

Good tier-gated UX has three moments:

1. **Pre-click**: disabled state with a reason.
2. **Click anyway** (e.g., tooltip dismissed, user insistent): modal with clear CTA.
3. **Server enforcement**: last line of defence, invisible to good-faith users.

This lesson builds moments 1 and 2, reusing the entitlement helpers from 10.1 and the error shape from 10.2.

## The Principal Engineer lens

**Disabled states need reasons.** An aria-disabled button with no explanation is hostile. Tooltips, inline hints, or badges turn a "why can't I?" into "oh, that makes sense — here's the upgrade button."

Corollary: **pass the tier and usage state down from the layout, not per-component.** If every component fetches its own tier, you have N requests and N chances for skew. The `(app)` layout loads both once; components read from `page.data`.

## Step 1 — Expose tier + usage from the layout

In `src/routes/(app)/+layout.server.ts` (the guard from Module 3.3):

```ts
// src/routes/(app)/+layout.server.ts
import type { LayoutServerLoad } from './$types';
import { requireUser } from '$lib/server/auth';

export const load: LayoutServerLoad = async (event) => {
	const { user } = await requireUser(event);
	const { supabase, tier } = event.locals;

	const { count } = await supabase
		.from('contacts')
		.select('*', { count: 'exact', head: true })
		.eq('user_id', user.id);

	return {
		user,
		tier,
		contactCount: count ?? 0
	};
};
```

Every page under `(app)` now has `page.data.tier` and `page.data.contactCount`. The count refreshes automatically after contact mutations because `form()`/`command()` invalidate layouts by default.

## Step 3 — The disabled "Add contact" button

In the contacts page component (from Module 4.5), the "New contact" button gains tier awareness:

```svelte
<script lang="ts">
	import { page } from '$app/state';
	import { canAddContact } from '$lib/shared/entitlements'; // see Step 4
	import Button from '$lib/components/Button.svelte';
	import UpgradeModal from '$lib/components/UpgradeModal.svelte';

	let upgradeOpen = $state(false);
	let entitlement = $derived(canAddContact(page.data.tier, page.data.contactCount));

	function handleClick() {
		if (!entitlement.allowed) {
			upgradeOpen = true;
			return;
		}
		// proceed to open the create dialog
		createDialogOpen = true;
	}
</script>

<Button
	onclick={handleClick}
	aria-disabled={!entitlement.allowed}
	title={entitlement.reason ?? 'Create a new contact'}
>
	New contact
</Button>

<UpgradeModal
	open={upgradeOpen}
	reason={entitlement.reason ?? ''}
	upgradeTo={entitlement.upgradeTo}
	onClose={() => (upgradeOpen = false)}
/>
```

Three subtle choices:

- **`aria-disabled` not `disabled`.** We *want* the click to still fire, so we can show the upgrade modal. A truly disabled button eats the click event.
- **`title` as a tooltip fallback.** Native, free, works without JS. We'll enhance with a proper tooltip component in Module 13 if design demands.
- **`$derived(canAddContact(...))`** — recomputes on every tier/count change. No manual invalidation.

## Step 4 — Sharing the entitlement helpers with the client

`src/lib/server/billing/entitlements.ts` lives under `$lib/server/` — SvelteKit refuses to import it from a `.svelte` file. That's correct for the server-side assertion path. But the UI also needs the pure evaluation logic.

Solution: split the file.

- `src/lib/shared/entitlements.ts` — pure functions (`tierAtLeast`, `canAddContact`, `canUseCsvImportExport`). Safe to import on client or server.
- `src/lib/server/billing/entitlements.ts` — re-exports the pure helpers, *plus* the server-only `assertEntitlement` and `EntitlementError`.

```ts
// src/lib/server/billing/entitlements.ts
export * from '$lib/shared/entitlements';
export { assertEntitlement } from './assert';
export { EntitlementError } from './errors';
```

Now UI code imports from `$lib/shared/entitlements` without dragging server code into the bundle. The helper functions have no secrets, no DB access, no `process.env` — they're pure data-in / data-out, so cross-bundle sharing is safe.

## Step 5 — The `UpgradeModal` component

`src/lib/components/UpgradeModal.svelte`:

```svelte
<script lang="ts">
	import Dialog from './Dialog.svelte';
	import type { TierId } from '$lib/config/pricing';

	type Props = {
		open: boolean;
		reason: string;
		upgradeTo?: TierId;
		onClose: () => void;
	};
	let { open, reason, upgradeTo, onClose }: Props = $props();

	const TIER_NAMES: Record<TierId, string> = { free: 'Free', plus: 'Plus', pro: 'Pro' };

	function upgradeHref(tier: TierId | undefined): string {
		if (!tier) return '/pricing';
		return `/pricing#${tier}`;
	}
</script>

<Dialog {open} title="Upgrade to continue" {onClose}>
	<p class="text-sm text-muted-foreground">{reason}</p>

	<div class="mt-6 flex gap-2 justify-end">
		<button type="button" class="rounded-md border border-border px-3 py-1.5 text-sm" onclick={onClose}>
			Not now
		</button>
		<a
			class="rounded-md bg-primary px-3 py-1.5 text-sm text-primary-foreground"
			href={upgradeHref(upgradeTo)}
		>
			{upgradeTo ? `Upgrade to ${TIER_NAMES[upgradeTo]}` : 'See plans'}
		</a>
	</div>
</Dialog>
```

Uses the `Dialog` from Module 4.3. The CTA either goes to a specific tier on the pricing page (`#plus` anchor) or to the page root. Short, clear, respectful.

## Step 6 — Inline "you're approaching the limit" hints

For Free users with 4 of 5 contacts used, a gentle heads-up is better UX than a surprise block at the next create. Add a small banner above the contacts list:

```svelte
<script lang="ts">
	import { page } from '$app/state';
	import { TIERS } from '$lib/config/pricing';

	let tierConfig = $derived(TIERS.find((t) => t.id === page.data.tier));
	let limit = $derived(tierConfig?.contactLimit ?? null);
	let remaining = $derived(limit === null ? null : Math.max(0, limit - page.data.contactCount));
	let showHint = $derived(remaining !== null && remaining > 0 && remaining <= 2);
</script>

{#if showHint}
	<div class="rounded-md border border-amber-300 bg-amber-50 px-3 py-2 text-sm dark:bg-amber-950 dark:border-amber-800">
		You have {remaining} of {limit} contact slots left.
		<a href="/pricing" class="underline">Upgrade for more</a>.
	</div>
{/if}
```

Shows up only when you're at 3–5 contacts on Free (remaining ≤ 2). Never shows for Pro (unlimited). Proactive, non-intrusive.

## Step 7 — Feature bullets with ✓ / ✗

On the pricing page (Module 8.4), each tier's bullets come from `presentation.bullets` — simple strings. For the `/account` page's plan summary, we can render a more comparative grid showing the user *what they'd gain*. Create a compact feature matrix:

```svelte
<script lang="ts">
	import { tierAtLeast } from '$lib/shared/entitlements';
	import type { TierId } from '$lib/config/pricing';

	type Props = { current: TierId };
	let { current }: Props = $props();

	type Feature = { label: string; min: TierId };
	const FEATURES: Feature[] = [
		{ label: 'Up to 5 contacts', min: 'free' },
		{ label: 'Up to 25 contacts', min: 'plus' },
		{ label: 'Unlimited contacts', min: 'pro' },
		{ label: 'Notes + search', min: 'plus' },
		{ label: 'CSV import/export', min: 'pro' },
		{ label: 'Priority email support', min: 'plus' },
		{ label: 'Premium support', min: 'pro' }
	];
</script>

<ul class="space-y-1 text-sm">
	{#each FEATURES as f (f.label)}
		<li class="flex items-center gap-2">
			<span aria-hidden="true" class={tierAtLeast(current, f.min) ? 'text-primary' : 'text-muted-foreground'}>
				{tierAtLeast(current, f.min) ? '✓' : '✗'}
			</span>
			<span class={tierAtLeast(current, f.min) ? '' : 'text-muted-foreground'}>
				{f.label}
			</span>
		</li>
	{/each}
</ul>
```

Reuses `tierAtLeast`. Pro users see every ✓. Free users see which features light up if they upgrade. No duplicated config — feature list declared once.

## Step 8 — Accessibility pass

- **Disabled buttons stay focusable.** `aria-disabled="true"` rather than the `disabled` attribute means screen readers announce the state *and* the tooltip reason.
- **Modals trap focus.** The `Dialog` component from Module 4.3 already handles this.
- **Upgrade CTAs use `<a>` for navigation, not `<button>`.** Correct semantics for "go to another page."
- **Don't rely on colour alone.** The ✓/✗ characters convey the state without depending on green/grey contrast.

## Step 9 — Don't overdo it

Every gated surface is a surface that has to stay in sync when you change tiers. Gating every minor UI element ("Plus-only: font weight slider!") is a quick road to 30 places to update next time you reshuffle pricing. Gate the *structural* features — counts, feature toggles — and leave cosmetic differences alone.

## Verify

- Free user at 5 contacts: "New contact" button is `aria-disabled`, tooltip shows the reason, click opens the upgrade modal.
- Free user at 4 contacts: banner shows "You have 1 of 5 contact slots left."
- Plus user at 25 contacts: banner gone (or says the Plus-specific message), button disabled, modal offers upgrade to Pro.
- Pro user: no banner, no disabled state, no modals. Unlimited.
- The feature matrix in `/account` highlights the correct set of rows for each tier.

## Common traps

- **Using `disabled` instead of `aria-disabled` on the gated button.** The click event doesn't fire → no modal → no discoverability.
- **Fetching `tier` in every gated component.** Load once in the layout. Components read from `page.data`.
- **Hardcoding tier labels (`"Plus"`, `"Pro"`) in component text.** Put them in one map, reuse. When marketing renames Plus to "Creator," you change one file.
- **Forgetting to invalidate after an upgrade.** When a user returns from Stripe's Customer Portal, `page.data.tier` is stale. Module 13.2 covers the better-redirect pattern that invalidates on return.
- **Assuming `contactCount` is always fresh.** It updates after mutations via layout invalidation, but out-of-band changes (direct DB edit, webhook-driven) may lag. Re-verify on server during the actual mutation (Module 10.2 already does).

## Recap

UI now tells users *before* they try what they can and can't do. Disabled states carry reasons; inline banners warn before the block; modals offer a one-click upgrade. Combined with the server-side gate from 10.2, every tier-gated feature has defence in depth. Next: the last piece — preventing a user from ending up on two paid plans at once.
