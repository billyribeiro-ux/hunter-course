# 10.1 — Validate Tier Helpers

> Three pure functions that answer "can this user do this thing?" without anyone arguing.

## Why this matters

By now, Contactly has tiers (Free / Plus / Pro), contact limits (5 / 25 / unlimited), and a subscriptions table that reflects Stripe. The remaining gap: a single place where the app asks "given user X's current subscription, can they do Y?" If every feature answers that question its own way, you end up with ten slightly different `if` statements and no unified idea of "what a Plus user can do."

This lesson centralises the logic in a tiny module (`src/lib/server/billing/entitlements.ts`) that every gated feature in Modules 10.2–10.4 will import. Three helpers, no surprises, easy to test.

## The Principal Engineer lens

**Entitlements are a pure function of `(tier, resource) → allowed | denied + reason`.** Once you internalise that, the rest of tier-based access control is plumbing. Everywhere a user tries to do something gated, you call the function, check the result, and either proceed or explain why not.

Corollary: **the function must not read the database.** Pass the tier in as an argument. The database lookup happens once per request (in the route guard), result reused across all entitlement checks. Pure functions are also trivially testable — no mocks.

## Step 1 — The tier ordering

Tiers have an implicit hierarchy: Pro > Plus > Free. Any action that Plus can do, Pro can also do. Encode this so we don't write `tier === 'plus' || tier === 'pro'` a hundred times:

```ts
// src/lib/server/billing/entitlements.ts
import type { TierId } from '$lib/config/pricing';

const RANK: Record<TierId, number> = {
	free: 0,
	plus: 1,
	pro: 2
};

export function tierAtLeast(actual: TierId, minimum: TierId): boolean {
	return RANK[actual] >= RANK[minimum];
}
```

One function. Dozens of call sites read better:

```ts
if (tierAtLeast(userTier, 'plus')) { /* show premium feature */ }
```

vs. the string-comparison soup it replaces.

## Step 2 — The contact-limit entitlement

The most common entitlement in Contactly is "can this user add one more contact?" It depends on both their tier *and* their current contact count. Model it:

```ts
// src/lib/server/billing/entitlements.ts (append)
import { TIERS } from '$lib/config/pricing';

export interface Entitlement {
	allowed: boolean;
	reason?: string; // set when allowed = false
	upgradeTo?: TierId; // hint for UI: "upgrade to <this> to unlock"
}

export function canAddContact(tier: TierId, currentCount: number): Entitlement {
	const cfg = TIERS.find((t) => t.id === tier);
	const limit = cfg?.contactLimit ?? 0;

	if (limit === null) return { allowed: true };
	if (currentCount < limit) return { allowed: true };

	// Over the limit — pick the next paid tier as the upgrade hint.
	const next: TierId | undefined =
		tier === 'free' ? 'plus' : tier === 'plus' ? 'pro' : undefined;

	return {
		allowed: false,
		reason:
			tier === 'pro'
				? `You've reached the contact limit for Pro — contact support.`
				: `You've reached the ${limit}-contact limit on the ${labelFor(tier)} plan.`,
		upgradeTo: next
	};
}

function labelFor(tier: TierId): string {
	return TIERS.find((t) => t.id === tier)?.name ?? tier;
}
```

Four things worth noticing.

## Step 3 — `allowed: true/false` over a boolean return

We return an `Entitlement` object rather than a bare `boolean`. Reasons:

- **Error messages travel with the decision.** When the UI shows "You can't do this," the message comes from the same place that made the check. No duplication.
- **Upgrade hints are structured data.** `upgradeTo: 'plus'` lets the UI render "Upgrade to Plus" CTAs without re-deriving which tier would unlock the action.
- **It scales.** When we add new entitlements (export CSV, invite teammates), they slot into the same shape.

Tiny effort, big downstream payoff.

## Step 4 — Why `contactLimit: null` means unlimited (and how we handle it)

From Module 5.5, `TIERS` uses `contactLimit: number | null`. Pro is `null`. The helper branches:

```ts
if (limit === null) return { allowed: true };
```

`null` is the explicit "no limit" signal. Using `Infinity` or a giant number would technically work but muddles intent. Every reader of the code immediately understands `null === unlimited`.

## Step 5 — The "you've hit the limit on Pro" branch

Pro is unlimited — if a Pro user somehow can't add a contact, it's a bug, not a tier issue. The reason string directs them to support. Principal-engineer move: distinguish "you need to upgrade" from "something's wrong" in the error message. Users read these; wording matters.

## Step 6 — Add a feature-level entitlement

Beyond contact limits, we have one other feature gated by tier: **CSV import/export**. Per the marketing copy in `pricing-page.ts`, this is a Pro-only feature. Model it:

```ts
// src/lib/server/billing/entitlements.ts (append)

export function canUseCsvImportExport(tier: TierId): Entitlement {
	if (tierAtLeast(tier, 'pro')) return { allowed: true };
	return {
		allowed: false,
		reason: 'CSV import/export is a Pro feature.',
		upgradeTo: 'pro'
	};
}
```

Notice: no resource count in this one. Feature gating ≠ quantity gating. Both shapes return the same `Entitlement` type, so the UI renders them the same way.

## Step 7 — Package the user's tier into request locals

We want every request to have `user.tier` available without every handler re-querying. In `hooks.server.ts` (extending what Module 2.3 and Module 3.3 set up):

```ts
// src/hooks.server.ts (inside the auth handle, after user is resolved)
import { getUserTier } from '$lib/server/billing/subscriptions';

// ...existing code that sets locals.user & locals.session...

if (locals.user) {
	try {
		locals.tier = await getUserTier(locals.supabaseAdmin, locals.user.id);
	} catch (err) {
		console.warn('[hooks] tier lookup failed:', err);
		locals.tier = 'free'; // safest default
	}
} else {
	locals.tier = 'free';
}
```

And add it to the `App.Locals` type in `src/app.d.ts`:

```ts
declare namespace App {
	interface Locals {
		supabase: SupabaseClient<Database>;
		supabaseAdmin: SupabaseClient<Database>;
		session: Session | null;
		user: User | null;
		tier: TierId;
	}
	// ...
}
```

Every server-side remote function, route guard, and `+page.server.ts` loader can now read `locals.tier` without another DB hop.

## Step 8 — The "safest default" rule

`catch (err) { locals.tier = 'free'; }` — why fall through to `'free'` on error rather than throwing?

A transient Supabase hiccup shouldn't prevent a logged-in user from loading the app's free functionality. Falling back to `'free'` means:

- Worst case: a Plus user momentarily sees upgrade prompts until the next request succeeds.
- Best case: the app stays usable even under degraded conditions.

The alternative — hard-failing the request — turns a recoverable database glitch into a visible "site down." Grade-A disaster trade. Bias toward continued availability.

## Step 9 — Quick unit-test sketch (full tests in Module 11)

Since these helpers are pure, they're trivial to test:

```ts
// hypothetical entitlements.test.ts
describe('canAddContact', () => {
	it('allows free user under limit', () => {
		expect(canAddContact('free', 3).allowed).toBe(true);
	});
	it('blocks free user at limit with upgrade hint', () => {
		const result = canAddContact('free', 5);
		expect(result.allowed).toBe(false);
		expect(result.upgradeTo).toBe('plus');
	});
	it('allows pro unlimited', () => {
		expect(canAddContact('pro', 1_000_000).allowed).toBe(true);
	});
});
```

Three tests cover all three branches. Pure functions make TDD cheap; use it.

## Verify

- `tierAtLeast('plus', 'free') === true`.
- `tierAtLeast('free', 'plus') === false`.
- `canAddContact('free', 4)` returns `{ allowed: true }`.
- `canAddContact('free', 5)` returns `{ allowed: false, reason: '...', upgradeTo: 'plus' }`.
- `canAddContact('pro', 10_000)` returns `{ allowed: true }`.
- `locals.tier` is available in any server-side handler after hooks run.

## Common traps

- **Reading Supabase inside the entitlement function.** Kills purity, makes tests hard, and fires N queries per request. Pass tier + count in.
- **Returning a plain boolean.** You'll end up re-deriving "what should the error message be?" three places. Structured returns for the win.
- **Storing tier in a cookie or localStorage.** Client-side tier data is untrusted input. Server re-derives every request from the Stripe-backed subscription.
- **Hardcoding the tier order.** We used a `RANK` map. If marketing adds an "Enterprise" tier tomorrow, one line changes. Hardcoded comparisons would need edits in ten places.

## Recap

`entitlements.ts` is 50 lines and does one job: given a tier + optional quantity, say yes or no with a reason. Every gated feature in the next three lessons calls it. Up next: enforcing those decisions at the action layer.
