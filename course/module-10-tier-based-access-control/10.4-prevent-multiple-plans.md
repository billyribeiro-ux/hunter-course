# 10.4 — Prevent Multiple Plans

> A user should never be subscribed to two paid tiers at once. Stripe makes that easy to avoid — if you know where to look.

## Why this matters

There are three ways to accidentally sell a user two subscriptions:

1. **Race condition at checkout.** User double-clicks "Upgrade to Plus" → two Checkout Sessions open → two payments.
2. **Upgrade-then-re-upgrade.** User on Plus clicks "Upgrade to Pro" from the pricing page, which (without guards) spawns a *new* subscription instead of updating the existing one.
3. **Stale session.** Tab from yesterday, sub already active, user clicks upgrade again.

All three produce the same bug: a `stripe_subscriptions` table with two rows in `active` status, double billing, confused refund chat. Stripe does *not* prevent this by default — it's your integration's job.

We defend at three layers: **pre-checkout lookup**, **portal routing**, and **webhook dedupe**. With all three in place, reaching "two active subs" becomes effectively impossible.

## The Principal Engineer lens

**Routing intent matters more than mechanical validation.** A user clicking "upgrade" on the pricing page when they're already subscribed doesn't want a *second* plan — they want to *change* plans. The right response is "send them to the Customer Portal," not "create a new checkout." The fix is routing logic, not a reject message.

Corollary: **when the user's intent is ambiguous, default to the least-damaging action.** Show the portal (reversible) rather than creating a new subscription (reversible only via refund + apology).

## Step 1 — The pre-checkout guard

In `createCheckoutSessionForLookupKey` (built in Module 9.1), before anything else, check for an active subscription:

```ts
// src/lib/server/billing/checkout.ts (refactor)
import { getActiveSubscription } from './subscriptions';

export async function createCheckoutOrPortal(
	admin: Admin,
	params: { userId: string; email: string; lookupKey: string; successUrl: string; cancelUrl: string }
): Promise<{ url: string; kind: 'checkout' | 'portal' }> {
	const existing = await getActiveSubscription(admin, params.userId);
	if (existing) {
		// User is already subscribed — send them to the Portal instead.
		const portalUrl = await createPortalSession(admin, params.userId, params.successUrl);
		return { url: portalUrl, kind: 'portal' };
	}

	// No active sub — create a fresh Checkout Session.
	const url = await createCheckoutSessionForLookupKey(admin, params);
	return { url, kind: 'checkout' };
}
```

One function. Two return paths. The caller doesn't care which — they get a URL and redirect.

## Step 2 — Why we didn't just reject

A reject-and-tell-the-user approach would be:

```ts
// ❌ Don't do this
if (existing) throw error(409, { message: 'Already subscribed' });
```

That's technically correct but user-hostile. The user clicked "Upgrade" — they have an intent. We know what that intent *probably* is (change my plan), and we have the exact tool for it (the Portal). Use it.

The reject pattern is right when intent is genuinely unknowable. For tier changes on an existing sub, intent is clear.

## Step 3 — Use it from the upgrade route

`src/routes/(app)/app/upgrade/+page.server.ts`:

```ts
import type { PageServerLoad } from './$types';
import { redirect } from '@sveltejs/kit';
import { requireUser } from '$lib/server/auth';
import { createCheckoutOrPortal } from '$lib/server/billing/checkout';
import { env } from '$lib/server/env';

export const load: PageServerLoad = async (event) => {
	const { user } = await requireUser(event);
	const lookupKey = event.url.searchParams.get('lookup');
	if (!lookupKey) throw redirect(303, '/pricing');

	const { url } = await createCheckoutOrPortal(event.locals.supabaseAdmin, {
		userId: user.id,
		email: user.email!,
		lookupKey,
		successUrl: `${env.PUBLIC_APP_URL}/billing/success?session_id={CHECKOUT_SESSION_ID}`,
		cancelUrl: `${env.PUBLIC_APP_URL}/pricing`
	});

	throw redirect(303, url);
};
```

Same entry point (`/app/upgrade?lookup=pro_monthly`), dispatches correctly whether the user is on Free (→ checkout) or Plus (→ portal with Pro as the target change).

## Step 4 — Closing the race-condition door

Even with the pre-check, two simultaneous requests for the same user can both see "no active sub" and both create a Checkout Session. Stripe's side saves us *if and only if* we use `idempotencyKey`:

```ts
// src/lib/server/billing/checkout.ts
const session = await stripe.checkout.sessions.create(
	{ /* ... */ },
	{ idempotencyKey: `checkout:${userId}:${lookupKey}:${minuteStamp()}` }
);

function minuteStamp(): string {
	return Math.floor(Date.now() / 60_000).toString();
}
```

Two requests within the same minute share the key → Stripe returns the same Checkout Session to both → both users get the same URL → only one actual checkout completes. `minuteStamp` gives us automatic "reset" after 60s, so legitimate re-attempts (after an hour, say) aren't blocked.

This is the same idempotency pattern we used for `getOrCreateStripeCustomer` in Module 7.3. Same lesson, different object.

## Step 5 — Webhook-layer dedupe

Even so, a truly pathological sequence could produce two `customer.subscription.created` webhooks for the same user with different sub IDs. This is rare (I've seen it exactly once in five years of Stripe) but when it happens, you want your webhook handler to degrade gracefully.

In `syncSubscriptionFromStripe` (Module 7.4), after upserting the sub, check for duplicates:

```ts
// src/lib/server/billing/subscriptions.ts (append to syncSubscriptionFromStripe, after successful upsert)

// Belt-and-braces: if this user somehow has >1 active sub, log it loudly
// so a human can investigate and refund / cancel one.
const { data: actives } = await admin
	.from('stripe_subscriptions')
	.select('id')
	.eq('user_id', userId)
	.in('status', ['trialing', 'active', 'past_due']);

if (actives && actives.length > 1) {
	console.error(
		`[subs] user ${userId} has ${actives.length} active subscriptions: ` +
			actives.map((a) => a.id).join(', ')
	);
}
```

This doesn't auto-resolve; it yells. An on-call engineer looks at the log, pulls up the two subs in Stripe, and decides which to cancel + refund. Don't automate the recovery — the right action depends on context you don't have at runtime (which plan the user *wanted*, whether they paid twice, etc.).

## Step 6 — Pricing-page CTA routing

The pricing page CTAs (Module 8.4) already point at `/app/upgrade?lookup=...`. With Step 3's dispatch in place, they correctly route subscribed users to the Portal. Verify:

| Viewer state | Clicks Plus CTA | Expected URL destination |
|---|---|---|
| Anon | `/register` | Sign-up form |
| Free | `/app/upgrade?lookup=plus_monthly` → Stripe Checkout | Stripe |
| Plus | `/app/upgrade?lookup=plus_monthly` → Stripe Portal | Stripe (portal) |
| Pro | `/app/upgrade?lookup=plus_monthly` → Stripe Portal | Stripe (portal) |

One CTA href per tier. One server-side dispatcher. Zero client-side branching.

## Step 7 — The "cancel at period end" subtlety

A user on Plus clicks "cancel subscription" in the Portal. Stripe sets `cancel_at_period_end: true` but `status` stays `active` until the period ends. Our `getActiveSubscription` still returns the sub (status = active). If the user *immediately* re-clicks "Upgrade to Plus" on the pricing page, our dispatcher sends them to the Portal — which is... right? They can un-cancel there.

This is the correct behaviour: don't create a new sub when the existing one is about to end. The Portal has an "undo cancellation" action. Trust the Portal to do the right thing.

## Step 8 — The dormant-past-due case

What if `getActiveSubscription` returns a `past_due` sub — dead card, retries exhausted? The user probably wants to start fresh. The Portal still handles this: "Update payment method" re-attempts the charge. If they really want a clean start, they cancel the dead sub from the Portal, wait for the webhook to land, and then checkout creates a new one.

Edge case enough that we don't optimise for it. The Portal offers every recovery action; the user (or support) walks through them.

## Step 9 — Monitoring & alerting

Once deployed, the `console.error` from Step 5 ought to page you (or at least show up in a daily digest). Production observability (Module 12.5) covers this; for now, know that "two active subs" is the single highest-value log line to alert on.

A companion alert: "total active subs > total unique users with active subs." If that ratio is ever >1.0, something went wrong somewhere.

## Verify

- Free user clicking "Upgrade to Plus" on the pricing page lands in Stripe Checkout.
- Plus user clicking "Upgrade to Pro" lands in the Stripe Portal.
- Rapid double-click on "Upgrade" opens one Checkout Session (Stripe's idempotency + our key).
- `stripe_subscriptions` table, across all test users, never has two rows in `trialing|active|past_due` status for the same `user_id`.
- Manual fake scenario: insert a second "active" sub row via SQL, trigger a webhook → the `console.error` from Step 5 fires.

## Common traps

- **Rejecting re-subscribe attempts outright.** Users have intent; match it with correct routing, not a 409.
- **Skipping the idempotency key on checkout.** Double-click → double sub. One header prevents it.
- **Automating "cancel the duplicate."** You don't know which is the duplicate. Log + human review.
- **Trusting the UI to prevent the double-click.** Disable the button on click, yes — but the server still has to be correct on its own.
- **Letting the dispatch logic live in the component.** Layering it as `/app/upgrade?lookup=...` → server-side dispatch → redirect means even a logged-in user who deep-links to checkout with an active sub gets the right experience.

## Recap

Three layers — pre-check, idempotency, webhook dedupe — make "two active subscriptions" a rounding error. The dispatch from checkout → portal on the user's behalf is the move that matters most: it converts an ambiguous click into the right outcome.
