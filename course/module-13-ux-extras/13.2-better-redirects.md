# 13.2 — Better Redirects

> When the user logs in, land them where they were trying to go. Small detail, huge trust signal.

## Why this matters

Click a deep link to `/app/contacts/42`. You're not logged in. The app redirects you to `/login`. You sign in. Now you're on `/app` — a different page from where you started. You have to find `/contacts/42` again.

That's friction. It's a tiny bug with a large perceived-quality cost. Users don't log the bug, they just leave the tab and go do something else.

This lesson plumbs a single query param through the login flow so post-auth redirects land back where the user came from — safely.

## The Principal Engineer lens

**Redirect URLs are attacker inputs.** The naive implementation — `window.location = searchParams.get('redirect')` — is an open-redirect vulnerability: an attacker sends `https://yourapp.com/login?redirect=https://evil.com`, the user signs in, your app redirects them to the phishing site. From the user's perspective, the phish page came from *you*.

Corollary: **never redirect to an absolute URL; only to a path you control.** Strip protocol and host, keep only the path. If it doesn't start with a single `/`, discard it and go to `/app`.

## Step 1 — The safe-path helper

Create `src/lib/shared/redirect.ts` (shared so both server and client can use it):

```ts
export function safeRedirectPath(raw: string | null | undefined): string {
	if (!raw) return '/app';

	// Must start with a single slash, not `//` (protocol-relative URL).
	if (!raw.startsWith('/') || raw.startsWith('//')) return '/app';

	// No backslashes (some browsers normalize `\\evil.com` to `//evil.com`).
	if (raw.includes('\\')) return '/app';

	// Avoid loops: don't redirect back to auth pages.
	if (raw === '/login' || raw.startsWith('/login?')) return '/app';
	if (raw === '/signup' || raw.startsWith('/signup?')) return '/app';

	return raw;
}
```

Four rules, all worth keeping:

- **Single leading slash.** `/app/contacts` is safe; `//evil.com` is a protocol-relative URL and isn't.
- **No backslashes.** A legacy browser quirk treats `\` as `/` in URLs.
- **No auth-loop redirects.** Redirecting to `/login` after login is infinite recursion.
- **Default to `/app`.** Our authenticated home.

Tested once, forgotten forever. The rest of the code calls `safeRedirectPath(raw)` and trusts it.

## Step 2 — Capture the path in the auth guard

In `src/hooks.server.ts` (or wherever the `(app)` layout redirects unauthenticated users), include the current path as `?redirect=`:

```ts
// src/routes/(app)/+layout.server.ts
import { redirect } from '@sveltejs/kit';

export const load = async ({ locals, url }) => {
	if (!locals.user) {
		const next = url.pathname + url.search;
		throw redirect(302, `/login?redirect=${encodeURIComponent(next)}`);
	}

	return { user: locals.user };
};
```

- `url.pathname + url.search` keeps the query string (e.g. `?tab=archive`), not just the path.
- `encodeURIComponent` prevents `?` or `&` in the target from breaking the redirect URL itself.

## Step 3 — Wire the login form

`src/routes/login/+page.svelte`:

```svelte
<script lang="ts">
	import { page } from '$app/state';
	import { loginCommand } from '$lib/remote/auth.remote.ts';
	import { safeRedirectPath } from '$lib/shared/redirect';
	import { goto } from '$app/navigation';

	let email = $state('');
	let password = $state('');
	let error = $state<string | null>(null);

	async function onSubmit(e: SubmitEvent) {
		e.preventDefault();
		const result = await loginCommand({ email, password });
		if (!result.ok) {
			error = result.error;
			return;
		}
		const raw = page.url.searchParams.get('redirect');
		await goto(safeRedirectPath(raw), { invalidateAll: true });
	}
</script>

<form onsubmit={onSubmit}>
	<!-- ... email/password fields ... -->
</form>
```

`invalidateAll: true` ensures the root layout re-runs and picks up the new session before rendering the destination.

## Step 4 — Carry redirect through signup too

Signups should respect the same param. Same capture in the `(app)` guard, same `safeRedirectPath` after the email-confirmation callback.

```ts
// src/routes/auth/callback/+server.ts (Supabase email-confirmation handler)
import { redirect } from '@sveltejs/kit';
import { safeRedirectPath } from '$lib/shared/redirect';

export const GET = async ({ url, locals }) => {
	// ... verify code, set session ...
	const raw = url.searchParams.get('redirect');
	throw redirect(303, safeRedirectPath(raw));
};
```

The redirect param survives the round trip: user signs up → email → click link → `auth/callback?redirect=/app/contacts/42` → lands on `/contacts/42`, logged in.

## Step 5 — The "stay here after login" form pattern

Some flows show a login form inline (e.g. an anonymous user hitting a rate-limited endpoint). For those, pass the current URL as a hidden field:

```svelte
<form method="post" action="?/login">
	<input type="email" name="email" required />
	<input type="password" name="password" required />
	<input type="hidden" name="redirect" value={page.url.pathname + page.url.search} />
	<button type="submit">Sign in</button>
</form>
```

Server-side handler:

```ts
export const actions = {
	login: async ({ request }) => {
		const data = await request.formData();
		// ... auth ...
		throw redirect(303, safeRedirectPath(data.get('redirect')?.toString()));
	}
};
```

## Step 6 — Open-redirect regression test

Playwright, in `tests/auth-redirect.spec.ts`:

```ts
import { test, expect } from '@playwright/test';

test.describe('login redirect', () => {
	test('redirects to original path', async ({ page }) => {
		await page.goto('/login?redirect=%2Fapp%2Fcontacts');
		await page.getByLabel('Email').fill('test@contactly.app');
		await page.getByLabel('Password').fill('Password123!');
		await page.getByRole('button', { name: 'Sign in' }).click();
		await expect(page).toHaveURL('/app/contacts');
	});

	test('ignores external redirect', async ({ page }) => {
		await page.goto('/login?redirect=https://evil.com/phish');
		await page.getByLabel('Email').fill('test@contactly.app');
		await page.getByLabel('Password').fill('Password123!');
		await page.getByRole('button', { name: 'Sign in' }).click();
		await expect(page).toHaveURL('/app');
	});

	test('ignores protocol-relative redirect', async ({ page }) => {
		await page.goto('/login?redirect=%2F%2Fevil.com%2Fphish');
		await page.getByLabel('Email').fill('test@contactly.app');
		await page.getByLabel('Password').fill('Password123!');
		await page.getByRole('button', { name: 'Sign in' }).click();
		await expect(page).toHaveURL('/app');
	});
});
```

Three cases, three attacker payloads, three defended outcomes. This test is the difference between "I *think* it's safe" and "I *know* it's safe."

## Verify

- Click a deep link while logged out → redirected to `/login?redirect=...` → after login, land on the original URL.
- Try `/login?redirect=https://evil.com` → after login, land on `/app` (not evil.com).
- Try `/login?redirect=//evil.com` → same: `/app`.
- Try `/login?redirect=/login` → after login, land on `/app` (no loop).
- The three Playwright tests pass.

## Common traps

- **Trusting `searchParams.get('redirect')` directly.** Open-redirect vulnerability. Always run it through `safeRedirectPath`.
- **Encoding the redirect twice.** If you `encodeURIComponent` the whole URL instead of the next-path, decoding gets doubled and you end up with literal `%2F` in the URL bar. Only encode the `next` value once, at insertion time.
- **Forgetting `invalidateAll: true` on `goto`.** The root layout still has the old (unauthenticated) data loaded. `/app` renders, sees no user, bounces back to `/login`. Infinite loop.
- **Losing query strings.** `url.pathname` alone drops `?tab=archive`. Use `url.pathname + url.search`.
- **No loop protection.** Without the `/login` guard, clicking a deep link that's actually `/login` creates infinite redirect.

## Recap

One helper, four rules, one test suite. Deep links now survive login; phishing payloads get quietly dropped. A feature most users will never notice — and the ones who do notice will tell a friend.
